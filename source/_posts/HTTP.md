## HTTP 常见字段有哪些？

### HTTP 请求头

HTTP请求头包括以下字段：

* **Request-line**：包含用于描述请求类型、要访问的资源以及所使用的HTTP版本的信息。
* **Host**：指定被请求资源的主机名或IP地址和端口号。
* **Accept**：指定客户端能够接收的媒体类型列表，用逗号分隔，例如 text/plain, text/html。
* **User-Agent**：客户端使用的浏览器类型和版本号，供服务器统计用户代理信息。
* **Cookie**：如果请求中包含cookie信息，则通过这个字段将cookie信息发送给Web服务器。
* **Connection**：表示是否需要持久连接（keep-alive）。

### HTTP 响应头

HTTP响应头包括以下字段：

* **Status-line**：包含协议版本、状态码和状态消息。
* **Content-Type**：响应体的MIME类型。
* **Content-Length**：响应体的字节数。
* **Set-Cookie**：服务器向客户端发送cookie信息时使用该字段。
* **Server**：服务器类型和版本号。
* **Connection**：表示是否需要保持长连接（keep-alive）。

## HTTP 请求方法

### GET：主要作用是从服务器获取资源，例如网页、图片、视频等 （非幂等）

GET 请求是"无副作用"的，不会改变服务器的状态。GET 请求通常用于以下场景：

* **获取网页内容**：浏览器向服务器请求 HTML 文件以显示网页内容。
* **获取 API 数据**：客户端向 API 发送 GET 请求以获取数据，例如获取用户信息、商品列表等。
* **加载资源文件**：获取静态资源，如图片、CSS、JavaScript 文件等。

### POST ：方法用于向服务器发送数据，通常是为了提交表单、上传文件、或调用 API 接口以进行数据处理 （非幂等）

POST 方法的典型使用场景包括：

* **提交表单数据**：用户在网页上填写表单后，点击提交按钮，浏览器会使用 POST 方法将表单数据发送到服务器。例如，用户注册、登录、提交评论等操作都通常使用 POST 方法。

示例：

* **上传文件**：POST 方法可以用于将文件上传到服务器。在这种情况下，请求体会包含文件数据，服务器处理后保存文件。

* **调用 API**：在 RESTful API 中，POST 方法通常用于创建新资源。例如，创建新的用户账户、发布新的文章或评论等。

#### 与 GET 请求相比，POST 请求在安全性方面有一些显著的优势：

* **数据不暴露在 URL 中**：由于 POST 请求的数据包含在请求体中，不会暴露在 URL 中，因此更适合传输敏感数据，如密码、信用卡信息等。
* **数据量不受 URL 长度限制**：POST 请求的数据量没有像 GET 请求那样受到 URL 长度的限制，因此可以传输较大的数据包，如文件上传、复杂表单提交等。

### DELETE 方法用于删除服务器上的指定资源

DELETE 请求涉及到资源的删除操作，因此需要特别注意以下几个方面的安全性问题：

* **身份验证与授权**：由于 DELETE 操作可能对系统或用户数据造成不可逆的影响，服务器应确保只有有权限的用户才能执行该操作。例如，用户只能删除自己的评论或账户，而管理员可能有权删除任何用户的评论或账户。
* **数据备份**：由于 DELETE 操作的不可逆性，建议在执行删除操作前进行数据备份，或者设计成软删除，即标记数据为已删除，而不是实际删除，以便在必要时进行恢复。
* **防止误操作**：为了防止用户或系统误操作删除数据，通常可以设计确认机制，例如在删除前要求用户确认操作，或者使用延迟删除机制，给用户一定时间撤销删除操作

### PATCH 方法用于对服务器上的资源进行部分更新

**与PUT 方法不同，PATCH 请求不需要包含完整的资源数据，而只需要传输需要更新的部分字段。因此，PATCH 方法非常适合用于需要频繁更新部分数据的场景。**

#### PATCH 请求主要用于部分更新，因此在安全性方面需注意以下几点：

* **身份验证与授权**：服务器应确保只有有权限的用户才能执行 PATCH 操作。例如，用户只能更新自己的资料，而不能更新其他用户的资料。
* **数据验证与完整性**：由于 PATCH 请求只传输部分数据，服务器在接收到请求后应确保数据的完整性，并验证更新后的数据是否符合业务规则或约束条件。
* **避免数据竞争**：在并发操作的场景下，如果多个 PATCH 请求同时对同一个资源进行不同的部分更新，可能会导致数据竞争问题。因此，建议在并发操作中使用锁机制或乐观锁策略，以避免数据不一致问题。

### HEAD 方法与 GET 方法非常相似，但它只请求资源的首部信息，而不包含资源的具体内容。

### CONNECT 方法用于建立一个到服务器的隧道连接，通常用于 HTTP 与 HTTPS 的代理请求。

### OPTIONS 方法用于查询服务器支持的请求方法或特定资源所支持的功能。

#### OPTIONS 方法的典型使用场景包括：

* **跨域资源共享（CORS）预检请求**：在跨域请求中，浏览器会自动发送一个 OPTIONS 请求来预检目标服务器是否允许实际的请求方法。服务器通过 OPTIONS 请求响应，指示是否允许实际请求继续执行。
* **查询服务器支持的请求方法**：客户端可以使用 OPTIONS 请求查询服务器支持哪些请求方法，帮助开发者了解服务器的功能和限制。

### TRACE 方法用于在服务器上发起一个回环测试，即服务器将收到的请求原样返回给客户端。

**TRACE 方法的主要用途是诊断或调试，帮助客户端检查请求在传输过程中是否被修改或损坏。**

#### TRACE 请求的典型使用场景包括：

* **检查代理服务器行为**：当客户端与服务器之间有多个代理服务器时，TRACE 请求可以用于检查请求在经过各个代理服务器时是否被修改，帮助诊断网络问题。

## HTTP 各版本区别

* HTTP/1.0：基础版本
* HTTP/1.1

+ 改进：

- 使用长连接
- 支持管道网络传输（不必等第一个请求回来）

+ 缺点：

- 头部信息无法压缩（延迟大）
- 队头阻塞（发生在 HTTP 层）
- 没有请求优先级控制（顺序处理）
- 服务器只能被动响应

* HTTP/2.0：基于 HTTPS

+ 改进：

- 头部压缩 HPACK 算法：客户端和服务器维护一个头部信息表
- 二进制数据格式：头部和数据体采用二进制编码
- 并发传输：接收端可以通过 Stream ID 有序组装成 HTTP 消息
- 服务器推送：客户端 Stream ID 是奇数，服务器是偶数（可以一起推送 HTML 和 CSS）

+ 缺点：

- 队头阻塞：发生在 TCP 层（丢包导致 TCP 数据不完整，触发 TCP 重传机制）

* HTTP/3.0：基于 UDP 和 QUIC 协议实现类似 TCP 的可靠性传输（未广泛普及）

+ QUIC 协议：

- 无队头阻塞：多个 stream 独立（只会阻塞丢包的 stream）
- 建立连接更快：QUIC 内部封装 TLS（不需要分开握手）
- 连接迁移：通过连接 ID 标记两个通信端点，IP 地址变化时可以复用原连接，避免重连

## HTTP 1.1 特性

* 优点：

+ 简单、灵活和易于扩展、应用广泛和跨平台

* 缺点：

+ 无状态：服务器不会记录 HTTP 状态（可以在请求和响应报文中写入 Cookie 信息）
+ 不安全：明文传输、不验证通信方身份、无法证明报文的完整性

* 性能：

+ 长连接：只要任一端没有提出断开连接，则保持 TCP 连接状态（长时间没有数据交互服务器也会断开）
+ 管道网络传输：同一个 TCP 连接里可以发起多个请求，服务器按照发送顺序响应请求（队头阻塞）
+ 队头阻塞：

- 某个请求耗时较长，导致后面的请求被阻塞无法响应
- HTTP 1.1 只解决了请求的队头阻塞，没有解决响应的队头阻塞

## HTTP1.0和HTTP1.1

HTTP1.0默认使用短连接，也就是每一个HTTP请求都会重新建立一个TCP连接，会有大量三次握手和四次挥手占用宽带。

HTTP1.1默认使用长连接，同一个客户端的HTTP请求可以复用一个TCP连接。

注意：HTTP1.0提供了长连接，通过请求头Connection: Keep-alive开启

HTTP的长短连接，实际上是TCP的长短连接。

## HTTP1.1和HTTP2.0

HTTP1.1使用文本格式传输，而HTTP2.0采用二进制帧传输，二进制帧更加紧凑，占用带宽更小。

HTTP1.1采用串行方式，一个请求响应结束才能进行下一个请求，而HTTP2.0采用多路复用，可以同时传输和连接多个请求和响应，将消息分解成二进制帧，在另一端组装起来。

2.0解决了http队头阻塞(即一个响应延迟，后续响应均延迟，用二进制帧解决) ，但没有解决tcp队头阻塞。

3.0用新协议QUIC，也就是对UDP进行优化，实现可靠性。解决了tcp队头阻塞，因为他压根就不是基于tcp。

## HTTP 和 HTTPS 区别

* HTTP 信息是明文传输；HTTPS 在 TCP 和 HTTP 之间加入了 SSL/TLS 安全协议，报文加密传输
* HTTP 连接简单，只需要经过 TCP 三次握手；HTTPS 还要进行 SSL/TLS 握手
* HTTP 默认端口为 80；HTTPS 默认端口 443
* HTTPS 需要向 CA 申请数字证书

**HTTPS是基于HTTP的，也就是在HTTP和TCP之间加了一层TLS安全协议，来保证数据传输安全的。**

**http端口 是80 https是443**

## HTTPS 对称加密和非对称加密

**对称加密**： 对称加密，又称私钥加密，其加密和解密过程使用相同的密钥。发送方使用密钥对数据进行加密，然后将加密后的数据发送给接收方。接收方使用相同的密钥对接收到的加密数据进行解密，从而得到原始数据。对称加密的优点在于加密解密速度快，适合处理大量数据。然而，其缺点在于密钥的传输和保管问题，因为双方必须确保密钥的安全交换和存储。

**非对称加密**： 非对称加密，又称公钥加密，使用一对密钥：公钥和私钥。公钥用于加密数据，而私钥用于解密数据。发送方使用接收方的公钥对数据进行加密，然后将加密后的数据发送给接收方。接收方使用自己的私钥对接收到的加密数据进行解密。非对称加密的优点在于密钥的传输更为安全，因为公钥可以公开，而私钥只需由接收方秘密保管。然而，非对称加密的加密解密速度相对较慢，不适合处理大量数据。但它非常适合用于数字签名和密钥交换等安全场景。

含义：

* 对称加密：通信双方使用同一个密钥加密和解密（密钥被截获则失去加密的作用）
* 非对称加密：先通过公钥加密、再使用私钥解密（私钥掌握在通信双方手中）

HTTPS 使用的是基于对称加密和非对称加密的混合加密：

* 通信建立前使用非对称加密的方式交换密钥（后续不再使用非对称加密）
* 通信过程中全部使用对称加密的方式加密明文数据

## HTTPS 如何建立连接

SSL / TLS 协议流程：

* 客户端向服务端索要并验证公钥
* 双方协商生产密钥
* 双方采用密钥进行加密通信

基于 RSA 算法的 TLS 握手：四次握手

* ClientHello：客户端向服务端发送

+ 支持的 TLS 版本（如 TLS 1.2）
+ 随机数（Client Random）
+ 支持的密码套件列表（如 RSA）

* ServerHello：

+ 确认 TLS 版本（浏览器不支持则关闭通信）
+ 服务端生产随机数（Server Random）
+ 确认密码套件列表（如 RSA）
+ 服务器的数字证书

* 客户端回应：通过浏览器或操作系统中的 CA 公钥，确认服务器数字证书的真实性。客户端从数字证书中取出服务器的公钥，向服务端发送随机数（pre-master key）、加密通信算法改变通知、客户端握手结束通知
* 服务端最后回应：收到三个随机数后，通过协商的加密算法，计算出会话密钥。向客户端发送加密通信算法改变通知（随后的信息都用会话密钥进行通信）、服务器握手结束通知

## HTTPS 一定安全可靠吗

**问题场景：**客户端通过浏览器向服务端发起 HTTPS 请求时，被假基站转发到了一个中间人服务器，于是客户端是和中间人服务器完成了 TLS 握手，然后这个中间人服务器再与真正的服务端完成 TLS 握手。中间人服务器与客户端在 TLS 握手过程中，实际上发送了自己伪造的证书给浏览器，而这个伪造的证书是能被浏览器（客户端）识别出是非法的，于是就会提醒用户该证书存在问题。

**结论：**这其实并不能说 HTTPS 不够安全，毕竟浏览器都已经提示证书有问题了，如果用户坚决要访问，那不能怪 HTTPS。所以 HTTPS 目前来说还是安全可靠的，没有任何漏洞。

## webSocket

WebSocket 是基于 TCP 的一种新的**网络协议**。它实现了浏览器与服务器全双工通信——浏览器和服务器只需要完成一次握手，两者之间就可以创建**持久性**的连接， 并进行**双向**数据传输。

**HTTP协议和WebSocket协议对比：**

* HTTP是**短连接**
* WebSocket是**长连接**
* HTTP通信是**单向**的，基于请求响应模式
* WebSocket支持**双向**通信
* HTTP和WebSocket底层都是TCP连接

![](../../资源/图片/yuque_ecf2a9286354.png)

**思考：**既然WebSocket支持双向通信，功能看似比HTTP强大，那么我们是不是可以基于WebSocket开发所有的业务功能？

**WebSocket缺点：**

服务器长期维护长连接需要一定的成本各个浏览器支持程度不一WebSocket 是长连接，受网络限制比较大，需要处理好重连

**结论：**WebSocket并不能完全取代HTTP，它只适合在特定的场景下使用

# 五、源码解析和实践感悟

## 1. HTTP/1.1 长连接——Connection: keep-alive 的 TCP 层面

HTTP/1.1 默认长连接意味着同一 TCP 连接可复用多个 HTTP 请求。关键是 Content-Length 和 Transfer-Encoding: chunked 决定消息边界。

```cpp
// 简易 HTTP 长连接服务器伪代码
void handle_http_keepalive(int client_fd) {
    char buf[4096];
    while (true) {
        ssize_t n = recv(client_fd, buf, sizeof(buf), 0);
        if (n <= 0) break;  // 连接关闭或出错
        
        HttpRequest req = parse_request(buf, n);
        HttpResponse resp = handle(req);
        
        std::string raw = resp.serialize();
        send(client_fd, raw.c_str(), raw.size(), 0);
        
        // 检查 Connection 头决定是否关闭
        if (req.get_header("Connection") == "close")
            break;
    }
    close(client_fd);
}
// 关键：Content-Length 必须正确，否则客户端无法判断响应结束
// chunked 编码：每个 chunk 前有十六进制长度，空 chunk (0\r\n\r\n) 表示结束
```

## 2. HTTPS TLS 1.2 握手——四次往返的核心

TLS 握手混合了非对称加密（密钥交换）和对称加密（数据传输），RSA 和 ECDHE 是两种主流密钥交换方式。

```cpp
// TLS 1.2 RSA 握手流程（简化）
// 1. ClientHello → 客户端随机数 + 支持的密码套件
// 2. ServerHello → 服务端随机数 + 选定密码套件 + 证书（含公钥）
// 3. ClientKeyExchange → 用公钥加密的 Pre-Master Secret
// 双方用 ClientRandom + ServerRandom + PreMaster → PRF → SessionKey
// 4. ChangeCipherSpec → 后续全用 SessionKey 对称加密

// 注意：RSA 模式无前向安全性（Forward Secrecy）
// 私钥泄露 → 历史所有会话可解密
// ECDHE 模式：临时生成 ECDH 密钥对，每次会话独立 → 前向安全
```

## 3. HTTP/2 多路复用——Stream 分帧与 HPACK

HTTP/2 在单一 TCP 连接上用多个 Stream 并发传输，通过 Stream ID 和帧类型区分不同请求/响应，解决 HTTP/1.1 的队头阻塞。

```cpp
// HTTP/2 帧结构（9 字节头）
struct Http2FrameHeader {
    uint32_t length : 24;  // 载荷长度
    uint8_t  type;         // DATA/HEADERS/PRIORITY/RST_STREAM/SETTINGS/PUSH_PROMISE/PING/GOAWAY/WINDOW_UPDATE
    uint8_t  flags;        // END_STREAM, END_HEADERS, PADDED 等
    uint32_t stream_id : 31;  // 客户端奇数，服务端偶数，0=连接控制
};
// 多路复用核心：不同 Stream 的帧在 TCP 连接上交错发送
// 接收端按 Stream ID 重组完整消息
// HPACK 头部压缩：静态表(61个常见头)+动态表+哈夫曼编码
// 但 TCP 层面仍有序：一个 Stream 丢包→TCP 重传→阻塞所有 Stream（TCP 队头阻塞）
```

## 实践经验

1. **HTTP/1.1 的队头阻塞是真实存在的性能瓶颈**：浏览器对同一域名通常只开 6-8 个 TCP 连接。如果第一个请求响应慢（如慢 SQL），后续请求全部排队。这是为什么大厂用域名分片（img1.cdn.com, img2.cdn.com）增加并发连接数的原因。
2. **HTTP/2 的实际收益取决于 RTT**：高延迟网络（如移动网络 100ms+ RTT）下 HTTP/2 多路复用收益巨大。低延迟内网（<1ms）下 HTTP/1.1 的 keep-alive + 连接池已经足够好，HTTP/2 的收益有限。
3. **HTTPS 不是绝对安全——证书信任链可能被攻破**：中间人攻击的核心是伪造证书。浏览器通过内置 CA 根证书验证链，但如果用户忽略证书警告继续访问，或被安装了恶意根证书，HTTPS 也会被破解。
4. **TLS 握手优化——Session Resumption**：完全握手需要 2-RTT（ECDHE）+ 证书传输。Session ID 缓存（服务端存）和 Session Ticket（客户端存加密状态）可将后续握手降为 1-RTT 甚至 0-RTT（TLS 1.3）。
5. **WebSocket 的 ping/pong 帧不是 TCP keepalive**：WebSocket 协议层的心跳用于检测对端是否存活（应用层），TCP keepalive 用于检测连接是否断开（传输层）。两层都应配置，WebSocket 心跳间隔应短于代理/负载均衡的空闲超时。
6. **HTTP/3 用 QUIC 解决 TCP 队头阻塞**：QUIC 基于 UDP，每个 Stream 独立传输，一个 Stream 丢包只阻塞该 Stream 不影响其他。但 QUIC 需要内核旁路实现（用户态），CPU 开销高于内核 TCP，目前主要用于 Google/Facebook 等大规模部署。

# 六、面试准备

## 面试问答

**Q1: HTTP 各版本的核心区别？**
A: (1) **HTTP/1.0**：短连接，每个请求新建 TCP。(2) **HTTP/1.1**：长连接（keep-alive）+ 管道化（但队头阻塞严重）。(3) **HTTP/2**：二进制帧 + 多路复用 + HPACK 头部压缩 + 服务器推送，解决 HTTP 层队头阻塞但 TCP 层仍存在。(4) **HTTP/3**：基于 QUIC(UDP)，0-RTT 握手，彻底消除 TCP 队头阻塞。

**Q2: HTTP 和 HTTPS 的区别？**
A: (1) HTTP 明文传输，HTTPS 在 TCP 和 HTTP 间加 TLS/SSL 加密；(2) HTTP 端口 80，HTTPS 端口 443；(3) HTTPS 需要 CA 数字证书；(4) HTTPS 握手多 TLS 层（额外 2-3 RTT）；(5) HTTPS 防止窃听/篡改/冒充。

**Q3: HTTPS 的 TLS 握手过程？**
A: ECDHE 模式（主流）：(1) ClientHello（支持的密码套件+随机数）；(2) ServerHello（选定套件+随机数+证书+ServerKeyExchange（ECDH 公钥））；(3) ClientKeyExchange（ECDH 公钥）+ ChangeCipherSpec；(4) 服务端 ChangeCipherSpec → 双方计算 SessionKey → 对称加密通信。共 2-RTT（TLS 1.2）或 1-RTT（TLS 1.3）。

**Q4: 对称加密和非对称加密在 HTTPS 中怎么用？**
A: **混合加密**。(1) 握手阶段：非对称加密（RSA/ECDHE）安全交换对称密钥，解决密钥分发问题；(2) 数据传输阶段：对称加密（AES-GCM/ChaCha20）加密通信内容，保证性能。非对称加密慢（RSA 2048 约 0.1ms/次），对称加密快（AES-NI 指令可达 GB/s）。

**Q5: HTTP 常见状态码及含义？**
A: (1) **1xx**：信息性（101 Switching Protocols）；(2) **2xx**：成功（200 OK，201 Created，204 No Content）；(3) **3xx**：重定向（301 永久，302 临时，304 Not Modified）；(4) **4xx**：客户端错误（400 Bad Request，401 Unauthorized，403 Forbidden，404 Not Found）；(5) **5xx**：服务端错误（500 Internal Server Error，502 Bad Gateway，503 Service Unavailable，504 Gateway Timeout）。

**Q6: GET 和 POST 的区别？**
A: (1) **语义**：GET 获取资源（幂等），POST 创建/提交数据（非幂等）；(2) **参数位置**：GET 在 URL 中（有长度限制 ~2KB），POST 在请求体中（无长度限制）；(3) **安全性**：GET 参数暴露在 URL/日志中，POST 相对隐蔽但都不是加密的（HTTPS 下均加密）；(4) **缓存**：GET 可缓存，POST 默认不缓存；(5) **幂等性**：GET/PUT/DELETE 幂等，POST/PATCH 非幂等。

**Q7: Cookie 和 Session 的区别？**
A: Cookie 是客户端存储（浏览器），每次请求自动携带，大小限制 4KB。Session 是服务端存储，通过 Cookie 中的 SessionID 关联。安全对比：Cookie 可被篡改（需 HttpOnly+Secure+SameSite 加固），Session 相对安全但需要服务端存储（分布式需共享 Session）。

**Q8: WebSocket 和 HTTP 长连接的区别？**
A: HTTP 长连接仍是请求-响应模式（客户端主动），WebSocket 是全双工（双方随时发）。WebSocket 通过 HTTP Upgrade 握手（101 状态码）后切换协议。适用场景：HTTP 适合请求驱动的 REST API，WebSocket 适合实时推送（聊天、行情、游戏）。

## 陷阱与反问

| 陷阱 | 错误认知 | 正确理解 |
|------|---------|---------|
| HTTPS 绝对安全 | 证书信任链被攻破或用户忽略警告时仍可被中间人攻击 | HTTPS 保证传输安全，不保证端点安全 |
| HTTP/2 一定比 HTTP/1.1 快 | 低延迟内网下 HTTP/1.1 + keep-alive + 连接池差异不大 | HTTP/2 优势在高延迟+高并发场景 |
| GET 请求不能有 Body | RFC 未明确禁止，但许多服务器/代理不支持 | 实际不推荐 GET 带 Body，用 POST 替代 |
| 301 和 302 只是语义区别 | 301 是永久重定向（浏览器缓存），302 是临时（每次请求都重定向） | 301 可能导致后续请求不再到达原 URL |
| Cookie 中的 Secure 标记表示加密 | Secure 只表示仅在 HTTPS 下传输，不表示内容加密 | 需配合 HttpOnly（防 JS 读取）+ SameSite（防 CSRF） |
