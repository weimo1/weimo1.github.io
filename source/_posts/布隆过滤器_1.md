# 布隆过滤器

## 一、项目/模块概述

- **模块定位**：布隆过滤器（Bloom Filter）是 LevelDB 读路径的关键优化组件——在读取 SSTable 的 data block 之前，快速判断一个 key 是否**一定不存在**于该文件。用约 1% 的误报率（false positive rate）消除 99% 的无效磁盘读取。
- **技术栈与依赖**：纯 C++ 实现，依赖 MurMurHash2 哈希函数，double-hashing 技术生成多个哈希值
- **模块边界**：
  - 输入：一组 key（构建阶段）或单个 key（查询阶段）
  - 输出：`true`（key 可能存在）或 `false`（key 一定不存在）
  - 上下游：作为 SSTable 的 Filter Block 嵌入，被 Table::InternalGet() 调用

## 二、架构设计（≥200字）

### 第一层：布隆过滤器原理

布隆过滤器是一个 m 位的位数组 + k 个独立的哈希函数：
- **插入**：对 key 计算 k 个哈希值，将对应的 k 个位设为 1
- **查询**：对 key 计算 k 个哈希值，检查对应的 k 个位——如果任何一位为 0，则 key **一定不在**集合中；如果全为 1，则 key **可能在**集合中

### 第二层：False Positives 概率推导

#### 误差率

布隆过滤器的误差率是指由于hash冲突，导致原本不在布隆过滤器中的数据，查询时显示在里面。

> 补充：当 k = ln(2) × m/n 时，误报率最小，约为 (0.6185)^(m/n)。LevelDB 默认 `bits_per_key = 10`，此时 k ≈ 7（10 × 0.69），理论误报率 ≈ 0.82%。这也是代码中 `k_ = bits_per_key * 0.69` 的数学依据。

### 第三层：关键设计决策

| 设计决策 | LevelDB 选择 | 理由 |
|----------|-------------|------|
| 哈希方案 | double-hashing（双哈希） | 只用一次 MurMurHash2，通过位旋转生成 k 个哈希值 |
| bits_per_key | 默认 10 | 约 1% 误报率，空间与精度的最佳平衡 |
| k 的范围 | [1, 30] | 防止极端配置（太小误报高，太大计算开销大） |
| 最小位数 | 64 bits (8 bytes) | 小数据量时保证最低精度 |

### 3.2 BloomFilterPolicy 完整实现

```c++
class BloomFilterPolicy final : public FilterPolicy {

public:

explicit BloomFilterPolicy(int bits_per_key) : bits_per_key_(bits_per_key) {

    // We intentionally round down to reduce probing cost a little bit
    k_ = static_cast<size_t>(bits_per_key * 0.69);  // 0.69 =~ ln(2)
    if (k_ < 1) k_ = 1;
    if (k_ > 30) k_ = 30;

}

const char* Name() const override { return "BloomFilter2"; }

void CreateFilter(const std::string* keys, int n,
                  std::string* dst) override {
    // Compute bloom filter size (in both bits and bytes)
    size_t bits = n * bits_per_key_;

    // For small n, we can see a very high false positive rate.  Fix it
    // by enforcing a minimum bloom filter length.
    if (bits < 64) bits = 64;

    size_t bytes = (bits + 7) / 8;
    bits = bytes * 8;

    const size_t init_size = dst->size();
    dst->resize(init_size + bytes, 0);
    dst->push_back(static_cast<char>(k_));  // Remember # of probes in filter
    char* array = &(*dst)[init_size];
    for (int i = 0; i < n; i++) {
        //BloomFilter理论是通过多个hash计算来减少冲突，
        //double-hashing的方式来达到同样的效果。
        //double-hashing的理论如下：
        //1、计算hash值；
        //2、hash值的高15位，低17位对调
        //3、按k_个数来存储当前hash值。
        //3-1、计算存储位置；
        //3-2、按bit存；
        //3-3、累加hash值用于下次计算 
        // Use double-hashing to generate a sequence of hash values.
        // See analysis in [Kirsch,Mitzenmacher 2006].
        uint32_t h = hash_func_.MurMurHash2(keys[i].c_str(), keys[i].size());
        const uint32_t delta = (h >> 17) | (h << 15);  // Rotate right 17 bits
        for (size_t j = 0; j < k_; j++) {
            const uint32_t bitpos = h % bits;
            array[bitpos / 8] |= (1 << (bitpos % 8));
            h += delta;
        }
    }
}

bool KeyMayMatch(const std::string& key,
                 const std::string& bloom_filter) override {
    const size_t len = bloom_filter.size();
    if (len < 2) return false;

    const char* array = bloom_filter.data();
    const size_t bits = (len - 1) * 8;

    // Use the encoded k so that we can read filters generated by
    // bloom filters created using different parameters.
    const size_t k = array[len - 1];
    if (k > 30) {
        // Reserved for potentially new encodings for short bloom filters.
        // Consider it a match.
        return true;
    }

    uint32_t h = hash_func_.MurMurHash2(key.c_str(), key.size());
    const uint32_t delta = (h >> 17) | (h << 15);  // Rotate right 17 bits
    for (size_t j = 0; j < k; j++) {
        const uint32_t bitpos = h % bits;
        if ((array[bitpos / 8] & (1 << (bitpos % 8))) == 0) return false;
        h += delta;
    }
    return true;
}

// Return a new filter policy that uses a bloom filter with approximately
// the specified number of bits per key.  A good value for bits_per_key
// is 10, which yields a filter with ~ 1% false positive rate.

private:
  size_t bits_per_key_;
  size_t k_;
  HashFunc hash_func_;
};

}  // namespace hard_core
```

### 3.3 测试程序

```c++
class BloomTest final {
 public:
  BloomTest(uint32_t bit_per_key = 10)
      : policy_(std::make_unique<BloomFilterPolicy>(bit_per_key)) {}

  ~BloomTest() {}

  void Reset() {
    keys_.clear();
    filter_.clear();
  }
  void SetData(std::vector<std::string>&& keys) { keys_ = std::move(keys); }
  void SetData(const std::vector<std::string>& keys) { keys_ = (keys); }

  void Add(const std::string& s) { keys_.emplace_back(s); }

  void Build() {
    filter_.clear();
    policy_->CreateFilter(&keys_[0], static_cast<int>(keys_.size()), &filter_);
    keys_.clear();
  }

  size_t FilterSize() const { return filter_.size(); }
  bool Matches(const std::string& s) {
    if (!keys_.empty()) {
      Build();
    }
    return policy_->KeyMayMatch(s, filter_);
  }

  double FalsePositiveRate(const std::vector<std::string>& data) {
    double result = 0;
    for (const auto& item : data) {
      if (Matches(item)) {
        result++;
      }
    }
    return result / 10000.0;
  }
  double FalsePositiveRate(const std::string& data) {
    double result = 0;
    {
      if (Matches(data)) {
        result++;
      }
    }
    return result / 10000.0;
  }

 private:
  std::unique_ptr<FilterPolicy> policy_;
  std::string filter_;
  std::vector<std::string> keys_;
};
```

## 四、工程实践（≥500字）

### 4.1 使用场景

布隆过滤器使用场景：

1. 黑名单校验
2. 快速去重
3. 爬虫URL校验
4. leveldb/rocksdb快速判断数据是否已经block中，避免频繁访问磁盘
5. 解决缓存穿透问题

### 4.2 构建方法

* 构建方法一：使用redis的module加载外部so文件
  - 优点：操作简单
  - 缺点：需要高版本的redis，容易形成大key

* 构建方法二：借助bitmap来实现，k个hash函数，创建n个bitmap(推荐)
  - 优点：操作简单
  - 缺点：由于redis的字符串要求最大为512M，所以需要拆分多个key，扩容稍微复杂

* 构建方法三：可以自己本地来实现布隆过滤器的计算，计算完之后再存入redis
  - 优点：自己操作更灵活
  - 缺点：流程复杂，需要额外服务重启或当机之后布隆过滤器丢失问题

### 4.3 LevelDB 中的 Double-Hashing

```c++
// 核心技巧：从一次 MurMurHash2 生成 k 个独立哈希值
uint32_t h = MurMurHash2(key);                // h₁
const uint32_t delta = (h >> 17) | (h << 15); // 位旋转生成步长
// h₂ = h₁ + delta, h₃ = h₂ + delta, ...
// 等价于: h_i = h₁ + (i-1) * delta
```

这是 Kirsch & Mitzenmacher (2006) 证明的技巧——一个哈希函数 + 一个增量足以模拟 k 个独立哈希函数，极大减少哈希计算开销。

### 4.4 优点

1. 节省内存空间
2. 插入和查询时间复杂度都为O(1)

### 4.5 缺点

1. 布隆过滤器不支持删除
2. 由于哈希冲突的原因，可能会出现假阳性

### 4.6 思考

* 布隆过滤器多适用于数据更新较少的场景，如果海量数据模式下，数据量又频繁变化，如何高效构建布隆过滤器呢？
  + 使用mapreduce来并行执行

* 布隆过滤器如何支持删除操作呢？
  + 计数布隆过滤器
  + 布谷鸟过滤器

## 五、源码解析和实践感悟（≥1000字）

### 5.1 k 的存储位置

一个重要细节：**k（哈希函数个数）被编码在过滤器字符串的最后一个字节**。这样：
- 同一个过滤器可以被不同 `bits_per_key` 配置的读取器正确解析
- 不需要额外的元数据通道
- `KeyMayMatch` 从 `array[len - 1]` 读出 k

### 5.2 难点与易错点

**陷阱1：`k > 30` 的处理**

```c++
if (k > 30) {
    return true;  // 兼容未来可能的新编码格式，保守返回 true
}
// 这意味着如果过滤器被未来格式编码，误报率为 100%
// 实际生产中，这永远不会触发（k 上限 30 是硬编码的）
```

**陷阱2：bits_per_key 过小导致高误报率**

```c++
// bits_per_key = 1 时，k = 0.69 → 取整为 1（被 clamp 到 1）
// 此时误报率 ≈ 1 - (1 - 1/m)^(k*n) ≈ 极高
// LevelDB 默认 bits_per_key = 10 是经过大量实验的推荐值
```

**陷阱3：布隆过滤器的"肯定"不可靠**

布隆过滤器返回 `true` 只是"可能存在"，必须再去 data block 中实际检查。依赖布隆过滤器做授权判断（如"该用户一定在黑名单中"）是错误的——存在假阳性。

### 5.3 经验总结

1. **布隆过滤器是读性能的"放大器"**——1% 误报率消除 99% 无效 IO，投入产出比极高
2. **double-hashing 是性能关键**——一次哈希替代 k 次哈希，避免了重复计算
3. **bits_per_key = 10 是"甜蜜点"**——空间开销 10 bit/key（约 1.25 byte/key），误报率 1%
4. **SSTable + Bloom Filter 是经典组合**——RocksDB、Cassandra、HBase 均采用

## 六、面试准备（≥10问法+5反问+5一句话，均带回答）

### 6.1 高频问法（≥10个）

**Q1：布隆过滤器的原理是什么？**
A：使用一个 m 位的位数组和 k 个哈希函数。插入时将 key 哈希后的 k 个位置设为 1；查询时检查这 k 个位置是否全为 1——全为 1 表明可能存在，任何一位为 0 表明一定不存在。

**Q2：为什么布隆过滤器会有误报（false positive）？**
A：因为不同 key 的哈希值可能映射到相同的位置（哈希冲突）。如果所有 k 个位置恰好都被其他 key 设置了，即使目标 key 从未被插入，也会返回"可能存在"。

**Q3：k 和 m 如何选择以最小化误报率？**
A：最优 k = ln(2) × m/n ≈ 0.693 × m/n。此时误报率 ≈ 0.6185^(m/n)。LevelDB 中 m/n = 10（bits_per_key），k ≈ 7，理论误报率约 0.82%。

**Q4：LevelDB 的 double-hashing 技巧是什么？**
A：用一次 MurMurHash2 生成 h₁，通过位旋转 `(h >> 17) | (h << 15)` 生成增量 delta，后续哈希值 = h + delta。根据 Kirsch & Mitzenmacher 的证明，这等价于使用 k 个独立哈希函数。

**Q5：布隆过滤器在 LevelDB 中如何使用？**
A：每个 SSTable 可附带一个布隆过滤器（filter block）。读操作先查询过滤器——如果返回 false，跳过该 SSTable 的磁盘读取；如果返回 true，再实际读取 data block 确认。

**Q6：布隆过滤器为什么不能删除元素？**
A：因为一个位可能被多个 key 共享。如果清零某个 key 对应的位，可能影响其他 key 的存在性判断。解决方案：计数布隆过滤器（将位改为计数器）或布谷鸟过滤器。

**Q7：bits_per_key 的含义？LevelDB 默认值是多少？**
A：每个 key 分配的位数。LevelDB 默认 10（即每个 key 用 10 bit = 1.25 byte 存储布隆信息），误报率约 1%。值越大误报率越低但空间越大。

**Q8：如何处理布隆过滤器的 k 在不同配置间的兼容性？**
A：将 k 编码在过滤器字符串的最后一个字节。读取时从该字节解析 k，而不是使用当前配置的 k——这样不同的 bits_per_key 配置可以互操作。

**Q9：什么场景不适合用布隆过滤器？**
A：1) 数据量极小（直接遍历更快）；2) 需要 100% 确定性的场景；3) 需要删除操作但不愿升级为计数布隆；4) 内存极度受限且无法接受任何误报。

**Q10：布谷鸟过滤器和布隆过滤器的区别？**
A：布谷鸟过滤器支持删除操作，在低误报率场景下空间效率更高（使用指纹替代位），但插入可能失败（需要 rehash）。布隆过滤器不支持删除，但插入一定成功。

### 6.2 反问点/陷阱点（≥5个）

- 你们在生产中对不同场景的 bits_per_key 是如何配置的？是否有针对冷热数据的差异化策略？
- 在你们的系统中，布隆过滤器的内存占用占总缓存的比例是多少？

- **陷阱问题1**："布隆过滤器返回 true 就说明 key 存在吗？"——不。true 只是"可能存在"，false 才是"一定不存在"。这是布隆过滤器最核心的认知——假阳性可接受，假阴性不可接受。
- **陷阱问题2**："布隆过滤器可以用在安全场景（如判断用户是否在黑名单）吗？"——不适合——假阳性意味着合法用户可能被误判，安全场景要求 100% 准确。
- **陷阱问题3**："计数布隆过滤器完美解决了删除问题吗？"——基本解决，但引入新问题：计数器可能溢出（通常 4 bits），且空间是普通布隆的 4×。

### 6.3 一句话答案（≥5个）

- 布隆过滤器的核心设计理念是：**用可控的误报率换取极致的空间效率和查询速度。**
- LevelDB 中布隆过滤器的关键参数：**bits_per_key = 10, k ≈ 7, 误报率 ~1%。**
- double-hashing 的核心技巧：**一次 MurMurHash2 + 位旋转增量 = k 个独立哈希值。**
- 布隆过滤器最大的局限：**不支持删除、存在假阳性、查询结果是概率性的。**
- 与缓存穿透防护的关系：**在缓存前加布隆过滤器——key 不存在时直接拒绝，避免穿透到 DB。**

- 当被问到"为什么不用哈希表替代布隆过滤器？"——回答："哈希表需要存储 key 本身（通常 8-256 字节/key），布隆过滤器只需 1-5 byte/key 的位数组。对于亿级数据，内存差距是数量级的。"
