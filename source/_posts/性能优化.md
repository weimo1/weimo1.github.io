# 性能优化

<https://zhuanlan.zhihu.com/p/4245202423>

### 影响多线程性能的因素

笔者认为，影响多线程性能的主要因素有以下两个：

**1.Lock Contention。** **2.Cache Coherency。**

Lock Contention对应使用锁来处理多线程同步问题的场景，而Cache Coherency则对应使用原子操作来处理多线程同步问题的场景。

### Lock Contention

在多线程环境中，多个线程同时尝试获取同一个锁（Lock）时，会发生竞争现象，这就是所谓的[锁竞争](https://zhida.zhihu.com/search?content_id=249871413&content_type=Article&match_order=1&q=%E9%94%81%E7%AB%9E%E4%BA%89&zhida_source=entity)（Lock Contention）。锁竞争会导致线程或进程被阻塞，等待锁被释放，从而影响系统的性能和响应时间。大多数情况下，开发人员会选择使用锁来解决线程间的同步问题，因此锁竞争问题也变得广为人知且容易理解。由于锁的存在，位于临界区的代码在同一时刻只能由一个线程执行。因此，优化的思路就是尽量避免多个线程同时访问同一资源。常见的优化方向有两种：

**1.减少临界区大小：临界区越小，这段代码的执行时间就越短，从而在整体程序运行时间中所占的比例也越小，冲突也就越少。** **2.对共享资源进行分桶操作：每个线程只会在某个桶上访问资源，理想情况下，每个线程都会访问不同的桶，这样就不会有冲突。**

减少临界区大小需要开发者对自己的代码进行仔细思考，将不必要的操作放在临界区外，例如一些初始化和内存分配操作。

对共享资源进行分桶操作在工程实践中也非常常见。例如，LevelDB的LRUCache中，每个Key只会固定在一个桶上。如果hash函数足够优秀且数据分布足够随机，这种方法可以大大提高LRUCache的性能。

### Cache Coherency

缓存一致性（Cache Coherency）是指在多处理器系统中，确保各个处理器的缓存中的数据保持一致的机制。由于现代计算机系统通常包含多个处理器，每个处理器都有自己的缓存（如L1、L2、L3缓存），因此在并发访问共享内存时，可能会出现缓存数据不一致的问题。缓存一致性协议旨在解决这些问题，确保所有处理器在访问共享内存时看到的是一致的数据。

当我们对一个共享变量进行写入操作时，实际上需要通过缓存一致性协议将该变量的更新同步到其他线程的缓存中，否则可能会读到不一致的值。实际上，这个同步过程的单位是一个缓存行（Cache Line），而且同步过程相对较慢，因为涉及到跨核通信。

由此引申出两个严重影响性能的现象：

**1.Cache Ping-Pong。** **2.False Sharing。**

### Cache Ping-Pong

[缓存乒乓效应](https://zhida.zhihu.com/search?content_id=249871413&content_type=Article&match_order=1&q=%E7%BC%93%E5%AD%98%E4%B9%92%E4%B9%93%E6%95%88%E5%BA%94&zhida_source=entity)（Cache Ping-Pong）是指在多处理器系统中，多个处理器频繁地对同一个缓存行（Cache Line）进行读写操作，导致该缓存行在不同处理器的缓存之间频繁地来回传递。这种现象会导致系统性能下降，因为缓存行的频繁传递会引起大量的缓存一致性流量和处理器间通信开销。

讲到这里，其实就可以解释为什么开头那段代码会随着线程数量的增加而性能反而下降。代码中的变量 s 是一个共享资源，但它使用了 shared\_ptr。在复制 shared\_ptr 时，会引起引用计数的增加（计数+1），多个线程频繁对同一个缓存行进行读写操作，从而引发缓存乒乓效应，导致性能下降

### False Sharing

[伪共享](https://zhida.zhihu.com/search?content_id=249871413&content_type=Article&match_order=1&q=%E4%BC%AA%E5%85%B1%E4%BA%AB&zhida_source=entity)（False Sharing）实际上是一种特殊的缓存乒乓效应（Cache Ping-Pong）。它指的是在多处理器系统中，多个处理器访问不同的数据，但这些数据恰好位于同一个缓存行中，导致该缓存行在不同处理器的缓存之间频繁传递。尽管处理器访问的是不同的数据，但由于它们共享同一个缓存行，仍然会引发缓存一致性流量，导致性能下降。

### Lock VS Atomic

可以看到，无论是哪一种情况，std::mutex 的性能都更优。当然，这个测试结果可能会因不同的操作系统而有所不同，但至少可以得出一个结论：这两者的性能是一个量级的，并不存在 atomic 一定比 std::mutex 更快的说法。这其实是因为现代 C++ 中的 std::mutex 实现已经高度优化，其实现与上面的自旋锁（SpinLock）非常相似，在低竞争的情况下并不会陷入内核态。

atomic 的优点有：

**1.可以实现内存占用极小的锁。** **2.当临界区操作可以等价于一个原子操作时，性能会更高。**

接下来结合这两个优点来看，链式数据结构的场景非常适合使用 atomic 变量。

**1.内存占用少：即使每个节点都实现一个自旋锁（SpinLock），也不会浪费太多内存。** **2.链式数据结构的临界区通常可以优化成一个指针的 CAS 操作。**

## 一、核心概念

- **定义**：性能优化是系统性识别和消除程序瓶颈的过程，核心原则是"先测量（profile）后优化，数据驱动决策"
- **关键词**：Lock Contention、Cache Coherency、False Sharing、AoS vs SoA、分支预测、noexcept 移动、pre-allocation
- **适用场景/边界**：适用于热点代码（占总运行时间 >10% 的路径）；不适用于"凭直觉优化"——未经 profiling 的优化往往是负优化

## 二、详细解析（≥200字）

- **原理拆解（三层递进）**：
  - **第一层——锁竞争（Lock Contention）**：多线程争抢同一互斥锁时，未获取锁的线程被阻塞。优化方向：① 缩小临界区（将不必要操作移出锁外）；② 分桶（hash 到不同桶，每个桶独立加锁，如 LevelDB LRUCache）
  - **第二层——缓存一致性问题**：① 缓存乒乓（Cache Ping-Pong）：多个核频繁读写同一缓存行导致该行在内核间来回传输（如 shared_ptr 引用计数）；② 伪共享（False Sharing）：不同核访问不同变量但变量碰巧在同一缓存行中，仍会引发缓存一致性流量
  - **第三层——CPU 微架构瓶颈**：分支预测失败（~15-20 cycles 流水线清空）、缓存未命中（L1~4 cycles / L2~12 / L3~40 / 主存~200+）、数据局部性差（AoS 遍历单字段浪费 67% 带宽）
- **关键数据结构/接口**：`alignas(64)` 隔离缓存行防伪共享；`SoA` 布局提升 SIMD 和缓存利用率
- **关键公式**：分支预测命中率对排序数据可达 ~100%，乱序数据可能低至 50%；noexcept 移动使 vector 扩容用 memmove 加速 30-50%

```c++
#include <algorithm>
#include <chrono>

// 1. False Sharing 示例与修复
alignas(64) struct PaddedCounter {  // 64 字节对齐隔离缓存行
    int count = 0;
};

// 2. AoS vs SoA 性能对比
struct AoS { int x, y, z; };  // 12 字节/元素
std::vector<AoS> aos(1'000'000);

struct SoA {  // 分离存储
    std::vector<int> x, y, z;
    SoA(int n) : x(n), y(n), z(n) {}
} soa(1'000'000);

// 遍历 AoS.x: 加载 12 字节只用 4 字节（缓存利用率 33%）
// 遍历 SoA.x: 加载 4 字节用 4 字节（缓存利用率 100%）

// 3. 分支预测优化——排序数据排序后分支预测 100% 命中
std::vector<int> data(1'000'000);
std::sort(data.begin(), data.end());  // 排序后分支预测率↑
long sum = 0;
for (int x : data) {

}

int main() { return 0; }
```

## 四、进阶应用（≥500字）

- **与其他主题的关联**：与并发编程（无锁数据结构、原子操作）、编译器优化（-O2/-O3 自动向量化）、内存模型（缓存一致性协议 MESI）、数据结构设计（cache-friendly 数据结构）强相关
- **工程中的真实用法**：
  - **性能排查流程**：`perf top` → 定位热点函数 → `perf record -g` 看调用路径 → 分析算法/缓存/分支三类瓶颈 → 针对性优化 → `perf stat` 验证
  - **锁 vs 原子操作**：现代 `std::mutex` 已高度优化（低竞争时不陷入内核），性能与 atomic 同量级。atomic 的优势在于：① 内存占用极小；② 临界区可简化为单条 CAS 指令时极快
  - **noexcept 对移动的性能影响**：`std::vector` 扩容时如果移动构造是 `noexcept`，走 memmove（O(1) 指针交换）；否则走拷贝（O(n) 深拷贝）。对含 `std::string`/`std::vector` 成员的类，缺省 noexcept 移动构造至关重要
  - **预分配（reserve）策略**：已知大小的 vector 用 `reserve()` 预分配，避免多次扩容——扩容的摊销操作仍需 O(log n) 次内存分配，每次都要拷贝所有已有元素
- **常见优化策略**：
  - **算法层面**：热点代码避免虚函数调用（无法内联+间接跳转~5-10ns）；字符串拼接用 `ostringstream` 或 `+=` 代替 `+` 链（减少临时对象）
  - **数据结构**：按值传递 ≤16 字节的小对象比传引用快（免间接访问）；优先用 `std::array`/`std::vector` 而非 `std::list`（连续内存 > 链表）
  - **编译器优化**：`-O3` 增加循环交换、自动向量化等激进优化；`-march=native` 启用 CPU 特定指令（AVX2/AVX512）
  - **具体技巧**：`alignas(64)` 隔离频繁写入的多线程共享变量防伪共享；用 `constexpr`/`const` 方便编译器常量传播和死代码消除；`__builtin_expect` 提示分支倾向

## 五、源码解析和实践感悟

### 1. 编译器优化的代价模型

```c++
// -O2 典型优化:
// 1. 内联: 小函数体直接替换到调用点，消除函数调用开销
// 2. 循环展开: 减少分支预测失败
// 3. 常量传播: 编译期计算常量表达式
// 4. 死代码消除: 移除不可达代码

// 分支预测案例:
// 排序后的数组遍历比乱序快 3-6x（分支预测命中率高）
if (a[i] > 128) sum += a[i];  // 排序后几乎 100% 预测正确
```

### 2. 缓存友好的数据结构

```c++
// AoS vs SoA 布局
struct AoS { int x, y, z; };  // Array of Structures - 遍历 x: stride=12
AoS arr[1000];
for (auto& a : arr) sum += a.x;  // 每次加载 12 字节只用 4 字节

// SoA 改建:
struct SoA { int x[1000], y[1000], z[1000]; };  // 遍历 x: stride=4
// 缓存利用率从 33% → 100%
```

### 实践经验
1. **测不准优化**：先 profile，热点处才优化
2. **数据局部性 > 算法复杂度**：线性扫描有序数组比二分查找快（小数据）
3. **按值传递小对象**：≤ 16 字节的值传递比引用传递快（避免间接访问）
4. **noexcept 让 vector 用 memmove**：标记移动构造 noexcept 获得 30-50% 扩容加速
5. **预分配**：reserve 避免 vector 的多次扩容和内存拷贝

## 六、面试准备

### Q&A（10题）

**Q1: 如何系统地进行性能优化？**
A: Profile→找热点→改算法→改数据结构→改内存访问→编译器优化→并行化

**Q2: 缓存未命中的代价有多大？**
A: L1 ~4 cycles, L2 ~12, L3 ~40, 主存 ~200+ cycles

**Q3: AoS 和 SoA 的区别？**
A: AoS 一个对象的所有字段连续，适合同时访问多字段；SoA 同字段集中，适合 SIMD/流式访问

**Q4: 分支预测失败的影响？**
A: 失败导致流水线清空，代价 ~15-20 cycles。排序数据、无分支写法可避免

**Q5: 虚函数的性能开销？**
A: 两次访存（vptr+vtable）+ 间接跳转（~5-10ns），加上无法内联的机会成本

**Q6: move 比 copy 快多少？**
A: 对 vector/string：move O(1)（交换指针），copy O(n)（深拷贝所有元素）

**Q7: return value optimization 有多重要？**
A: 完全消除拷贝/移动，等价于在调用方直接构造。对大型对象收益巨大

**Q8: 为什么预分配（reserve）能提速？**
A: 避免多次扩容时的内存分配 + 元素拷贝，扩容的摊销成本从 O(log n) 次分配变为 1 次

**Q9: 热点代码避免哪些操作？**
A: 虚函数调用、动态内存分配、锁竞争、异常处理路径、间接跳转

**Q10: -O2 和 -O3 的区别？**
A: -O3 增加更激进的循环优化（如自动向量化、循环交换），但可能增加代码体积

### 陷阱与反问（5个）
1. **陷阱**：盲目优化→"过早优化是万恶之源"，没有 profile 的优化是猜测
2. **反问**：性能重要还是可读性重要？→ 先保证正确+可读，热点处优化并加注释
3. **陷阱**：inline 关键字的误用→ inline 主要是链接属性，真正内联决定权在编译器
4. **反问**：用 SIMD 手写汇编值得吗？→ 优先用编译器自动向量化，不够再手写
5. **陷阱**：字符串拼接用 + 循环→每次创建临时对象，用 ostringstream 或 +=

### 一句话答案（8个）
1. **Profile first**：先测量后优化
2. **缓存命中**：访问连续内存（数组 >> 链表）
3. **AoS vs SoA**：AoS 多字段一起访问，SoA 单字段 SIMD 遍历
4. **分支预测**：排序数据、cmov 无分支写法
5. **虚函数**：每次 ~5-10ns 额外开销
6. **RVO/NRVO**：零拷贝返回值优化
7. **reserve**：预分配避免扩容
8. **noexcept 移动**：vector 扩容用 memmove
