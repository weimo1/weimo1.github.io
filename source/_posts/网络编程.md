# 网络编程

> 适用范围：Linux I/O模型（BIO/NIO/AIO）、I/O多路复用（select/poll/epoll）、用户态/内核态切换与数据拷贝、C10K并发模型选型

## 一、核心概念

- **定义**：网络编程中的 I/O 模型描述了应用程序如何与内核协作完成网络数据的收发。从阻塞 I/O (BIO) 到非阻塞轮询 (NIO) 再到 I/O 多路复用 (select/poll/epoll) 和异步 I/O (AIO)，核心演进目标是提高并发处理能力
- **关键词**：阻塞I/O、非阻塞I/O、I/O多路复用、select、poll、epoll、LT/ET、Reactor、Proactor、C10K
- **适用场景/边界**：
  - 高并发网络服务器（Web 服务器、代理、消息队列）
  - 需要同时管理多个网络连接的场景
  - 边界：纯计算密集型程序不需要 I/O 多路复用；单连接高吞吐场景用简单阻塞模型即可

## 二、详细解析（≥200字）

### 2.1 I/O 模型分类

从应用程序角度看，I/O 操作经历两个阶段：(1) 等待数据到达内核缓冲区；(2) 从内核缓冲区拷贝到用户空间。根据两个阶段的处理方式，分为五种 I/O 模型：

- **阻塞 I/O (BIO)**：两阶段均阻塞，线程完全等待
- **非阻塞 I/O (NIO)**：第一阶段轮询不阻塞，第二阶段阻塞拷贝
- **I/O 多路复用**：单线程通过 select/poll/epoll 阻塞等待多个 fd 就绪，就绪后执行 I/O
- **信号驱动 I/O**：第一阶段通过信号通知不阻塞
- **异步 I/O (AIO)**：两阶段均不阻塞，内核完成后通知

### 2.2 内核态/用户态切换与数据拷贝

每次 I/O 复用调用涉及：
- **用户态→内核态切换**：进入系统调用
- **数据拷贝**：用户空间 ↔ 内核空间传递 fd 集合或就绪事件
- **内核态→用户态切换**：系统调用返回

| 机制 | 每次调用切换次数 | 每次调用数据拷贝 |
|------|-----------------|-----------------|
| select | 2次 | 2次（传入 fd_set + 传出 fd_set） |
| poll | 2次 | 2次（传入 pollfd[] + 传出 pollfd[]） |
| epoll | 2次（epoll_wait） | 1次（仅传出就绪事件） |

epoll 的拷贝次数显著减少：`epoll_ctl` 仅在注册时拷贝一次，`epoll_wait` 只拷贝就绪事件而非全量 fd。

## 三、动手实践（代码案例）

### 3.1 select 多连接示例

```c++
fd_set read_fds;
int max_fd = listen_sock;
while (1) {
    FD_ZERO(&read_fds);
    FD_SET(listen_sock, &read_fds);
    for (int i = 0; i < client_count; i++) {
        FD_SET(client_fds[i], &read_fds);
        if (client_fds[i] > max_fd) max_fd = client_fds[i];
    }
    int ret = select(max_fd + 1, &read_fds, NULL, NULL, NULL);
    if (FD_ISSET(listen_sock, &read_fds)) {
        int new_fd = accept(listen_sock, NULL, NULL);
        client_fds[client_count++] = new_fd;
    }
    for (int i = 0; i < client_count; i++) {
        if (FD_ISSET(client_fds[i], &read_fds))
            read(client_fds[i], buf, sizeof(buf));
    }
}
```

### 3.2 poll 多连接示例

```c++
struct pollfd fds[MAX_CLIENTS];
fds[0].fd = listen_sock;
fds[0].events = POLLIN;
int nfds = 1;
while (1) {
    int ret = poll(fds, nfds, -1);
    if (fds[0].revents & POLLIN) {
        int new_fd = accept(listen_sock, NULL, NULL);
        fds[nfds].fd = new_fd;
        fds[nfds].events = POLLIN;
        nfds++;
    }
    for (int i = 1; i < nfds; i++) {
        if (fds[i].revents & POLLIN)
            read(fds[i].fd, buf, sizeof(buf));
    }
}
```

### 3.3 epoll 多连接示例（ET 模式）

```c++
int epfd = epoll_create1(0);
struct epoll_event ev, events[MAX_EVENTS];
ev.events = EPOLLIN | EPOLLET;  // 边缘触发
ev.data.fd = listen_sock;
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_sock, &ev);

while (1) {
    int nfds = epoll_wait(epfd, events, MAX_EVENTS, -1);
    for (int i = 0; i < nfds; i++) {
        if (events[i].data.fd == listen_sock) {
            int conn = accept(listen_sock, NULL, NULL);
            ev.events = EPOLLIN | EPOLLET;
            ev.data.fd = conn;
            epoll_ctl(epfd, EPOLL_CTL_ADD, conn, &ev);
        } else {
            char buf[1024];
            while (1) {  // ET 必须循环读到 EAGAIN
                ssize_t n = read(events[i].data.fd, buf, sizeof(buf));
                if (n <= 0) break;
            }
        }
    }
}
```

## 四、进阶应用（≥500字）

### 4.1 C10K → C100K → C10M 的技术演进

| 级别 | 并发数 | 核心方案 | 代表技术 |
|------|-------|---------|---------|
| C10K | 10,000 | I/O 多路复用 | epoll/kqueue + 非阻塞 I/O |
| C100K | 100,000 | 多核 + 零拷贝 | 多线程 epoll + sendfile/splice |
| C10M | 10,000,000 | 内核旁路 | DPDK/XDP + 用户态协议栈 |

### 4.2 Reactor vs Proactor

- **Reactor（反应器）**：被动等待事件（epoll_wait）→ 通知 handler 处理（同步 I/O）。代表：Nginx, Redis, Netty
- **Proactor（前摄器）**：主动提交 I/O 请求 → 内核完成 I/O 后通知（异步 I/O）。代表：Boost.Asio (Windows IOCP), io_uring

```
Reactor:  epoll_wait → 就绪通知 → 用户执行 read/write
Proactor: aio_read 提交 → 内核执行 I/O → 完成通知（回调/信号）
```

### 4.3 跨平台 I/O 复用库

- **libuv**：Node.js 底层引擎，封装 epoll/kqueue/IOCP/event ports
- **libevent**：Memcached 使用，跨平台事件通知
- **libev**：轻量级事件循环，只封装 epoll/kqueue 等
- **Boost.Asio**：C++ 标准提案基础 (Networking TS)，Proactor 模式

### 4.4 与其他主题的关联

| 关联主题 | 关联点 |
|---------|--------|
| TCP Socket | I/O 多路复用主要监视对象 |
| 虚拟文件系统 | select/poll/epoll 均基于 VFS poll 机制 |
| 并发编程 | 事件循环 + 线程池的混合并发模型 |
| io_uring | 下一代异步 I/O，在存储场景替代 epoll |

### 4.5 生产环境选型建议

- **Linux 专用 + 高并发**：epoll + ET + 非阻塞 I/O
- **跨平台**：libuv 或 Boost.Asio
- **简单场景（<1000 连接）**：poll（简单够用）
- **存储密集型**：io_uring
- **超低延迟（纳秒级）**：DPDK/XDP 内核旁路

## 五、源码解析和实践感悟（≥1000字）

### 5.1 select 内核实现核心路径

```c
// fs/select.c
static int do_select(int n, fd_set_bits *fds, struct timespec64 *end_time)
{
    ktime_t expire, *to = NULL;
    int retval;
    
    for (;;) {
        unsigned long *rinp, *routp, *rexp, *inp, *outp, *exp;
        inp = fds->in; outp = fds->out; exp = fds->ex;
        rinp = fds->res_in; routp = fds->res_out; rexp = fds->res_ex;
        
        for (int i = 0; i < n; ++rinp, ++routp, ++rexp) {
            unsigned long in, out, ex, all_bits, bit = 1, j;
            in = *inp++; out = *outp++; ex = *exp++;
            all_bits = in | out | ex;
            
            // 遍历每个 fd（位图 O(n)）
            for (j = 0; j < BITS_PER_LONG; ++j, bit <<= 1) {
                struct fd f;
                if (!(all_bits & bit)) continue;
                f = fdget(i * BITS_PER_LONG + j);
                if (f.file) {
                    // 调用 VFS poll 检查就绪
                    mask = vfs_poll(f.file, wait);
                    if (mask & in) *rinp |= bit;
                }
            }
        }
        if (retval || timed_out || signal_pending(current)) break;
        // 无事件，阻塞等待
        poll_schedule_timeout(&table, TASK_INTERRUPTIBLE, to, slack);
    }
    return retval;
}
```

### 5.2 poll 内核实现核心路径

```c
// fs/select.c
static int do_poll(struct poll_list *list, struct poll_wqueues *wait,
                   struct timespec64 *end_time)
{
    for (;;) {
        struct poll_list *walk;
        // 遍历 poll_list 链表（O(n)）
        for (walk = list; walk; walk = walk->next) {
            struct pollfd *pfd = walk->entries;
            for (int i = walk->len; i; i--, pfd++) {
                // 对每个 fd 调用 vfs_poll
                pfd->revents = vfs_poll(f.file, &wait->pt);
            }
        }
        if (count || timed_out || signal_pending(current)) break;
        poll_schedule_timeout(wait, TASK_INTERRUPTIBLE, to, slack);
    }
    return count;
}
```

### 5.3 实践经验

1. **select 的 fd_set 大小陷阱**：`FD_SETSIZE` 默认 1024，虽然可修改重编译内核但极少有人这么做。poll 用动态数组彻底解决此限制。

2. **select 会修改传入的 fd_set**：每次 select 返回时 `fd_set` 被修改为就绪集合。必须在每次调用前重新 `FD_ZERO` + `FD_SET`，否则只监听上次就绪的 fd。

3. **poll 的 revents 独立于 events**：poll 的设计更好——传入 `events`（期望事件）和传出 `revents`（实际就绪事件）分离，无需每次重建数组。

4. **epoll 的 O(1) 只是就绪事件获取**：`epoll_wait` 返回就绪事件是 O(k)，k=就绪数。但 `epoll_ctl` 增删改是 O(log n)，n=总 fd 数。所以 epoll 适合"大量 fd 但少数活跃"的场景。

5. **跨平台 I/O 复用混用陷阱**：select 在 Windows 上只支持 socket 不支 持管道/文件，需要 libuv 这样的抽象层统一 API。

### 6.1 面试高频问答

## 什么是IO

IO描述了**计算机系统和外部设备通信的过程**。  
  
常见IO有**磁盘IO**和**网络IO**。  
  
从应用程序角度来理解IO,进程的地址空间分成**用户空间**和**内核空间**，我们平时使用的应用程序都是运行在用户空间，当需要操作系统级别的资源的时候（如内存管理、文件管理、进程通信），就需要依赖内核空间。  
  
当用户进程需要执行IO操作，需要向内核发起**系统调用**，由内核执行具体IO操作。  
执行具体IO**读**操作，内核经历两个步骤：

1.等待数据读到**内核缓冲区**

2.将内核缓冲区的数据从内核空间拷贝到用户空间的用户缓冲区中。

## IO模型

IO 模型即输入 / 输出模型，它描述了数据在计算机系统中的输入和输出方式。

### BIO**（Blocking I/O，阻塞式 I/O）**

1. **工作原理**：

+ 在 BIO 模型中，当进行输入或输出操作时，如果数据不可用，线程会被阻塞，一直等待数据准备好或者操作完成。
+ 例如，在进行网络编程时，当客户端发起连接请求后，服务器端的线程会一直阻塞在 accept 方法处，直到有客户端连接到来。同样，当线程进行读取操作时，如果没有数据可读，它也会一直阻塞等待数据的到来。

2. **特点**：

+ 实现简单直观，易于理解和使用。
+ 但这种模型的效率较低，因为在等待数据的过程中，线程处于阻塞状态，无法进行其他操作，会浪费大量的系统资源，特别是在处理大量并发连接时，可能会导致系统性能严重下降。

### NIO**（Non-blocking I/O，非阻塞式 I/O）**

1. **工作原理**：

+ NIO 模型中，当进行输入或输出操作时，如果数据不可用，不会阻塞线程，而是立即返回一个状态值，表示数据不可用。线程可以继续执行其他任务，然后通过**轮询的方式**不断检查数据是否可用，当数据可用时再进行相应的操作。
+ 在 Java 中，**NIO 主要通过通道（Channel）和缓冲区（Buffer）**来实现。通道表示对数据源或数据目标的连接，缓冲区则用于存储数据。

2. **特点**：

+ 相比 BIO，NIO 能够更好地利用系统资源，提高系统的并发处理能力。
+ 但由于需要不断地轮询检查数据是否可用，会消耗一定的 CPU 资源。

### AIO**（Asynchronous I/O，异步 I/O）**

1. **工作原理**：

+ AIO 模型中，当进行输入或输出操作时，线程发起一个异步操作请求后立即返回，不会被阻塞。操作系统在后台完成数据的读取或写入操作，并在操作完成后通知应用程序。
+ 例如，在进行文件读取操作时，线程发起一个异步读取请求后可以继续执行其他任务，当操作系统完成文件读取后，会通过回调函数或者事件通知的方式告知应用程序读取结果。

2. **特点**：

+ 真正实现了异步非阻塞，充分利用了操作系统的异步处理能力，能够极大地提高系统的性能和响应速度。
+ 但实现相对复杂，需要操作系统的支持，目前并不是所有的操作系统都完全支持异步 I/O 操作。

IO 多路复用是一种同步 I/O 模型，用于高效地处理多个 I/O 操作。它允许单个进程或线程同时监视多个文件描述符（例如网络连接、文件等），以确定哪个描述符已准备好进行 I/O 操作（可读、可写或有异常情况），而无需为每个描述符创建一个单独的线程或进程。

以下是 IO 多路复用的主要特点和优势：

**一、工作原理**

IO 多路复用通常使用一个特殊的系统调用（如 select、poll、epoll 等）来实现。这个系统调用会阻塞等待，直到有一个或多个文件描述符准备好进行 I/O 操作。一旦有文件描述符就绪，系统调用就会返回，告知程序哪些描述符可以进行相应的 I/O 操作。

以网络服务器为例，服务器程序可以使用 IO 多路复用同时监听多个客户端连接。当有客户端发送数据时，服务器能够快速响应并处理该连接上的请求，而不必不断地轮询每个连接以查看是否有数据到达。

**二、主要实现方式**

1. **select**：

+ 它通过**遍历**文件描述符集合，检查每个描述符是否就绪。
+ 缺点是文件描述符数量受限，并且每次调用都需要重新设置描述符集合，效率相对较低。

2. **poll**：

+ 与 select 类似，**但没有文件描述符数量的限制。**
+ 同样在每次调用时需要遍历描述符集合，效率方面也有待提升。

3. **epoll**：

+ 采用**事件驱动**的方式，当文件描述符状态发生变化时，内核会通知应用程序。
+ 只需要在初始化时设置一次描述符集合，后续无需重复设置，效率非常高。

**三、优势**

1. **提高系统资源利用率**：避免为每个 I/O 操作创建单独的线程或进程，减少了系统资源的消耗，特别是在处理大量连接时，可以显著降低内存和 CPU 开销。
2. **高效处理大量连接**：对于高并发的服务器应用，能够轻松应对成千上万的连接，提高系统的吞吐量和响应速度。
3. **简化编程模型**：开发者可以使用统一的接口来处理多个 I/O 源，无需关心底层的实现细节，使得编程更加简洁和高效

# **1. select**

**底层原理补充**：

* **内核实现**：

+ 在`fs/select.c`中，`do_select`函数通过遍历`fd_set`位图中的每个fd，调用`vfs_poll`检查设备驱动层的就绪状态。
+ **时间复杂度**：O(n)，每次调用需遍历所有注册的fd。

**多连接示例**：

```
fd_set read_fds;
int max_fd = listen_sock;
while (1) {
    FD_ZERO(&read_fds);
    FD_SET(listen_sock, &read_fds);
    // 添加所有客户端fd到read_fds
    for (int i = 0; i < client_count; i++) {
        FD_SET(client_fds[i], &read_fds);
        if (client_fds[i] > max_fd) max_fd = client_fds[i];
    }
    // 调用select
    int ret = select(max_fd + 1, &read_fds, NULL, NULL, NULL);
    // 处理新连接
    if (FD_ISSET(listen_sock, &read_fds)) {
        int new_fd = accept(listen_sock, ...);
        client_fds[client_count++] = new_fd;
    }
    // 处理客户端数据
    for (int i = 0; i < client_count; i++) {
        if (FD_ISSET(client_fds[i], &read_fds)) {
            read(client_fds[i], ...);
        }
    }
}
```

# **2. poll**

**底层原理补充**：

* **内核实现**：

+ 在`fs/select.c`中，`do_poll`函数遍历`struct pollfd`数组，对每个fd调用`vfs_poll`。
+ **时间复杂度**：O(n)，与select相同，但支持动态fd数量。

**多连接示例**：

```
struct pollfd *fds = malloc(MAX_CLIENTS * sizeof(struct pollfd));
fds[0].fd = listen_sock;
fds[0].events = POLLIN;
int nfds = 1;
while (1) {
    int ret = poll(fds, nfds, -1);
    // 处理新连接
    if (fds[0].revents & POLLIN) {
        int new_fd = accept(listen_sock, ...);
        fds[nfds].fd = new_fd;
        fds[nfds].events = POLLIN;
        nfds++;
    }
    // 处理客户端数据
    for (int i = 1; i < nfds; i++) {
        if (fds[i].revents & POLLIN) {
            read(fds[i].fd, ...);
        }
    }
}
```

# **3. epoll**

**底层原理详细解析**：

* **核心数据结构**：

1. `struct eventpoll`：

- 定义在`fs/eventpoll.c`中，表示一个epoll实例。
- 包含两个关键成员：

```
struct rb_root_cached rbr;  // 红黑树根节点，存储所有监听的fd（epitem）
struct list_head rdllist;   // 就绪队列（rdlist），保存已就绪的epitem
```

2. `struct epitem`：

- 红黑树节点，代表一个被监听的fd：

```
struct epitem {
    struct rb_node rbn;          // 红黑树节点
    struct list_head rdllink;    // 就绪队列链表节点
    struct epoll_filefd ffd;     // 包含被监听的fd和其对应的file指针
    struct eventpoll *ep;        // 指向所属的eventpoll实例
    struct epoll_event event;    // 用户设置的监听事件（EPOLLIN等）
};
```

3. `rdllist`**（就绪队列）**：

- 双向链表，保存所有已就绪的epitem。当fd有事件触发时，内核通过回调函数`ep_poll_callback`将其添加到rdllist。

* **关键流程**：

1. `epoll_create`：

- 创建一个`eventpoll`对象，并返回其文件描述符（epfd）。

2. `epoll_ctl`：

- 操作红黑树：添加（EPOLL\_CTL\_ADD）、删除（EPOLL\_CTL\_DEL）或修改（EPOLL\_CTL\_MOD）一个epitem。
- 内核调用`ep_insert`函数：

* 初始化epitem，注册回调`ep_poll_callback`到设备的等待队列（例如socket的sk\_wq）。

3. `epoll_wait`：

- 检查`rdllist`是否为空：

* 若不为空，直接拷贝就绪的`epoll_event`到用户空间。
* 若为空，进程进入阻塞状态，直到超时或rdllist非空（通过`ep_poll`函数实现）。

* **回调机制**：

+ 当socket数据到达时，网卡触发中断，内核协议栈处理数据后，调用socket的唤醒回调（例如`sock_def_readable`）。
+ 该回调最终调用`ep_poll_callback`，将对应的epitem添加到`rdllist`，并唤醒阻塞在`epoll_wait`的进程。

**多连接示例**：

```
#define MAX_EVENTS 64
int epfd = epoll_create1(0);
struct epoll_event event, events[MAX_EVENTS];
// 监听listen_sock
event.events = EPOLLIN;
event.data.fd = listen_sock;
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_sock, &event);

while (1) {
    int nready = epoll_wait(epfd, events, MAX_EVENTS, -1);
    for (int i = 0; i < nready; i++) {
        if (events[i].data.fd == listen_sock) {
            // 接受新连接
            int new_fd = accept(listen_sock, ...);
            event.events = EPOLLIN | EPOLLET; // ET模式
            event.data.fd = new_fd;
            epoll_ctl(epfd, EPOLL_CTL_ADD, new_fd, &event);
        } else {
            // 处理客户端数据（需一次性读完，ET模式）
            char buf[1024];
            while (1) {
                ssize_t n = read(events[i].data.fd, buf, sizeof(buf));
                if (n <= 0) break; // EAGAIN或EOF
                // 处理数据...
            }
        }
    }
}
```

# 关键问题

## **1. select vs poll**

* **数据结构**：

+ `select`使用固定大小的`fd_set`位图（上限`FD_SETSIZE`）。
+ `poll`使用动态数组`struct pollfd`，无数量限制。

* **性能**：两者均为`O(n)`遍历，性能差异不大。

## **epoll高效的核心原因**

1. **红黑树管理fd**：

+ 插入/删除时间复杂度为O(log n)，适合动态增删高并发场景。

2. **就绪队列（rdllist）**：

+ 事件触发时，通过回调直接加入队列，`epoll_wait`只需遍历就绪队列（O(1)复杂度）。

3. **零遍历开销**：

+ 无需像select/poll全量遍历所有fd，仅处理活跃事件。

# **ET vs LT的底层差异**

* **LT模式**：

+ 当fd处于就绪状态时，`ep_poll_callback`会不断将epitem加入rdllist，直到状态被处理。

* **ET模式**：

+ 仅在fd状态变化时触发一次`ep_poll_callback`，后续即使仍有数据，也不会重复加入rdllist，除非有新事件触发。

# I/O多路复用技术中的用户态/内核态切换与数据拷贝

## **1. select**

### **用户态/内核态切换**

1. **调用**`select`**时**：

+ 用户程序调用`select`，进入内核态。
+ 内核遍历所有注册的fd，检查其就绪状态。

2. **返回时**：

+ 内核将就绪的fd集合（`fd_set`）返回给用户程序，切换回用户态。

每次调用`select`都会发生**两次用户态/内核态切换**（调用和返回）。

### **数据拷贝**

1. **调用**`select`**时**：

+ 用户程序将`fd_set`（包含所有监听的fd）从用户态拷贝到内核态。

2. **返回时**：

+ 内核将修改后的`fd_set`（标记就绪的fd）从内核态拷贝回用户态。

每次调用`select`都会发生**两次数据拷贝**（传入和传出）。

### select 优缺点

* 优点：跨平台
* 缺点

+ 单个进程能够监视的文件描述符的数量存在最大限制，通常是 1024。当然可以更改数量，但由于 select(2) 采用轮询的方式扫描文件描述符，文件描述符数量越多，性能越差
+ 每次调用 select(2)，都需要把 fd\_set 对象从用户空间拷贝到内核空间，在返回时，从内核空间拷贝到用户空间
+ select(2) 返回的是含有整个监视的文件描述符，应用程序需要遍历整个数组才能发现哪些句柄发生了事件
+ 会（清空）修改传入的 fd\_set 对象（地址传递），返回的使用当作返回空间。所以应用程序所以每次都需要重新拷贝，传入副本，以免自己维持的 fd\_set 被污染

---

## **2. poll**

### **用户态/内核态切换**

1. **调用**`poll`**时**：

+ 用户程序调用`poll`，进入内核态。
+ 内核遍历所有注册的fd（`struct pollfd`数组），检查其就绪状态。

2. **返回时**：

+ 内核将修改后的`struct pollfd`数组返回给用户程序，切换回用户态。

每次调用`poll`都会发生**两次用户态/内核态切换**（调用和返回）。

### **数据拷贝**

1. **调用**`poll`**时**：

+ 用户程序将`struct pollfd`数组从用户态拷贝到内核态。

2. **返回时**：

+ 内核将修改后的`struct pollfd`数组从内核态拷贝回用户态。

每次调用`poll`都会发生**两次数据拷贝**（传入和传出）。

### poll 优缺点

* 优点

+ select(2) 会修改传入的 fd\_set 参数，把它当作返回的空间存储返回的数据，而 poll(2) 不会，返回数据和传入的数据不互相干扰；
+ poll(2) 的描述符类型使用链表实现，没有描述符数量的限制；

* 缺点

+ 每次调用 poll(2)，都需要把 pollfd 链表从用户空间拷贝到内核空间，在返回时，将返回数据从内核空间拷贝到用户空间
+ poll(2) 返回的是含有整个 pollfd 链表，应用程序需要遍历整个链表才能发现哪些句柄发生了事件

---

## **3. epoll**

### **用户态/内核态切换**

1. **调用**`epoll_ctl`**时**：

+ 用户程序调用`epoll_ctl`（添加、删除或修改fd），进入内核态。
+ 内核更新红黑树中的`epitem`节点。
+ 操作完成后，切换回用户态。

2. **调用**`epoll_wait`**时**：

+ 用户程序调用`epoll_wait`，进入内核态。
+ 内核检查`rdllist`（就绪队列），若不为空，则拷贝就绪事件到用户空间；若为空，则阻塞等待。
+ 返回时，切换回用户态。

每次调用`epoll_ctl`和`epoll_wait`都会发生**两次用户态/内核态切换**（调用和返回）。但`epoll_wait`的切换频率远低于`select/poll`，因为它只处理活跃事件。

### **数据拷贝**

1. **调用**`epoll_ctl`**时**：

+ 用户程序将`struct epoll_event`从用户态拷贝到内核态（仅注册时一次）。

2. **调用**`epoll_wait`**时**：

+ 内核将就绪的`struct epoll_event`从内核态拷贝回用户态。

`epoll`的**数据拷贝次数显著减少**：

* `epoll_ctl`仅在注册fd时拷贝一次。
* `epoll_wait`只拷贝就绪事件，而不是全量fd集合。

---

## 对比总结

|  |  |  |
| --- | --- | --- |
| 机制 | 用户态/内核态切换次数（每次调用） | 数据拷贝次数（每次调用） |
| select | 2次（调用+返回） | 2次（传入fd\_set+传出fd\_set） |
| poll | 2次（调用+返回） | 2次（传入pollfd数组+传出pollfd数组） |
| epoll | 2次（调用+返回） | 1次（仅传出就绪事件） |

## 详细场景分析

### **1. select**

* **用户态/内核态切换**：

+ 每次调用`select`时，用户程序进入内核态，内核遍历所有fd后返回用户态。
+ 例如：监控1000个fd，每次调用`select`都会遍历1000个fd，发生2次切换。

* **数据拷贝**：

+ 每次调用`select`时，用户程序将1000个fd的`fd_set`拷贝到内核态。
+ 内核返回时，将修改后的`fd_set`拷贝回用户态。

### **2. poll**

* **用户态/内核态切换**：

+ 每次调用`poll`时，用户程序进入内核态，内核遍历所有fd后返回用户态。
+ 例如：监控1000个fd，每次调用`poll`都会遍历1000个fd，发生2次切换。

* **数据拷贝**：

+ 每次调用`poll`时，用户程序将1000个`struct pollfd`拷贝到内核态。
+ 内核返回时，将修改后的`struct pollfd`数组拷贝回用户态。

### **3. epoll**

* **用户态/内核态切换**：

+ 调用`epoll_ctl`时，用户程序进入内核态，更新红黑树后返回用户态。
+ 调用`epoll_wait`时，用户程序进入内核态，检查`rdllist`后返回用户态。
+ 例如：监控1000个fd，只有10个fd就绪时，`epoll_wait`只需处理10个fd，发生2次切换。

* **数据拷贝**：

+ 调用`epoll_ctl`时，用户程序将`struct epoll_event`拷贝到内核态（仅注册时一次）。
+ 调用`epoll_wait`时，内核将10个就绪的`struct epoll_event`拷贝回用户态。

---

在 Linux 高性能网络编程中，`epoll` 的性能优势显著，但 `select` 和 `poll` 仍被使用的原因可以从多个角度分析。以下是关键点：

### **1. 跨平台兼容性**

* `select` **和** `poll` 是 **POSIX 标准**，支持所有主流操作系统（Linux、Windows、macOS、BSD 等）。
* `epoll` 是 Linux 特有 的机制，无法直接移植到其他系统。
* 适用场景：

+ 跨平台项目（如 Nginx 通过抽象层支持多平台）。
+ 需兼容旧系统（如嵌入式设备使用旧内核）。

---

### **2. 简单场景下的轻量级需求**

* 连接数少时：select 和poll的代码更简单，无需处理复杂的事件注册机制。示例：

```
// select 示例（监听单个 socket）
fd_set read_fds;
FD_ZERO(&read_fds);
FD_SET(sockfd, &read_fds);
select(sockfd + 1, &read_fds, NULL, NULL, NULL);
```

* `epoll` **需要初始化、事件注册等步骤**，代码复杂度更高。

---

### **3. 历史遗留代码和维护成本**

* 旧项目依赖：早期代码基于 select/poll实现，若运行稳定，重构风险高。

+ 如 Apache 1.x 使用 `select`，而 Apache 2.x 引入多模块支持（包括 `epoll`）。

* **团队熟悉度**：维护者对 `select`/`poll` 更熟悉，短期无需切换。

---

### **4. 文件描述符类型的支持**

* `select` **和** `poll` 支持 **所有文件描述符类型**（如管道、终端、套接字）。
* `epoll` 主要优化 **网络套接字**，对其他类型支持较弱（如无法直接监视普通文件）。

---

### **5. 性能并非唯一考量**

* **低并发场景**：当连接数小于 1000 时，`select`/`poll` 的性能与 `epoll` 差异不大。
* **资源占用**：`epoll` 需要内核维护事件表，可能占用更多内存（极端场景需权衡）。

---

### **6. 特殊场景下的行为差异**

* **信号处理**：`select` 在等待时可能被信号中断，需手动处理 `EINTR`，而 `epoll` 通过 `epoll_pwait` 支持原子操作。
* **超时精度**：`poll` 支持毫秒级超时，`select` 支持微秒（但实际精度依赖内核），`epoll` 支持纳秒级（`epoll_wait` 的 `timeout` 参数）。

---

### **7. 设计哲学对比**

|  |  |  |
| --- | --- | --- |
| **机制** | **优势** | **劣势** |
| `select` | 跨平台、简单易用 | 文件描述符数量限制（1024）、线性扫描效率低 |
| `poll` | 无文件描述符数量限制 | 仍需线性扫描、跨平台但性能一般 |
| `epoll` | 高性能（事件驱动，O(1) 复杂度）、支持大并发 | Linux 独有、代码复杂、需内核 2.6+ |

---

### **8. 实际应用场景示例**

* 使用 `select`/`poll` 的场景：

+ 跨平台工具（如 `libevent` 内部根据平台选择后端）。
+ 旧版服务器或低并发控制程序（如小型 IoT 设备）。
+ 需同时监听多种文件描述符（如串口 + 网络）。

* 必须用 `epoll` 的场景：

+ 高性能服务器（如 Nginx、Redis）。
+ 单机数十万并发连接（如 WebSocket 推送服务）。

---

### **总结**

* **优先用** `epoll`：若项目是 Linux 专用且需要高并发。
* **选择** `select`**/**`poll`：若需跨平台、维护旧代码，或连接数较少。
* **混合使用**：现代框架（如 libuv）通过抽象层封装多种机制，自动选择最优实现。

## 六、面试准备

### 6.1 面试高频问答

**Q1：select/poll/epoll 的演进路线是什么？**

A：select (1983) 解决多 fd 阻塞问题但限制 1024；poll (1997) 用链表突破数量限制但仍是 O(n) 遍历；epoll (2002) 通过事件驱动实现 O(1) 就绪获取，彻底解决 C10K。

**Q2：epoll 为什么是 O(1)？**

A：epoll_ctl 用红黑树管理所有监视 fd（O(log n) 增删），epoll_wait 直接从就绪链表取事件（O(1) 就绪数），无遍历开销。

**Q3：水平触发(LT)和边缘触发(ET)的区别？**

A：LT 模式下只要 fd 就绪就持续通知（类似 select/poll），ET 只在状态变化时通知一次。ET 要求非阻塞 I/O + 循环读取直到 EAGAIN。

**Q4：libuv/libevent 等网络库解决了什么问题？**

A：封装 select/poll/epoll/kqueue/IOCP 的跨平台差异，提供统一的异步 I/O API，内置定时器、信号处理、线程池等。

**Q5：网络编程中常见的并发模型有哪些？**

A：单线程 Reactor（Redis）、多线程 Reactor（每个线程一个事件循环，如 memcached）、Proactor（Asio）、协程模型（Go 的 goroutine + netpoller）。

### 6.2 陷阱与反问

**陷阱1**：ET 模式下只读一次就返回 → 可能丢数据（必须循环读到 EAGAIN）
**陷阱2**：跨平台的 I/O 复用混用 → select 在 Windows 只支持 socket
**陷阱3**：回调中做耗时操作 → 事件循环阻塞

**反问**：C10K、C100K、C10M 分别用什么方案？
*答案：C10K 用 epoll + 非阻塞 I/O；C100K 多线程/多进程 + epoll + 零拷贝；C10M 需要内核旁路（DPDK/XDP）或用户态协议栈。*

### 6.3 一句话答案

1. **I/O 多路复用**：单线程监视多个 fd，就绪时通知应用处理
2. **select/poll/epoll**：三代演进，从 O(n) 遍历到 O(1) 事件驱动
3. **LT vs ET**：水平触发反复通知，边缘触发仅通知一次需循环读
4. **libuv**：跨平台异步 I/O 库，Node.js 底层引擎
5. **Reactor**：被动等待事件通知后处理，epoll 的典型使用模式
6. **C10K**：单机万级并发连接的挑战，epoll 是经典答案
