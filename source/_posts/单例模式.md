# 单例模式

# 单例模式

**确保一个类最多只有一个实例，并提供一个全局访问点**

有的时候我们希望一个对象在全局是唯一的，在程序的这次运行过程中，不管我什么时候、在哪里、多少次获取这个对象，它还是那个它。

听起来很简单，我们来看实现，单例的实现分为两种：

* 饿汉式：类加载就会导致该单实例对象被创建
* 懒汉式：类加载不会导致该单实例对象被创建，而是首次使用该对象时才会创建

## 局部静态变量

我们知道当一个函数中定义一个局部静态变量，那么这个局部静态变量只会初始化一次，就是在这个函数第一次调用的时候，以后无论调用几次这个函数，函数内的局部静态变量都不再初始化。

```
class Single2 {
private:
    Single2()
    {
    }
    Single2(const Single2&) = delete;
    Single2& operator=(const Single2&) = delete;
public:
    static Single2& GetInst()
    {
        static Single2 single;
        return single;
    }
};
```

## 饿汉式初始化

```
//饿汉式
class Single2Hungry
{
private:
    Single2Hungry()
    {
    }
    Single2Hungry(const Single2Hungry&) = delete;
    Single2Hungry& operator=(const Single2Hungry&) = delete;
public:
    static Single2Hungry* GetInst()
    {
        if (single == nullptr)
        {
            single = new Single2Hungry();
        }
        return single;
    }
private:
    static Single2Hungry* single;
};
```

## 懒汉式初始化

很多人觉得什么时候调用初始化是用户的权利，不应该加以限制，所以就有了懒汉式方式初始化资源，在用到时如果没有初始化单例则初始化，如果初始化了则直接使用.

```
class SinglePointer
{
private:
    SinglePointer()
    {
    }
    SinglePointer(const SinglePointer&) = delete;
    SinglePointer& operator=(const SinglePointer&) = delete;
public:
    static SinglePointer* GetInst()
    {
        if (single != nullptr)
        {
            return single;
        }
        s_mutex.lock();
        if (single != nullptr)
        {
            s_mutex.unlock();
            return single;
        }
        single = new SinglePointer();
        s_mutex.unlock();
        return single;
    }
private:
    static SinglePointer* single;
    static std::mutex s_mutex;
};
```

## call\_once

C++11 提出了`call_once`函数，我们可以配合一个局部的静态变量`once_flag`实现线程安全的初始化。  
`call_once`函数时，会判断`once_flag`是否被初始化，如没被初始化则进入初始化流程，调用我们提供的初始化函数。

```
class SingletonOnce {
private:
    SingletonOnce() = default;
    SingletonOnce(const SingletonOnce&) = delete;
    SingletonOnce& operator = (const SingletonOnce& st) = delete;
    static std::shared_ptr<SingletonOnce> _instance;

public :
    static std::shared_ptr<SingletonOnce> GetInstance() {
        static std::once_flag s_flag;
        std::call_once(s_flag, [&]() {
            _instance = std::shared_ptr<SingletonOnce>(new SingletonOnce);
            });

        return _instance;
    }

    void PrintAddress() {
        std::cout << _instance.get() << std::endl;
    }

    ~SingletonOnce() {
        std::cout << "this is singleton destruct" << std::endl;
    }
};

std::shared_ptr<SingletonOnce> SingletonOnce::_instance = nullptr;
```

## 单例模板（多次使用单例类）

```
//为了让单例更加通用，可以做成模板类
template <typename T>
class Singleton {
protected:
    Singleton() = default;
    Singleton(const Singleton<T>&) = delete;
    Singleton& operator=(const Singleton<T>& st) = delete;
    static std::shared_ptr<T> _instance;
public:
    static std::shared_ptr<T> GetInstance() {
        static std::once_flag s_flag;
        std::call_once(s_flag, [&]() {
            _instance = std::shared_ptr<T>(new T);
            });
        return _instance;
    }
    void PrintAddress() {
        std::cout << _instance.get() << std::endl;
    }
    ~Singleton() {
        std::cout << "this is singleton destruct" << std::endl;
    }
};
template <typename T>
std::shared_ptr<T> Singleton<T>::_instance = nullptr;
```

## 总结

### 使用单例模式的原因

* 资源控制：单例模式可以用来控制系统中的资源，例如数据库连接池或线程池，确保这些关键资源不会被过度使用。
* 内存节省：当需要一个对象进行全局访问，但创建多个实例会造成资源浪费时，单例模式可以确保只创建一个实例，节省内存。
* 共享：单例模式允许状态或配置信息在系统的不同部分之间共享，而不需要传递实例。
* 延迟初始化：单例模式支持延迟初始化，即实例在首次使用时才创建，而不是在类加载时。
* 一致的接口：单例模式为客户端提供了一个统一的接口来获取类的实例，使得客户端代码更简洁。
* 易于维护：单例模式使得代码更易于维护，因为所有的实例都使用相同的实例，便于跟踪和修改变更。

### 单例模式的应用场景

* 配置管理器：在应用程序中，配置信息通常只需要读取一次，并全局使用。单例模式用于确保配置管理器只被实例化一次。
* 日志记录器：一个系统中通常只需要一个日志记录器来记录所有的日志信息，使用单例模式可以避免日志文件的重复写入。
* 数据库连接池：数据库连接是一种有限的资源，使用单例模式可以确保数据库连接池的唯一性，并且能够重用连接，减少连接创建和销毁的开销。
* 线程池：类似于数据库连接池，线程池也是有限的资源，使用单例模式可以避免创建过多的线程，提高应用程序的并发性能。
* 任务调度器：在需要全局调度和管理的场景下，如定时任务调度器，单例模式提供了一个集中的管理方式。
* 网站的计数器：一般也是采用单例模式实现，否则难以同步。

单例模式中GetInst()为什么是静态的？

1）静态方法可以通过类名直接访问，无需创建类的实例。这样可以方便地获取唯一实例，而不需要先实例化类。 2）类的构造函数已经被私有化，无法直接实例化对象，智能通过定义静态成员函数的方式通过类名::方法名的方式进行构造访问 3）静态局部变量的方式是线程安全的，能确保在多线程环境下也只会创建一个实例

## 五、源码解析和实践感悟

### 5.1 源码解析

#### 局部静态变量的线程安全实现（C++11 起）

```cpp
// C++11 标准保证局部静态变量初始化的线程安全
static Single2& GetInst() {
    static Single2 single;  // 编译器插入类似 call_once 的守卫
    return single;
}
// 编译器生成的伪代码：
// static bool initialized = false;
// static std::mutex init_mutex;
// if (!initialized) {
//     lock_guard lock(init_mutex);
//     if (!initialized) {
//         new (&single) Single2();
//         initialized = true;
//     }
// }
```

这是 C++11 后最推荐的单例写法——零学习成本、零锁手动管理、编译器保证线程安全。

#### DCLP（双重检查锁定）的内存序陷阱

```cpp
// 危险的 DCLP 写法——C++11 前无内存模型保证
SinglePointer* SinglePointer::GetInst() {
    if (single == nullptr) {          // ① 第一重检查（无锁）
        lock_guard lock(s_mutex);
        if (single == nullptr) {      // ② 第二重检查（有锁）
            single = new SinglePointer(); // ③ 危险！
            // new 分三步：分配内存 → 构造对象 → 赋值给指针
            // CPU 可能重排：先赋值指针再构造 → ① 读取到非空但未初始化的指针
        }
    }
    return single;
}
```

C++11 虽有内存模型，但仍建议直接用局部静态变量或 `call_once`，避免与 CPU 乱序执行较劲。

#### call_once + once_flag 的内部机制

```cpp
// std::call_once 的简化内核
class once_flag {
    atomic<int> state{0};  // 0=未执行, 1=执行中, 2=已完成
};

void call_once(once_flag& flag, Callable f) {
    int expected = 0;
    if (flag.state.compare_exchange_strong(expected, 1, memory_order_acquire)) {
        // 当前线程获得执行权
        f();
        flag.state.store(2, memory_order_release); // 广播完成
    } else {
        while (flag.state.load(memory_order_acquire) != 2) {
            this_thread::yield();  // 等待执行完成
        }
    }
}
```

### 5.2 实践经验

1. **首选局部静态变量**：C++11 起编译器保证线程安全，代码量最少，是 Meyers Singleton
2. **需要懒加载时注意析构顺序**：单例之间互相引用时，析构顺序不确定可能导致访问已销毁对象
3. **单例模板（继承方式）注意友元**：子类构造私有需声明 `friend class Singleton<T>`
4. **不要滥用单例**：单例本质是全局变量，增加耦合、难以测试、不利于多实例部署——能用依赖注入代替就别用单例
5. **shared_ptr 单例有双重释放风险**：`_instance` 和外部 shared_ptr 各自持有引用计数导致重复析构
6. **多 DLL 环境下单例模板不可靠**：每个 DLL 有独立的静态存储区，`singleton<T>()` 可能创建多个实例

## 六、面试准备

### 6.1 面试 Q&A

**Q1: 饿汉式和懒汉式单例的区别？**

饿汉式：程序启动时即创建实例（全局变量/静态成员直接初始化），线程安全但可能浪费资源。懒汉式：首次调用时才创建（局部静态变量/DCLP），资源按需分配但需处理线程安全。C++11 局部静态变量是懒汉+线程安全的最佳实现。

**Q2: 为什么 C++11 后局部静态变量单例是线程安全的？**

C++11 标准（N2660）明确要求：多线程同时首次进入含局部静态变量的函数时，只有一个线程执行初始化，其他线程阻塞等待初始化完成。编译器通过插入类似 `call_once` 的守卫实现。

**Q3: DCLP 在 C++11 前为什么有问题？**

C++03 没有内存模型，`single = new T()` 的三步操作（分配、构造、赋值）可被 CPU/编译器重排。线程 A 先赋值指针再构造，线程 B 通过第一重检查读到非空指针，使用未初始化对象 → 未定义行为。

**Q4: std::call_once 和 局部静态变量的选择？**

局部静态变量最简单（一行代码），适合单例工厂函数。`call_once` 适合延迟初始化任何资源（不只对象创建），且 `once_flag` 可复用（reset 后重新初始化）。

**Q5: 单例模板的友元设计为什么是必需的？**

```cpp
template<typename T> class Singleton {
protected: Singleton() = default;  // 子类可访问
};
class MyClass : public Singleton<MyClass> {
private: MyClass() {}  // 私有构造
    friend class Singleton<MyClass>;  // 必须！否则 Singleton 无法 new MyClass
};
```
模板基类需要访问子类私有构造函数，`friend` 声明是唯一途径。

**Q6: 单例的析构问题如何处理？**

局部静态变量：程序退出时按构造逆序销毁，但依赖其他已销毁单例可能出错。shared_ptr 单例：引用计数管理，但需注意循环引用。推荐方案：单例中不持有其他单例的裸指针，用 `weak_ptr` 或注册 atexit 回调。

**Q7: 单例模式是否违反单一职责原则？**

有争议——单例类既要管业务逻辑又要管实例创建（两个职责）。实践中如果实例管理很简单（局部静态变量），可以接受；如果初始化逻辑复杂，应分离为工厂 + 单例持有。

**Q8: 如何测试使用单例的代码？**

主要困难：单例的全局状态会渗入测试用例。解决办法：① 提供 `reset()` 或 `set_instance()` 接口允许测试注入 Mock；② 使用依赖注入替代直接访问单例；③ 测试间隔离（每个测试前重建单例）。

### 6.2 常见陷阱与面试反问

1. **陷阱**：线程 A 和 B 同时调用 `GetInst()`，DCLP 无内存屏障 → 读到半初始化对象。**修复**：改用局部静态变量或 `call_once`。

2. **陷阱**：`static Single2 single;` 定义在头文件中且非 inline → 多个 TU 各自创建实例。**修复**：声明与定义分离，或加 `inline`（C++17）。

3. **陷阱**：单例析构时被其他线程访问 → use-after-free。**修复**：确保所有线程在单例析构前退出，或用 shared_ptr 延长生命周期。

4. **反问**：「什么时候不应该用单例？」希望听到：需多实例、需 mock 测试、需多态（不同子类实例）、对象有状态且需隔离的场景。

5. **反问**：「C++ 中销毁一个单例后如何重新创建？」希望听到：`call_once` 配合 `once_flag.reset()`（C++17 无此接口）、placement new 销毁后重新构造、或使用 shared_ptr + reset。
