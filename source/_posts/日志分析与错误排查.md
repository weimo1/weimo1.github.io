# 日志分析与错误排查

> 适用范围：Linux 线上问题排查——日志分类、grep 进阶、系统诊断工具链、内核日志与网络抓包分析。

## 一、核心概念

- **定义**：日志分析与错误排查是后端开发与 SRE 的核心技能，涵盖系统日志、应用日志、内核日志的分类解读，以及 grep/journalctl/dmesg/strace/tcpdump 等工具的组合使用。
- **关键词**：系统日志（syslog/messages）、认证日志（auth.log/secure）、内核日志（kern.log/dmesg）、应用日志（nginx/自定义）、结构化日志（journald）
- **适用场景/边界**：
  - 线上服务异常（500、超时、崩溃）的快速定位
  - 安全事件审计（认证失败、权限异常）
  - 不适合：大规模日志聚合分析（需 ELK/Loki 等平台）

### 日志分类

| 类型 | Debian/Ubuntu 路径 | RHEL/CentOS 路径 | 内容 |
|------|-------------------|-----------------|------|
| 系统日志 | `/var/log/syslog` | `/var/log/messages` | 系统级事件、服务启停 |
| 认证日志 | `/var/log/auth.log` | `/var/log/secure` | SSH 登录、sudo 操作 |
| 内核日志 | `/var/log/kern.log` | `/var/log/kern.log` | 内核模块加载、硬件错误 |
| 应用日志 | `/var/log/nginx/access.log` | 同 | Web 服务器访问日志 |
| 自定义日志 | 开发者定义 | 同 | 业务逻辑日志 |

## 二、详细解析

### grep 高效查找错误

```bash
# 查找所有错误（忽略大小写）
grep -i "error" app.log

# 查找特定错误代码
grep "404" access.log

# 查找错误并显示上下文
grep -C 5 "exception" app.log   # 前后各5行
grep -A 3 "failed" app.log      # 后3行
grep -B 2 "timeout" app.log     # 前2行
```

### 多关键词搜索

```bash
# AND 关系：同时包含 "error" 和 "connection"
grep "error" app.log | grep "connection"
grep -E "error.*connection|connection.*error" app.log
awk '/error/ && /connection/' app.log

# OR 关系：包含 "error" 或 "warning"
grep -E "error|warning" app.log
grep -E "404|500|503" access.log

# 排除关键词：查 error 但排除 "timeout"
grep "error" app.log | grep -v "timeout"
grep -P "error(?!.*timeout)" app.log
```

### 错误分析进阶

```bash
# 时间范围分析
sed -n '/2023-08-01 14:00:00/,/2023-08-01 15:00:00/p' app.log | grep "error"
grep "error" app.log | awk '$1" "$2 >= "2023-08-01 14:00:00" && $1" "$2 <= "2023-08-01 15:00:00"'

# 错误统计（按类型聚合）
grep "error" app.log | awk '{print $5}' | sort | uniq -c | sort -nr

# 错误频率直方图（按分钟）
grep "error" app.log | awk '{print $1, $2}' | cut -c 1-16 | uniq -c

# 关联分析：查找错误相关的请求 ID
grep "error" app.log | awk '{print $8}' | xargs -I {} grep {} access.log

# 实时错误监控
tail -f app.log | grep --line-buffered "error"
multitail -e "error" app.log
```

## 三、动手实践

### 3.1 19 种排查工具速查

**1. dmesg** — 内核环形缓冲区消息（硬件错误、驱动异常、OOM）

```bash
dmesg | less          # 分页查看
dmesg -T              # 人类可读时间戳
dmesg | grep -i error # 过滤错误
```

**2. journalctl** — systemd 日志（比 dmesg 更全面）

```bash
journalctl -xe                           # 最新日志跳到末尾
journalctl -u nginx.service              # 指定服务日志
journalctl --since "2024-01-01" --until "2024-01-02"
```

**3. tail / less** — 日志文件查看

```bash
tail -f /var/log/nginx/error.log   # 实时跟踪
less /var/log/syslog               # 分页查看（支持搜索）
```

**4. grep** — 文本搜索

```bash
grep -r "Connection refused" /var/log/   # 递归搜索目录
ps aux | grep nginx                      # 过滤进程
```

**5. find** — 文件搜索

```bash
find /var/log -name "*.log" -mtime -1   # 24h内修改的日志
find / -size +100M -exec ls -lh {} \;   # 大于100MB的文件
```

**6. lsof** — 列出打开的文件

```bash
lsof /var/log/syslog          # 谁在读写此文件
lsof -i :80                   # 占用80端口的进程
lsof -p PID                   # 指定进程打开的文件
```

**7. netstat / ss** — 网络连接统计（推荐 ss）

```bash
ss -tulnp | grep :80                    # 监听80端口的进程
netstat -anp | grep ESTABLISHED         # 已建立连接
```

**8. ip / ifconfig** — 网络配置

```bash
ip addr show      # 所有网络接口 IP
ip route show     # 路由表
```

**9. ping** — 连通性测试

```bash
ping 8.8.8.8
ping -c 4 google.com
```

**10. traceroute / mtr** — 路由跟踪

```bash
traceroute google.com
mtr -r google.com    # 实时跟踪更直观
```

**11. nslookup / dig** — DNS 查询

```bash
dig google.com       # 详细 DNS 解析
nslookup google.com  # 快速查询
```

**12. top / htop** — 实时进程监控

```bash
top                  # 按 CPU 排序
htop                 # 增强版（鼠标操作、树状显示）
```

**13. ps** — 进程快照

```bash
ps aux | grep nginx  # nginx 相关进程
ps -efj              # 进程树结构
```

**14. free** — 内存使用

```bash
free -h              # 人类可读（GB/MB）
free -s 5            # 每5秒刷新
```

**15. df** — 磁盘空间

```bash
df -h                # 所有挂载点
df -h /home          # 指定目录所在磁盘
```

**16. du** — 目录大小

```bash
du -sh /var/log      # 总大小
du -h --max-depth=1 /  # 根目录一级子目录大小
```

**17. iostat** — 磁盘 IO 统计

```bash
iostat -x 2          # 每2秒扩展统计
```

**18. strace** — 系统调用跟踪

```bash
strace -p PID                      # 跟踪运行中进程
strace -e trace=open,read,write ls # 跟踪特定系统调用
```

**19. uptime** — 系统负载

```bash
uptime  # 输出 1/5/15 分钟 load average
```

**20. tcpdump** — 网络抓包

```bash
tcpdump -i eth0 port 80       # 抓 HTTP 流量
tcpdump -n icmp               # 抓 ICMP 包
tcpdump -w dump.pcap          # 保存供 Wireshark 分析
```

## 四、进阶应用

### 4.1 线上服务不可访问排查链

```bash
# 1. 本地确认服务可达
curl -v localhost:端口
# 2. 确认进程存活和监听
ss -tunlp | grep 端口
# 3. 检查 TCP 统计（重传率、连接失败）
netstat -s | grep -E "retransmit|failed"
# 4. 检查 OOM
dmesg | tail -20 | grep -i oom
# 5. 资源检查
top -bn1 | head -5 && df -h
```

### 4.2 日志轮转（logrotate）配置

```bash
# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily              # 每天轮转
    rotate 30          # 保留30天
    compress           # 压缩旧日志
    delaycompress      # 延迟压缩（保留一天未压缩）
    missingok          # 日志不存在不报错
    notifempty         # 空文件不轮转
    copytruncate       # 复制后截断（不重启服务）
}
```

### 4.3 结构化日志与 journald

```c
#include <systemd/sd-journal.h>

// 应用发送结构化日志到 journald
sd_journal_send(
    "MESSAGE=Connection refused from %s:%d", client_ip, client_port,
    "PRIORITY=%d", LOG_ERR,           // 0=emerg, 7=debug
    "SYSLOG_IDENTIFIER=%s", "myapp",  // 应用标识
    "ERRNO=%d", errno,
    "CODE_FILE=%s", __FILE__,
    "CODE_LINE=%d", __LINE__,
    NULL);
```

按字段高效查询：`journalctl PRIORITY=3 SYSLOG_IDENTIFIER=myapp`

## 五、源码解析和实践感悟

### 5.1 strace 系统调用捕获内核路径（源码级）

```c
// Linux kernel ptrace.c + syscall_trace_enter
// strace -p PID 的底层：ptrace(PTRACE_SYSCALL) 设置跟踪标志
static inline void syscall_trace_enter(struct pt_regs *regs) {
    // TIF_SYSCALL_TRACEPOINT: ftrace/SystemTap 用的
    if (test_thread_flag(TIF_SYSCALL_TRACEPOINT))
        trace_sys_enter(regs, regs->syscallno);
    // TIF_SYSCALL_TRACE: ptrace/strace 用的
    if (test_thread_flag(TIF_SYSCALL_TRACE)) {
        // 暂停被跟踪进程，通知 tracer（strace 进程）
        ptrace_report_syscall(regs);
        // tracer 可在此读取 regs（syscall 号+参数）
    }
}

// strace 用户态的打印逻辑（简化）
void print_syscall(struct tcb *tcp) {
    // tcp->u_arg[0..5] 是系统调用的 6 个参数
    // tcp->scno 是系统调用号（__NR_openat, __NR_read 等）
    const struct sysent *ent = &sysent[tcp->scno];
    tprintf("%s(", ent->sys_name);
    for (int i = 0; i < ent->nargs; i++) {
        print_arg(tcp, i);  // 按类型解析参数（fd, path, flags...）
    }
    tprintf(") = ");
    // 等 syscall 返回后打印返回值
}
```

### 5.2 tcpdump 的 BPF 过滤器编译

```c
// tcpdump 将人类可读的过滤表达式编译为 BPF 字节码注入内核
// "tcp port 80" → BPF 指令序列
// libpcap/gencode.c — 过滤表达式编译器
struct bpf_insn {
    u_short code;    // BPF 操作码（LD/ST/ALU/JMP/RET）
    u_char  jt;      // 条件真跳转
    u_char  jf;      // 条件假跳转
    bpf_u_int32 k;   // 通用字段
};

// 示例：过滤 "tcp port 80" 部分生成的 BPF
// (000) ldh [12]          ; 加载以太网帧类型
// (001) jeq #0x86dd jt 2 jf 10  ; 是 IPv6 则跳到 IPv6 逻辑
// (002) ldb [23]          ; IPv4 协议字段
// (003) jeq #0x6 jt 4 jf 20  ; 是 TCP？
// (004) ldh [20]          ; 标记和分片偏移
// (005) jset #0x1fff jt 20 jf 6  ; 跳过分片包
// (006) ldxb 4*([14]&0xf) ; 计算 IP 头长度
// (007) ldh [x+14]        ; 加载源端口
// (008) jeq #0x50 jt 19 jf 9  ; 源端口 = 80?
// (009) ldh [x+16]        ; 加载目的端口
// (010) jeq #0x50 jt 19 jf 20 ; 目的端口 = 80?
// (019) ret #65535        ; 匹配，保留包
// (020) ret #0            ; 不匹配，丢弃
```

### 5.3 journalctl 与 systemd-journald 的日志采集

```c
// systemd journal 的核心：sd_journal_send()
// 应用可主动将结构化日志发送到 journald
#include <systemd/sd-journal.h>

// sd_journal_send 是可变参数函数
int sd_journal_send(
    "MESSAGE=Connection refused from %s:%d", client_ip, client_port,
    "PRIORITY=%d", LOG_ERR,          // 0=emerg, 7=debug
    "SYSLOG_IDENTIFIER=%s", "myapp",  // 应用标识
    "ERRNO=%d", errno,
    "CODE_FILE=%s", __FILE__,
    "CODE_LINE=%d", __LINE__,
    NULL);  // 结束标志

// journald 内部：将日志写入 /run/log/journal/（易失）或 /var/log/journal/（持久）
// 结构化存储意味着可按字段高效查询：journalctl PRIORITY=3 SYSLOG_IDENTIFIER=myapp
```

### 实践感悟

1. **strace -c 先看统计，再钻细节**：`strace -c -p PID` 先输出系统调用次数和耗时汇总表格，找到 top 3 高耗时 syscall 后，再 `strace -e trace=futex,read,write` 精细化跟踪。避免一次打印过多信息淹没关键线索。
2. **tcpdump 先用 -c 控制抓包数**：生产网卡流量巨大，`tcpdump -i eth0 -c 1000 -w dump.pcap` 抓 1000 个包就停，避免抓包文件失控。用 Wireshark 分析 pcap 文件比命令行更高效。
3. **journalctl 的 --since/--until 是查错利器**：`journalctl -u nginx --since "10 minutes ago"` 快速看最近 10 分钟的服务日志，比 grep 大文件快得多。
4. **grep -C 是上下文之王**：错误日志的上下文（前后 N 行）往往比错误行本身更有价值。`grep -C 10 "FATAL" log` 能看到错误发生前后的状态变化。
5. **/proc/sysrq-trigger 是救命快捷键**：服务器卡死时，`echo w > /proc/sysrq-trigger` 列出所有 D 状态进程的调用栈（无需任何工具），`echo t` 列出所有任务栈。无需安装额外工具。
6. **日志轮转（logrotate）是被忽视的可靠性基石**：生产环境必须配置 logrotate（按大小/时间轮转 + 压缩 + 保留天数），否则 /var/log 迟早撑爆根分区。

## 六、面试准备

### Q1: 线上服务突然不可访问，你的排查思路？
**答**：① `curl/wget localhost:端口` 确认本地可访问（排除网络问题）；② `ss -tunlp | grep 端口` 确认进程存活和监听状态；③ `netstat -s` 看 TCP 统计（重传率、连接失败数）；④ `dmesg | tail` 检查 OOM；⑤ `top/htop` 看 CPU 和内存；⑥ `df -h` 确认磁盘没满。

### Q2: 进程 CPU 100% 但不知道在做什么，怎么定位？
**答**：① `top -H -p PID` 找到 CPU 最高的线程 TID；② `printf "%x\n" TID` 转 16 进制；③ `pstack PID | grep 16进制TID`（或 gdb attach + thread apply all bt）看线程调用栈；④ 也可以用 `perf top -p PID` 实时看函数级热点。

### Q3: 如何排查内存泄漏？
**答**：① `top` 看 RES 列是否持续增长；② `pmap -x PID | tail -1` 看总 RSS 并对比 `ps -o rss PID`；③ 用 valgrind 离线分析（`valgrind --leak-check=full --show-leak-kinds=all`）；④ 在线用 gperftools HEAPPROFILE；⑤ 无工具可用时，对比 `/proc/PID/smaps` 的每次快照找出增长的 VMA。

### Q4: 磁盘空间满了怎么紧急处理？
**答**：① `df -h` 定位满分区；② `du -sh /* 2>/dev/null` 层层下钻；③ `find 路径 -size +1G -exec ls -lh {} \;` 找大文件；④ 检查日志是否未轮转（/var/log、应用日志目录）；⑤ `lsof +L1` 找被删除但仍占空间的僵尸文件。

### Q5: strace 会不会影响生产服务性能？
**答**：会！ptrace 会让被跟踪进程每次系统调用 stop-resume，高频 syscall 的进程（Redis、Nginx）性能下降可达 50%+。生产环境优先用 `perf trace`（低开销）或 `strace -c` 先看统计。

### Q6: tcpdump 抓包分析怎么看三次握手？
**答**：`tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0'`。正常握手有 SYN→SYN-ACK→ACK 三个包。如果只看到 SYN 没 SYN-ACK，说明服务端端口未监听或被防火墙拦截；只看到 SYN、SYN-ACK 没 ACK，可能是 SYN flood 或客户端网络 NAT 问题。

### Q7: 如何判断系统 IO 瓶颈？
**答**：① `iostat -x 2`：`%util` 接近 100% 表示 IO 饱和，`await` 远大于 `svctm` 表示 IO 排队严重；② `iotop` 看哪个进程在大量读写；③ `cat /proc/PID/io` 看进程级读写字节量和 cancelled write bytes。

### Q8: dmesg 中的 OOM Killer 日志怎么分析？
**答**：关键字段：`Killed process PID (name)` 被杀进程，`total-vm` 虚拟内存，`anon-rss` 匿名页驻留内存，`file-rss` 文件页驻留内存。用 `grep -i "invoked oom-killer" /var/log/messages` 定位触发点。反向查 `/proc/PID/oom_score`（越高越容易被杀）和 `oom_score_adj`（-1000 免杀）。

### 面试陷阱

1. **「top 里的 VIRT 就是实际内存用量」** → 错！VIRT 是虚拟内存（含未分配和共享库），RES 才是物理内存（但包含共享内存）。实际进程独占内存看 RES-SHR 或 PSS。
2. **「df 和 du 结果一定一致」** → 错！文件被 rm 但仍被进程持有（fd 未关）时，df 显示占用、du 看不到。`lsof | grep deleted` 定位。
3. **「netstat -tunlp 是看端口的标准命令」** → 不推荐！`ss -tunlp` 更快更好。netstat 读取 /proc 解析慢，大规模连接时可能遗漏瞬时状态。
4. **「strace -f 跟踪多线程进程很方便」** → 慎用！-f 跟踪所有子线程，对多线程进程的 syscall 放大效应更严重，经常导致服务响应超时。
5. **「tcpdump -w 可以抓任意流量」** → 在云原生环境（容器、k8s）中，tcpdump 需注意网络命名空间（`nsenter -t PID -n tcpdump`），否则抓的是宿主机上的虚拟网卡流量。

### 一句话答案速记表

| 关键词 | 一句话答案 |
|-------|-----------|
| 服务不通 | curl local→ss端口→dmesg OOM→top资源→df磁盘 |
| CPU 100% | top -H 找线程→16进制TID→pstack/gdb 调用栈 |
| 内存泄漏 | top RES增长→pmap→valgrind/gperftools→/proc/smaps |
| 磁盘满 | df定位→du下钻→find大文件→lsof deleted |
| strace 影响 | ptrace使每次syscall stop-resume，高频进程性能降50%+ |
| 三次握手 | tcpdump SYN→SYN-ACK→ACK，缺则排查端口/防火墙 |
| IO 瓶颈 | iostat %util+await, iotop按进程定位 |
| OOM 分析 | dmesg grep oom, oom_score被杀的评分依据 |
