## 一、核心概念

- **定义**：服务器架构设计的核心是**三层分离**——网络层（Asio 底层通信）、逻辑层（业务处理）、数据层。网络层通过 Reactor 模式监听 I/O 事件，将数据投递到逻辑层的消息队列，逻辑线程异步处理业务
- **关键词**：三层分离、asio 底层通信、Reactor 模式、`epoll_wait` 事件循环、消息投递（`post`）、逻辑队列
- **适用场景/边界**：所有中型以上网络服务器。小服务可以合并网络层+逻辑层，大服务必须分离以避免 I/O 线程阻塞

## 二、详细解析（≥200字）

- **原理拆解（三层递进）**：
  - **第一层——Asio 底层通信（网络层）**：`async_read` 调用链路：应用层 → `io_context` 注册事件 → `epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN)` → `io_context.run()` 中 `epoll_wait` 监听到 EPOLLIN → 取出 `operation` → 调用回调。就绪事件先进入就绪事件队列，再逐一回调
  - **第二层——逻辑层结构**：网络回调中不直接处理业务，而是将数据封装为消息投递到逻辑队列。逻辑线程独立于 I/O 线程，从队列取消息、查找回调映射表、执行业务逻辑。关键：逻辑线程阻塞不影响网络层继续接收数据
  - **第三层——Reactor 模式的死循环**：`epoll_reactor::run()` 中 `while(running_) { int n = epoll_wait(epfd_, events, MAX, -1); for(each event) complete_read/write/error(); }`。每个就绪事件调用 `op->complete_xxx()`，触发应用层回调
- **关键数据结构/接口**：`epoll_event` 含 `events`（EPOLLIN/OUT/ERR）+ `data.ptr`（指向 `operation` 对象）；`io_context` 封装 reactor + 回调调度；逻辑层消息队列解耦 I/O 与业务
- **关键公式**：网络延迟 = `epoll_wait` 返回延迟 + 回调执行时间；吞吐 = min(网络带宽, I/O 处理速率, 业务处理速率)

## 三、动手实践（代码案例）

```c++
#include <boost/asio.hpp>
#include <queue>
#include <mutex>
#include <thread>
using namespace boost::asio;
using namespace boost::asio::ip;

io_context ioc;
std::queue<std::string> logic_queue;
std::mutex q_mtx;

// 网络层回调：投递到逻辑队列
void on_recv(std::string data) {
    { std::lock_guard<std::mutex> lk(q_mtx); logic_queue.push(data); }
}

// 逻辑线程：独立消费
void logic_worker() {
    while (true) {
        std::string msg;
        { std::lock_guard<std::mutex> lk(q_mtx);
          if (!logic_queue.empty()) { msg = logic_queue.front(); logic_queue.pop(); } }
        if (!msg.empty()) process(msg);
    }
}

int main() {
    std::thread logic(logic_worker);
    // 网络层启动...
    ioc.run();
    logic.join();
}
```

## 四、进阶应用（≥500字）

### 网络层→逻辑层的投递方式

```c++
// 方式 1：直接推入队列（简单，需加锁）
logic_system.PostMsgToQue(msg);

// 方式 2：通过 io_context::post 投递（线程安全）
post(logic_ioc, [msg]{ logic_system.Handle(msg); });

// 方式 3：无锁队列（高性能）
lockfree_queue.push(msg);
```

### 优雅停机的层次顺序

```
1. 停止 acceptor（不再接受新连接）
2. 等待现有连接处理完毕
3. 停止网络层 io_context
4. 清空逻辑队列（处理完积压消息）
5. 停止逻辑线程
6. 释放资源
```

### 架构选型决策表

| 并发量 | 架构 | io_context 数 | 线程数 |
|--------|------|---------------|--------|
| < 100 | 单线程 | 1 | 1(网络+逻辑) |
| 100-1000 | 网络+逻辑分离 | 1 | 1(I/O)+1(逻辑) |
| 1000-10000 | 多 Reactor | N | N(I/O)+M(逻辑) |
| 10000+ | Reactor + 协程 | N | N |

**工程经验**：(1) 三层分离是服务器设计的铁律——混合 I/O 和业务是性能杀手；(2) 逻辑线程数通常 ≤ CPU 核数；(3) `epoll_wait` 超时设为 -1 无限阻塞，`epoll_wait(..., 0)` 立即返回用于优雅退出。

## 五、源码解析和实践感悟

### 5.1 源码解析

#### 异步事件注册的内部链路

`async_read` 调用链：`socket.async_read_some(buffer, handler)` → `io_context` 的 `scheduler` → 平台 `reactor::start_op()` → `epoll_ctl(EPOLL_CTL_ADD, fd, {EPOLLIN, ptr_to_op})`。回调函数被封装为 `operation` 子类，通过 `epoll_event.data.ptr` 关联。

#### Reactor 模式的核心循环伪代码

```c++
class epoll_reactor {
    void run() {
        epoll_event events[MAX_EVENTS];
        while (running_) {
            int n = epoll_wait(epfd_, events, MAX_EVENTS, -1);
            for (int i = 0; i < n; ++i) {
                auto* op = static_cast<operation*>(events[i].data.ptr);
                if (events[i].events & EPOLLIN)  op->complete_read();
                if (events[i].events & EPOLLOUT) op->complete_write();
                if (events[i].events & (EPOLLERR|EPOLLHUP)) op->complete_error();
            }
        }
    }
};
```

### 5.2 实践经验

1. 逻辑层和网络层必须分离——回调中直接做业务逻辑会阻塞事件循环
2. 逻辑层通过消息队列与网络层通信，实现解耦和异步处理
3. `io_context` 的选择决定整体架构：单 `io_context` 简单但瓶颈明显，多 `io_context` pool 利用多核
4. 逻辑层线程独立于 I/O 线程，通过 `post/dispatch` 交互
5. 服务器架构设计时先明确"连接-读写-业务处理"三层分离

## 六、面试准备

### 6.1 面试高频问答

**Q1：async_read 的调用链是什么？**

A：`socket.async_read_some()` → `io_context::scheduler` → 平台相关 `reactor::start_op()` → `epoll_ctl(EPOLL_CTL_ADD)` 注册读事件 → epoll_wait 就绪时通过 `epoll_event.data.ptr` 找回 `operation` 并执行回调。

**Q2：为什么网络层和逻辑层要分离？**

A：网络层处理 I/O 事件（高频、阻塞少），逻辑层处理业务计算（可能耗时、涉及数据库等）。不分离会导致耗时业务阻塞 `io_context::run()`，影响其他连接。

**Q3：Reactor 和 Proactor 的区别？**

A：Reactor：被动等待 I/O 就绪 → 用户线程主动读写；Proactor：主动发起异步 I/O → OS 完成后通知。Asio 模拟了 Proactor，在 Linux 上实际用 Reactor(epoll) 实现。

**Q4：事件就绪队列的作用？**

A：解耦事件检测和事件处理——epoll_wait 将就绪事件批量取出放入队列，`io_context::run()` 逐个处理，避免在处理一个事件时阻塞其他事件的检测。

**Q5：如何保证消息可靠到达逻辑层？**

A：使用线程安全的消息队列 + 条件变量通知，失败重试机制，连接断开时清理待投递消息。

### 6.2 陷阱与反问

**陷阱1**：在回调中执行耗时操作（如文件写入）→ 阻塞事件循环
**陷阱2**：逻辑层队列无限增长→ 内存泄漏
**陷阱3**：忘记在连接关闭时通知逻辑层清理 → 悬空指针
**陷阱4**：`epoll` 边缘触发(ET)模式下必须循环读取直到 EAGAIN，否则丢事件

**反问**：为什么 Asio 在 Linux 上要用 Reactor 模拟 Proactor？
*答案：Linux 原生异步 I/O (AIO) 对 socket 支持不完善，epoll+非阻塞 I/O 是更可靠的选择。*

### 6.3 一句话答案

1. **async_read 注册链路**：socket → scheduler → reactor → epoll_ctl
2. **网络层/逻辑层分离**：I/O 线程只负责收发，业务线程处理逻辑，消息队列通信
3. **Proactor 模拟**：Linux 上用 epoll + 非阻塞 I/O 模拟 Windows IOCP 的 Proactor 语义
4. **事件就绪队列**：epoll_wait 批量提取，`run()` 逐个回调
5. **逻辑队列**：线程安全的消息中转，解耦网络层和逻辑层
