# 对象池

```
#include <string>
#include <functional>
#include <memory>
#include <map>
#include "NonCopyable.hpp"
using namespace std;

const int MaxObjectNum = 10;

template<typename T>
class ObjectPool : NonCopyable
{
	template<typename... Args>
	using Constructor = std::function<std::shared_ptr<T>(Args...)>;
public:
	//默认创建多少个对象
	template<typename... Args>
	void Init(size_t num, Args&&... args)
	{
		if (num<= 0 || num> MaxObjectNum)
			throw std::logic_error("object num out of range.");

		auto constructName = typeid(Constructor<Args...>).name(); //不区分引用
		for (size_t i = 0; i <num; i++)
		{
			m_object_map.emplace(constructName, shared_ptr<T>(new T(std::forward<Args>(args)...), [this, constructName](T* p) //删除器中不直接删除对象，而是回收到对象池中，以供下次使用
			{
				m_object_map.emplace(std::move(constructName), std::shared_ptr<T>(p));
			}));
		}
	}

	//从对象池中获取一个对象
	template<typename... Args>
	std::shared_ptr<T> Get()
	{
		string constructName = typeid(Constructor<Args...>).name();

		auto range = m_object_map.equal_range(constructName);
		for (auto it = range.first; it != range.second; ++it)
		{
			auto ptr = it->second;
			m_object_map.erase(it);
			return ptr;
		}

		return nullptr;
	}

private:
	multimap<string, std::shared_ptr<T>> m_object_map;
};
```

## 一、核心概念

- **定义**：对象池（Object Pool）是一种对象创建模式，预先构造一定数量的对象缓存在池中，需要时借出、用完归还，避免高频构造/析构的开销。本质是**用空间换时间**——用预分配的内存和预构造状态换取零分配延迟
- **关键词**：预构造、借出/归还、shared_ptr 自定义删除器、multimap 分组、typeid 签名区分、`std::pmr::memory_resource`
- **适用场景/边界**：对象构造开销大（数据库连接、线程、大缓冲区）；高频分配/释放（游戏子弹、网络包）；固定数量对象不超出池容量。不适用：简单对象（构造便宜的不值得池化）、不定数量对象（超出池容量时需退化到 new）、生命周期超越池的对象

## 二、详细解析（≥200字）

- **原理拆解（三层递进）**：
  - **第一层——预构造与缓存**：`Init(size, args...)` 预先创建 `size` 个对象，包装为 `shared_ptr<T>` 存入 `multimap<string, shared_ptr<T>>`。Key = `typeid(Constructor<Args...>).name()` 区分不同构造参数签名。池满时 Get 返回 nullptr（需检查）
  - **第二层——借出与归还（自定义删除器）**：`Get()` 从 multimap 取出一个 shared_ptr，删除对象（erase）。归还机制：借出对象的 shared_ptr 引用计数归零时，自定义删除器被调用——不是 `delete`，而是将原始指针重新包装为新的 `shared_ptr` 放回 multimap。**核心风险**：池析构后删除器访问已销毁的容器 → UB
  - **第三层——生命周期管理**：池必须比所有借出对象长寿，否则悬挂 shared_ptr 析构时删除器访问野引用。解决方案：用 `weak_ptr` 追踪借出对象数量，或 `enable_shared_from_this` 让池自身被 shared_ptr 管理
- **关键数据结构/接口**：`multimap<string, shared_ptr<T>>` 按构造签名分组；`Constructor<Args...>` = `function<shared_ptr<T>(Args...)>`；`Get<Args...>()` 签名必须与 Init 匹配
- **关键公式**：池命中延迟 ≈ O(log n)（multimap 查找）；无锁链表实现可达 O(1)；对象池 vs 裸 new 的平衡点在构造开销 > shared_ptr 引用计数原子操作开销

## 三、动手实践（代码案例）

```c++
#include <memory>
#include <iostream>
#include <map>
using namespace std;

template<typename T>
class SimplePool {
    multimap<string, shared_ptr<T>> pool_;
public:
    template<typename... Args>
    void init(size_t n, Args&&... args) {
        for (size_t i = 0; i < n; ++i)
            pool_.emplace("default", make_shared<T>(forward<Args>(args)...));
    }

    shared_ptr<T> get() {
        auto it = pool_.find("default");
        if (it == pool_.end()) return nullptr;
        auto ptr = it->second;
        pool_.erase(it);
        return ptr;
    }

    size_t available() const { return pool_.count("default"); }
};

// 测试
int main() {
    SimplePool<string> pool;
    pool.init(3, "hello");
    cout << pool.available() << endl;  // 3
    auto s = pool.get();
    cout << *s << endl;                 // "hello"
    cout << pool.available() << endl;  // 2
}
```

**运行**：
```bash
g++ -std=c++17 pool_demo.cpp -o pool && ./pool
```

## 四、进阶应用（≥500字）

### shared_ptr 自定义删除器回收方案

```c++
template<typename T>
class RecyclePool {
    multimap<string, shared_ptr<T>> pool_;
public:
    template<typename... Args>
    shared_ptr<T> create(Args&&... args) {
        auto key = typeid(void).name();
        auto deleter = [this, key](T* p) {
            pool_.emplace(key, shared_ptr<T>(p));  // 归还
        };
        return shared_ptr<T>(new T(forward<Args>(args)...), deleter);
    }
};
// 风险：pool_ 析构后 deleter 访问 this → UB
// 安全版：用 weak_ptr<decltype(pool_)> 捕获，deleter 中 lock() 检查
```

### C++17 std::pmr 内存池（底层替代）

```c++
#include <memory_resource>
char buffer[4096];
std::pmr::monotonic_buffer_resource pool{buffer, sizeof(buffer)};
std::pmr::vector<int> vec{&pool};  // vector 内存从池中分配
// pmr 只管内存不管对象状态，更底层更通用，可替代对象池的大部分场景
```

### 无锁对象池（多线程优化）

```c++
#include <atomic>
template<typename T, size_t N>
class LockFreePool {
    T objects_[N];
    atomic<size_t> head_{0};
    atomic<bool> used_[N]{};
public:
    T* acquire() {
        for (size_t i = 0; i < N; ++i) {
            bool expected = false;
            if (used_[i].compare_exchange_weak(expected, true))
                return &objects_[i];
        }
        return nullptr;
    }
    void release(T* p) {
        size_t idx = p - objects_;
        used_[idx].store(false);
    }
};
// 用 CAS 替代 mutex，单次 acquire 延迟 ~10-20 cycles（无竞争）
```

### 对象池 vs 内存池 vs 直接分配

| 方案 | 构造开销 | 内存分配 | 线程安全 | 碎片 |
|------|---------|---------|---------|------|
| 对象池 | 仅 Init 时一次 | 仅 Init 时一次 | 需额外加锁 | 无 |
| 内存池(pmr) | 每次 acquire | 无（预分配） | 取决于实现 | 无 |
| new/delete | 每次构造 | 每次分配 | 内置(malloc 锁) | 可能 |

**选择建议**：构造开销 > 100 cycles 且对象数量固定 → 对象池；仅需快速内存分配 → pmr；简单对象 → 直接 new/delete 更快（shared_ptr 原子操作可能更贵）。

## 五、源码解析和实践感悟

### 1. 自定义删除器的回收机制

```c++
// 关键：shared_ptr 的自定义删除器不释放内存，而是回收到池中
auto deleter = [this, constructName](T* p) {
    // 对象引用计数归零时调用此删除器
    // 不是 delete p，而是将 p 重新包装为 shared_ptr 放回池中
    m_object_map.emplace(constructName, std::shared_ptr<T>(p));
    // ★ 风险：此处 p 被新的 shared_ptr 接管，旧 shared_ptr 的引用计数已归零
    //   如果池外还有其他 shared_ptr 引用此对象 → 双重释放
};
```

### 2. 构造器签名区分

```c++
// 用 typeid 区分不同构造参数签名的对象
template<typename... Args>
using Constructor = std::function<std::shared_ptr<T>(Args...)>;

auto constructName = typeid(Constructor<Args...>).name();
// 不同参数类型生成不同的名称，"pool[int]" 和 "pool[int,double]" 分开管理

// 注意：typeid 不区分 int& 和 int（引用被剥离），所有相同值类别参数算同一种
```

### 3. 对象池与 shared_ptr 的兼容性陷阱

```c++
// 正确：池析构时，map 中所有 shared_ptr 析构，对象才真正释放
auto pool = ObjectPool<Heavy>();
pool.Init(5);
auto obj = pool.Get();  // 从池中取出
// obj 离开作用域 → 自定义删除器触发 → 对象回收到池中
// pool 析构 → map 中所有 shared_ptr 析构 → 对象最终 delete

// 错误：池已析构后还有外部 shared_ptr 引用
std::shared_ptr<Heavy> hanging;
{
    ObjectPool<Heavy> pool;
    pool.Init(5);
    hanging = pool.Get();
}  // pool 析构，但 hanging 仍持有对象
// hanging 析构时触发删除器 → 访问已析构的 m_object_map → UB
```

### 实践经验

1. **对象池生命周期**：池必须比所有借出对象活得久，否则删除器访问已析构容器
2. **类型签名区分**：`typeid(...).name()` 返回值是实现定义的，不同编译器可能不同
3. **最大数量限制**：`MaxObjectNum` 硬编码，生产应改为构造函数参数
4. **线程安全缺失**：multimap 操作无锁保护，多线程需加 mutex
5. **回收不等于析构**：自定义删除器只是改变了 shared_ptr 引用计数归零时的行为
6. **更优方案**：用 `std::pmr::memory_resource`（C++17）做内存池，而非对象池

## 六、面试准备

### Q&A（8题）

**Q1: 对象池和内存池的区别？**
A: 对象池缓存已构造的对象（直接复用），内存池缓存裸内存（需重新构造）。对象池多一层构造状态管理

**Q2: shared_ptr 自定义删除器的作用？**
A: 引用计数归零时调用删除器，默认 delete。可用于对象池回收、资源释放后置、调试日志

**Q3: 自定义删除器实现对象池的风险？**
A: 池析构后借出对象的删除器访问已销毁的容器 → UB。池必须比所有外部引用长寿

**Q4: 如何区分不同构造参数的对象？**
A: 用 `std::type_index` + `typeid(Constructor<Args...>)` 生成唯一标识

**Q5: 为什么用 multimap 而非 map？**
A: 同一种构造参数可能有多个对象，multimap 允许重复键

**Q6: 对象池的适用场景？**
A: 对象构造开销大（数据库连接、线程）、高频分配/释放、固定数量对象

**Q7: `std::pmr` 和自定义对象池的区别？**
A: pmr 是内存分配层面的池，不管理对象构造状态，更底层更通用

**Q8: 线程安全的对象池怎么做？**
A: mutex 保护 Get/Init，或 `std::lock_free` 结构。也可用 `std::shared_mutex` 读写锁

### 陷阱与反问（5个）

1. **陷阱**：池析构后借出对象仍持有 shared_ptr → 删除器访问野引用
2. **反问**：对象池一定比 new/delete 快吗？→ 不一定，shared_ptr 引用计数有原子操作开销，简单对象反而更慢
3. **陷阱**：`typeid(...).name()` 跨编译器不兼容 → 改用 `std::type_index` 做 key
4. **反问**：能用对象池替代 GC 吗？→ 不能，对象池不追踪引用关系，不能回收循环引用
5. **陷阱**：池满时 Get 返回 nullptr 未检查 → 空指针解引用

### 一句话答案（5个）

1. **对象池核心**：缓存已构造对象，避免反复构造/析构
2. **删除器回收**：shared_ptr 引用归零时归还池而非 delete
3. **生命周期铁律**：池必须比所有借出对象长寿
4. **构造函数区分**：用构造参数类型签名做 key
5. **线程安全**：多线程访问需加锁
