# MySQL 索引

> 适用范围：InnoDB 索引架构、B+树结构、聚簇索引与二级索引、回表查询、覆盖索引

## 一、项目/模块概述

- **模块定位**：MySQL InnoDB 索引是数据库查询性能的核心，决定了数据检索效率。
- **技术栈与依赖**：InnoDB 存储引擎、B+树数据结构、页（16KB）、行格式（Compact/Dynamic）。
- **模块边界**：输入为 SQL 查询，输出为数据行定位。上游是查询优化器，下游是磁盘 I/O。

## 二、架构设计

### 设计拆解

**第一层：索引类型体系**

```
聚簇索引（1个）：叶子节点 = 完整数据行
二级索引（多个）：叶子节点 = 索引列值 + 主键值
```

**第二层：B+树结构**

```
聚簇索引B+树：
    页1（根） → 指向页2、页3
    页2（内部） → 指向页4、页5、页6
    页4、5、6（叶子）→ 存储实际数据行
```

**第三层：查询路径设计**
- 主键查询：聚簇索引 → 直接返回完整行
- 二级索引查询：二级索引 → 回表查聚簇索引
- 覆盖索引：二级索引叶子包含所需列 → 无需回表

### 关键数据结构

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,            -- 聚簇索引
    name VARCHAR(100),             -- 二级索引
    email VARCHAR(100) UNIQUE,    -- 唯一二级索引
    age INT,                      -- 二级索引
    INDEX idx_name (name),
    INDEX idx_age (age),
    UNIQUE INDEX idx_email (email)
) ENGINE=InnoDB;
```

## 三、核心实现

### 3.1 多个索引的物理存储

```
users.ibd 文件结构：
┌───────────────聚簇索引B+树───────────────┐
│  根页 → 内部页 → 数据页（完整行）         │
├───────────────idx_name B+树──────────────┤
│  ["Alice",id=1] ["Bob",id=2] ...         │
├───────────────idx_email B+树─────────────┤
│  ["a@x.com",id=1] ["b@x.com",id=2] ...  │
├───────────────idx_age B+树───────────────┤
│  [20,id=3] [25,id=1] [30,id=2] ...      │
└──────────────────────────────────────────┘
```

### 3.2 回表查询过程

```
SELECT * FROM users WHERE name = 'Alice';

1. idx_name B+树 → 查找 "Alice" → 得到 ["Alice", id=1]
2. 聚簇索引 B+树 → 用 id=1 查找 → 返回完整数据行
   这个过程称为"回表查询"
```

### 3.3 覆盖索引（无需回表）

```sql
SELECT id, name FROM users WHERE name = 'Alice';
-- id 和 name 都在 idx_name 索引中，直接返回
```

### 3.4 复合索引

```sql
CREATE INDEX idx_name_city ON users(name, city);

-- 叶子节点：["Alice","Beijing",id=1] ["Bob","NY",id=2] ...
-- 相当于建立 (name)、(name,city) 两个索引（最左前缀原则）
```

### 3.5 页内结构

```
每个索引页（16KB）：
┌─────────────┐
│ 页头 (38B)   │
├─────────────┤
│ Infimum+Supremum │
├─────────────┤
│ 用户记录（有序）  │
├─────────────┤
│ 页目录（槽）     │
├─────────────┤
│ 页尾 (8B)    │
└─────────────┘
```

## 四、工程实践

- **索引选择**：MySQL 优化器基于统计信息自动选索引，可通过 `FORCE INDEX` 强制指定。
- **维护成本**：每个索引都是独立 B+树，增删改需更新所有相关索引。索引越多写越慢。
- **常见优化**：用覆盖索引减少回表；复合索引遵循最左前缀；`EXPLAIN` 分析执行计划。

## 五、源码解析和实践感悟

### 感悟
1. **聚簇索引决定了物理存储顺序**：主键选择至关重要，UUID 会导致大量页分裂。
2. **回表是最大性能杀手**：`SELECT *` 通常要回表，覆盖索引是解决方案。
3. **索引不是越多越好**：每个索引都是一棵 B+树，写放大效应明显。
4. **最左前缀是复合索引的生命线**：`(a,b,c)` 只能匹配 `a`、`a,b`、`a,b,c` 的查询。

## 六、面试准备

### 6.1 高频问法

**Q1：InnoDB 聚簇索引和二级索引区别？**
聚簇索引叶子存完整数据行（只有1个）；二级索引叶子存索引列+主键，需回表。

**Q2：什么是回表查询？**
二级索引找到主键后，再到聚簇索引查完整行。覆盖索引可避免。

**Q3：复合索引的最左前缀原则？**
`(a,b,c)` 建立 `(a)`、`(a,b)`、`(a,b,c)` 三个索引。查询 `WHERE b=1` 不走索引。

**Q4：为什么建议用自增主键？**
自增保证数据按顺序插入，避免页分裂和随机 I/O。UUID 会导致大量页分裂。

**Q5：覆盖索引是什么？**
SELECT 的列都在索引中，无需回表。`SELECT id,name FROM t WHERE name='x'` 在 idx_name 上就是覆盖。

**Q6：索引失效的常见场景？**
like '%x' 开头、OR 条件部分无索引、索引列用函数/运算、隐式类型转换、!= / IS NULL。

**Q7：EXPLAIN 关键字段含义？**
type（访问类型：const>ref>range>index>ALL）、key（实际用到的索引）、rows（扫描行数）、Extra（Using filesort/temporary 需优化）。

**Q8：B+树和B树区别？为什么用B+树？**
B+树非叶子不存数据（存更多索引项），叶子链表支持范围查询。B树非叶子也存数据。

**Q9：索引下推（ICP）是什么？**
MySQL 5.6+ 将 WHERE 条件下推到存储引擎层过滤，减少回表次数。

**Q10：如何分析慢查询？**
`slow_query_log` 开启慢日志 → `mysqldumpslow` 聚合 → `EXPLAIN` 分析 → 加索引/改写 SQL。

### 6.2 反问点

| # | 反问 | 要点 |
|---|------|------|
| 1 | 索引越多查询越快？ | 写操作代价增大，需要平衡读写比例 |
| 2 | 为什么有时索引不生效？ | 优化器认为全表扫描更快，可通过 FORCE INDEX 验证 |
| 3 | 唯一索引和普通索引性能有区别吗？ | 唯一索引插入需检查冲突，略慢于普通索引 |
| 4 | 什么是索引选择性？ | 不同值的数量/总行数，越高越好，< 0.1 不建议建索引 |
| 5 | 联合索引字段顺序如何决定？ | 区分度高的放前面，等值查询的列放范围查询列前面 |

### 6.3 一句话答案
- 聚簇索引 = B+树叶子存完整数据行，1个
- 二级索引 = B+树叶子存索引+主键，回表查完整行
- 覆盖索引 = SELECT 的列都在索引中，零回表
- 最左前缀 = 复合索引从最左列开始匹配
- 页分裂 = 插入导致页满时拆分为两页，随机 I/O 来源
- B+树优势 = 非叶子不存数据（高扇出）+ 叶子有序链表（范围查询）

### 原第一章：InnoDB 索引的基本架构

#### 1. 主索引（聚簇索引）

```
唯一的一个聚簇索引（Clustered Index）：
    ┌─────────────────┐
    │ 内部节点        │
    │ [10, 20, 30]    │
    └──────┬──────────┘
           │
    ┌──────┴──────────────────────────────────┐
    │ 叶子节点 = 实际数据行                   │
    │ [key=1, 其他所有列数据...]              │
    │ [key=2, 其他所有列数据...]              │
    │ [key=3, 其他所有列数据...]              │
    └─────────────────────────────────────────┘
```

* 每个 InnoDB 表只有一个聚簇索引
* 叶子节点存储完整的**数据行**
* 物理上**按主键顺序**存储

#### 2. 二级索引（辅助索引/非聚簇索引）

```
多个二级索引（Secondary Indexes）：
    ┌─────────────────┐
    │ 内部节点        │
    │ ["Alice", "Bob"]│
    └──────┬──────────┘
           │
    ┌──────┴─────────────┐
    │ 叶子节点           │
    │ ["Alice", 主键=1]  │
    │ ["Bob",   主键=2]  │
    │ ["Charlie",主键=3] │
    └────────────────────┘
```

* 每个二级索引都是一个独立的 B+树
* 叶子节点存储：**索引列值 + 主键值**
* 需要**回表查询**获取完整数据

### 原第四章：索引的物理存储细节

#### 页（Page）结构

InnoDB 中所有索引都以页为单位存储：

```
每个索引页（16KB大小）：
┌─────────────────────────────────┐
│ 页头 (38字节)                   │
├─────────────────────────────────┤
│ Infimum + Supremum 记录         │
├─────────────────────────────────┤
│ 用户记录（按顺序存储）           │
├─────────────────────────────────┤
│ 页目录（槽，用于二分查找）       │
├─────────────────────────────────┤
│ 页尾 (8字节)                    │
└─────────────────────────────────┘
```

#### 不同索引的页内容

| 索引类型 | 叶子节点存储内容 | 非叶子节点存储内容 |
| --- | --- | --- |
| 聚簇索引 | 完整数据行 | 主键值 + 子页指针 |
| 二级索引 | 索引列值 + 主键值 | 索引列值 + 子页指针 |

#### 页间连接

```
聚簇索引B+树：
    页1（根） → 指向页2、页3
    页2（内部） → 指向页4、页5、页6
    页4、5、6（叶子）→ 存储实际数据行
    ┌─────┐    ┌─────┐    ┌─────┐
    │页1  │───→│页2  │───→│页4  │ (数据)
    └─────┘    └─────┘    └─────┘
       ↓          ↓
    ┌─────┐    ┌─────┐
    │页3  │───→│页5  │ (数据)
    └─────┘    └─────┘
                 ↓
              ┌─────┐
              │页6  │ (数据)
              └─────┘
```

### 原第五章：多索引的查询过程

#### 场景1：通过主键查询

```sql
SELECT * FROM users WHERE id = 123;
```

```
1. 从聚簇索引根节点开始
2. 向下查找找到对应叶子节点
3. 直接返回完整数据行
4. 无需访问二级索引
```

#### 场景2：通过二级索引查询（回表）

```sql
SELECT * FROM users WHERE name = 'Alice';
```

```
1. 在 idx_name 索引B+树中查找
   ┌─────────────┐
   │ idx_name    │ → 查找"Alice"
   └─────────────┘
        ↓
   ┌─────────────┐
   │ 找到:       │ → ["Alice", id=1]
   └─────────────┘
        ↓
2. 获取主键值 id=1
        ↓
3. 回到聚簇索引查找完整数据
   ┌─────────────┐
   │ 聚簇索引    │ → 用 id=1 查找
   └─────────────┘
        ↓
   ┌─────────────┐
   │ 返回完整行  │
   └─────────────┘
这个过程称为"回表查询"
```

#### 场景3：覆盖索引（无需回表）

```sql
SELECT id, name FROM users WHERE name = 'Alice';
```

```
1. 在 idx_name 索引B+树中查找
   ┌─────────────┐
   │ idx_name    │ → 查找"Alice"
   └─────────────┘
        ↓
   ┌─────────────┐
   │ 找到:       │ → ["Alice", id=1]
   └─────────────┘
        ↓
2. id 和 name 都在索引中
3. 直接返回，无需回表！
```

### 原第七章：索引维护与性能

#### 插入数据时的索引更新

```
插入新行 [id=4, name="David", age=28, email="d@x.com"]:

1. 更新聚簇索引：
   - 找到id=4应该插入的位置
   - 插入完整数据行

2. 更新 idx_name 索引：
   - 在idx_name B+树中插入 ["David", id=4]

3. 更新 idx_email 索引：
   - 在idx_email B+树中插入 ["d@x.com", id=4]

4. 更新 idx_age 索引：
   - 在idx_age B+树中插入 [age=28, id=4]

每个索引都是一个独立的B+树，都需要维护！
```

#### 索引选择与使用

```sql
-- 查询优化器会选择使用哪个索引
EXPLAIN SELECT * FROM users WHERE name = 'Alice' AND age = 25;
```

可能的执行计划：
1. 使用 idx_name 索引
2. 使用 idx_age 索引
3. 全表扫描
4. 使用 idx_name_city 复合索引（如果存在）

### 原第八章：总结

在 InnoDB 中多个索引的结构：

1. **每个索引都是独立的 B+树**
   + 聚簇索引：1个，存储完整数据
   + 二级索引：多个，存储（索引列 + 主键）

2. **物理存储特点**：
   + 每个B+树有独立的根页、内部页、叶子页
   + 以16KB页为单位存储
   + 页内有序，页间通过指针连接

3. **查询过程**：
   + 主键查询：直接走聚簇索引
   + 二级索引查询：先查二级索引，再回表查聚簇索引
   + 覆盖索引：直接返回，无需回表

4. **维护成本**：
   + 每个索引都需要独立维护
   + 增删改需要更新所有相关索引
   + 索引越多，写操作越慢

这种设计保证了：
* 快速的主键查询（O(logN)）
* 灵活的二级索引
* 高效的范围查询
* 事务和并发控制的支持
