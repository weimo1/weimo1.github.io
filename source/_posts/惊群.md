# 惊群

> 多个进程/线程同时等待同一事件，事件到来时全部被唤醒，但只有一个能处理，其余白唤醒。

## 一、核心概念

**补充**

- 定义：多个进程/线程阻塞在同一资源上，当资源就绪时，所有等待者被同时唤醒，但最终只有一个能成功获取资源，其余无效唤醒后重新睡眠。
- 关键词：惊群效应(thundering herd)、epoll、accept、自旋锁、Nginx
- 适用场景：多进程网络服务器 accept 新连接；多线程条件变量广播
- 本质：内核调度层面的无效唤醒，浪费 CPU 和上下文切换

## 二、详细解析

我所理解的"惊群"现象：

多个进程（当然每个进程都有各自的epoll\_fd)把同一个[描述符](https://zhida.zhihu.com/search?content_id=13616090&content_type=Answer&match_order=1&q=%E6%8F%8F%E8%BF%B0%E7%AC%A6&zhida_source=entity)fd加入了自己的epoll中，那么等到此fd上有事件发生的时候，内核会驱动这多个进程去处理这个事件，这是不科学的。

比如：在accept的时候，如果ABC三个进程都把listenfd加入了自己的epoll中，那么当客户端连接来的时候，这三个进程都去accept这个client吗？显然会降低效率。

而Nginx里面很好滴解决了这一难题：

首先启动进程的时候，不把[listenfd](https://zhida.zhihu.com/search?content_id=13616090&content_type=Answer&match_order=2&q=listenfd&zhida_source=entity)加入自己的epoll中，等待进程初始化完毕，开始处理事件的时候，这时候的第一步就是抢锁，即抢占对listenfd的控制权，哪个进程抢到，立刻加入自己的[epoll](https://zhida.zhihu.com/search?content_id=13616090&content_type=Answer&match_order=5&q=epoll&zhida_source=entity)。没抢到的进程继续自己的处理，但是不会accept。

抢到listenfd的进程，就会accept新的连接。

总之，一把锁，就很好滴解决了惊群现象

顺便说下 这个锁是 [自旋锁](https://zhida.zhihu.com/search?content_id=13616090&content_type=Answer&match_order=1&q=%E8%87%AA%E6%97%8B%E9%94%81&zhida_source=entity) 用[原子变量](https://zhida.zhihu.com/search?content_id=13616090&content_type=Answer&match_order=1&q=%E5%8E%9F%E5%AD%90%E5%8F%98%E9%87%8F&zhida_source=entity)实现的 不会造成进程的睡眠和阻塞。

## 三、动手实践（代码案例）

**补充** — Nginx 惊群解决示意（accept 互斥锁）：

```c
// Nginx 的 accept_mutex 实现思路（简化）
ngx_int_t ngx_trylock_accept_mutex(ngx_cycle_t *cycle) {
    // 用原子 CAS 尝试获取全局锁
    if (ngx_atomic_cmp_set(&ngx_accept_mutex_held, 0, 1)) {
        // 抢到锁的进程把 listenfd 加入 epoll
        if (epoll_ctl(ep, EPOLL_CTL_ADD, listenfd, &ev) == -1) {
            return NGX_ERROR;
        }
        return NGX_OK;
    }
    // 没抢到的进程把 listenfd 从 epoll 移除
    if (epoll_ctl(ep, EPOLL_CTL_DEL, listenfd, NULL) == -1) {
        return NGX_ERROR;
    }
    return NGX_DECLINED;
}
```

## 四、进阶应用（知识链接）

**补充**

- Linux 内核 3.9+ 引入 `SO_REUSEPORT`，内核层面将连接分发到不同 socket，从根源上避免惊群
- 条件变量的 `notify_one()` vs `notify_all()`：用 `notify_one()` 只唤醒一个等待者，是避免惊群的常用手段
- 惊群不限于网络 accept——线程池用 `notify_all()` 而非 `notify_one()` 也可能造成类似效果

## 五、源码解析和实践感悟

**补充**

- Nginx 的 `accept_mutex` 位于 `ngx_event_accept.c`，核心逻辑就是 CAS 抢锁 + epoll_ctl 动态增删 listenfd
- Linux 内核在 4.5+ 对 epoll 做了惊群修复：当多个进程 epoll 同一个 fd 时，内核只唤醒一个进程

## 六、面试准备（八股、难点、深入点）

**补充**

- 高频问法：
  - "什么是惊群效应？怎么解决？"
  - "Nginx 怎么处理 accept 惊群？"
  - "SO_REUSEPORT 是怎么解决惊群的？"
- 反问点/陷阱点：
  - "notify_all 一定能唤醒所有线程吗？"（不一定，可能有虚假唤醒）
  - "自旋锁解决惊群不会浪费 CPU 吗？"（accept 互斥锁持有时间极短，自旋比睡眠-唤醒开销更小）
- 一句话答案：
  - Nginx 用 CAS 自旋锁 + 动态 epoll_ctl 保证同一时刻只有一个进程监听 accept fd，避免惊群
