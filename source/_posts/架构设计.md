# 架构设计

> 架构设计是构建软件系统的蓝图，涉及系统分解、模块划分、通信模式、数据流设计等关键决策。好的架构设计决定了系统的可扩展性、可维护性和性能上限。

## 一、核心概念

- 定义：软件架构设计是指在系统构建之前，对系统的整体结构、组件关系、接口协议、数据流向、部署拓扑等做出的高层设计决策。
- 关键词：模块化、分层架构、微服务、领域驱动设计（DDD）、CQRS、事件驱动、CAP 定理、唯一 ID 生成
- 适用场景/边界：
  - 新系统从零搭建时的顶层设计
  - 遗留系统重构时的架构升级
  - 技术选型的权衡决策
  - 跨团队协作时的接口约定

## 二、详细解析（≥200字）

### 原理拆解（三层递进）

**第一层：架构设计的基本要素**

架构设计需要回答以下核心问题：
- **系统如何分解**？模块化 vs 单体 vs 微服务
- **模块间如何通信**？同步 RPC vs 异步消息队列 vs 事件总线
- **数据如何流转**？请求-响应 vs 事件驱动 vs 流式处理
- **如何保证可靠性**？冗余、降级、熔断、限流
- **如何支持扩展**？水平扩展 vs 垂直扩展、无状态 vs 有状态

**第二层：常见架构模式**

- **分层架构**（Layered Architecture）：表示层 → 业务层 → 持久层 → 数据库
- **微服务架构**（Microservices）：按业务领域拆分独立部署的服务
- **事件驱动架构**（Event-Driven）：服务间通过事件异步通信
- **CQRS**（Command Query Responsibility Segregation）：读写分离
- **六边形架构**（Hexagonal/Ports & Adapters）：核心业务与外部依赖解耦

**第三层：架构权衡**

架构设计是权衡的艺术：
- **一致性 vs 可用性**（CAP 定理）：分布式系统中只能同时满足两个
- **性能 vs 可维护性**：极致优化的代码通常难维护
- **灵活性 vs 简单性**：过度设计带来不必要的复杂度
- **开发速度 vs 运维复杂度**：微服务加速开发但增加运维成本

### 关键设计原则

1. **单一职责**：每个模块只做一件事
2. **开闭原则**：对扩展开放、对修改封闭
3. **依赖倒置**：依赖抽象而非具体实现
4. **接口隔离**：不依赖不需要的接口
5. **最少知识**（迪米特法则）：模块间尽量少了解对方

## 三、动手实践（代码案例）

### 唯一 ID 生成器设计

参考：PayPal 支付接入思考——唯一 ID 生成

```c++
// Twitter Snowflake 风格的分布式 ID 生成器
#include <chrono>
#include <atomic>
#include <cstdint>

class SnowflakeIDGenerator {
    // 41位时间戳 | 10位机器ID | 12位序列号
    static constexpr uint64_t EPOCH = 1700000000000ULL; // 自定义起始时间
    static constexpr uint64_t MACHINE_BITS = 10;
    static constexpr uint64_t SEQUENCE_BITS = 12;
    static constexpr uint64_t MAX_SEQUENCE = (1ULL << SEQUENCE_BITS) - 1;
    
    uint64_t machine_id;
    std::atomic<uint64_t> sequence{0};
    uint64_t last_timestamp = 0;
    
    uint64_t current_millis() {
        return std::chrono::duration_cast<std::chrono::milliseconds>(
            std::chrono::system_clock::now().time_since_epoch()
        ).count();
    }
    
public:
    explicit SnowflakeIDGenerator(uint64_t machine) : machine_id(machine) {}
    
    uint64_t next_id() {
        uint64_t timestamp = current_millis();
        
        if (timestamp < last_timestamp) {
            // 时钟回拨处理：等待或抛异常
            while (current_millis() <= last_timestamp) {}
            timestamp = current_millis();
        }
        
        if (timestamp == last_timestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {  // 当前毫秒序列号用完
                while (current_millis() <= timestamp) {}
                timestamp = current_millis();
            }
        } else {
            sequence = 0;
        }
        
        last_timestamp = timestamp;
        
        return ((timestamp - EPOCH) << (MACHINE_BITS + SEQUENCE_BITS))
             | (machine_id << SEQUENCE_BITS)
             | sequence;
    }
};
```

### 回调通知校验设计

参考：PayPal 支付接入思考——通知校验机制

```c++
// 支付回调校验框架
class PaymentNotificationHandler {
    // 防止重放攻击：用 nonce + timestamp
    bool verify_notification(const std::string& payload, 
                             const std::string& signature,
                             const std::string& nonce,
                             uint64_t timestamp) {
        // 1. 验证时间戳在合理窗口内（防重放）
        uint64_t now = current_millis();
        if (std::abs(static_cast<int64_t>(now - timestamp)) > 300'000) {
            return false;  // 超过 5 分钟
        }
        
        // 2. 验证 nonce 未被使用（防重放）
        if (used_nonces_.contains(nonce)) return false;
        used_nonces_.insert(nonce);
        
        // 3. 验证签名
        std::string expected = hmac_sha256(payload + nonce + std::to_string(timestamp), secret_key_);
        return constant_time_compare(expected, signature);  // 防止时序攻击
    }
};
```

## 四、进阶应用（≥500字）

### 与其他主题的关联

- **性能优化**：架构设计决定了性能的天花板（如单体架构的垂直扩展上限 vs 微服务的水平扩展能力）
- **分布式系统**：CAP 定理、一致性协议（Raft/Paxos）、分布式事务（Saga/TCC）
- **领域驱动设计（DDD）**：通过限界上下文划分微服务边界
- **IM 系统架构**：长连接网关、消息路由、分布式缓存、水平扩展

### 工程中的真实用法

- **微信/QQ**：IM 架构中的多 IDC 部署、异地多活
- **PayPal**：支付回调的幂等性设计、签名校验防篡改
- **电商系统**：订单服务的 CQRS 读写分离
- **游戏服务器**：逻辑层和数据层分离，战斗服和匹配服务独立部署

### 常见优化策略

- **唯一 ID 生成**：Snowflake 变体（美团 Leaf、百度 UidGenerator）
  - 时间戳 + 机器 ID + 序列号，保证趋势递增 + 全局唯一
  - 时钟回拨问题：等待、备用机器 ID、或使用数据库号段模式
- **回调通知校验**：
  - 签名校验：HMAC-SHA256 防篡改
  - 幂等性：nonce + 业务唯一键去重
  - 时序攻击防护：constant-time compare
  - 重试机制：指数退避（Exponential Backoff）

**从 PayPal 支付接入的架构思考：**
- 唯一 ID 生成是分布式系统的基础设施——需要考虑全局唯一性、趋势递增（数据库索引友好）、高可用、低延迟
- 通知校验机制是异步系统可靠性的关键——回调可能丢失、乱序、重复，需要处理所有异常情况

## 五、源码解析和实践感悟（≥1000字）

### 架构设计中的权衡案例

**案例 1：单体 vs 微服务**

假设一个 IM 系统初期用户量 1 万：
- 单体架构：所有功能在一个进程中（登录、消息、群组、文件）。开发快、部署简单、调试方便。瓶颈：垂直扩展有限，单点故障
- 微服务架构：按功能拆分为用户服务、消息服务、群组服务等。独立部署、独立扩展、技术栈灵活。代价：分布式事务、网络延迟、运维复杂度

选择依据：
- 团队规模 <10 人 → 单体或模块化单体优先
- 需要独立扩展不同模块 → 微服务
- 业务逻辑复杂且变更频繁 → 单体更快迭代

**案例 2：同步 vs 异步通信**

支付回调场景中：
- 同步：客户端等待支付结果返回 → 简单但阻塞
- 异步：支付完成后通过回调/消息通知 → 解耦但增加复杂度

PayPal 的实践：支付请求同步返回（立即确认），状态更新通过异步回调通知（webhook）。关键设计：
1. 回调需要**幂等**（同一条支付结果多次推送结果一致）
2. 回调需要**验证**（签名防止伪造）
3. 回调需要**重试**（网络不可靠）

### 案例 3：分布式唯一 ID 的演进

**方案 1：数据库自增**
```sql
REPLACE INTO tickets64 (stub) VALUES ('a');
SELECT LAST_INSERT_ID();
```
- 优点：简单、严格递增
- 缺点：数据库成为瓶颈和单点

**方案 2：Snowflake**
```
格式：[41位时间戳][10位机器ID][12位序列号]
```
- 优点：无依赖、高性能、趋势递增
- 缺点：时钟回拨问题

**方案 3：号段模式（Leaf）**
```
批量从 DB 获取号段 [1000, 2000]，在内存中逐步分配
```
- 优点：DB 访问频率低、容灾能力强
- 缺点：ID 不严格递增（跳号）

### 难点与易错点

1. **过度设计**：为未来不确定的需求预留过多扩展点，增加复杂度
2. **忽略非功能性需求**：只关注功能实现，忽略性能、安全、可观测性
3. **缺少降级方案**：依赖的外部服务故障时没有 fallback
4. **硬编码配置**：环境相关的配置硬编码在代码中
5. **文档缺失**：架构决策没有记录，后期维护困难

### 经验总结（补充）

1. **YAGNI 原则**（You Aren't Gonna Need It）：不要为"将来可能需要"的需求过度设计
2. **渐进式架构演进**：先简单实现验证业务，再根据瓶颈逐步重构
3. **架构决策记录（ADR）**：记录每个重大架构决策的背景、选项、选择理由和后果
4. **可观测性优先**：日志、指标、链路追踪是架构的基础设施，不是事后补充
5. **接口优先设计**：先定义模块间的接口协议，再实现模块内部

## 六、面试准备（高频问法≥10个，反问点/一句话答案≥5个，均带回答）

### 6.1 高频问法（≥10个）

**基础理解：**

Q1：如何划分微服务的边界？

A：遵循 DDD 的限界上下文（Bounded Context）原则：1) 按业务能力划分（用户服务、订单服务）2) 按数据所有权划分（每个服务拥有自己的数据库）3) 按变更频率划分（稳定模块和频繁变更模块分离）。

Q2：什么是 CQRS？什么场景适用？

A：CQRS（Command Query Responsibility Segregation）是将读操作和写操作分离的架构模式。适用场景：1) 读写负载差异大（读多写少）2) 读模型和写模型不同 3) 需要事件溯源（Event Sourcing）。

Q3：如何设计分布式唯一 ID 生成器？

A：Snowflake 方案：时间戳 + 机器 ID + 序列号。保证全局唯一、趋势递增。关键处理：时钟回拨（等待或备用 ID）、机器 ID 分配（ZooKeeper/数据库）。

**原理深入：**

Q4：CAP 定理如何影响架构选型？

A：分布式系统中只能在一致性（C）、可用性（A）、分区容错（P）中同时满足两个。CP 系统（如 ZooKeeper）优先一致性；AP 系统（如 Cassandra）优先可用性。金融支付系统倾向于 CP。

Q5：事件驱动架构的优缺点是什么？

A：优点：服务解耦、异步处理、天然支持 CQRS 和事件溯源。缺点：调试困难（事件追踪）、最终一致性（非强一致）、事件顺序保证复杂。

Q6：如何保证支付回调的可靠性？

A：1) 幂等性设计（nonce/业务唯一键）2) 签名校验 3) 重试机制（指数退避）4) 回调队列持久化 5) 对账机制兜底（定时全量对账）。

**实践应用：**

Q7：如何做技术选型？请举例说明。

A：从五个维度评估：1) 功能匹配度 2) 性能要求 3) 团队熟悉度 4) 社区活跃度 5) 许可协议。例如：消息队列选 Kafka（高吞吐日志收集）vs RabbitMQ（复杂路由和事务消息）。

Q8：如何设计一个高可用的系统？

A：1) 消除单点故障（多副本、多机房）2) 故障转移（健康检查 + 自动切换）3) 限流降级 4) 数据备份和恢复 5) 监控和告警。

Q9：什么是六边形架构？

A：六边形架构（Ports & Adapters）将核心业务逻辑放在中心，通过端口（Port）定义接口，通过适配器（Adapter）连接外部依赖（数据库、API、消息队列）。好处是核心业务与基础设施解耦，易于测试。

Q10：如何做架构评审？

A：1) 明确评审目标（功能性、非功能性）2) 架构图展示（C4 模型）3) 关键决策和权衡说明 4) 风险识别和缓解方案 5) 部署和运维方案 6) 演进路线图。

### 6.2 反问点/陷阱点（≥5个）

**针对面试官的深度问题：**

- 贵公司目前的微服务拆分粒度是如何确定的？是否遇到微服务过细带来的运维难题？
- 在进行架构升级时，团队如何保证不影响线上业务？有没有灰度迁移的方案？

**常见陷阱问题：**

- 陷阱 1："微服务一定比单体好？" — 微服务不是银弹。对于小团队和小规模系统，微服务带来的分布式复杂度（网络延迟、分布式事务、运维成本）可能远远超过其收益。
- 陷阱 2："分布式事务用两阶段提交（2PC）？" — 2PC 在分布式系统中性能和可用性极差。现代系统更倾向于 Saga（补偿事务）或 TCC（Try-Confirm-Cancel）等最终一致性方案。
- 陷阱 3："所有状态都存 Redis？" — Redis 主要适合缓存和临时状态。如果数据不能丢失或有强一致性要求，必须用持久化存储（MySQL/PostgreSQL）。

### 6.3 一句话答案（≥5个）

- 架构设计的核心是：权衡取舍——在一致性、可用性、性能、可维护性、成本之间找到平衡点。
- 微服务拆分的依据是：按业务领域（限界上下文）拆分，而非按技术层（前端/后端/数据库）。
- 分布式唯一 ID 的关键是：时间戳（趋势递增） + 机器标识（全局唯一） + 序列号（高并发）。
- 避免架构过度设计的方法是：YAGNI 原则——只为当前需求设计，为可知的扩展预留接口。
- 回调可靠性的保证是：幂等 + 签名验证 + 重试 + 对账兜底。
- 当被问到"这个架构怎么优化"时回答："先看瓶颈在哪里——是计算瓶颈、I/O 瓶颈还是数据瓶颈，然后再讨论具体的架构调整方案。"
