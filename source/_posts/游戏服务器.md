# 游戏服务器

> 适用范围：游戏服务器架构设计、帧同步/状态同步、AOI 算法、房间匹配、分布式部署

## 一、项目/模块概述

- **模块定位**：游戏服务器是网络游戏的核心后端，负责玩家认证、房间管理、消息转发、状态同步、防作弊校验等功能，是连接所有玩家并维护游戏世界一致性的中枢。
- **技术栈与依赖**：C++/Go/Java（主流后端语言）、TCP/UDP/KCP（网络协议）、Protobuf/FlatBuffers（序列化）、Redis/MySQL（数据持久化）、etcd/Consul（服务发现）。
- **模块边界**：客户端负责输入采集 + 渲染表现，服务器负责逻辑运算 + 状态权威 + 持久化，前后端通过约定协议通信。

## 二、架构设计

### 服务器分层架构

游戏服务器通常采用**微服务化分层架构**：

```
┌────────────────────────────────────────┐
│  Gate Server（网关层）                    │
│  负责 TCP 连接管理、协议加解密、负载均衡     │
├────────────────────────────────────────┤
│  Logic Server（逻辑层）                    │
│  核心游戏逻辑：战斗、AI、技能、任务         │
├────────────────────────────────────────┤
│  Match/Room Server（房间层）               │
│  匹配算法、房间状态、组队管理              │
├────────────────────────────────────────┤
│  Chat/IM Server（社交层）                 │
│  私聊、群聊、好友、公会                   │
├────────────────────────────────────────┤
│  Data/DB Proxy（数据层）                  │
│  数据持久化、缓存、读写分离               │
└────────────────────────────────────────┘
```

### 同步模型选择

| 模型 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **帧同步（Lockstep）** | 服务器收集所有玩家输入，广播给所有客户端，客户端确定性模拟 | 带宽低、适合 RTS/MOBA | 延迟敏感、浮点确定性问题 |
| **状态同步** | 服务器计算权威状态，广播状态快照给客户端 | 防作弊强、客户端简单 | 带宽高、延迟感知明显 |
| **快照插值** | 客户端缓存多个服务器快照，插值渲染平滑表现 | 画面平滑 | 引入额外延迟 |

### AOI（Area of Interest）算法

玩家只关心视野范围内的实体。常用算法：
- **九宫格**：地图分网格，玩家只需同步所在格及相邻8格
- **十字链表**：X/Y 轴双向链表维护实体排序，快速查询视野范围
- **灯塔**：空间划分区域，每个区域维护实体列表

## 三、核心实现

### 3.1 网关层（Gate Server）

```cpp
class GateServer {
    // 连接管理：accept → 握手 → 绑定 PlayerID
    // 职责：
    // 1. TCP 长连接保活（心跳 30s）
    // 2. 协议加解密（AES + 动态密钥协商）
    // 3. 消息路由：根据 msgId 转发到对应的 Logic Server
    // 4. 负载均衡：新连接分配到负载最低的 Logic Server
    // 5. 断线重连：session 保持 + 快照恢复
};
```

### 3.2 帧同步核心

```
帧同步流程：
1. 客户端收集 frameId=N 的玩家输入，发送到服务器
2. 服务器收集所有玩家 N 帧输入（或超时用上一帧补位）
3. 服务器广播 frameId=N 的所有输入
4. 所有客户端执行相同的模拟逻辑 → 结果一致

关键保证：
→ 浮点数用定点数（Fixed-point math）
→ 随机数种子统一
→ 遍历顺序一致（如用有序容器）
```

## 四、工程实践

- **心跳与超时**：客户端每 10~30s 发送心跳，服务器超过 2 次心跳未响应断开连接。心跳包体积极小（4 bytes）。
- **断线重连**：服务器保留 session（30~60s 窗口期），客户端重连后恢复状态。核心：sessionId + 待确认消息队列 + 快照缓存。
- **防作弊分层**：服务器端权威校验（伤害计算、速度校验、CD 检查）→ 无法被客户端篡改。客户端仅做表现和预判，不做最终裁决。
- **消息可靠性**：事件型消息（开火、技能）使用可靠有序传输（TCP 或 RUDP）；状态型消息（位置同步）可使用不可靠传输（UDP），因为下一帧会覆盖。
- **无损扩容**：无状态 Gate 可水平扩展；Logic Server 按场景/房间分片（Sharding）；DB 层读写分离 + 分库分表。
- **灰度发布**：新版本 Logic Server 先承载 5% 流量，监控无异常后逐步扩大。

## 五、源码解析

### 5.1 简化帧同步服务端

```cpp
class LockstepServer {
    static constexpr int PLAYER_COUNT = 2;
    static constexpr int FRAME_RATE = 15;          // 每秒 15 帧
    static constexpr int INPUT_TIMEOUT = 100;      // ms，超时补位

    struct FrameInput {
        uint32_t frameId;
        std::array<uint32_t, PLAYER_COUNT> inputs; // 按键位掩码
        bool ready = false;
    };

    std::map<uint32_t, FrameInput> pendingFrames_; // 待收集的帧
    uint32_t nextFrameId_{0};

public:
    // 接收玩家输入
    void onPlayerInput(uint8_t playerId, uint32_t frameId, uint32_t input) {
        auto& frame = pendingFrames_[frameId];
        frame.frameId = frameId;
        frame.inputs[playerId] = input;

        // 所有玩家输入到齐，广播
        if (++frame.ready) { // 简化判断
            broadcast(frame);
            pendingFrames_.erase(frameId);
        }
    }

    // 超时检查（定时器驱动）
    void checkTimeout(uint32_t currentFrame) {
        for (auto& [frameId, frame] : pendingFrames_) {
            if (frameId < currentFrame - 5) {
                // 超时帧：缺失玩家用上一帧输入补位
                for (auto& input : frame.inputs)
                    if (input == 0) input = lastInput_; // 补位
                broadcast(frame);
            }
        }
    }
};
```

### 5.2 九宫格 AOI 实现

```cpp
class GridAOI {
    struct GridCell {
        std::unordered_set<uint64_t> entities;
    };

    double cellSize_; // 格子大小（视野范围）
    std::unordered_map<int64_t, GridCell> grid_;

    int64_t hash(int gx, int gy) { return ((int64_t)gx << 32) | (uint32_t)gy; }

public:
    // 实体进入场景
    void enter(uint64_t entityId, double x, double y) {
        int gx = x / cellSize_, gy = y / cellSize_;
        grid_[hash(gx, gy)].entities.insert(entityId);
    }

    // 获取实体视野内的其他实体
    std::unordered_set<uint64_t> getAOI(uint64_t entityId, double x, double y) {
        std::unordered_set<uint64_t> result;
        int gx = x / cellSize_, gy = y / cellSize_;
        for (int dx = -1; dx <= 1; ++dx)     // 九宫格
            for (int dy = -1; dy <= 1; ++dy)
                for (auto e : grid_[hash(gx + dx, gy + dy)].entities)
                    result.insert(e);
        result.erase(entityId);
        return result;
    }
};
```

### 5.3 消息路由与分发

```cpp
// 基于 msgId 的自动分发
class MessageDispatcher {
    using Handler = std::function<void(Session&, const uint8_t*, size_t)>;
    std::unordered_map<uint16_t, Handler> handlers_;

public:
    template<typename MsgType>
    void registerHandler(uint16_t msgId, 
        std::function<void(Session&, const MsgType&)> handler) {
        handlers_[msgId] = [handler](Session& s, const uint8_t* data, size_t len) {
            MsgType msg;
            msg.ParseFromArray(data, len); // Protobuf 反序列化
            handler(s, msg);
        };
    }

    void dispatch(Session& session, uint16_t msgId, 
                  const uint8_t* data, size_t len) {
        if (auto it = handlers_.find(msgId); it != handlers_.end())
            it->second(session, data, len);
    }
};
```

## 六、面试准备

### 6.1 高频问法

**Q1：帧同步和状态同步的区别？如何选型？**
帧同步：服务器只转发输入，客户端执行确定性模拟（带宽低、延迟敏感、防作弊弱）。适合 RTS/MOBA。状态同步：服务器计算权威结果并广播（带宽高、防作弊强、客户端简单）。适合 MMO/FPS。

**Q2：如何保证帧同步的确定性？**
定点数替代浮点数、统一随机数种子、有序容器保证遍历一致、同一帧内输入顺序一致、物理引擎确定性模式。

**Q3：AOI 算法有哪些？各有什么适用场景？**
九宫格（简单、适合均匀分布）、十字链表（适合动态场景、O(n) 查询）、灯塔算法（分层管理、适合大规模 MMO）。核心权衡：维护成本 vs 查询效率。

**Q4：如何处理网络延迟和丢包？**
TCP 可靠传输（适合事件型消息）、UDP + 自定义重传（适合状态同步）、客户端预测 + 服务器校正（FPS）、快照插值（画面平滑）。KCP 协议在 UDP 上实现可靠、低延迟传输。

**Q5：断线重连如何实现？**
服务器保留 session（30~60s），重连后：若为帧同步则快进模拟到最新帧；若为状态同步则下发全量状态快照。核心：sessionId 持久化 + 待确认消息缓存。

**Q6：如何防止外挂？**
服务器端权威校验（伤害/速度/CD）、移动路径合理性检测、敏感数据不发送给客户端、行为分析（异常 APM 检测）、反作弊 SDK（VAC/EAC 等）。

**Q7：游戏服务器如何水平扩展？**
无状态网关层（DNS/Nginx 负载均衡）、Logic 层按场景/房间分片（一致性哈希）、数据层读写分离 + 分库分表、服务发现（etcd/Consul）。

**Q8：心跳机制的设计要点？**
客户端间隔发送（10~30s），服务器端超时检测（2~3 次心跳间隔无响应断开）。心跳包应极简（4~8 bytes 含 seq/ack）。

**Q9：为什么游戏服务器多采用 UDP 而非 TCP？**
TCP 的队头阻塞问题——丢包导致后续所有包被阻塞，不适合实时游戏。UDP 可自定义可靠性策略（重要消息重传，位置消息直接丢弃用下一帧覆盖）。

**Q10：广播风暴如何解决？**
AOI 按需广播（只发给视野内玩家）、消息合并（同一帧多次状态变更合并为一条）、频率控制（同类型消息不超过 N 次/秒）。

### 6.2 反问点

- 你们项目用的是帧同步还是状态同步？帧率多少？延迟容忍度？
- AOI 用的是什么算法？服务端逻辑是用什么语言写的？
- 防作弊主要依赖服务器校验还是第三方反作弊方案？
- 协议序列化用 Protobuf 还是 FlatBuffers？为什么？
- 高并发场景下如何做压测？QPS/在线人数的瓶颈在哪里？

### 6.3 一句话答案

- 帧同步 = 服务器转发输入，客户端确定性模拟（适合 MOBA/RTS）
- 状态同步 = 服务器计算权威结果广播（适合 MMO/FPS）
- AOI = 视野管理，九宫格/十字链表/灯塔
- 客户端预测 = 本地先动，服务器校正（FPS 标配）
- 断线重连 = session 保留 + 快照恢复
- 服务端权威 = 服务端做最终校验，客户端不可信
- KCP = 基于 UDP 的可靠低延迟传输协议
