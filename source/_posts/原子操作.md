# 原子操作

# 原子操作

## 原子操作及其类型

* **原子操作**是不可分割的操作。在系统的任一线程中，我们不会观察到这种操作处于**半完成状态**；它或者完全做好，或者完全没做。
* **非原子操作**在完成到一半的时候，有可能为另一线程所见。假定由原子操作组合出非原子操作，例如向结构体的原子数据成员赋值，那么别的线程有可能观察到其中的某些原子操作已完成，而某些却还没开始，若多个线程同时赋值，而底层操作相交进行，本来意图完整存入的数据就会彼此错乱。

当多个线程或进程并发访问同一内存位置，并且至少一个线程在写入数据，其他线程在读取或写入数据，而没有适当的同步机制来保护该内存位置时，称这些**表达式冲突**。**拥有两个冲突的求值的程序就有数据竞争**，除非

* 两个求值都在同一线程上，或者在同一信号处理函数中执行，或
* 两个冲突的求值都是原子操作（见 std::atomic），或
* 一个冲突的求值发生早于 另一个（见 std::memory\_order）

**原子操作都是线程安全的吗？**

根据上面原子操作的概念：\*原子操作过程中不可被打断，所以寄存器内的内容就不会被其它线程修改，在原子操作结束后，结果存入内存，才会被切换到别的线程，听起来似乎没有问题。这一系列操作中，原子操作一定能将任务完成，并且返回正确的结果写入内存。\*所以你可能会认为原子操作是线程安全的。

其实并不尽然，在多线程环境中使用原子操作并不一定是线程安全的，因为线程安全需要确保在多线程情况下，整个代码的逻辑是正确的，而不仅仅是某个操作的原子性。当程序逻辑依赖多个操作的组合，而这些操作之间的整体性没有被原子化处理时，就可能不具有线程安全。

|  |  |  |
| --- | --- | --- |
| **场景** | **是否线程安全** | **原因** |
| **检查并更新值** | ❌ 不安全 | 操作依赖多个步骤的逻辑组合，没有整体原子化，可能导致竞态条件。 |
| **简单计数器递增** | ✅ 安全 | 操作独立，单个原子操作即可完成，无需额外的同步机制。 |
| **复合逻辑操作（如检查和修改）** | ❌ 不安全 | 原子操作只能保证单次操作的不可分割性，无法保证跨多次操作的逻辑正确性。 |

**总结：**

1. 如果操作是**单步的、独立的**，使用原子操作即可保证线程安全。
2. 如果操作需要**多个步骤或涉及依赖其他共享状态**，应使用锁或其他同步机制来保护代码块的逻辑完整性。

## 原子类型

标准原子类型的定义位于头文件`<atomic>`内。我们可以通过`atomic<>`定义一些原子类型的变量，如`atomic<bool>`,`atomic<int>` 这些类型的操作全是原子化的。

从C++17开始，所有的原子类型都包含一个静态常量表达式成员变量，`std::atomic::is_always_lock_free`。这个成员变量的值表示在任意给定的目标硬件上，原子类型X是否始终以无锁结构形式实现。如果在所有支持该程序运行的硬件上，原子类型X都以无锁结构形式实现，那么这个成员变量的值就为true；否则为false。

只有一个原子类型不提供`is_lock_free()`成员函数：`std::atomic_flag` 。类型`std::atomic_flag`的对象在初始化时清零，随后即可通过成员函数`test_and_set()`查值并设置成立，或者由`clear()`清零。整个过程只有这两个操作。其他的`atomic<>`的原子类型都可以基于其实现。

`std::atomic_flag`的`test_and_set`成员函数是一个原子操作，他会先检查`std::atomic_flag`当前的状态是否被设置过，

1 如果没被设置过(比如初始状态或者清除后)，将`std::atomic_flag`当前的状态设置为`true`，并返回`false`。

2 如果被设置过则直接返回`ture`。

对于`std::atomic<T>`类型的原子变量，还支持`load()`和`store()`、`exchange()`、`compare_exchange_weak()`和`compare_exchange_strong()`等操作。

## 自旋锁

```
#include <iostream>
#include <atomic>
#include <thread>

class SpinLock {
public:
    void lock() {
        //1 处
        while (flag.test_and_set(std::memory_order_acquire)); // 自旋等待，直到成功获取到锁
    }

    void unlock() {
        //2 处
        flag.clear(std::memory_order_release); // 释放锁
    }

private:
    std::atomic_flag flag = ATOMIC_FLAG_INIT;
};
```

## 五、源码解析和实践感悟

### 5.1 源码解析

#### atomic_flag 的 test_and_set 硬件实现

```cpp
// x86-64 上 atomic_flag::test_and_set 的底层——LOCK XCHG 指令
bool test_and_set(std::memory_order order) {
    // 伪代码：x86 的 LOCK BTS (Bit Test and Set) / LOCK XCHG
    // LOCK 前缀锁定缓存行，保证原子性
    bool old = flag;
    flag = true;
    return old;  // 返回旧值
}
```

`test_and_set` 在 x86 上对应一条带 LOCK 前缀的指令——硬件保证原子性，无需软件锁。这也是自旋锁能高效工作的基础：自旋等待的线程在不断执行 LOCK 指令，不陷入内核。

#### compare_exchange_weak vs compare_exchange_strong 的区别

```cpp
// CAS 循环的经典模式
std::atomic<int> value{0};
int expected = value.load();
while (!value.compare_exchange_weak(expected, expected + 1)) {
    // weak 版本可能 spurious fail（伪失败），expected 自动更新为当前值
    // 在循环中使用 weak 比 strong 更高效（strong 内部有额外重试逻辑）
}
```

- **weak**：即使 expected==current 也可能返回 false（spurious failure），适合循环重试
- **strong**：只有在 expected!=current 时才返回 false，内部有重试逻辑，开销略大
- **选择原则**：循环中优先用 weak（更高效），单次 CAS 用 strong

#### 自旋锁 vs 互斥量的内核切换成本

```cpp
// 自旋锁的关键——忙等在用户态
void spinlock_lock() {
    while (flag.test_and_set(memory_order_acquire)) {
        // ① x86: PAUSE 指令降低功耗，提示 CPU 这是自旋循环
        // ② ARM: YIELD 指令让出流水线
        // 不陷入内核——切换开销 ~0
    }
}

// 互斥量——竞争时陷入内核
void mutex_lock() {
    if (!try_lock()) {
        // futex(FUTEX_WAIT) 系统调用——上下文切换 ~1-10μs
        syscall(SYS_futex, &futex, FUTEX_WAIT, ...);
    }
}
```

自旋锁在用户态忙等，锁持有时间极短时性能远超互斥量；但若持有时间长，自旋浪费 CPU。经验法则：临界区 < 1μs 用自旋锁，否则用互斥量。

### 5.2 实践经验

1. **自旋锁只适合极短临界区**：加锁后只做几行代码（如更新计数器），绝不调用任何可能阻塞的函数
2. **atomic<T> 的 `is_lock_free` 检查**：不是所有类型都支持无锁操作，大结构体（>16 字节）通常用内部锁实现——`is_lock_free()` 返回 false 时要警惕性能陷阱
3. **memory_order 不要过度使用**：默认 `seq_cst` 安全但最慢；确认无顺序要求时用 `relaxed`（计数器）；生产者-消费者用 `release/acquire`
4. **atomic 不能替代所有锁**：CAS 只能保护单个变量，多变量一致性操作仍需互斥量
5. **复合操作不是原子的**：`value = value + 1` 即使 value 是 atomic，这个复合操作也不能保证原子性——用 `fetch_add` 替代
6. **atomic 变量应避免放在同一缓存行**：False sharing——多个 atomic 变量在同一 cache line 时，一个 CPU 修改会导致其他 CPU 的 cache line 失效

## 六、面试准备

### 6.1 面试 Q&A

**Q1: 原子操作和互斥量的区别？**

| 维度 | 原子操作 | 互斥量 |
|------|----------|--------|
| 级别 | 硬件/指令级 | OS 级 |
| 内核切换 | 无 | 竞争时陷入内核 |
| 粒度 | 单变量 | 代码块 |
| 开销 | ~10ns | ~1-10μs |
| 适用 | 简单计数器、flag | 多变量一致性 |

**Q2: compare_exchange_weak 为什么需要循环？**

CAS 可能遇到两类失败：① 值不匹配（正常失败）② spurious failure（伪失败，LL/SC 架构如 ARM 上常见）。循环保证即使伪失败也能重试，weak 比 strong 少一层内部循环，总体吞吐更高。

**Q3: memory_order_relaxed 什么时候用？**

只关心原子性、不关心顺序时——如计数器递增、引用计数。`fetch_add(1, memory_order_relaxed)` 保证原子 +1，但不保证其他线程何时看到结果。

**Q4: atomic_flag 为什么是唯一的 lock-free 保证？**

C++ 标准保证 `atomic_flag` 在所有平台上都是无锁的——因为它只需要一个 bit，任何 CPU 都能用单条指令实现。`atomic<int>` 在 32 位平台上是无锁的，但 `atomic<BigStruct>` 可能用内部互斥量。

**Q5: 自旋锁和互斥量各适合什么场景？**

自旋锁：临界区 < 1μs、线程数 ≤ CPU 核数、不允许睡眠的上下文（中断处理）。互斥量：临界区可能阻塞、线程数远大于 CPU 核数、允许睡眠。

**Q6: 为什么原子操作不能保证复合操作的线程安全？**

"检查后修改"需要两次原子操作（load + store），中间可能被其他线程插入修改——这是 TOCTOU 问题。需要用 CAS 循环（无锁编程）或互斥量保护整个逻辑。

**Q7: False Sharing 是什么？如何避免？**

两个 atomic 变量在同一 cache line（通常 64 字节），CPU A 修改变量 1 导致 CPU B 的 cache line 失效——即使 B 只访问变量 2。解决：用 `alignas(64)` 或 padding 错开。

**Q8: atomic 和 volatile 的区别？**

`volatile` 不保证原子性、不保证内存序、不防止编译器重排；`atomic` 三者都保证。`volatile` 仅用于内存映射 IO / 信号处理；多线程同步只用 `atomic`。

### 6.2 常见陷阱与面试反问

1. **陷阱**：`if (flag.load()) flag.store(false);`——非原子复合操作。**修复**：用 `flag.exchange(false)` 或 CAS 循环。

2. **陷阱**：大结构体的 `atomic<BigStruct>`——`is_lock_free()` 返回 false，内部用锁实现。**修复**：改用指针 + `atomic<BigStruct*>` + 无锁 CAS。

3. **陷阱**：自旋锁中调用 sleep/IO——自旋线程占用 CPU 却不干活。**修复**：自旋锁内绝不调用可能阻塞的函数。

4. **反问**：「单核 CPU 上自旋锁还有意义吗？」希望听到：无意义——自旋线程占用唯一 CPU 且不会释放锁（锁持有者也在同一核上）。单核场景必须用互斥量。

5. **反问**：「CAS 的 ABA 问题怎么解决？」希望听到：ABA = 值 A→B→A，CAS 认为没变但语义已变。解决：带版本号的 CAS（`atomic<versioned_ptr>`）或 hazard pointer/RCU。

### 6.3 一句话答案速记

| 问题 | 一句话答案 |
|------|------------|
| 原子操作是什么？ | 不可分割的操作，不会被线程切换打断 |
| CAS 原理？ | 比较当前值与期望值，相等则替换，否则返回当前值 |
| weak vs strong？ | weak 容许伪失败，循环中使用更高效 |
| 自旋锁原理？ | test_and_set 忙等，用户态不陷入内核 |
| 自旋 vs 互斥？ | 自旋适合 <1μs 临界区，互斥适合可能阻塞的场景 |
| False Sharing？ | 同 cache line 的两个变量被不同 CPU 修改导致互相失效 |
| atomic vs volatile？ | atomic 保证原子性+内存序，volatile 仅禁止编译器优化 |
| memory_order？ | 控制编译器/CPU 重排程度，默认 seq_cst 最安全
