# 服务器和客户端

# 客户端和服务器

## 网络编程基本流程

网络编程的基本流程对于服务端是这样的  
服务端  
1）socket----创建socket对象。

2）bind----绑定本机ip+port。

3）listen----监听来电，若在监听到来电，则建立起连接。

4）accept----再创建一个socket对象给其收发消息。原因是现实中服务端都是面对多个客户端，那么为了区分各个客户端，则每个客户端都需再分配一个socket对象进行收发消息。

5）read、write----就是收发消息了。

对于客户端是这样的  
客户端  
1）socket----创建socket对象。

2）connect----根据服务端ip+port，发起连接请求。

3）write、read----建立连接后，就可发收消息了。

## 同步读写的服务器和客户端

### **客户端**

设计基本思路是根据服务器对端的ip和端口创建一个endpoint，然后创建socket连接这个endpoint，之后就可以用同步读写的方式发送和接收数据了。

```
#include <iostream>
#include <boost/asio.hpp>
using namespace std;
using namespace boost::asio::ip;
const int MAX_LENGTH = 1024;
int main()
{
    try {
        //创建上下文服务
        boost::asio::io_context   ioc;
        //构造endpoint
        tcp::endpoint  remote_ep(address::from_string("127.0.0.1"), 10086);
        tcp::socket  sock(ioc);
        boost::system::error_code   error = boost::asio::error::host_not_found; ;
        sock.connect(remote_ep, error);
        if (error) {
            cout << "connect failed, code is " << error.value() << " error msg is " << error.message();
            return 0;
        }

        std::cout << "Enter message: ";
        char request[MAX_LENGTH];
        std::cin.getline(request, MAX_LENGTH);
        size_t request_length = strlen(request);
        boost::asio::write(sock, boost::asio::buffer(request, request_length));

        char reply[MAX_LENGTH];
        size_t reply_length = boost::asio::read(sock,
            boost::asio::buffer(reply, request_length));
        std::cout << "Reply is: ";
        std::cout.write(reply, reply_length);
        std::cout << "\n";
    }
    catch (std::exception& e) {
        std::cerr << "Exception: " << e.what() << endl;
    }
    return 0;
}
```

### 服务器

```
#include <iostream>
#include <boost/asio.hpp>
#include <set>
#include <memory>
 
using  boost::asio::ip::tcp;
using std::cout;
using std::endl;
const int MAX_LENGTH = 1024; // 发送和接收的长度为1024字节
typedef std::shared_ptr<tcp::socket> socket_ptr;
std::set<std::shared_ptr<std::thread>> thread_set;
 
void session(socket_ptr sock); // 处理某个客户端连接之后数据的读和写（收发）
void server(boost::asio::io_context& io_context, unsigned short port); // 接收客户端的连接
 
int main()
{
    try {
        cout << "服务器已启动！\n";
        boost::asio::io_context ioc;
        server(ioc, 10086);
        // 主线程必须等到子线程结束之后，主线程才会结束
        for (auto& t : thread_set) {
            if (t->joinable())  // t.joinable()检查t（即当前遍历到的std::thread对象）是否可以被连接
                t->join(); // 调用join()的线程将阻塞，直到t所代表的线程执行完毕才会继续下一行
        }
    }
    catch (std::exception& e) {
        std::cerr << "Exception: " << e.what() << endl;
    }
 
    return 0;
}
 
 
void session(socket_ptr sock) {
    try {
        // 该段代码是循环的，当第一次接收到数据后，程序走到最后又重回第一行，如果第二次没有
        // 读到任何信息，那么length==0，此时error未eof，相当于客户端不在发送信息，连接中止
        for (;;) {
            char data[MAX_LENGTH]; // 缓存收到的数据
            memset(data, '\0', MAX_LENGTH); // 将char数组中的数据全部设为\0
            boost::system::error_code error;
            // 服务器可能不会一次读完，而用read或receive可能会造成堵塞
            // 因为这里是独立的线程而不是主程序，所以这里可以用read,一直等，但直到读到最大长度才会返回
            //size_t length = boost::asio::read(sock, boost::asio::buffer(data, MAX_LENGTH), error);
            // read_some实际只会读收到的长度，在没有粘包的情况下用read_some比较好
            size_t length = sock->read_some(boost::asio::buffer(data, MAX_LENGTH), error);
            if (error == boost::asio::error::eof) { // 连接被关闭
                std::cout << "connection closed by peer" << endl;
                break;
            }
            else if (error) // 读取失败
                throw boost::system::system_error(error);
            
            cout << "receive from " << sock->remote_endpoint().address().to_string() << endl;
            cout << "receive message is " << data << endl;
            // 回传给对方
            boost::asio::write(*sock, boost::asio::buffer(data, length));
        }
    }
    catch (std::exception& e) {
        cout << "Exception in thread: " << e.what() << "\n" << endl;
    }
}
 
void server(boost::asio::io_context& io_context, unsigned short port) {
    // 生成一个用于接收客户端连接的acceptor，绑定的端点是服务器的地址（用ipv4的方式绑定）以及自定义的端口
    tcp::acceptor a(io_context, tcp::endpoint(tcp::v4(), port));
    while (1) {
        // 生成一个socket来处理客户端的请求，相当于服务员
        socket_ptr socket(new tcp::socket(io_context));
        // accept接收到请求后，用socket对请求进行处理
        a.accept(*socket);
        // 生成一个线程，相当于服务员将客户带到包间，大厅仍进行客人的招待
        // 线程中也就是包间中，用session作为招待服务，session就是服务器的读和写
        // 如果不创建线程，而是直接session，那么如果对端不发送数据，程序就会阻塞一直不运行下一行，其他的连接也会无法接收
        // 之所以将线程存储到智能指针中，是为了管理其生命周期，防止线程对象被提前销毁
        auto t = std::make_shared<std::thread>(session, socket);
        // thread_set是全局变量而不是局部变量，当server函数结束后，thread_set仍会保留
        thread_set.insert(t);
    }
}
```

### Session类

Session类主要是处理[客户端](https://so.csdn.net/so/search?q=客户端&spm=1001.2101.3001.7020)消息收发的会话类，为了简单起见，我们不考虑[粘包](https://zhida.zhihu.com/search?content_id=248169672&content_type=Article&match_order=1&q=粘包&zhida_source=entity)问题，也不考虑支持手动调用发送的接口，只以应答的方式发送和接收固定长度(1024[字节长度](https://so.csdn.net/so/search?q=字节长度&spm=1001.2101.3001.7020))的数据

```
class Session
{
private:
    tcp::socket _socket;
    enum { max_length = 1024 };
    char _data[max_length];
 
    // headle回调函数
    void headle_read(const boost::system::error_code& error, size_t bytes_transferred);
    void haddle_write(const boost::system::error_code& error);
public:
    Session(boost::asio::io_context& ioc) : _socket(ioc){}
    tcp::socket& Socket() { return _socket; }
 
    void Start();
};


void Session::Start() {
    memset(_data, 0, max_length); // 缓冲区清零
    // 从套接字中读取数据，并绑定回调函数headle_read
    _socket.async_read_some(boost::asio::buffer(_data, max_length),
        std::bind(&Session::headle_read, this, std::placeholders::_1, std::placeholders::_2));
}

void Session::headle_read(const boost::system::error_code& error, size_t bytes_transferred) {
    if (!error) {
        cout << "server receive data is " << _data << endl;
        boost::asio::async_write(_socket, boost::asio::buffer(_data, bytes_transferred),
            std::bind(&Session::haddle_write, this, std::placeholders::_1));
    }
    else {
        cout << "read error" << endl;
        delete this;
    }
}

void Session::haddle_write(const boost::system::error_code& error) {
    if (!error) {
        memset(_data, 0, max_length);
        _socket.async_read_some(boost::asio::buffer(_data, max_length),
            std::bind(&Session::headle_read, this, std::placeholders::_1, std::placeholders::_2));
    }
    else {
        cout << "write error" << error.value() << endl;
        delete this;
    }
}
```

### Server类

设计[服务器管理](https://so.csdn.net/so/search?q=服务器管理&spm=1001.2101.3001.7020)接收连接的类：server类

```
class Server
{
private:
    void start_accept();  // 启动一个acceptor
    // 当acceptor接收到连接后启动该函数
    void handle_accept(Session* new_session, const boost::system::error_code& error);
    boost::asio::io_context& _ioc;
    tcp::acceptor _acceptor;
public:
    Server(boost::asio::io_context& ioc, short port);
};

// 初始化服务器对象，绑定 I/O 上下文和监听的端口，并启动服务器
Server::Server(boost::asio::io_context& ioc, short port) : _ioc(ioc),
_acceptor(ioc, tcp::endpoint(tcp::v4(), port)) {
    cout << "Server start success, on port: " << port << endl;
    // 开始异步地接受客户端连接请求。服务器启动后就进入等待客户端连接的状态
    start_accept();
}

void Server::start_accept() {，
    // 创建一个新的 Session 对象，表示一个与客户端的会话。每个 Session 对象负责处理一个客户端连接。
    // Session 的构造函数接收 _ioc 作为参数，因为 Session 也需要处理异步操作
    Session* new_session = new Session(_ioc);
    // 开始一个异步接受操作，当new_session的socket与客户端连接成功时，调用回调函数handle_accept
    _acceptor.async_accept(new_session->Socket(), std::bind(&Server::handle_accept, this, new_session,
        std::placeholders::_1));
}

// 异步接受操作的回调函数，负责处理客户端连接的结果
void Server::handle_accept(Session* new_session, const boost::system::error_code& error) {
    // 如果没有错误（error 为 false），调用 new_session->Start() 来启动与旧客户端的会话
    if (!error) new_session->Start();
    // 如果发生了错误（如连接失败或出现其他问题），则删除 new_session，释放分配的内存
    else delete new_session;
    // 无论当前连接是否成功，都重新调用 start_accept()，以便服务器能够继续接受下一个新客户端的连接请求。
    // 服务器始终保持在监听状态，随时准备接受新连接
    start_accept();
}
```

**boost::asio::async\_write?socket.async\_read\_some?socket.async\_send？有什么区别**

|  |  |  |
| --- | --- | --- |
| 函数 | 特性 | 适用场景 |
| async\_write | 保证缓冲区中数据全部传输，自动管理分批写入 | TCP连接、大数据块传输、需要保证完整性 |
| async\_read\_some | 只读取部分数据，不保证读取到完整的数据 | 流式数据读取、数据长度不确定的情况 |
| async\_send | 不保证数据的完整性，适用于数据报传输（如UDP） | 无[连接通信](https://zhida.zhihu.com/search?content_id=248169672&content_type=Article&match_order=1&q=连接通信&zhida_source=entity)、数据包传输、轻量级传输 |

## 一、核心概念

- **定义**：基于 Boost.Asio 的网络编程。服务器端基本流程为 socket → bind → listen → accept → read/write；客户端为 socket → connect → write/read。Asio 支持同步和异步两种模式
- **关键词**：`tcp::socket`、`tcp::acceptor`、`tcp::endpoint`、`async_accept`/`async_read`/`async_write`、同步读写、异步回调、`io_context`
- **适用场景/边界**：同步模式适合简单原型和低并发场景（每连接一线程）；异步模式适合高并发服务器（单线程处理数千连接）

## 二、详细解析

- **原理拆解（三层递进）**：
  - **第一层——同步读写模型**：客户端 `connect()` 阻塞直到三次握手完成，`write()` 阻塞直到数据发送到内核缓冲区，`read()` 阻塞直到接收完整数据。服务端 `acceptor.accept()` 阻塞等待新连接，每个连接创建一个线程调用同步 `read()/write()`。实现简单但 N 连接 = N 线程，C10K 问题无法解决
  - **第二层——异步读写模型**：`async_accept(acceptor, handler)` 注册接受回调后立即返回，io_context 事件循环在有新连接时回调 handler。`async_read(socket, buffer, handler)` 同样异步——内核数据就绪后回调。**单线程即可管理数千连接**，线程开销仅在于业务处理
  - **第三层——Asio 封装下的 endpoint 与 socket 生命周期**：`tcp::endpoint(address::from_string("127.0.0.1"), 10086)` 封装 IP+端口。服务端 `acceptor` 绑定 endpoint 后监听，每个新连接通过 `acceptor.async_accept()` 获取新 socket 对象（用 `shared_ptr` 管理以保证回调时对象存活）
- **关键数据结构/接口**：`tcp::socket(io_context)` 绑定 io_context 后可异步；`tcp::acceptor` 监听 + 接受连接；`boost::asio::buffer(data, len)` 包装数据缓冲区；错误码 `boost::system::error_code` 判断操作成败
- **关键公式**：同步模型线程数 = 连接数（不可扩展）；异步模型线程数 = CPU 核数 × N（N 由业务决定）；`async_accept` 必须链式调用——回调中再次 `async_accept` 保持监听不中断

## 三、动手实践

```c++
#include <boost/asio.hpp>
#include <iostream>
using namespace boost::asio;
using namespace boost::asio::ip;

// 异步 echo 服务器
class Server {
    io_context ioc_;
    tcp::acceptor acceptor_{ioc_, tcp::endpoint(tcp::v4(), 10086)};
public:
    void run() {
        do_accept();
        ioc_.run();
    }
private:
    void do_accept() {
        auto sock = std::make_shared<tcp::socket>(ioc_);
        acceptor_.async_accept(*sock, [this, sock](auto ec) {
            if (!ec) {
                std::cout << "New connection!" << std::endl;
                auto buf = std::make_shared<std::array<char, 1024>>();
                sock->async_read_some(buffer(*buf), [sock, buf](auto ec, size_t n) {
                    if (!ec) async_write(*sock, buffer(buf->data(), n), [](auto, auto){});
                });
            }
            do_accept();  // 继续监听下一个连接
        });
    }
};
```

## 四、进阶应用

### 同步 vs 异步选择

| 维度 | 同步 | 异步 |
|------|------|------|
| 代码复杂度 | 线性清晰 | 回调嵌套 |
| 并发能力 | 每连接一线程 | 单线程数千连接 |
| 适用场景 | 原型/低并发 | 生产高并发 |
| 错误处理 | 异常/错误码直接 | 回调中检查 error_code |

### 防止 async_accept 中断的链式调用

```c++
// 关键：回调中再次调用 do_accept()，否则只接受一次连接
void do_accept() {
    acceptor_.async_accept([this](auto ec, tcp::socket sock) {
        handle(sock);
        do_accept();  // 如果没有这行，服务器只接受一次连接！
    });
}
```

### shared_ptr 生命周期管理

```c++
// 异步操作中 socket 必须用 shared_ptr，否则回调时 socket 可能已析构
auto sock = make_shared<tcp::socket>(ioc_);
sock->async_read_some(..., [sock](auto, auto){});  // 捕获 shared_ptr 延长生命周期
```

**工程经验**：(1) `bind` 必须在新 socket 创建前完成，accept 后才真正建立连接；(2) 异步回调中检查 `error_code`——连接断开、超时都通过 ec 通知；(3) 同步服务器适合学习网络编程流程，生产环境异步是主流。

## 五、源码解析和实践感悟

### 5.1 源码解析

#### async_read_some 与 async_write 的差异

```c++
// async_read_some: 读到多少算多少，不保证填满缓冲区
socket.async_read_some(buffer(data, max_length), handler);

// async_write: 保证全部数据发送完毕才回调
async_write(socket, buffer(data, length), handler);
```

`async_read_some` 是"尽力读"——底层 `recv` 一次返回多少就回调多少，适合流式数据（如 HTTP 请求行不固定长度）。`async_write` 是"保证写"——内部循环调用 `send` 直到所有数据发送完毕，适合已知长度的响应。

#### shared_from_this 的引用计数保护

```c++
class CSession : public std::enable_shared_from_this<CSession> {
    void HandleRead(error_code ec, size_t n, shared_ptr<CSession> self) {
        // self 额外持有引用，保证 CSession 在回调执行期间不被析构
        if (!ec) {
            async_write(_socket, buffer(_data, n),
                bind(&CSession::HandleWrite, this, _1, self));  // 传递 self
        } else {
            _server->ClearSession(_uuid);  // 错误时清理
        }
    }
};
```

普通 `shared_ptr(this)` 会创建新引用计数块（double-delete），`shared_from_this()` 使用内部 `weak_ptr` 返回共享同一计数块的 `shared_ptr`。

#### Round-Robin 连接分配

```c++
// 从 IOServicePool 获取 io_context
auto& io = AsioIOServicePool::GetInstance()->GetIOService();
auto session = make_shared<CSession>(io, this);  // session 绑定到指定 io_context
acceptor.async_accept(session->GetSocket(), handler);
```

新连接到达时分配到不同 `io_context`，该连接的所有后续 I/O 操作都在该 `io_context` 的线程中执行，避免了连接间的锁竞争。

### 5.2 实践经验

1. **同步 vs 异步模型选择**：同步模型代码简单但每连接一线程，C10K 问题下资源耗尽；异步模型单线程可处理上万连接
2. **`delete this` 的危险**：同步 Session 中 `delete this` 假设没有其他地方持有引用，多线程环境极易悬空——应改用 `shared_ptr`+`shared_from_this`
3. **send_que 的必要性**：异步发送时如果上次 `async_write` 未完成就再次发送，会导致数据交织或 `async_write` 重叠错误
4. **`_self_shared` 参数传递**：每个回调都传递 `shared_ptr<CSession>`，形成闭包链，最后一个持有者析构时才真正销毁对象
5. **`ClearSession` 的线程安全**：从 map 中删除 session 需要加锁或使用单线程 `io_context` 保证串行访问
6. **`read_some` vs `async_read_some`**：同步版 `read_some` 会阻塞当前线程（适合独立线程模型），异步版注册回调后立即返回

## 六、面试准备

### 6.1 面试高频问答

**Q1：`async_read_some` 和 `async_read` 的区别？**

A：`async_read_some` 读到部分数据就回调（可能不填满缓冲区），适合流式解析。`async_read` 保证读满指定字节或出错才回调，内部循环调用 `async_read_some`。

**Q2：为什么用 `shared_from_this()` 而不是 `this`？**

A：`shared_from_this()` 返回与其他 `shared_ptr` 共享引用计数的智能指针，避免 double-delete。`shared_ptr(this)` 会创建独立的引用计数块。

**Q3：异步回调中 `delete this` 有什么风险？**

A：如果有其他地方持有对象指针或正在执行其他回调，`delete this` 会导致悬空指针/use-after-free。应用 `shared_ptr` 管理生命周期。

**Q4：为什么需要 `send_que` 发送队列？**

A：`async_write` 未完成时再次调用会触发 `operation_not_supported` 错误。队列让发送串行化：正在发时 push 到队列，完成时从队列取下一个。

**Q5：`enable_shared_from_this` 的内部实现？**

A：基类持有 `weak_ptr<T>`。`shared_from_this()` 返回从该 `weak_ptr` lock 得到的 `shared_ptr`。对象必须已经被某个 `shared_ptr` 管理过才能调用。

**Q6：同步服务器每连接一线程，高并发下会有什么问题？**

A：线程数 = 连接数，C10K 场景下 10000 线程的内存（栈+TCB）约 10GB，上下文切换频繁（CPU 时间浪费在调度上），吞吐量急剧下降。

**Q7：异步服务器的 `io_context::run()` 在哪执行？**

A：在 `main` 线程或 `IOServicePool` 的工作线程中执行。`run()` 阻塞等待 I/O 事件，有事件时调用对应回调，回调返回后继续等待。

**Q8：`async_accept` 回调中再次调用 `start_accept()` 的作用？**

A：保持 acceptor 始终在监听状态。如果不递归注册，accept 一次连接后就不再接受新连接。

### 6.2 陷阱与反问

**陷阱1**：`shared_from_this()` 在构造函数中调用 → `weak_ptr` 尚未初始化，未定义行为
**陷阱2**：忘记把 `_self_shared` 传递给下一个异步操作 → 对象可能在中间回调执行后提前析构
**陷阱3**：多线程 model 下 `CServer` 的 `_sessions` map 未加锁 → 数据竞争
**陷阱4**：同步版 `read` 在独立线程中阻塞，但线程数过多时 OS 调度开销超过 I/O 等待
**陷阱5**：回调 lambda 捕获引用 `[&]` 而引用对象已销毁 → 悬空引用

**反问**：同步和异步服务器的内存/CPU 开销各有什么特点？
*答案：同步模型内存开销大（每线程栈 ~1MB），CPU 浪费在上下文切换。异步模型内存开销小（每连接只需 buffer），CPU 集中在 I/O 多路复用系统调用。但异步代码复杂度更高（回调地狱）。*

### 6.3 一句话答案

1. **async_read_some**：读到部分数据就回调，不保证填满缓冲区
2. **async_write**：保证全部数据发送完才回调，内部循环 send
3. **shared_from_this**：返回与其他 shared_ptr 共享引用计数的智能指针
4. **send_que**：串行化异步发送，防止重叠 write
5. **enable_shared_from_this**：基类持有 weak_ptr，保证 shared_from_this 安全
6. **start_accept 递归**：保持 acceptor 持续监听新连接
7. **C10K 问题**：单机 10000+ 并发连接的处理挑战，异步 I/O 是核心解决方案
