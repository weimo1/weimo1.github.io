# 用户域设计与实现

> 适用范围：基于领域驱动设计（DDD）思想对 IM 系统中"用户"这一核心领域进行建模，涵盖用户实体、好友关系、在线状态、用户仓储和领域服务。

## 一、核心概念

- **定义**：用户域是 IM 系统的用户身份与关系管理域，负责定义用户的属性（昵称、头像、状态）、用户之间的关系（好友、黑名单、群组成员）、用户的在线状态管理，以及面向外部的用户查询服务。
- **关键词**：用户聚合根、好友关系实体、在线状态值对象、用户仓储、缓存回源、主从数据库、领域事件
- **适用场景/边界**：
  - 适用于 IM 系统中所有用户身份、关系、在线状态的建模
  - 边界：聚焦用户本身的数据和行为，不涉及消息收发和推送逻辑

## 二、详细解析（≥200字）

### 原理拆解（三层递进）

**第一层：基本工作原理**

用户域以"用户"为聚合根，包含用户的身份信息（UserID、昵称、头像）和在线状态。用户之间的关系（好友、黑名单）建模为独立的实体，通过 UserID 对 关联到用户聚合。用户域的查询（如查找用户资料、获取好友列表）是 IM 系统最高频的读操作，因此需要精心的缓存设计。

**第二层：关键步骤详解**

1. **用户实体设计**：
   - User 聚合根包含：UserID（全局唯一）、Nickname、Avatar、Status（在线/离线/隐身）、LastSeenTime 等
   - UserID 通常由注册时分配，全局唯一，IM 系统中作为消息路由的主键
2. **好友关系建模**：
   - 好友关系是"双向关系实体"，包含 (UserID_A, UserID_B, RelationType, CreateTime)
   - 关系类型：FRIEND（好友）、BLOCKED（拉黑）、DELETED（已删除）
   - 好友申请通过领域事件流转：FriendRequestSent → FriendRequestAccepted/Rejected → FriendshipCreated
3. **在线状态管理**：
   - 状态类型：ONLINE（在线）、OFFLINE（离线）、INVISIBLE（隐身）
   - 在线状态不是持久化到 MySQL，而是存在 Redis 中（因为变化频繁、需要实时性）
   - 用户上线 → 网关感知 → 更新 Redis 状态 → 发布 UserOnlineEvent 领域事件 → 好友收到上线通知

**第三层：底层机制**

- **缓存回源架构**：用户资料是最典型的"读多写少"场景。采用 Cache-Aside 模式：查询先查 Redis，命中直接返回；未命中则回源 MySQL 查询，写入 Redis 后再返回。缓存的 TTL 设为 1 小时，用户修改资料时主动失效缓存。
- **主从数据库读写分离**：用户域写操作少（注册、修改资料），读操作极多（每次消息展示都需拉取用户头像和昵称）。MySQL 主库负责写入，从库负责查询。读写分离通过中间件（如 ProxySQL）或 ORM 配置实现。

### 关键数据结构/接口

```go
// 用户聚合根
type User struct {
    UserID       int64
    Nickname     string
    Avatar       string

// 用户仓储接口

// 好友仓储接口
type FriendshipRepository interface {
    FindFriends(ctx context.Context, userID int64) ([]*Friendship, error)

```

### 关键公式/复杂度

- 用户资料批量查询：N 个用户 ID 走 Redis MGET（O(N)），miss 的部分回源 MySQL IN 查询（O(log N)）
- 好友关系判断：通过 MySQL 索引 (UserID_A, UserID_B) 等值查询，O(log N)

## 三、动手实践（代码案例）

```go
// 用户域领域服务
type UserDomainService struct {
    userRepo       UserRepository
    friendshipRepo FriendshipRepository
    cache          *redis.Client
}

// 查询用户资料（带缓存回源）
func (s *UserDomainService) GetUserProfile(ctx context.Context, userID int64) (*User, error) {
    // 1. 查 Redis 缓存
    cacheKey := fmt.Sprintf("user:profile:%d", userID)
    cached, err := s.cache.Get(ctx, cacheKey).Result()
    if err == nil {
        var user User
        json.Unmarshal([]byte(cached), &user)
        return &user, nil
    }
    
    // 2. 缓存未命中，回源 MySQL（从库）
    user, err := s.userRepo.FindByID(ctx, userID)
    if err != nil {
        return nil, err
    }
    
    // 3. 写入缓存（TTL 1 小时）
    data, _ := json.Marshal(user)
    s.cache.Set(ctx, cacheKey, data, time.Hour)
    
    return user, nil
}

// 批量查询用户资料（优化：一次 MGET）
func (s *UserDomainService) BatchGetUserProfiles(ctx context.Context, userIDs []int64) (map[int64]*User, error) {
    if len(userIDs) == 0 {
        return nil, nil
    }
    
    // 1. 批量查 Redis
    keys := make([]string, len(userIDs))
    for i, id := range userIDs {
        keys[i] = fmt.Sprintf("user:profile:%d", id)
    }
    cached, _ := s.cache.MGet(ctx, keys...).Result()
    
    result := make(map[int64]*User)
    var missedIDs []int64
    
    for i, raw := range cached {
        if raw == nil {
            missedIDs = append(missedIDs, userIDs[i])
            continue
        }
        var user User
        json.Unmarshal([]byte(raw.(string)), &user)
        result[userIDs[i]] = &user
    }
    
    // 2. 批量回源 MySQL
    if len(missedIDs) > 0 {
        users, err := s.userRepo.BatchFindByIDs(ctx, missedIDs)
        if err != nil {
            return nil, err
        }
        for _, u := range users {
            result[u.UserID] = u
            data, _ := json.Marshal(u)
            s.cache.Set(ctx, fmt.Sprintf("user:profile:%d", u.UserID), data, time.Hour)
        }
    }
    
    return result, nil
}

// 更新在线状态 + 发布领域事件
func (s *UserDomainService) UpdateUserStatus(ctx context.Context, userID int64, status UserStatus) error {
    // 1. 更新 Redis 在线状态（不落 MySQL，变化太快）
    key := fmt.Sprintf("user:status:%d", userID)
    s.cache.Set(ctx, key, int(status), 0)  // 无过期时间，用户下线时删除

    // 2. 发布领域事件（通知好友状态变更）
    event := &UserStatusChangedEvent{
        UserID:    userID,
        NewStatus: status,
        Timestamp: time.Now().Unix(),
    }
    s.eventBus.Publish(ctx, event)

    return nil
}
```

## 四、进阶应用（≥500字）

### 与其他主题的关联

- **消息协议设计 / 消息领域**：User 聚合根是消息的发送者和接收者，消息实体的 SenderID 和 TargetID 引用 UserID。消息展示时需要批量反查用户资料（昵称、头像）
- **长连接网关**：网关持有 userID→连接映射，用户上下线时更新网关路由表，同时通知用户域更新在线状态
- **分布式缓存设计**：用户资料的缓存策略是该模块的核心——缓存命中率直接影响消息列表的渲染速度

### 工程中的真实用法

**微信用户域架构实践**：

1. **用户资料分层存储**：
   - 基础信息（UserID、昵称、头像）：高频读，走 Redis 缓存 + MySQL 从库
   - 隐私信息（手机号、实名认证）：低频读，走 MySQL 主库，不缓存
   - 设置信息（消息免打扰、字体大小）：客户端本地 + 云端同步，走 Redis Hash
2. **好友关系双向存储**：
   - 每对好友关系存两条记录：`(A, B)` 和 `(B, A)`，A 拉黑 B 时修改 `(A, B)` 记录为 BLOCKED，`(B, A)` 保持 FRIEND
   - 这保证了：B 看到 A 仍是好友（可发消息），但 A 收不到 B 的消息
3. **在线状态投递策略**：
   - 聚焦投递：用户上线时只通知"活跃"好友（最近 7 天有过对话），而非全量好友，降低推送风暴
   - 懒加载：用户打开好友列表时才拉取所有好友的在线状态，不做全量实时推送

**用户域缓存架构总结**：

| 数据      | 存储位置       | TTL    | 更新策略     |
|-----------|---------------|--------|-------------|
| 用户资料  | Redis + MySQL | 1 小时  | 修改时主动失效 |
| 在线状态  | Redis only    | 永久    | 上下线时更新   |
| 好友列表  | Redis Set     | 30 分钟 | 增删好友时更新 |
| 黑名单    | Redis Set     | 永久    | 拉黑/取消时更新 |

### 常见优化策略

- **布隆过滤器防穿透**：大量查询不存在用户的请求会穿透缓存打到 MySQL。在缓存层前加布隆过滤器，先判断 userID 是否可能存在，不存在直接返回空，避免数据库压力
- **用户资料异步刷新**：缓存过期时不阻塞请求等待回源，而是返回旧缓存 + 异步回源更新。适合"头像/昵称短暂不一致可接受"的场景
- **好友列表分页 + 游标**：好友数量大时（如 5000+），全量加载不可取。改为按创建时间倒序 + 游标分页，每次只拉取一页（如 50 个）

## 五、源码解析和实践感悟（≥1000字）

### 关键实现路径

**用户资料缓存管理器（Cache-Aside 模式）**：

```go
// 带防穿透和异步刷新的缓存管理器
type UserCacheManager struct {
    cache       *redis.Client
    db          UserRepository
    bloomFilter *bloom.BloomFilter  // 布隆过滤器
    semaphore   chan struct{}       // 回源并发控制
}

func NewUserCacheManager(cache *redis.Client, db UserRepository) *UserCacheManager {
    m := &UserCacheManager{
        cache:       cache,
        db:          db,
        bloomFilter: bloom.New(10000000, 5), // 1000万用户, 误判率1%
        semaphore:   make(chan struct{}, 100), // 最多100个并发回源
    }
    // 从 MySQL 加载所有用户 ID 初始化布隆过滤器
    go m.initBloomFilter()
    return m
}

func (m *UserCacheManager) Get(ctx context.Context, userID int64) (*User, error) {
    // 1. 布隆过滤器快速判断用户是否存在
    if !m.bloomFilter.Test([]byte(fmt.Sprintf("%d", userID))) {
        return nil, ErrUserNotFound  // 99.9% 概率用户不存在，直接返回
    }
    
    // 2. 查 Redis
    cacheKey := fmt.Sprintf("user:%d", userID)
    data, err := m.cache.Get(ctx, cacheKey).Bytes()
    if err == nil {
        var user User
        json.Unmarshal(data, &user)
        return &user, nil
    }
    
    // 3. 缓存未命中，回源 MySQL（控制并发）
    return m.loadFromDB(ctx, userID, cacheKey)
}

func (m *UserCacheManager) loadFromDB(ctx context.Context, userID int64, cacheKey string) (*User, error) {
    // 获取回源信号量
    select {
    case m.semaphore <- struct{}{}:
        defer func() { <-m.semaphore }()
    case <-ctx.Done():
        return nil, ctx.Err()
    }
    
    // 双重检查：获取信号量后可能其他协程已加载
    data, err := m.cache.Get(ctx, cacheKey).Bytes()
    if err == nil {
        var user User
        json.Unmarshal(data, &user)
        return &user, nil
    }
    
    // 回源 MySQL
    user, err := m.db.FindByID(ctx, userID)
    if err != nil {
        // 缓存空对象，防止缓存穿透（TTL 短，1 分钟）
        m.cache.Set(ctx, cacheKey, "NULL", time.Minute)
        return nil, err
    }
    
    // 写入缓存
    userData, _ := json.Marshal(user)
    m.cache.Set(ctx, cacheKey, userData, time.Hour)
    
    return user, nil
}

func (m *UserCacheManager) Invalidate(ctx context.Context, userID int64) {
    // 用户修改资料时主动删除缓存
    cacheKey := fmt.Sprintf("user:%d", userID)
    m.cache.Del(ctx, cacheKey)
}
```

**好友关系存储的双向写入**：

```go
// 好友关系服务
type FriendshipService struct {
    repo  FriendshipRepository
    cache *redis.Client
}

func (s *FriendshipService) AddFriend(ctx context.Context, userA, userB int64) error {
    // 1. 写入 MySQL（双向两条记录）
    if err := s.repo.AddFriend(ctx, userA, userB); err != nil {
        return err
    }
    if err := s.repo.AddFriend(ctx, userB, userA); err != nil {
        // 补偿：删除已写入的记录
        s.repo.RemoveFriend(ctx, userA, userB)
        return err
    }
    
    // 2. 更新 Redis 好友列表缓存
    keyA := fmt.Sprintf("friends:%d", userA)
    keyB := fmt.Sprintf("friends:%d", userB)
    pipe := s.cache.Pipeline()
    pipe.SAdd(ctx, keyA, userB)
    pipe.SAdd(ctx, keyB, userA)
    _, err := pipe.Exec(ctx)
    
    return err
}
```

### 难点与易错点

**陷阱1：缓存穿透**

大量查询不存在的 userID（恶意扫描或 bug），每次都穿透 Redis 打到 MySQL。解决方案：
- 布隆过滤器：在缓存层前加 Bloom Filter，用极小内存判断 key 是否可能存在
- 空值缓存：查询到不存在用户时，缓存一个特殊标记（如 "NULL"），TTL 设为 1 分钟，防止同 ID 短时间内反复穿透

**陷阱2：缓存与数据库的双写一致性**

用户修改资料时，先更新 MySQL 再删 Redis，存在时间窗口：MySQL 已更新但 Redis 未删除时，其他请求读到旧数据。解决方案：
- **先删除缓存，再更新数据库**（Cache-Aside 标准做法）：虽有小概率新数据被旧请求覆盖缓存，但可通过延迟双删缓解
- **最终一致性**（IM 场景推荐）：用户资料允许短暂不一致（1 秒内的头像不一致对用户体验影响极小），不做强一致

**陷阱3：好友关系的双向状态不一致**

用户 A 拉黑 B：需要更新 `(A, B)` 状态为 BLOCKED，但 `(B, A)` 保持 FRIEND（B 仍以为 A 是好友）。关键点：
- A 拉黑 B 后，A 不再接收 B 的消息（服务端过滤）
- B 发消息给 A 时，消息正常走上行流程，但投递阶段检查 A 对 B 的关系状态，发现是 BLOCKED 则返回"消息已发出但被对方拒收"的 ACK

### 经验总结

1. **用户域是"读多写少"的典型**：缓存命中率是用户域最重要的性能指标。90%+ 的请求应命中 Redis 缓存。需要持续监控缓存命中率，低于 85% 就要排查。
2. **在线状态不是持久化数据**：在线状态变化频率极高（用户切后台、断网重连都可能触发），不应写入 MySQL。Redis 是唯一存储，服务重启通过心跳重建。
3. **布隆过滤器是缓存穿透的银弹**：用几 MB 内存就能将 99% 的无效查询挡在缓存前，性价比极高。但注意布隆过滤器不支持删除，用户注销场景需定期重建。
4. **批量查询是关键优化**：消息列表通常需要一次性展示几十个用户的头像和昵称。将 N 次单次查询合并为一次 MGET 或 batch MySQL 查询，性能提升数十倍。

## 六、面试准备

### 6.1 高频问法（≥10个）

**基础理解：**

Q1：IM 系统中的用户域包含哪些核心实体？分别承担什么职责？

A：核心实体包括：User 聚合根（用户身份、资料、在线状态）、Friendship 实体（好友关系、黑名单）。User 聚合根是外部访问的入口，Friendship 通过 UserID 对关联到 User。用户域的查询是系统最高频操作，缓存架构是本域核心设计。

Q2：用户的在线状态在 IM 系统中如何存储和同步？

A：在线状态存在 Redis 中（不落 MySQL），因为变化极高频（上下线、切后台都会触发更新）。存储结构为 `user:status:{userID} → ONLINE/OFFLINE/INVISIBLE`。同步方式：用户 A 上线 → 更新 Redis → 发布 UserOnlineEvent → 查询 A 的活跃好友列表 → 批量推送 NOTIFY 告知好友"用户 A 上线了"。

Q3：好友关系如何处理双向拉黑？

A：好友关系存储两条记录：`(A, B)` 和 `(B, A)`。A 拉黑 B 时只修改 `(A, B)` 状态为 BLOCKED，`(B, A)` 保持 FRIEND。消息投递时：B 发消息给 A → 投递阶段查 `(A, B)` 关系状态 → 发现为 BLOCKED → 返回拒收 ACK。B 看不到自己已被拉黑。

**原理深入：**

Q4：用户资料查询为什么需要缓存回源？Cache-Aside 模式的完整流程是怎样的？

A：用户资料是"读多写少"型数据，如果每次查询都走 MySQL，数据库扛不住。Cache-Aside 流程：1）请求先查 Redis；2）命中直接返回；3）未命中回源 MySQL；4）查询结果写入 Redis（设 TTL）；5）返回结果。用户修改资料时删除对应缓存，下次查询自然回源更新。

Q5：为什么要将用户资料查询从单次查询优化为批量查询？如何实现？

A：消息列表展示 20 条消息，涉及最多 20 个不同用户，单次查询需要 20 次 Redis 往返 = 20ms。批量查询用 Redis MGET 一次性获取所有 key，只需 1 次往返 = 1ms。实现：收集所有 userID → `MGET user:profile:{id1} user:profile:{id2} ...` → 对比结果按位置组装。miss 的 ID 批量 `SELECT WHERE user_id IN (...) ` 回源 MySQL。

Q6：布隆过滤器在用户域中解决什么问题？原理是什么？

A：解决缓存穿透：恶意请求大量不存在的 userID 会导致每次穿透到 MySQL。布隆过滤器用多个哈希函数将 userID 映射到位数组。查询时如果任一位为 0，则 userID 一定不存在；如果所有位都为 1，则大概率存在（有误判率，可调节）。用几 MB 内存过滤掉 99% 的无效查询。

**实践应用：**

Q7：用户修改头像后，如何保证所有看到该用户的客户端都能显示新头像？

A：1）修改头像 → 更新 MySQL → 删除 Redis 缓存；2）其他客户端下次查询该用户资料时，缓存已失效，回源 MySQL 拿到新头像 URL；3）头像 URL 变化时附加版本号或随机参数（如 ?v=20250101），浏览器/客户端自动重新加载图片；4）主动推送 NOTIFY 告知在线的相关客户端刷新。

Q8：批量查询用户资料时，如何处理缓存击穿（热点 key 过期）？

A：1）逻辑过期 + 异步刷新：缓存的 value 中包含一个逻辑过期时间，查询时判断是否"逻辑过期"。如果过期则返回旧值 + 异步提交回源任务，不等锁；2）互斥锁：获取回源信号量，保证同一 key 只有一个协程回源，其他协程等待结果。IM 场景推荐方案 1（逻辑过期），因为头像短暂不一致可接受。

Q9：用户注销后，如何清理用户相关的所有数据？

A：1）用户状态标记为 DEACTIVATED（软删除），立即生效——无法登录、收不到消息；2）好友关系标记为 DELETED，好友列表不再展示；3）消息数据保留 30 天后物理删除（为纠纷处理留窗口）；4）缓存主动清理所有相关 key；5）30 天后 cron job 物理删除 MySQL 中的用户记录和好友关系。

Q10：如何设计用户资料的可扩展字段（如增加个性签名、地区等）？

A：在 User 实体中预留扩展字段（Extra map），使用 JSON 存储。新增字段时不修改数据库 Schema，只修改应用层解析逻辑。高频查询字段应单独建列加索引，低频字段放 Extra JSON 中。MySQL 5.7+ 支持 JSON 类型和虚拟列索引。

### 6.2 反问点/陷阱点（≥5个）

**针对面试官的深度问题：**

贵公司 IM 系统的用户资料存储方案中，是如何平衡读写性能和数据一致性的？

对于上亿用户量的场景，好友关系的存储层采用的是什么数据库？有没有做分库分表？

在线状态的实时同步，在高并发场景下如何避免广播风暴？

**常见的陷阱问题：**

陷阱问题1：线上用户资料缓存命中率突然从 95% 降到 50%，可能的原因是什么？答案：1）大量缓存 key 同时过期（缓存雪崩），TTL 需加随机偏移；2）Redis 内存上限被触发，大量 key 被 LRU 淘汰；3）上线了新功能对所有用户做了全量查询导致缓存被更新。排查思路：先看 Redis 内存和淘汰策略，再看是否有批量操作。

陷阱问题2：好友删除了我，但他还在我的好友列表里。这是 bug 还是设计如此？答案：通常是设计如此。删除是单向操作（和拉黑类似），A 删除 B → `(A, B)` 状态变为 DELETED，`(B, A)` 不变。B 可继续向 A 发消息，但 A 收不到（投递阶段过滤）。需要双向删除时才更新两条记录。

陷阱问题3：用户 A 同时用手机和电脑登录，A 的手机修改了昵称，电脑端何时能看到新昵称？答案：取决于同步策略：1）主动拉取：电脑端下次打开聊天列表时，重新查询用户资料（触发缓存回源拿到新数据）；2）被动推送：昵称修改后广播 NOTIFY 到 A 的所有在线设备，设备收到后刷新本地缓存。推荐两种方案结合。

### 6.3 一句话答案（≥5个）

用户域设计的核心是：以 User 为聚合根管理身份和状态，以 Friendship 实体管理关系，通过 Cache-Aside 缓存回源架构支撑海量读请求。

在线状态存 Redis 不落 MySQL 的根本原因是：状态变化频率极高（秒级），关系型数据库无法承受如此高频的写入。

缓存穿透的三级防护是：布隆过滤器（挡不存在 key）→ 空值缓存（挡重复穿透）→ 回源并发控制（挡热点回源打爆 DB）。

好友关系双向存储的意义是：支持单向操作（拉黑、删除），A 拉黑 B 不影响 B 看到 A 的好友状态。

当被问到"用户资料怎么缓存"时，回答："Cache-Aside 模式，Redis 缓存 + TTL 1 小时，修改时主动失效，Miss 时回源 MySQL 从库，布隆过滤器防穿透，批量查询走 MGET。"

当被问到"如何保证缓存一致性"时，回答："采用先删缓存再写库的顺序，加延迟双删兜底。IM 场景优先保证可用性，接受百毫秒级的数据不一致。"
