# 游戏引擎架构

> 适用范围：游戏引擎核心架构、渲染管线、物理引擎、ECS 架构、游戏循环与时间管理

## 一、项目/模块概述

- **模块定位**：游戏引擎是游戏开发的基础框架，提供渲染、物理、音频、输入、资源管理等核心子系统，让游戏开发者专注于游戏逻辑而非底层实现。
- **技术栈与依赖**：C++（主流引擎语言）、OpenGL/Vulkan/DirectX（图形 API）、Bullet/PhysX（物理引擎）、FMOD/Wwise（音频）、Lua/Python（脚本层）。
- **模块边界**：引擎层提供通用能力（渲染/物理/音频/资源/输入/网络），游戏逻辑层通过脚本或 C++ 调用引擎 API，不直接操作底层硬件。

## 二、架构设计

游戏引擎通常采用**分层架构**，自底向上分为：平台抽象层 → 核心系统层 → 资源管理层 → 游戏框架层 → 游戏逻辑层。各大子系统通过事件总线或服务定位器松耦合通信。

### 核心子系统关系

```
┌─────────────────────────────────────────────┐
│                  游戏逻辑层                   │
│            (脚本/Lua/C++ Gameplay)           │
├─────────────────────────────────────────────┤
│  游戏框架层：场景管理、GameObject、事件系统    │
├──────┬──────┬──────┬──────┬──────┬──────────┤
│ 渲染  │ 物理  │ 音频  │ 输入  │ 网络  │ 资源   │
│ 管线  │ 引擎  │ 系统  │ 系统  │ 模块  │ 管理   │
├──────┴──────┴──────┴──────┴──────┴──────────┤
│         核心系统层（内存/线程/文件/数学库）      │
├─────────────────────────────────────────────┤
│         平台抽象层（Window/iOS/Android/Console）│
└─────────────────────────────────────────────┘
```

### 游戏主循环（Game Loop）

游戏引擎的核心是主循环，每一帧执行：**输入处理 → 逻辑更新 → 物理模拟 → 渲染**。现代引擎通常在多个线程上并行执行这些阶段（如渲染线程独立于逻辑线程），通过双缓冲或命令队列同步。

```
while (running) {
    processInput();          // 收集输入事件
    update(deltaTime);       // 更新游戏逻辑（FixedUpdate + Update）
    physics->simulate();     // 物理步进（通常固定时间步长）
    render();                // 提交绘制命令到 GPU
    swapBuffers();           // VSync 或自适应同步
}
```

## 三、核心实现

### 3.1 ECS（Entity-Component-System）架构

现代游戏引擎（Unity DOTS、Unreal Mass、Flecs）普遍采用 ECS 替代传统 GameObject 继承体系：

- **Entity**：空 ID，不包含任何数据或行为
- **Component**：纯数据（Position、Velocity、Health…），由 ComponentStore 按类型连续存储
- **System**：遍历拥有特定组件组合的实体并执行逻辑

```cpp
// ECS 核心思想伪代码
struct Position { float x, y, z; };
struct Velocity { float vx, vy, vz; };

class MovementSystem {
    void update(float dt, World& world) {
        for (auto [pos, vel] : world.query<Position, Velocity>()) {
            pos.x += vel.vx * dt;
            pos.y += vel.vy * dt;
            pos.z += vel.vz * dt;
        }
    }
};
```

ECS 相比 OOP 继承的优势：**数据局部性（Cache-Friendly）**、**组合优于继承**、**便于并行化（System 间无依赖可并行）**。

### 3.2 渲染管线

从 CPU 到 GPU 的核心管线：**顶点着色器 → 曲面细分 → 几何着色器 → 光栅化 → 片段着色器 → 混合/深度测试**。现代引擎的关键优化技术包括：

- **视锥体裁剪**：剔除视野外的物体
- **LOD（细节层次）**：远处物体使用低精度模型
- **遮挡剔除**：被遮挡的物体不渲染
- **实例化渲染**：同一模型批量提交
- **延迟渲染**：先写 G-Buffer 再统一光照计算（适合多光源场景）

### 3.3 物理引擎

物理引擎的核心是**碰撞检测**（Broad Phase → Narrow Phase）和**动力学求解**（力 → 加速度 → 速度 → 位置积分）。常用积分方法：半隐式欧拉 > 显式欧拉（更稳定）。

## 四、工程实践

- **固定时间步长物理**：物理更新使用固定 dt（如 1/60s），避免帧率波动影响物理确定性。游戏逻辑更新可追赶多次物理步进。
- **内存管理策略**：引擎层使用对象池 → 减少碎片；GPU 端使用环形缓冲区 → 避免每帧分配；资源加载使用异步 I/O + 引用计数。
- **多线程架构**：典型的并行模式包括：渲染线程独立（主线程 → 渲染命令队列 → 渲染线程消费）、Job System（C++ 任务调度器分发并行任务）、System 并行化（ECS 中无数据依赖的 System 可同时执行）。
- **资源管理**：引用计数 + 异步加载 + 资源句柄（Handle）设计。资源生命周期由资源管理器控制，游戏逻辑只持有 Handle，资源卸载时 Handle 失效。
- **热更新支持**：C++ 编译为动态库 + Lua/Python 脚本层，允许不重启游戏即可修改逻辑。
- **性能剖析**：集成 Tracy/Remotery/Perfetto 做帧级别性能分析，标记每个子系统的 GPU/CPU 耗时。

## 五、源码解析

### 5.1 游戏循环的 deltaTime 与固定更新

```cpp
class GameLoop {
    using Clock = std::chrono::high_resolution_clock;
    using Duration = std::chrono::duration<double>;

    const Duration fixedDt{1.0 / 60.0}; // 固定物理步长
    Duration accumulator{0};
    Clock::time_point lastTime;

public:
    void run() {
        lastTime = Clock::now();
        while (running_) {
            auto now = Clock::now();
            Duration frameTime = now - lastTime;
            lastTime = now;

            // 防止螺旋式追赶（spiral of death）
            if (frameTime > Duration{0.25}) frameTime = Duration{0.25};

            accumulator += frameTime;
            while (accumulator >= fixedDt) {
                fixedUpdate(fixedDt);  // 物理/固定逻辑
                accumulator -= fixedDt;
            }

            double alpha = accumulator / fixedDt; // 插值因子
            variableUpdate(frameTime);
            render(alpha); // 渲染时使用插值平滑显示
        }
    }
};
```

### 5.2 简化版 ECS 实现

```cpp
// 组件类型 ID 生成
using ComponentType = size_t;
template<typename T>
ComponentType getComponentType() {
    static ComponentType id = nextTypeId_++;
    return id;
}

// 世界：管理所有实体和组件
class World {
    std::unordered_map<ComponentType, 
        std::unordered_map<Entity, std::any>> components_;
    std::vector<Entity> entities_;
    Entity nextEntity_{0};

public:
    Entity createEntity() { return nextEntity_++; }

    template<typename T>
    void addComponent(Entity e, T comp) {
        components_[getComponentType<T>()][e] = std::move(comp);
    }

    template<typename... Ts>
    std::vector<std::tuple<Entity, Ts&...>> query() {
        std::vector<std::tuple<Entity, Ts&...>> result;
        for (auto e : entities_) {
            if ((hasComponent<Ts>(e) && ...)) {
                result.emplace_back(e, getComponent<Ts>(e)...);
            }
        }
        return result;
    }
};
```

### 5.3 碰撞检测的 Broad Phase（空间哈希）

```cpp
class SpatialHashGrid {
    double cellSize_;
    std::unordered_map<int64_t, std::vector<Entity>> grid_;

    int64_t hash(int cx, int cy) { return (int64_t(cx) << 32) | uint32_t(cy); }

public:
    void insert(Entity e, double x, double y) {
        int cx = int(x / cellSize_), cy = int(y / cellSize_);
        grid_[hash(cx, cy)].push_back(e);
    }

    std::vector<std::pair<Entity, Entity>> queryPotentialPairs() {
        std::vector<std::pair<Entity, Entity>> pairs;
        for (auto& [key, bucket] : grid_) {
            for (size_t i = 0; i < bucket.size(); ++i)
                for (size_t j = i + 1; j < bucket.size(); ++j)
                    pairs.emplace_back(bucket[i], bucket[j]);
        }
        return pairs;
    }
};
```

## 六、面试准备

### 6.1 高频问法

**Q1：游戏主循环有哪几种模式？各有什么优劣？**
传统单线程循环、固定时间步长+可变渲染、多线程并行（渲染/逻辑分离）。固定时间步长保证物理确定性，可变渲染保证画面流畅。

**Q2：ECS 和传统 GameObject 继承体系的区别？**
继承体系容易产生"钻石继承"和"基类膨胀"，新需求往往需要修改基类。ECS 采用组合（Entity 挂载 Component），数据与逻辑分离，System 只操作关心数据，天然并行友好。

**Q3：如何做帧同步（Lockstep）？**
客户端收集输入 → 发送到服务器 → 服务器广播所有玩家输入 → 所有客户端执行相同的模拟步进。核心难点：浮点数确定性（需定点数）、网络延迟容忍。

**Q4：为什么物理模拟要用固定时间步长？**
浮点精度影响物理确定性。dt 不固定 → 相同输入产生略不同的结果 → 多人联机不同步。固定 dt 保证确定性。

**Q5：GPU 渲染管线的主要阶段？**
顶点着色器（变换）→ 图元装配 → 光栅化（生成片段）→ 片段着色器（着色）→ 深度/模板测试 → 混合输出。

**Q6：延迟渲染和前向渲染的区别？**
前向渲染：每个物体遍历所有光源（光源多时性能差）；延迟渲染：先写到 G-Buffer（位置、法线、颜色等），再统一光照计算（适合多光源，但不支持半透明 + MSAA 复杂）。

**Q7：如何管理游戏中的大量对象（如子弹、粒子）？**
对象池模式预分配内存避免频繁 new/delete，配合环形缓冲区或空闲链表复用。ECS 中可基于 Archetype 的 Chunk 分配。

**Q8：LOD 的实现思路？**
为同一模型准备多个细节层次，根据相机距离选择显示版本。切换阈值根据屏幕占比计算，配合平滑过渡（Dithering/Alpha Blend）避免突变。

**Q9：如何处理跨平台渲染？**
使用抽象层（RHI - Render Hardware Interface）：定义统一的绘制接口，各平台分别实现（DX12/Vulkan/Metal）。着色器可用 SPIR-V 中间表示或转换工具。

**Q10：资源引用计数和生命周期管理？**
Handle 模式：游戏逻辑只持有轻量 Handle，资源管理器维护引用计数。Handle 失效时返回错误/默认资源（粉红纹理），避免悬垂指针。

### 6.2 反问点

- 你们引擎的渲染后端是 DX 还是 Vulkan？如何做多线程渲染？
- 游戏逻辑用 C++ 还是脚本语言？热更新方案是什么？
- ECS 是自研还是用现成库（EnTT/Flecs）？Archetype 还是 Sparse Set？
- 多人联机用的是帧同步还是状态同步？怎么处理浮点数确定性？
- CI/CD 流程中资源打包和 Cook 是如何组织的？

### 6.3 一句话答案

- Game Loop = Input → Update → Render，循环驱动游戏运行
- ECS = Entity(空ID) + Component(纯数据) + System(逻辑遍历)
- Fixed Timestep = 物理用固定 dt，逻辑追赶/插值渲染保证流畅
- Lockstep = 所有客户端执行相同输入序列保证确定性同步
- 对象池 = 预分配 + 复用，避免频繁 new/delete
- LOD = 远小近大，根据距离切换模型精度
- 延迟渲染 = 先写 G-Buffer 再统一光照，适合多光源场景
- Handle = 轻量资源引用，资源卸载后自动失效
