# TCP  UDP

## **UDP(User Datagram Protocol)传输**与**IP传输**非常类似，它的传输方式也是"**Best** **Effort**"的，所以[**UDP协议**](https://zhida.zhihu.com/search?content_id=120565168&content_type=Article&match_order=1&q=UDP%E5%8D%8F%E8%AE%AE&zhida_source=entity)也是**不可靠**的

当应用程序**对传输的可靠性要求不高**，但是对**传输速度和延迟要求较高**时，可以用UDP协议来替代TCP协议在传输层控制数据的转发。

## UDP 协议头

UDP报文分为**UDP报文头**和**UDP数据区域**两部分。报头由源端口、目的端口、报文长度以及校验和组成。

UDP头部的标识如下：

**16位源端口号：**源主机的应用程序使用的端口号。

**16位目的端口号：**目的主机的应用程序使用的端口号。

**16位UDP长度：**是指UDP头部和UDP数据的字节长度。因为UDP头部长度为8字节，所以该字段的最小值为8。

**16位UDP校验和：**该字段提供了与TCP校验字段同样的功能；该字段是可选的。

**每个 UDP socket 都有一个接收缓冲区，但没有发送缓冲区**

#### UDP数据包

UDP数据包的最大大小应该是1500字节 – IP头(20字节) – UDP头(8字节) = 1472字节。不过鉴于Internet上的标准MTU值为576字节，所以建议在进行Internet的UDP编程时，最好将UDP的数据长度控制在 (576-8-20)548字节以内

### 粘包/拆包 问题产生原因：

发生TCP粘包或拆包有很多原因，现列出常见的几点：

1. 要发送的数据大于TCP发送缓冲区剩余空间大小，将会发生拆包。
2. 待发送数据大于MSS（TCP报文长度 - TCP头部长度 > MSS最大报文长度），TCP在传输前将根据MSS大小进行拆包分段发送。
3. 要发送的数据小于TCP发送缓冲区的大小，TCP将多次写入缓冲区的数据包合并为一次发送，将发生粘包（Nagle算法优化，避免tcp报文头重脚轻的情况发生）
4. 接收数据端的应用层没有及时读取接收缓冲区中的数据，将发生粘包。

**补充：**

MTU 最大传输单元 （链路层）：

数据链路层传输的帧大小是有限制的，不能把一个太大的包直接塞给链路层，这个限制被称为「最大传输单元（Maximum Transmission Unit, MTU）」

以太网的帧最大的帧是 1518 字节，除去 14 字节头部和 4 字节 CRC，有效荷载最大为 1500，这个值就是以太网的 MTU。

 

MSS TCP最大段大小 Maximum Segment Size（传输层，可传输tcp数据包大小）：

TCP 为了避免被发送方分片，会主动把数据分割成小段再交给网络层，最大的分段大小称之为 MSS（Max Segment Size）。

这样一个 MSS 的数据恰好能装进一个 MTU 而不用分片。

一般，在以太网中 TCP 的 MSS = 1500（MTU） - 20（IP 头大小） - 20（TCP 头大小）= **1460**

**总结：**IP 数据包长度超过链路的 MTU 时，在发送之前需要分片，而 TCP 层为了 IP 层不用分片主动将包切割成 MSS 大小。

### 解决 粘包/拆包 问题：

解决问题关键在于如何给每个数据包添加边界信息用于区分不同数据包

1. 消息分为tcp首部和tcp消息体，tcp首部中应保存数据包的长度（**TCP的首部原本是没有表示数据长度的字段，因为可由IP层计算出：TCP数据包长度 = IP首部的数据包长度 - IP首部长度（20字节 ）- TCP包首部长度（20字节 ）**）。这样接收端在接收到数据后，通过读取包首部的长度字段，就知道每个数据包的实际长度了。
2. 发送端在每个包的末尾使用固定的分隔符（如 \r\n），这样接收端通过这个边界就可以将不同的数据包拆分开（如 FTP协议）。
3. 发送端将每个数据包封装为固定长度（不够的可以通过补0填充），这样接收端每次从接收缓冲区中读取固定长度的数据就自然而然的把每个数据包拆分开来。不推荐这种方式，尤其是在高并发大流量的业务场景下，会消耗不必要的资源...

### 为什么TCP有粘包？

TCP协议粘包拆包问题是因为TCP协议数据传输是基于 "字节流" 的，它不包含消息、数据包等概念，需要应用层协议自己设计消息边界。日常网络应用开发大都在传输层进行，因此粘包拆包问题大都只发生在TCP协议中。

### 为什么UDP没有粘包？

1. UDP有消息保护边界，不会发生粘包拆包问题
2. UDP发送的时候，不经过**Nagle**算法优化，不会将多个小包合并一次发送出去。
3. UDP协议的接收端，采用了链式结构来记录每一个到达的UDP包。UDP是基于报文发送的，从UDP的帧结构可以看出，在UDP首部采用了16bit字段来指示UDP数据报文的长度，因此在应用层能很好的将不同的数据报文区分开，从而避免粘包和拆包的问题。

**补充：**"消息保护边界"，就是指传输协议把数据当作一条独立的消息在网络上传输，接收端只能接收独立消息。也就是说存在保护消息边界，接收端一次只能接收发送端发出的一个数据包。而面向字节流是指无消息保护边界的，如果发送端连续发送数据，接收端有可能在一次接收动作中，会接收两个或者更多的数据包。

### 1. UDP 与 IP 分片：一个“懒惰”的组合

* **UDP的职责**：UDP协议本身非常简单。它的唯一职责是从应用程序接收数据块，加上一个简单的8字节头（源端口、目标端口、长度、校验和），然后就将整个东西扔给IP层去处理。**它不关心也不感知MTU的存在。**
* **IP层的职责**：当IP层从UDP收到一个数据报（Datagram）时，它会检查这个数据报的大小是否大于出口链路的MTU。

+ 如果 **是**，IP层会自动将这个UDP数据报**分片（Fragment）** 成多个小的IP包，每个都小于MTU。
+ 如果 **否**，则直接发送。

所以，从协议栈的角度看，UDP+IP的组合可以处理任意大小的数据（受限于最大IP包长度65535字节），分片是IP层自动、透明完成的。

### 2. 为什么避免分片如此重要？（“稳定性”的真正含义）

您提到的“稳定性”，在实际网络中更多地表现为 **“更高的成功送达率”** 和 **“更可预测的性能”** 。而IP分片会严重破坏这种稳定性，原因如下：

1. **分片丢失，全部重传**：一个UDP数据报被分成3个IP分片。如果其中任意1个分片在网络传输中丢失，整个原始UDP数据报就无法在目的地重组。对于UDP而言，这意味着整个数据报就丢了。发送方需要重传整个原始的大数据报，而不是只重传丢失的那个小分片。**效率极其低下。**
2. **无重传机制**：UDP本身没有重传机制，重传依赖于应用程序。如果应用层不知道底层发生了分片，它很难实现高效的重传逻辑。
3. **增加延迟和抖动**：分片和重组操作需要消耗路由器和服务器的CPU和内存资源。这可能会引入不可预测的延迟（抖动），对于音视频、游戏等实时应用是致命的。
4. **防火墙/NAT兼容性问题**：许多严格的网络防火墙和NAT设备配置为丢弃分片包，因为它们无法完整检查被分片的包的内容（第一个分片之后的分片没有传输层头信息）。这意味着你的大数据报很可能根本无法到达目的地。

### 3. 最佳实践：应用程序主动管理包大小

因此，为了获得“稳定性”，**最佳实践是由应用程序负责确保发出的UDP数据报不会在路径上触发IP分片。**

如何做到这一点呢？

* **路径MTU发现（PMTUD）**：这是一种技术，主机通过发送不允许分片的大包，并监听来自路由器的“需要分片”ICMP错误消息，来动态发现到达目的地的整条路径上的最小MTU。然而，PMTUD在实践中常常因为网络设备禁用ICMP而失败。
* **保守的默认值**：由于PMTUD不可靠，应用程序通常会采用一个**保守的、公认安全的大小**。互联网的默认最小MTU是576字节。因此，一个常见的策略是：  
  **应用层数据 + UDP头(8B) + IP头(20B) ≤ 576字节**  
  计算得出：**应用层数据最大 ≤ 576 - 28 = 548字节**。

这样生成的IP包总长为576字节，保证了它在互联网的任何路径上传输都**绝对不会被分片**。

由于IP协议提供为上层协议切割和重组报文的功能，因此传输层协议的数据包长度原则上来说没有限制。

实际上限制还是有的，由于IP包的标识字段终究不可能无限长，依照IPv4。好像上限应该是4G(64K\*64K)。

依靠这样的机制。**TCP包头中就没有“包长度”字段。而全然依靠IP层去处理分帧。**

**这就是为什么TCP经常被称作一种“流协议”的原因**。开发人员在使用TCP服务的时候，不必去关心数据包的大小。仅仅需讲SOCKET看作一条数据流的入口。往里面放数据就是了，TCP协议本身会进行拥塞/流量控制

### 1.高通信实时性要求和低持续性要求的场景下：

**在分组交换通信当中，协议栈的成本主要表现在以下两方面：**

* [1] 封装带来的空间复杂度；
* [2] 缓存带来的时间复杂度。

以上两者是对立影响的，如果想减少封装消耗，那么就必须缓存用户数据到一定量在一次性封装发送出去，这样每个协议包的有效载荷将达到最大化，这无疑是节省了带宽空间，带宽利用率较高，但是延时增大了。如果想降低延时，那么就需要将用户数据立马封装发出去，这样显然会造成消耗更多的协议头等消耗，浪费带宽空间。  
因此，我们进行协议选择的时候，需要重点考虑一下空间复杂度和时间复杂度间的平衡。  
**通信的持续性对两者的影响比较大，根据通信的持续性有两种通信类型：**

* [1] 短连接通信；
* [2] 长连接通信。

对于短连接通信，一方面如果业务只需要发一两个包并且对丢包有一定的容忍度，同时业务自己有简单的轮询或重复机制，那么采用UDP会较为好些。在这样的场景下，如果用TCP，仅仅握手就需要3个包，这样显然有点不划算，一个典型的例子是DNS查询。另一方面，如果业务实时性要求非常高，并且不能忍受重传，那么首先就是UDP了或者只能用UDP了，例如NTP 协议，重传NTP消息纯属添乱(为什么呢？重传一个过期的时间包过来，还不如发一个新的UDP包同步新的时间过来)。如果NTP协议采用TCP，撇开握手消耗较多数据包交互的问题，由于TCP受Nagel算法等影响，用户数据会在一定情况下会被内核缓存延后发送出去，这样时间同步就会出现比较大的偏差，协议将不可用。

### 2.多点通信

对于一些多点通信的场景，如果采用有连接的TCP，那么就需要和多个通信节点建立其双向连接，然后有时在NAT环境下，两个通信节点建立其直接的TCP连接不是一个容易的事情，在涉及NAT穿越的时候，UDP协议的无连接性使得穿透成功率更高（原因详见：由于UDP的无连接性，那么其完全可以向一个组播地址发送数据或者轮转地向多个目的地持续发送相同的数据，从而更为容易实现多点通信。）  
一个典型的场景是多人实时音视频通信，这种场景下实时性要求比较高，可以容忍一定的丢包率。比如：对于音频，对端连续发送p1、p2、p3三个包，另一端收到了p1和p3，在没收到p2的保持p1的最后一个音（也是为什么有时候网络丢包就会听到嗞嗞嗞嗞嗞嗞…或者卟卟卟卟卟卟卟卟…重音的原因），等到到p3就接着播p3了，不需要也不能补帧，一补就越来越大的延时。对于这样的场景就比较合适用UDP了，如果采用TCP，那么在出现丢包的时候，就可能会出现比较大的延时。

## UDP实现数据必达

### 解决方案1：回复+重发+编号机制

***1）***接收方收到数据后，回复一个确认包：  
如果你不回复，那么发送端是不会知道接收方是否成功收到数据的。比如：A 要发数据 “{data}” 到 B，那 B 收后，可以回复一个特定的确认包 “{OK}”，表示成功收到。  
但是如果只做上面的回复处理，还是有问题：比如 B 收到数据后回复给 A 的数据 "{OK}" 的包，A 没收到，怎么办呢？  
***2）***当 A 没有收到B的 "{OK}" 包后，要做定时重发数据：  
定时重发，直到成功接收到确认包为止，再发下面的数据，当然，重发了一定数量后还是没能收到确认包，可以执行一下 ARP 的流程，防止对方网卡更换或别的原因。  
但是这样的话，B 会收到很多重复的数据，假如每次都是 B 回复确认包 A 收不到的话。  
***3）***发送数据的包中加个标识符 - 编号：  
比如 A 要发送的数据 "标识符data" 到 B，B 收到后，先回复 “{OK}" 确认包，再根据原有的标识符进行比较，如果标识符相同，则数据丢失，如果不相同，则原有的标识符 = 接收标识符，且处理数据。  
当 A 发送数据包后，没有收到确认包，则每隔 x 秒，把数据重发一次，直到收到确认包后，更新一下标识符，再进行后一包的数据发送。  
经过上面*1）、2）、3）*点的做法，则可以保证数据百分百到达对方，当然，标识符用 ID 号来代替更好。

## 一、核心概念

- **定义**：TCP（传输控制协议）是面向连接、可靠、基于字节流的传输层协议；UDP（用户数据报协议）是无连接、不可靠、基于报文的传输层协议。两者是 TCP/IP 协议栈传输层的两大核心协议
- **关键词**：MTU（最大传输单元）、MSS（最大段大小）、IP 分片、粘包/拆包、Nagle 算法、消息边界、三次握手、序列号、校验和
- **适用场景/边界**：TCP → 可靠性优先（HTTP/文件传输/邮件）；UDP → 实时性优先（音视频/DNS/在线游戏）。UDP 可通过应用层实现可靠性（QUIC），TCP 无法去掉可靠性带来的延迟

## 二、详细解析（≥200字）

- **原理拆解（三层递进）**：
  - **第一层——TCP 面向字节流 vs UDP 面向报文**：TCP 没有消息边界，发方 3 次 write 可能被收方 1 次 read 全部读出（粘包）。UDP 有消息保护边界——每个 `sendto` 对应一个完整数据报，接收方 `recvfrom` 一次接收一个完整报文。这是 TCP"流协议"本质决定的：TCP 将数据视为无结构的字节流，由 IP 层分帧，TCP 头中无"包长度"字段
  - **第二层——MTU/MSS/IP分片链路**：链路层 MTU（以太网=1500B）限制帧大小。TCP 通过 MSS（=MTU-IP头-TCP头=1460B）主动分段避免 IP 分片。UDP 不做分段，超过 MTU 的数据报由 IP 层被动分片。IP 分片风险：任一片丢失 → 整个数据报丢弃（UDP 无重传）→ 应用层需重传全部数据
  - **第三层——粘包解决方案**：(1) 固定长度消息；(2) 分隔符边界（HTTP 的 `\r\n`）；(3) 长度前缀（包头含 body 长度，最通用）。UDP 天然无粘包问题，因为 16 位"UDP 长度"字段标记了报文边界
- **关键数据结构/接口**：TCP 头(20B)：序列号+确认号+控制位(SYN/ACK/FIN/RST)+窗口大小+校验和；UDP 头(8B)：源/目的端口+长度+校验和
- **关键公式**：MSS = MTU - 20(IP头) - 20(TCP头) = 1460B(以太网)；安全 UDP 载荷 ≤ 576 - 28 = 548B（互联网最小 MTU）

## 三、动手实践（代码案例）

```c++
#include <iostream>
#include <cstring>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
using namespace std;

// TCP 客户端（演示粘包处理：长度前缀方案）
void tcp_client() {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8080);
    inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr);
    connect(fd, (sockaddr*)&addr, sizeof(addr));
    
    string msg = "Hello TCP";
    uint32_t len = htonl(msg.size());
    send(fd, &len, 4, 0);        // 先发 4 字节长度
    send(fd, msg.data(), msg.size(), 0);  // 再发消息体
    close(fd);
}

// UDP 客户端（天然无粘包）
void udp_client() {
    int fd = socket(AF_INET, SOCK_DGRAM, 0);
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(9090);
    inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr);
    
    string msg = "Hello UDP";
    sendto(fd, msg.data(), msg.size(), 0, (sockaddr*)&addr, sizeof(addr));
    // 每个 sendto 是一个独立数据报，不需处理粘包
    close(fd);
}
```

struct ReliableUDP {

### TCP vs UDP 选择决策树

| 需求 | 推荐 | 原因 |
|------|------|------|
| 文件传输/网页 | TCP | 零容忍丢包 |
| 实时音视频 | UDP | 延迟敏感，可容忍丢帧 |
| DNS 查询 | UDP | 短连接，一个包搞定 |
| 在线游戏 | UDP | 状态实时同步，延迟比可靠性重要 |
| 数据库连接 | TCP | 数据完整性不可妥协 |

**工程经验**：(1) 粘包是 TCP 开发的必修课——无论什么框架，自定义消息边界是必须的；(2) UDP 虽不可靠但效率高，可通过应用层协议（序列号+ACK+重传）实现可靠性；(3) Nagle 算法对延迟敏感应用是反模式，务必设置 TCP_NODELAY；(4) IP 分片是 UDP 的隐形杀手，生产环境 UDP 包最好控制在 548B 以内。

### 5.1 源码解析

#### TCP 确认与重传的核心状态机

```c++
// TCP 发送简化逻辑
void tcp_sendmsg(struct sock *sk, struct msghdr *msg) {
    while (msg->len > 0) {
        int mss = tcp_current_mss(sk);                    // 获取当前 MSS
        int seg_size = min(msg->len, mss) - tcp_header;
        struct sk_buff *skb = alloc_skb(seg_size);        // 分配 skb
        copy_from_user(skb->data, msg->buf, seg_size);
        tcp_send_skb(sk, skb);                            // 发送段
        msg->len -= seg_size;
    }
}
// 重传定时器
void tcp_retransmit_timer(struct sock *sk) {
    struct sk_buff *skb = tcp_send_head(sk);
    if (tcp_packets_in_flight(sk) >= tp->snd_cwnd) return;
    tcp_retransmit_skb(sk, skb);
    tcp_reset_xmit_timer(sk, TCP_TIME_RETRANS, max(tp->rto, TCP_TIMEOUT_MIN));
}
```

### 5.2 实践经验

1. TCP 适用 99% 的常规应用，UDP 仅在实时性压倒可靠性时使用
2. UDP 数据包控制在 548 字节以内避免 IP 分片
3. QUIC（HTTP/3）在 UDP 上层重写了 TCP 的确认重传逻辑
4. TCP Nagle 算法在延迟敏感场景（SSH、游戏）应通过 `TCP_NODELAY` 关闭
5. MTU 和 MSS 关系：`MSS = MTU - IP头(20) - TCP头(20) = 1460`
6. UDP 没有发送缓冲区，`sendto` 直接送到 IP 层——队列满则丢弃

## 六、面试准备

### 6.1 面试高频问答

**Q1：TCP 为什么可靠？**

A：序列号+确认应答、超时重传、滑动窗口流量控制、拥塞控制、校验和。

**Q2：UDP 可靠吗？如何让 UDP 变可靠？**

A：UDP 本身不可靠。应用层通过编号+确认+重传+去重实现可靠传输（如 QUIC、KCP）。

**Q3：TCP 粘包的根本原因？UDP 为何不粘包？**

A：TCP 面向字节流无消息边界。UDP 面向数据报，每个 `sendto` 对应独立数据报有消息边界保护。

**Q4：MTU、MSS 的关系？**

A：MTU 是链路层最大传输单元（以太网 1500）。MSS = MTU - IP头(20) - TCP头(20) = 1460。TCP 自动按 MSS 分段。

**Q5：Nagle 算法的作用和副作用？**

A：合并小包减少网络开销，但增加延迟。交互式应用需关闭（`TCP_NODELAY`）。

**Q6：TCP 三次握手为什么是三次？**

A：防旧连接请求产生错误连接 + 同步双方初始序列号。两次不够（服务端不知客户端是否收到 SYN-ACK），四次冗余。

**Q7：UDP 数据包最大多少？**

A：理论上 65507 字节，但超过 MTU 会分片。实际安全大小约 548 字节。

**Q8：QUIC 相比 TCP 的优势？**

A：基于 UDP 避免 TCP 队头阻塞；0-RTT 握手；连接迁移（切换网络不断连）；每个流独立拥塞控制。

### 6.2 陷阱与反问

**陷阱1**：TCP 无消息边界 → 应用层不处理粘包导致数据错乱
**陷阱2**：UDP 包大于路径 MTU → IP 分片 → 丢一片全丢
**陷阱3**：TCP keep-alive 默认 2 小时探测 → 远高于应用层心跳
**陷阱4**：关闭 Nagle 后连续小包 → tinygram 泛滥
**陷阱5**：UDP connect() 后仍可收到其他来源数据

**反问**：TCP 和 UDP 在什么场景可以混合使用？
*答案：HTTP/3 (QUIC) 底层用 UDP 传输但实现 TCP 可靠性。DNS 通常 UDP，超 512 字节切 TCP。WebRTC UDP 传音视频 + TCP/SCTP 传信令。*

### 6.3 一句话答案

1. **TCP 可靠性**：序列号 + 确认 + 重传 + 流控 + 拥塞控制
2. **UDP 无粘包**：数据报有消息边界，一个 sendto = 一个独立包
3. **MSS = 1460**：MTU(1500) - IP头(20) - TCP头(20)
4. **Nagle**：合并小包减少开销，延迟敏感场景关闭
5. **三次握手**：防旧连接+同步 ISN
6. **UDP 安全大小**：548 字节避免分片
7. **QUIC**：基于 UDP 的下一代传输协议，HTTP/3 传输层
