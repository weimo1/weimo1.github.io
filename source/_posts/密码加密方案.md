# 密码加密方案

> 适用范围：用户密码安全存储、加盐哈希、密钥延申、传输加密、bcrypt/Argon2 选型

## 一、项目/模块概述

- **模块定位**：用户密码安全是 IM 系统的基础安全要求，涵盖存储端加盐哈希和传输端加密。密码一旦泄露会导致用户全网账号风险（用户通常多平台共用密码）。
- **技术栈与依赖**：SHA-256 / bcrypt / Argon2（哈希算法）、HTTPS/TLS（传输层加密）、ECC 椭圆曲线（非对称加密）、CSPRNG（安全随机数）。
- **模块边界**：前端加密 → HTTPS 传输 → 服务端验证 → Token 返回。服务端永不存储密码明文，也永不知道密码原文。

## 二、架构设计

### 完整流程

```
1. 用户输入密码
2. 前端加盐哈希 → 非对称加密 → HTTPS 传输
3. 服务端解密 → 取出存储的 salt + password_hash
4. 用相同算法计算 hash(salt + 传入密码) → 比对
5. 一致则返回 token，不一致则拒绝
```

### 三层安全防护

| 层级 | 技术 | 防护目标 |
|------|------|----------|
| 存储层 | 加盐哈希 + 密钥延申 | 防彩虹表攻击、防暴力破解 |
| 传输层 | HTTPS (TLS 1.3) | 防中间人窃听 |
| 认证层 | Token + 过期机制 + 刷新 | 防重放攻击、限时访问 |

### 为什么不能只存哈希？

```
只用 SHA-256(password) 的问题：
- 彩虹表：预先计算常见密码（123456, password, qwerty...）的 SHA-256 值
- 数据库泄露 → 直接反查彩虹表 → 秒级还原密码
- 相同密码 = 相同哈希 → 攻击者一眼看出哪些用户用了相同密码

加盐后：SHA-256(salt + password)
- 每个用户独立随机 salt（32 bytes CSPRNG）
- 相同密码 → 不同哈希值
- 彩虹表失效（需要为每个 salt 建表，计算量不可行）
```

## 三、核心实现

### 3.1 加盐哈希原理

```
存储端：
  salt = CSPRNG(32)  // 每个用户独立的随机盐
  password_hash = SHA-256(salt + password)  // 或 bcrypt/Argon2

验证端：
  取出该用户的 salt
  计算 hash = SHA-256(salt + 用户输入的密码)
  比较 hash == password_hash
```

### 3.2 密钥延申（Key Derivation）

暴力破解的代价取决于哈希计算速度。SHA-256 设计目标是"快"，反而不利于密码存储。

| 算法 | salt | cost 控制 | 抗 GPU/ASIC | 推荐度 |
|------|------|-----------|-------------|--------|
| SHA-256 | 需手动管理 | 无 | 弱 | ⭐⭐ |
| bcrypt | 内置 | 可调 rounds (2^n) | 中（内存 4KB 固定） | ⭐⭐⭐ |
| Argon2id | 内置 | 内存 + 迭代 + 并行度 | 强（内存可调至 GB） | ⭐⭐⭐⭐⭐ |

### 3.3 ECC 椭圆曲线

相比 RSA 用更短的密钥达到同等安全强度：256 位 ECC ≈ 3072 位 RSA。计算更快、带宽更小，适合移动端。

## 四、工程实践

- **密码哈希算法选择**：优先 bcrypt（成熟稳定）或 Argon2id（抗 GPU/ASIC 最强）。SHA-256 仅适合 HMAC 场景，不应直接用于密码哈希。
- **salt 要求**：每个用户独立、加密安全的随机数生成器（CSPRNG，如 `/dev/urandom`）、至少 16 字节（推荐 32 字节）。
- **cost factor 调优**：bcrypt rounds 设置以"服务端单次验证耗时 200~500ms"为目标，兼顾安全性与用户体验。
- **HTTPS 强制**：所有认证相关接口必须走 HTTPS（TLS 1.2+），防止中间人窃取密码。HSTS 头防止降级攻击。
- **数据库存储**：salt 和 password_hash 分开字段存储，验证时取出 salt 重新计算哈希比对。
- **密码强度策略**：最小长度 8 位、至少包含大小写字母+数字+特殊字符中的 3 类、禁止常见密码（123456 等）。
- **登录限流**：同一 IP/账号连续失败 N 次后加验证码或临时锁定，防止暴力破解。

## 五、源码解析

### 5.1 bcrypt 服务端验证示例

```cpp
#include <bcrypt/BCrypt.hpp>

// 注册时：生成 salt + 哈希
std::string hashPassword(const std::string& password) {
    // bcrypt 自动生成 salt 并嵌入到结果中
    // 格式：$2a$10$<22-char-salt><31-char-hash>
    return BCrypt::generateHash(password, 12); // rounds = 2^12 = 4096
}

// 登录时：验证密码
bool verifyPassword(const std::string& password, const std::string& hash) {
    return BCrypt::validatePassword(password, hash);
}
```

### 5.2 手动 SHA-256 加盐实现（不推荐生产环境用）

```cpp
#include <openssl/sha.h>
#include <openssl/rand.h>

struct PasswordHash {
    std::string salt;   // 32 bytes hex
    std::string hash;   // 64 bytes hex (SHA-256)
};

PasswordHash createHash(const std::string& password) {
    PasswordHash result;

    // 生成 32 字节随机 salt
    unsigned char saltBytes[32];
    RAND_bytes(saltBytes, sizeof(saltBytes));
    result.salt = toHex(saltBytes, sizeof(saltBytes));

    // SHA-256(salt + password)
    std::string combined = result.salt + password;
    unsigned char hashBytes[SHA256_DIGEST_LENGTH];
    SHA256(reinterpret_cast<const unsigned char*>(combined.c_str()),
           combined.size(), hashBytes);
    result.hash = toHex(hashBytes, sizeof(hashBytes));

    return result;
}

bool verifyPassword(const std::string& password,
                    const std::string& salt,
                    const std::string& storedHash) {
    std::string combined = salt + password;
    unsigned char hashBytes[SHA256_DIGEST_LENGTH];
    SHA256(reinterpret_cast<const unsigned char*>(combined.c_str()),
           combined.size(), hashBytes);
    return toHex(hashBytes, SHA256_DIGEST_LENGTH) == storedHash;
}
```

## 六、面试准备

### 6.1 高频问法

**Q1：为什么不能直接存密码明文？**
数据库泄露 = 所有用户密码直接暴露。用户通常多平台共用密码，一处泄露处处危险。且内部人员也可能恶意查看。

**Q2：为什么加盐？不直接哈希？**
防止彩虹表攻击。相同密码不同用户产生不同哈希值，攻击者无法批量反查，必须为每个 salt 单独暴力破解。

**Q3：bcrypt 和 SHA-256 如何选择？**
bcrypt 内置 salt + 可调 cost factor（迭代次数），暴力破解更困难。SHA-256 设计目标是"快"而非"安全存密码"，需自己管理 salt，易出错。

**Q4：Argon2 比 bcrypt 好在哪？**
Argon2 可配置内存消耗（如 64MB），对抗 GPU/ASIC 并行攻击。bcrypt 仅 4KB 固定内存，专用硬件可大量并行。Argon2 是 2015 年密码哈希竞赛冠军。

**Q5：HTTPS 在密码传输中的作用？**
防止中间人窃听。即使前端做了加盐哈希，HTTP 明文传输仍可被截获。TLS 提供端到端加密通道。

**Q6：忘记密码怎么办？能恢复原文吗？**
不能。哈希是单向的，无法从 hash 反推原文。只能通过验证邮箱/手机号 → 重置为新密码。

**Q7：什么是彩虹表攻击？如何防御？**
彩虹表 = 预先计算的 "常见密码 → 哈希值" 映射表。数据库泄露后直接查表还原密码。防御方式：加盐（每个用户独立 salt，彩虹表失效）。

**Q8：salt 应该存在哪里？**
和 password_hash 存在同一张表（不同字段）。salt 不是秘密（不需要保密），它的作用是让相同密码产生不同哈希、让彩虹表失效。

**Q9：bcrypt 的 cost factor 如何选择？**
以服务端单次验证耗时 200~500ms 为目标，测试调整。rounds = 2^cost。太高影响用户体验，太低容易被暴力破解。通常 cost=10~12。

**Q10：如何防止暴力破解？**
(1) 登录限流：同一 IP/账号连续失败 5 次后锁定 15 分钟；(2) 验证码：失败 3 次后需要验证码；(3) bcrypt/Argon2 本身计算慢 → 单次尝试耗时 200ms+ → 大幅降低暴力破解效率。

### 6.2 反问点

- 你们的密码存储用的是 bcrypt 还是 Argon2？cost factor 多少？
- 登录有没有限流/验证码机制？失败几次触发？
- 密码重置的验证渠道（邮箱/短信）是否安全？
- 有没有做过密码强度校验？（如禁止弱密码列表）
- 数据库备份中的密码哈希是否也受到同等保护？

### 6.3 一句话答案

- 加盐哈希 = salt + password → hash，防彩虹表
- bcrypt > SHA-256：内置 salt + 可调 cost，专为密码存储设计
- Argon2 > bcrypt：可配置内存消耗抗 GPU/ASIC 并行
- 服务端不知道密码原文 → 只能重置不能恢复
- HTTPS = 传输层加密，防明文窃听
- 彩虹表 = 预计算的常见密码哈希表，加盐使其失效
- 登录限流 = 连续失败锁定/验证码，防暴力破解
- salt 不是秘密 = 可以明文存储，作用是让相同密码不同哈希
