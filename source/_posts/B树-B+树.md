# B树  B+树

**mysql 中一个页大小时16KB，如果用b树来存储，但是数据很大，所以一个page存储的数据量就大大减小，所以B+访问更稳定**

**再正常的业务中，数据内容一般很大，主键比较小，用B+树可以存下更多的索引，最后导致B+的层数更低**

**叶子存在指针返回数据比较块**

# B树

[B-树](https://zhida.zhihu.com/search?content_id=120633484&content_type=Article&match_order=1&q=B-%E6%A0%91&zhida_source=entity)是一种平衡的多路查找树，注意： **B树就是B-树，"-"是个连字符号，不是减号** 。 在大多数的[平衡查找树](https://zhida.zhihu.com/search?content_id=120633484&content_type=Article&match_order=1&q=%E5%B9%B3%E8%A1%A1%E6%9F%A5%E6%89%BE%E6%A0%91&zhida_source=entity)（Self-balancing search trees)，比如 AVL 树 和[红黑树](https://zhida.zhihu.com/search?content_id=120633484&content_type=Article&match_order=1&q=%E7%BA%A2%E9%BB%91%E6%A0%91&zhida_source=entity)，都假设所有的数据放在主存当中。那为什么要使用 B-树呢（或者说为啥要有 B-树呢）？要解释清楚这一点，我们假设我们的数据量达到了亿级别，主存当中根本存储不下，我们只能以块的形式从磁盘读取数据，与主存的访问时间相比，磁盘的 I/O 操作相当耗时，而提出 B-树的主要目的就是减少磁盘的 I/O 操作。大多数平衡树的操作（查找、插入、删除，最大值、最小值等等）需要 次磁盘访问操作，其中 是树的高度。但是对于 B-树而言，树的高度将不再是 (其中 是树中的结点个数），而是一个我们可控的高度 （通过调整 B-树中结点所包含的键【你也可以叫做数据库中的索引，本质上就是在磁盘上的一个位置信息】的数目，使得 B-树的高度保持一个较小的值）。一般而言，B-树的结点所包含的键的数目和磁盘块大小一样，从数个到数千个不等。由于B-树的高度 h 可控（一般远小于 ），所以与 AVL 树和红黑树相比，B-树的磁盘访问时间将极大地降低。

**B树是对二叉查找树的改进。它的设计思想是，将相关数据尽量集中在一起，以便一次读取多个数据，减少硬盘操作次数。B树为系统最优化大块数据的读和写操作。B树算法减少定位记录时所经历的中间过程，从而加快存取速度。普遍运用在数据库和文件系统。**

* 每个节点最多有m-1个**关键字**（可以存有的键值对）。
* 根节点最少可以只有1个**关键字**。
* 非根节点至少有m/2个**关键字**。
* 每个节点中的关键字都按照从小到大的顺序排列，每个关键字的左子树中的所有关键字都小于它，而右子树中的所有关键字都大于它。
* 所有叶子节点都位于同一层，或者说根节点到每个叶子节点的长度都相同。
* 每个节点都存有索引和数据，也就是对应的key和value。

**B树特点：**

B树相对平衡二叉树在节点空间的利用率上进行改进，B树在每个节点保存更多的数据，减少了树的高度，从而提升了查找的性能，在数据库应用中，B树的每个节点存储的数据量大约为4K, 这是因为考虑到磁盘数据存储是采用块的形式存储的，每个块的大小为4K，每次对磁盘进行IO数据读取时，同一个磁盘块的数据会被一次性读取出来，所以每一次磁盘IO都可以读取到B树中一个节点的全部数据。

# B+树

**不同点**。

* B+树有两种类型的节点：内部结点（也称[索引结点](https://zhida.zhihu.com/search?content_id=117127620&content_type=Article&match_order=1&q=%E7%B4%A2%E5%BC%95%E7%BB%93%E7%82%B9&zhida_source=entity)）和[叶子结点](https://zhida.zhihu.com/search?content_id=117127620&content_type=Article&match_order=1&q=%E5%8F%B6%E5%AD%90%E7%BB%93%E7%82%B9&zhida_source=entity)。内部节点就是非叶子节点，内部节点不存储数据，只存储索引，数据都存储在叶子节点。
* 内部结点中的key都按照从小到大的顺序排列，对于内部结点中的一个key，左树中的所有key都小于它，右子树中的key都大于等于它。叶子结点中的记录也按照key的大小排列。
* 每个叶子结点都存有相邻叶子结点的指针，叶子结点本身依关键字的大小自小而大顺序链接。

区别：

B+**树查询速度更稳定**：B+所有关键字数据地址都存在**叶子**节点上，所以每次查找的次数都相同所以查询速度要比B树更稳定。

2、B+**树天然具备排序功能：**B+树所有的**叶子**节点数据构成了一个有序链表，在**查询大小区间**的数据时候更方便，数据紧密性很高，缓存的命中率也会比B树高。

3、B+**树全节点遍历更快：**B+树遍历整棵树只需要遍历所有的**叶子**节点即可，而不需要像B树一样需要对每一层进行遍历，这有利于数据库做全表扫描。

**B树**相对于**B+树**的优点是，如果经常访问的数据离根节点很近，而**B树**的**非叶子**节点本身存有关键字和数据，所以在查询这种数据检索的时候会要比**B+树**快。

### MySQL为什么选择B+树

在[MySQL](https://cloud.tencent.com/product/cdb?from_column=20065&from=20065)中，索引是用来加速数据查询的，因此索引的设计非常重要。MySQL采用的是B+树作为索引的数据结构，原因如下：

1. B+树的查询性能更好，因为数据都存储在叶子节点中，查询时只需要遍历一次叶子节点即可得到查询结果。
2. B+树的叶子节点之间通过指针连接起来，形成一个有序链表，方便范围查询和排序操作。
3. B+树的非叶子节点中只包含索引，因此占用的空间更小，可以存储更多的索引信息。
4. B+树的阶可以自由调整，可以根据实际情况进行调整，灵活性更高。

### **4.****与B树的区别**

B+树在以下方面区别于B树

* [数据存储](https://cloud.tencent.com/product/cos?from_column=20065&from=20065)**位置**：B树内部节点存数据，B+树仅叶子节点存数据。
* **链表结构**：B+树叶子节点通过链表连接，B树无此设计。
* **查询稳定性**：B+树查询必须到叶子节点，路径固定；B树可能在内部节点提前终止查询。

### **5.****实际应用中的优势**

* **减少磁盘I/O**：更高的节点键值密度降低树高度，减少寻道次数
* **缓存友好**：内部节点可全缓存于内存，仅需访问磁盘读取叶子节点
* **适合大规模数据**：对数级时间复杂度使其在处理海量数据时仍保持高效

#### 为什么索引结构默认使用B+树，而不是B-Tree，Hash哈希，二叉树，红黑树?

简单版回答如下：

* Hash哈希，只适合等值查询，不适合范围查询。
* 一般二叉树，可能会特殊化为一个链表，相当于全表扫描。
* 红黑树，是一种特化的平衡二叉树，[MySQL](https://cloud.tencent.com/product/cdb?from_column=20065&from=20065) 数据量很大的时候，索引的体积也会很大，内存放不下的而从磁盘读取，树的层次太高的话，读取磁盘的次数就多了。
* B-Tree，叶子节点和非叶子节点都保存数据，相同的数据量，B+树更矮壮，也是就说，相同的数据量，B+树数据结构，查询磁盘的次数会更少。

B+树的优势：

1.B+的磁盘读写代价更低

B+的内部结点并没有指向关键字具体信息的指针。因此其内部结点相对B树更小。如果把所有同一内部结点的关键字放在同一盘块中，那么盘块所能容纳的关键字数量也越多。数据存放的更加紧密，具有更好的空间局部性。一次性读入内存中的需要查找的关键字也就越多。因此访问叶子节点上关联的数据也具有更好的缓存命中率。相对来说IO读写次数也就降低了。

2.B+tree的查询效率更加稳定

由于非终结点并不是最终指向文件内容的结点，而只是叶子结点中关键字的索引。所以任何关键字的查找必须走一条从根结点到叶子结点的路。所有关键字查询的路径长度相同，导致每一个数据的查询效率相当。

3.便于区间查找

B+树的叶子结点都是相链的，因此对整棵树的便利只需要一次线性遍历叶子结点即可。而且由于数据顺序排列并且相连，所以便于区间查找和搜索。而B树则需要进行每一层的递归遍历。相邻的元素可能在内存中不相邻，所以缓存命中性没有B+树好。

B+树是[平衡多路查找树](https://zhida.zhihu.com/search?content_id=186320675&content_type=Article&match_order=1&q=%E5%B9%B3%E8%A1%A1%E5%A4%9A%E8%B7%AF%E6%9F%A5%E6%89%BE%E6%A0%91&zhida_source=entity)，主要是通过降低树的高度来存储上亿级别的数据，但是它的应用场景是内存放不下的时候能够用最少的IO访问次数从磁盘获取数据。比如数据库[聚簇索引](https://zhida.zhihu.com/search?content_id=186320675&content_type=Article&match_order=1&q=%E8%81%9A%E7%B0%87%E7%B4%A2%E5%BC%95&zhida_source=entity)，成百上千万的数据内存无法满足查找就需要到内存查找，而因为B+树层高很低，只需要几次磁盘IO就能获取数据到内存，所以在这种磁盘到内存访问上[B+树](https://zhida.zhihu.com/search?content_id=186320675&content_type=Article&match_order=4&q=B%2B%E6%A0%91&zhida_source=entity)更适合。

# 五、源码解析和实践感悟

## 1. B+树节点二分查找——InnoDB Page Directory 查找

InnoDB 每个数据页内部有一个 Page Directory（槽数组），存储指向记录的指针。页内查找 key 时，先在 Page Directory 中二分查找确定目标槽，再在槽对应的记录组中线性查找。

```cpp
// B+树节点内部二分查找定位 key 位置（简化为内存版）
template<typename K, int ORDER>
int BPlusNode<K, ORDER>::binary_search(const K& key) const {
    int low = 0, high = num_keys_ - 1;
    while (low <= high) {
        int mid = (low + high) / 2;
        if (keys_[mid] < key)
            low = mid + 1;
        else if (keys_[mid] > key)
            high = mid - 1;
        else
            return mid;  // 精确命中
    }
    return low;  // 返回应插入/下沉位置
}

// 非叶子节点指针定位：找到第一个 keys_[i] >= key 的分支
int idx = binary_search(key);
// 继续在 children[idx] 子树中递归查找
```

## 2. B+树插入与节点分裂——自底向上传播

B+树插入的核心是分裂传播：叶子节点插入超限后分裂为两个节点，将中间 key 提升到父节点；父节点可能递归分裂直至根节点，导致树高+1。

```cpp
template<typename K, typename V, int ORDER>
void BPlusTree<K, V, ORDER>::insert(const K& key, const V& value) {
    // 1. 找到目标叶子节点
    auto leaf = find_leaf(key);
    
    // 2. 插入到叶子（保持有序）
    int pos = leaf->binary_search(key);
    leaf->insert_at(pos, key, value);
    
    // 3. 叶子节点溢出 → 分裂
    if (leaf->num_keys() >= ORDER) {
        auto new_leaf = leaf->split();  // 后半部分移入新节点
        // new_leaf 的第一个 key 提升到父节点
        auto promote_key = new_leaf->get_key(0);
        insert_in_parent(leaf, promote_key, new_leaf);
    }
}

// 父节点分裂（递归）
void insert_in_parent(Node* old_node, const K& key, Node* new_node) {
    auto parent = old_node->parent();
    if (!parent) {  // 根分裂 → 树高+1（B+树增长的唯一方式）
        root_ = new InternalNode();
        root_->insert_child(0, old_node);
        root_->insert_key(0, key);
        root_->insert_child(1, new_node);
        return;
    }
    // 在父节点插入索引和子节点指针
    int pos = parent->binary_search(key);
    parent->insert_key(pos, key);
    parent->insert_child(pos + 1, new_node);
    if (parent->num_keys() >= ORDER) {
        // 父节点递归分裂
        auto new_parent = parent->split();
        insert_in_parent(parent, new_parent->get_key(0), new_parent);
    }
}
```

## 3. InnoDB 聚簇索引的 Page 遍历与范围扫描

InnoDB 的 B+ 树叶子节点通过双向链表连接，范围扫描（`WHERE id BETWEEN 100 AND 200`）只需要一次 B+ 树定位到起始值，然后沿链表顺序读取。

```cpp
// B+树范围查询：利用叶子节点链表
std::vector<Value> range_query(const Key& start, const Key& end) {
    std::vector<Value> results;
    auto leaf = find_leaf(start);  // 定位到包含 start 的叶子
    int idx = leaf->binary_search(start);
    
    while (leaf) {
        for (int i = idx; i < leaf->num_keys(); ++i) {
            Key k = leaf->get_key(i);
            if (k > end) return results;  // 超出范围，结束
            results.push_back(leaf->get_value(i));
        }
        leaf = leaf->next();  // 走叶子链表，无需回溯父节点！
        idx = 0;              // 新叶子从头遍历
    }
    return results;
}
// 时间复杂度：O(logN + K)，K为范围内记录数
// B树无法做到此优化——需递归遍历内部节点
```

## 实践经验

1. **为什么索引字段要尽量小**：InnoDB 页 16KB，key 越小单页存的 key 越多，树高越低。用 `BIGINT`（8B）比 `VARCHAR(255)` 的索引每个页多存几十倍记录，2000万行数据可能差 1 层高度=差一次随机 IO。
2. **联合索引的"最左前缀"本质是 B+ 树的键比较顺序**：`INDEX(a,b,c)` 的 B+ 树按 `(a,b,c)` 字典序排列。`WHERE b=1` 不满足最左前缀，因为全局来看 a 不同时 b 是无序的，B+ 树无法二分定位。
3. **回表 vs 覆盖索引的性能差异**：二级索引叶子存主键值，若 SELECT 的列不在索引中，需额外一次聚簇索引查找（回表）。`EXPLAIN` 中 `Using index` 表示覆盖索引无需回表，性能可差 10-100 倍。
4. **页分裂是随机 IO 的来源**：插入乱序主键（如 UUID）时，新记录随机落入不同的页，频繁分裂导致页的物理顺序不再连续，范围扫描退化为随机读。自增主键则新数据始终追加在最后。
5. **Buffer Pool 对 B+ 树的实际性能影响巨大**：命中率 99% 的 100GB Buffer Pool 意味着只有 1% 的查询需要物理 IO。这也是为什么云数据库的 `innodb_buffer_pool_size` 通常设为物理内存的 70-80%。
6. **B+ 树的高度估算公式**：h ≤ 1 + ⌈log_⌈M/2⌉((N+1)/2)⌉。实际 MySQL 中 2000 万行表（每行 1KB），树高约 3 层：根常驻内存 → 实际只需 2 次磁盘 IO。

# 六、面试准备

## 面试问答

**Q1: B 树和 B+ 树的区别？**
A: 三点核心区别：(1) 数据存储位置——B 树内部节点存数据，B+ 树仅叶子存数据，内部节点只存索引 key；(2) 叶子结构——B+ 树叶子有双向链表，B 树无；(3) 查询稳定性——B+ 树必须到叶子才拿到数据（路径固定），B 树可能在内部节点提前命中。B+ 树因此更适合数据库索引：更矮（内部节点 key 密度高）、范围查询快（链表遍历）、IO 次数稳定。

**Q2: MySQL 为什么选择 B+ 树而不是跳表？**
A: (1) 磁盘 IO 模型不同。B+ 树每个节点恰好是一个磁盘页（16KB），一次 IO 加载一个完整节点，充分利用磁盘预读。跳表节点分散，磁盘上不连续，随机 IO 多。(2) B+ 树高度更低（分支因子可达数百），层数更少意味着磁盘 IO 次数更少。(3) 跳表的平衡靠概率（随机层高），极端情况下可能退化。B+ 树保证严格平衡。但跳表在内存场景（如 Redis ZSet）非常优秀。

**Q3: 为什么不用 Hash 索引而用 B+ 树？**
A: Hash 索引只支持等值查询（`=`、`IN`），不支持范围查询（`>`、`BETWEEN`）、排序（`ORDER BY`）、模糊前缀匹配（`LIKE 'abc%'`）。而实际业务中范围查询极为常见（分页、时间范围、价格区间）。B+ 树天然有序，支持所有场景。MySQL 中 Memory 引擎可以建 Hash 索引，但 InnoDB 的自适应哈希索引（AHI）是对特定热点页的自动优化。

**Q4: B+ 树的高度如何估算？2000万行数据需要多少层？**
A: 以 InnoDB 为例：页大小 16KB，主键 BIGINT（8B）+ 指针（6B）= 14B，每页约存 16KB/14B ≈ 1170 个索引。叶子节点存整行数据（假设 1KB），每页约 16 行。h=2 时索引量 1170²≈137 万；h=3 时 1170³≈16 亿。所以 2000 万行 h=3（根+2 层内部+叶子），根常驻内存 → 实际只需 2 次磁盘 IO。

**Q5: 聚簇索引和二级索引在 B+ 树中的区别？**
A: 聚簇索引的叶子节点存储整行数据（数据即索引），一张表只有一个聚簇索引（通常是主键）。二级索引的叶子节点存储主键值（而非数据），查到主键后还需要"回表"查聚簇索引拿完整行。这也是为什么建议主键尽量小：二级索引叶子会存主键值，主键大会导致二级索引膨胀。

**Q6: B+ 树页分裂的流程是怎样的？**
A: (1) 叶子插入导致节点满（≥ ORDER）；(2) 分配新页，将原页后半部分记录移到新页；(3) 将新页的最小 key 提升到父节点作为分界索引；(4) 若父节点也满，递归分裂直至根；(5) 若根分裂，创建新根，树高+1。分裂以 key 中点为界，保证分裂后两页各占约一半空间，避免连续分裂。

**Q7: 什么是覆盖索引？为什么它能提高性能？**
A: 覆盖索引指查询的所有列都在索引中，无需回表。例如 `INDEX(name, age)` + `SELECT name, age FROM t WHERE name='x'`，B+ 树叶子直接返回结果，不查聚簇索引。`EXPLAIN` 中 `Extra: Using index` 即为覆盖索引。减少一次随机 IO，对高并发场景极为重要。

**Q8: 自增主键 vs UUID 主键对 B+ 树的影响？**
A: 自增主键：新数据始终追加在 B+ 树最右侧叶子节点，页分裂只在最后一个页发生，填充率高（~15/16），磁盘上页物理连续，范围扫描效率高。UUID：随机插入导致所有页都可能分裂，叶子页填充率低（~65%），页物理分散，范围扫描退化为随机读。自增主键写入性能通常比 UUID 高 30-50%。

## 陷阱与反问

| 陷阱 | 错误认知 | 正确理解 |
|------|---------|---------|
| B+ 树一定比 B 树好 | 场景决定——若热点数据在根附近，B 树提前命中更快 | B+ 树是为磁盘 IO 优化设计的，内存场景 B 树也有优势 |
| 索引越多越好 | 每个索引都是一棵 B+ 树，写入时要维护所有索引 | 索引数=写入时需更新的 B+ 树数量，写多读少场景尽量少建索引 |
| 联合索引 `INDEX(a,b)` 与 `INDEX(a), INDEX(b)` 等效 | `WHERE b=1` 在联合索引中不走索引，在两个单列索引中可能用 index_merge | 联合索引有最左前缀原则，设计时要考虑查询模式 |
| `ORDER BY` 一定用索引 | 仅当排序列与索引前缀匹配且 ASC/DESC 一致时才用 | `ORDER BY a DESC, b ASC` 在联合索引 (a,b) 上可能无法使用索引排序 |
| InnoDB 表一定要有主键 | 可以不显式指定，InnoDB 会自动选唯一非空索引或创建隐藏 ROW_ID | 但推荐显式指定自增主键，避免隐藏 ROW_ID 的 6 字节开销和无法复制的限制 |

## 一句话答案速记表

| 关键词 | 一句话 |
|--------|--------|
| B树 vs B+树 | B 树节点存数据（任何层可能命中），B+ 树仅叶子存数据+叶子有链表 |
| 为什么 B+ 树 | 矮（键密度高）+ 范围快（链表）+ 稳定（每次到叶子） |
| 聚簇索引 | 叶子=数据行，一张表一个，通常主键 |
| 回表 | 二级索引查主键 → 聚簇索引查数据，两次 B+ 树查找 |
| 覆盖索引 | 查询列全在索引中，不回表，EXPLAIN 显示 Using index |
| 页分裂 | 节点满 → 分裂 → 中值提升父 → 递归 → 可能增高 |
| 树高估算 | 2000万行 ~3层，根常驻内存 → 2次IO |
| 最左前缀 | 联合索引按 (a,b,c) 字典序，跳过前导列无法用二分
