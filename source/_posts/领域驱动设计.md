# 领域驱动设计

> 适用范围：领域驱动设计（Domain-Driven Design, DDD）核心方法论，涵盖战略设计（限界上下文、子域划分）、战术设计（实体、值对象、聚合根、仓储、领域服务）和分层架构。

## 一、核心概念

- **定义**：领域驱动设计（DDD）是一种以业务领域为核心的软件设计方法论，通过建立"领域模型"来捕捉业务知识，使用统一语言（Ubiquitous Language）消除业务方与技术方的沟通鸿沟，将复杂业务系统按业务边界拆分为可独立演进的限界上下文。
- **关键词**：领域模型、统一语言、限界上下文、实体、值对象、聚合根、仓储、领域服务、领域事件、战略设计、战术设计
- **适用场景/边界**：
  - 适用于业务逻辑复杂的系统（如 IM、电商、金融、ERP），不适合纯 CRUD 或技术密集型系统
  - 边界：DDD 是方法论而非框架，关注业务建模，不限制具体技术实现

## 二、详细解析（≥200字）

### 原理拆解（三层递进）

**第一层：DDD 的核心思想**

DDD 的核心思想可以概括为：**用业务语言建立模型，让代码直接表达业务**。传统开发中，需求文档用业务语言，代码用技术语言，中间的翻译过程导致信息失真。DDD 通过"统一语言"消除翻译损耗——产品、开发、测试使用同一套术语沟通，术语直接映射为代码中的类名和方法名。

DDD 分为两大阶段：
- **战略设计**：从宏观角度规划系统，划分领域、子域和限界上下文。回答"系统如何拆分、边界在哪"
- **战术设计**：在单个限界上下文内，使用实体、值对象、聚合、仓储等模式进行细节建模。回答"代码如何组织、模型如何构建"

**第二层：关键概念详解**

**战略设计核心概念**：

| 概念 | 定义 | IM 系统示例 |
|------|------|-----------|
| 领域（Domain） | 业务的范围和边界 | IM 即时通讯 |
| 子域（Subdomain） | 领域的进一步拆分：核心域、支撑域、通用域 | 消息域（核心）、用户域（核心）、认证域（通用） |
| 限界上下文（Bounded Context） | 一个明确边界的业务范围，内部有独立的统一语言和模型 | 消息上下文、用户上下文、群组上下文 |
| 上下文映射（Context Map） | 描述不同限界上下文之间的关系 | 消息上下文通过 UserID 引用用户上下文（共享内核关系） |

**战术设计核心概念**：

| 概念 | 定义 | 特征 |
|------|------|------|
| 实体（Entity） | 具有唯一标识、有生命周期的业务对象 | 通过 ID 判断相等，状态可变 |
| 值对象（Value Object） | 没有唯一标识、通过属性值判断相等的对象 | 不可变、可替换、无副作用 |
| 聚合（Aggregate） | 一组相关对象的集合，对外提供一致性边界 | 聚合根是唯一入口 |
| 仓储（Repository） | 提供聚合的持久化和查询能力 | 屏蔽存储细节，接口在领域层、实现在基础设施层 |
| 领域服务（Domain Service） | 不属于任何单一实体的业务逻辑 | 无状态的操作，协调多个聚合 |
| 领域事件（Domain Event） | 领域中发生的有业务含义的事件 | 用于解耦限界上下文，实现最终一致性 |

**第三层：底层机制**

- **聚合的一致性边界**：聚合通过"聚合根"控制对内部对象的访问，保证业务不变量（Invariant）永远成立。外部不能直接修改聚合内部对象。
- **领域事件的事件驱动架构**：一个限界上下文发生事件后发布到事件总线，其他上下文订阅处理。事件本身是不可变的（已发生的事实），携带时间戳和必要数据。

### 关键数据结构/接口

```go
// 实体：有唯一标识
type Message struct {
    MsgID   string    // 唯一标识
    Content string
    Status  MsgStatus
    // 实体的相等性仅由 MsgID 决定
}

// 值对象：无唯一标识，不可变
type UserProfile struct {
    Nickname string
    Avatar   string
    // 值对象的相等性由所有属性决定
}

// 聚合根：外部只能通过聚合根访问内部对象
type User struct {
    UserID  int64
    Profile UserProfile     // 值对象
    friends []Friendship    // 实体集合
}

func (u *User) AddFriend(target *User) error {
    if u.IsBlocked(target.UserID) {
        return errors.New("cannot add blocked user")
    }
    u.friends = append(u.friends, Friendship{...})
    return nil
}

// 仓储接口（领域层定义）
type MessageRepository interface {
    Save(ctx context.Context, msg *Message) error
    FindByMsgID(ctx context.Context, msgID string) (*Message, error)
}
```

### 关键公式/复杂度

- 限界上下文数量经验公式：核心子域 2-3 个 + 支撑子域 3-5 个 + 通用子域 1-2 个 = 6-10 个上下文（中等复杂度系统）
- 聚合大小原则：一个聚合尽量在 3-5 个实体以内

## 三、动手实践（代码案例）

```go
// DDD 四层架构在 IM 消息模块中的落地

// ===== 1. 接口层（Interface Layer）=====
type MessageController struct {
    appService *MessageApplicationService
}

func (c *MessageController) SendMessage(ctx context.Context, req *pb.SendMessageReq) (*pb.SendMessageRsp, error) {
    cmd := &SendMessageCmd{
        SenderID: req.SenderId,
        TargetID: req.TargetId,
        Content:  req.Content,
    }
    msgID, err := c.appService.SendMessage(ctx, cmd)
    return &pb.SendMessageRsp{MsgId: msgID}, err
}

// ===== 2. 应用层（Application Layer）=====
type MessageApplicationService struct {
    msgDomainService *MessageDomainService
    eventBus         EventBus
}

func (s *MessageApplicationService) SendMessage(ctx context.Context, cmd *SendMessageCmd) (string, error) {
    // 事务边界：整个发送操作在一个事务内
    msgID, err := s.msgDomainService.Send(ctx, cmd)
    if err != nil {
        return "", err
    }
    // 发布领域事件（事务提交后异步发送）
    s.eventBus.Publish(ctx, &MessageSentEvent{MsgID: msgID})
    return msgID, nil
}

// ===== 3. 领域层（Domain Layer）=====
type MessageDomainService struct {
    msgRepo MessageRepository  // 接口，非实现
}

func (s *MessageDomainService) Send(ctx context.Context, cmd *SendMessageCmd) (string, error) {
    msg := &Message{
        MsgID:   generateMsgID(),
        Content: cmd.Content,
        Status:  MsgStatusSending,
    }
    if err := msg.Validate(); err != nil {
        return "", err
    }
    if err := s.msgRepo.Save(ctx, msg); err != nil {
        return "", err
    }
    msg.MarkAsSent()
    return msg.MsgID, nil
}

// ===== 4. 基础设施层（Infrastructure Layer）=====
type MessageRepoImpl struct {
    db    *sql.DB
    cache *redis.Client
}

func (r *MessageRepoImpl) Save(ctx context.Context, msg *Message) error {
    _, err := r.db.ExecContext(ctx,
        "INSERT INTO message (msg_id, content, status) VALUES (?, ?, ?)",
        msg.MsgID, msg.Content, msg.Status)
    return err
}
```

## 四、进阶应用（≥500字）

### 与其他主题的关联

- **消息协议设计**：DDD 的消息实体最终通过 Protobuf 协议序列化传输
- **微服务拆分**：DDD 的限界上下文天然是微服务拆分的依据，一个上下文对应一个微服务
- **数据库设计**：仓储模式将领域模型与数据库 Schema 解耦

### 工程中的真实用法

**IM 系统 DDD 落地的三个阶段**：

**阶段一：事件风暴（Event Storming）**

事件风暴是 DDD 的核心建模工作坊，所有相关人员（产品、开发、领域专家）参与：
1. 识别领域事件：贴上橙色便签，写出所有会发生的事情（"消息已发送""好友请求已接受""用户已上线"）
2. 识别命令：触发事件的用户操作（"发送消息""添加好友""登录"）
3. 识别聚合：将相关事件和命令归类，找出核心的"事物"及其职责

**阶段二：限界上下文划分**

```
┌─────────────────────────────────────────────┐
│  IM 系统                                    │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐ │
│  │ 消息上下文 │ │ 用户上下文 │ │ 群组上下文 │ │
│  │ Message   │ │ User      │ │ Group     │ │
│  │ Session   │ │ Friendship│ │ Member    │ │
│  └───────────┘ └───────────┘ └───────────┘ │
│  ┌───────────┐ ┌───────────┐               │
│  │ 认证上下文 │ │ 文件上下文 │               │
│  │ AuthToken │ │ FileInfo  │               │
│  └───────────┘ └───────────┘               │
└─────────────────────────────────────────────┘
```

**阶段三：战术设计落地**

每个上下文内部采用四层架构：
- **接口层**：gRPC/HTTP 端点，参数校验和转换
- **应用层**：事务管理、权限校验、编排领域服务
- **领域层**：实体、值对象、聚合、领域服务（纯业务，无外部依赖）
- **基础设施层**：MySQL、Redis、Kafka 的具体实现

### 常见优化策略

- **聚合设计原则**：一个聚合只修改自己的数据。跨聚合的一致性通过领域事件实现最终一致性
- **CQRS 读写分离**：命令侧走领域模型（强一致），查询侧走专门读模型（可冗余、可缓存）
- **事件的幂等消费**：领域事件消费者必须做幂等处理（通过 eventID 去重）

## 五、源码解析和实践感悟（≥1000字）

### 关键实现路径

**领域事件总线实现**：

```go
type DomainEvent interface {
    EventID() string
    OccurredAt() time.Time
    EventName() string
}

type EventHandler interface {
    Handle(ctx context.Context, event DomainEvent) error
    SubscribedEvents() []string
}

type EventBus struct {
    handlers map[string][]EventHandler
    mu       sync.RWMutex
}

func (bus *EventBus) Register(handler EventHandler) {
    bus.mu.Lock()
    defer bus.mu.Unlock()
    for _, eventName := range handler.SubscribedEvents() {
        bus.handlers[eventName] = append(bus.handlers[eventName], handler)
    }
}

func (bus *EventBus) Publish(ctx context.Context, event DomainEvent) {
    bus.mu.RLock()
    handlers := bus.handlers[event.EventName()]
    bus.mu.RUnlock()
    for _, handler := range handlers {
        go func(h EventHandler) {
            if err := h.Handle(ctx, event); err != nil {
                log.Errorf("handle event %s: %v", event.EventName(), err)
            }
        }(handler)
    }
}

// 消息发送事件处理器
type MessageSentHandler struct {
    pushService PushService
    counterRepo CounterRepository
}

func (h *MessageSentHandler) SubscribedEvents() []string {
    return []string{"MessageSent"}
}

func (h *MessageSentHandler) Handle(ctx context.Context, event DomainEvent) error {
    e := event.(*MessageSentEvent)
    h.pushService.Push(ctx, e.TargetID, e.MsgID)
    h.counterRepo.IncrUnread(ctx, e.TargetID)
    return nil
}
```

**仓储模式中聚合的完整加载与保存**：

```go
func (r *userRepoImpl) FindByID(ctx context.Context, userID int64) (*User, error) {
    row := r.db.QueryRowContext(ctx,
        "SELECT user_id, nickname, avatar, status FROM users WHERE user_id = ?", userID)
    user := &User{}
    var status int
    err := row.Scan(&user.UserID, &user.Profile.Nickname, &user.Profile.Avatar, &status)
    if err != nil {
        return nil, err
    }
    user.Status = UserStatus(status)
    
    // 加载聚合内部对象（好友列表）
    rows, err := r.db.QueryContext(ctx,
        "SELECT user_id_b, relation_type FROM friendships WHERE user_id_a = ?", userID)
    if err != nil {
        return nil, err
    }
    defer rows.Close()
    for rows.Next() {
        var f Friendship
        rows.Scan(&f.UserID_B, &f.RelationType)
        user.friends = append(user.friends, f)
    }
    return user, nil
}

func (r *userRepoImpl) Save(ctx context.Context, user *User) error {
    tx, _ := r.db.BeginTx(ctx, nil)
    defer tx.Rollback()
    
    tx.ExecContext(ctx,
        `UPDATE users SET nickname=?, avatar=?, status=? WHERE user_id=?`,
        user.Profile.Nickname, user.Profile.Avatar, user.Status, user.UserID)
    
    tx.ExecContext(ctx, "DELETE FROM friendships WHERE user_id_a = ?", user.UserID)
    for _, f := range user.friends {
        tx.ExecContext(ctx,
            "INSERT INTO friendships (user_id_a, user_id_b, relation_type) VALUES (?, ?, ?)",
            user.UserID, f.UserID_B, f.RelationType)
    }
    return tx.Commit()
}
```

### 难点与易错点

**陷阱1：聚合设计过大**

错误做法：把所有相关东西塞进一个聚合。IM 中把 User、UserProfile、Friendship、UserSettings、UserDevices 全放进 User 聚合→每次修改任何小属性都锁住整个聚合，并发差，仓储加载内存开销大。

正确做法：控制聚合大小 3-5 个实体，UserSettings 和 UserDevices 可拆为独立聚合，通过 UserID 关联。

**陷阱2：跨聚合的直接引用**

```go
// 错误：跨聚合直接引用对象
type Message struct {
    Sender *User    // 不应直接引用其他聚合根
}

// 正确：通过 ID 引用
type Message struct {
    SenderID int64  // 仅持有 ID，需要时通过仓储查询
}
```

**陷阱3：仓储返回 DTO 而非领域对象**

错误做法：仓储直接返回 ORM 对象，调用方手动转换为领域对象。正确做法：仓储负责完整数据映射，组装领域对象（含聚合内部所有子对象），调用方拿到即可用的聚合。

### 经验总结

1. **DDD 不是银弹**：适合业务复杂系统。判断标准：当 Service 层代码超过 500 行且难以维护时引入 DDD；简单 CRUD 用 MVC 就够了。
2. **战略设计比战术设计更重要**：限界上下文边界决定可维护性。边界划错，后续战术设计再精妙也难以补救。黄金标准：一个上下文内的概念含义一致。
3. **领域事件是上下文解耦的关键**：不要用 RPC 代替领域事件。消息上下文不需要知道推送上下文存在，它只发布"消息已发送"事件。
4. **统一语言是 DDD 落地的第一步**：产品和开发用不同术语描述同一概念，后续实践都会绕路。先对齐术语，代码类名直接用术语表词汇。

## 六、面试准备

### 6.1 高频问法（≥10个）

**基础理解：**

Q1：什么是领域驱动设计（DDD）？它解决什么问题？

A：DDD 是以业务领域为核心的软件设计方法论，核心是建立"领域模型"捕捉业务知识。解决问题：1）需求与代码脱节（统一语言消除翻译损耗）；2）系统难以按业务拆分（限界上下文提供依据）；3）业务逻辑散落 Service 层（战术设计将业务逻辑内聚到领域对象）。

Q2：DDD 分为哪两大阶段？各阶段的核心产出是什么？

A：战略设计和战术设计。战略设计：宏观视角规划系统，产出限界上下文图和上下文映射图。战术设计：单个上下文内建模，产出聚合设计、实体/值对象定义、仓储接口和领域服务。

Q3：实体（Entity）和值对象（Value Object）的核心区别是什么？

A：1）实体有唯一标识（ID），通过 ID 判断相等；值对象无 ID，通过属性值判等。2）实体状态可变，有生命周期；值对象不可变。3）实体有行为方法；值对象通常只有属性和自校验。例：User 是实体（UserID 决定是谁），Address 是值对象（街道+城市决定是否是同一地址）。

**原理深入：**

Q4：聚合（Aggregate）的设计原则是什么？

A：1）聚合根是外部唯一入口；2）一个事务只修改一个聚合；3）聚合 3-5 个实体以内，通过 ID 引用其他聚合；4）聚合内部保证业务不变量（如"订单总价=Σ订单项价格"）。

Q5：限界上下文和子域有什么区别？

A：子域是业务概念（问题空间），限界上下文是技术概念（解决方案空间）。一个子域可对应多个限界上下文。核心子域需自研，通用子域可采购开源方案。

Q6：仓储（Repository）在 DDD 中的作用？为什么接口定义在领域层？

A：仓储封装聚合持久化操作，领域层只依赖接口。好处：1）领域层不依赖外部框架；2）方便 Mock 测试；3）换存储不影响领域层。

**实践应用：**

Q7：如何用 DDD 方法论拆分微服务？

A：1）事件风暴梳理业务事件和命令；2）按业务内聚性划限界上下文；3）每个上下文对应一个微服务；4）上下文间通过 API（同步）或领域事件（异步）通信；5）跨上下文一致性通过最终一致性和补偿机制。

Q8：领域事件和普通消息队列消息有什么区别？

A：领域事件是业务语义层概念（如"订单已支付"），命名用业务语言，携带业务数据。普通消息是技术层面的通信载体。领域事件是"已发生的事实"（不可变），消费者自行决定如何处理。区别在于建模层次和语义清晰度。

Q9：IM 系统中，DDD 如何指导消息相关的代码组织？

A：1）消息上下文负责消息 CRUD 和状态管理；2）Message 是聚合根，MessageStatus 是值对象；3）MessageRepository 定义存储接口；4）消息发送后发布 MessageSentEvent；5）推送上下文订阅该事件负责推送；6）未读计数上下文订阅该事件更新计数器。各上下文独立部署、独立演进。

Q10：什么时候不该用 DDD？

A：1）纯 CRUD 系统（数据录入+展示，无复杂业务规则）；2）团队对 DDD 不熟悉，没有领域专家参与；3）项目周期极短（DDD 前期建模投入大）；4）技术密集型系统（如音视频编解码引擎），业务规则少。

### 6.2 反问点/陷阱点（≥5个）

**针对面试官的深度问题：**

贵公司是在什么阶段引入 DDD 的？是项目一开始就采用还是重构阶段引入？遇到过哪些阻力？

在微服务拆分时，贵团队的限界上下文粒度是如何把握的？一个上下文对应几个微服务？

对于跨限界上下文的查询场景（如消息列表需展示用户头像和群名称），团队是用 API 组合还是 CQRS 读模型？

**常见的陷阱问题：**

陷阱问题1：领域服务和普通 Service 的区别是什么？答案：领域服务是"不属于任何实体/值对象的业务逻辑"，它在领域层而非应用层，必须有明确的业务含义。普通 Service 可能只是协调调用，不包含领域知识。

陷阱问题2：聚合根在数据库中外键如何关联？答案：聚合之间通过 ID 引用，不在数据库层面设外键。跨聚合的数据一致性通过领域事件保证最终一致，而非数据库约束。

陷阱问题3：一个 HTTP 请求涉及修改 3 个聚合，DDD 怎么处理？答案：一个事务只修改一个聚合。要么拆分为 3 个独立操作（通过领域事件协调，最终一致），要么重新审查聚合边界（可能是聚合设计不当需要合并）。

### 6.3 一句话答案（≥5个）

DDD 的核心是：用统一语言建立领域模型，通过战略设计划分限界上下文，通过战术设计内聚业务逻辑。

实体 vs 值对象：实体有 ID 可变（用户），值对象无 ID 不可变（地址）。

聚合的设计要点：小（3-5 实体）、ID 引用、一个事务只改一个聚合、聚合根是唯一入口。

限界上下文的划分原则：一个上下文内的概念含义一致，上下文之间通过 ID 引用或领域事件协作。

当被问到"为什么用 DDD"时，回答："DDD 让代码直接表达业务，通过限界上下文实现业务内聚，通过领域事件实现上下文解耦，让复杂系统可维护、可扩展。"

当被问到"DDD 如何落地"时，回答："事件风暴建模 → 划限界上下文 → 每个上下文内四层架构（接口/应用/领域/基础设施），聚合根保证一致性，领域事件解耦上下文。"
