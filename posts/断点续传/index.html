断点续传

断点续传是文件传输中的关键功能，允许在网络中断后从已完成的部分继续传输，而不必从头开始。在 IM 系统中用于图片、视频、文件等多媒体消息的上传和下载。

参考：腾讯云断点续传实现

一、核心概念

  • 定义：断点续传指在下载或上传时，如果碰到网络故障，可以从已上传/下载的部分继续传输，无需重头开始。适用于大文件在网络不稳定环境下的传输。
  • 关键词：文件分块、断点记录、Range 请求、分片上传、续传日志、进度恢复
  • 适用场景/边界：
    • IM 中的大文件（图片/视频/文件）上传
    • 弱网环境下的可靠文件传输
    • 适合 >1MB 的文件；小文件断点续传收益不大

二、详细解析（≥200字）

原理拆解（三层递进）

第一层：基本实现思路

将大文件均分成几块后，每个线程/协程分别处理一块数据的读取和写入。每次写入都要更新记录的日志文件，断网或暂停后重新开始时，根据日志文件继续传输。

第二层：关键步骤

  1. 文件分块：将文件分成多个固定大小的数据块（如 1MB）
  2. 发送文件信息：发送文件名、文件大小、文件块数、文件 hash（用于完整性校验）
  3. 发送文件块：按顺序发送每个数据块，记录已发送的块数
  4. 接收文件信息：接收基本信息，根据信息创建文件和日志
  5. 接收文件块：按顺序接收并写入文件
  6. 断点续传：出错或中断时记录已传输块数，下次续传

第三层：HTTP Range 请求

HTTP 协议原生支持断点续传——通过 Range 请求头和 206 Partial Content 响应：

关键公式/复杂度

分块数 = 文件大小 / 块大小
传输进度 = 已完成块数 / 总分块数
续传后总耗时 = (总块数 - 已完成块数) × 单块耗时

四、进阶应用（≥500字）

与其他主题的关联

  • HTTP Range：HTTP 协议原生断点续传支持
  • 局部敏感哈希：文件去重——相同文件不重复上传
  • 分片上传 + 合并：对象存储（MinIO/S3）的 multipart upload
  • 校验和：MD5/SHA256 校验文件完整性

工程中的真实用法

  • 腾讯云 COS：分片上传 API，每片独立上传，支持并发分片
  • MinIO/S3：Multipart Upload 支持断点续传
  • 微信文件传输：大文件分片传输 + 断点续传

常见优化策略

  • 并发分片：多线程同时上传不同分片，提升速度
  • 增量 hash 校验：对整个文件和每个分片计算 hash，确保完整性
  • 去重：局部敏感哈希识别重复文件，避免重传

五、源码解析和实践感悟（≥1000字）

断点续传的边界条件

  1. 文件被修改：上传中断期间文件内容变化 → 通过文件 hash 校验检测，提示用户重新上传
  2. 服务端分片过期：服务端临时存储的分片有过期时间（如 24 小时），过期后需重新上传
  3. 并发续传：慎防多个续传请求互相覆盖断点日志

断点记录的存储位置

  • 本地日志：简单但切换设备无法续传
  • 服务端记录：切换设备可续传，但增加服务端状态
  • Redis 记录：临时存储分片进度，TTL 自动过期

经验总结

  1. 断点续传的核心不是”快”，而是”可靠”——在不可靠网络下保证文件最终完整性
  2. 小文件（<1MB）不需要断点续传——断点记录开销可能大于重传开销
  3. 分片大小需要权衡：太小→HTTP 请求开销大，太大→重传浪费多。1-5MB 是常用值
  4. 文件去重比断点续传更常用——相同文件直接秒传，避免任何传输

六、面试准备（高频问法≥10个，反问点/一句话答案≥5个，均带回答）

6.1 高频问法（≥10个）

Q1：什么是断点续传？

A：文件传输过程中断网后，可以从已完成的部分继续传输，而非从头开始。通过文件分块 + 断点日志记录实现。

Q2：断点续传的实现思路是什么？

A：1) 文件分块 2) 逐块传输 3) 每完成一块记录断点到日志 4) 中断后从日志恢复，继续剩余块。

Q3：HTTP 协议如何支持断点续传？

A：通过 Range 请求头指定字节范围，服务端返回 206 Partial Content。常用于下载场景。

Q4：对象存储的分片上传原理是什么？

A：Initiate → Upload Part（每片独立上传，可并发）→ Complete（合并）。每片上传时可以重试，分片间独立。

Q5：断点日志应该存在哪里？

A：本地文件（简单但不跨设备）、Redis（临时，TTL 自动过期）、服务端数据库（持久但增加服务端状态）。根据场景选择。

Q6：文件上传过程中文件被修改了怎么办？

A：开始上传时计算文件 hash，上传完成时校验文件 hash。不一致则提示用户文件已变更，需重新上传。

Q7：并发分片上传如何保证顺序？

A：每片有编号（PartNumber），所有片上传完成后按编号顺序合并。分片间无顺序依赖。

Q8：如何实现秒传（相同文件跳过上传）？

A：上传前计算文件 MD5/SHA256 hash，查询服务端是否已存在相同 hash 的文件。存在则直接引用，无需上传。

Q9：分片大小如何选择？

A：太小→HTTP 请求开销大（大量小请求），太大→重传浪费多。1-5MB 是常用折中值。网络好的环境下可加大。

Q10：分片上传时部分分片失败怎么办？

A：只重传失败的分片。已完成的分片服务端保留（有过期时间）。通过 ListParts 接口查询已完成分片。

6.2 反问点/陷阱点（≥5个）

  • 贵公司的文件上传使用的是哪种断点续传方案？有没有遇到过并发续传的冲突问题？

  • 大文件传输在弱网环境下的成功率如何？做了哪些特殊优化？

  • 陷阱 1：”断点续传就是 HTTP Range？” — Range 主要用于下载的断点续传。上传的断点续传通常通过分片上传（Multipart Upload）实现。

  • 陷阱 2：”所有文件都需要断点续传？” — 不需要。小于 1MB 的文件重传开销小，断点续传的日志维护成本可能大于收益。

  • 陷阱 3：”分片越多上传越快？” — 不一定。分片过多导致 HTTP 请求次数暴增，连接建立和头部开销增加。且服务端并发处理分片有上限。

6.3 一句话答案（≥5个）

  • 断点续传的核心是：文件分块 + 逐块传输 + 断点日志 + 中断恢复。
  • 分片上传的优势是：并发分片加速 + 失败只重试失败分片 + 支持断点续传。
  • 秒传的实现原理是：上传前计算文件 hash → 查询服务端是否已存在 → 存在则跳过上传。
  • 分片大小的选择是：1-5MB 折中——避免过多 HTTP 请求，又不会因为单片失败浪费太多。
  • 当被问到”如何实现断点续传”时回答：”文件分块、逐块上传、每完成一块记录进度。中断后从上次完成的块续传。服务端分片上传 API 原生支持。”
