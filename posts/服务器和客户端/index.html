客户端和服务器

网络编程基本流程

网络编程的基本流程对于服务端是这样的
服务端
1）socket—-创建socket对象。

2）bind—-绑定本机ip+port。

3）listen—-监听来电，若在监听到来电，则建立起连接。

4）accept—-再创建一个socket对象给其收发消息。原因是现实中服务端都是面对多个客户端，那么为了区分各个客户端，则每个客户端都需再分配一个socket对象进行收发消息。

5）read、write—-就是收发消息了。

对于客户端是这样的
客户端
1）socket—-创建socket对象。

2）connect—-根据服务端ip+port，发起连接请求。

3）write、read—-建立连接后，就可发收消息了。

shared_from_this()函数并不是session的成员函数，要使用这个函数需要继承std::enable_shared_from_this

shared_ptr(this)生成的新智能指针和this之前绑定的智能指针new_session并不共享引用计数，所以要通过shared_from_this()函数返回智能指针，该智能指针和其他管理这块内存的智能指针共享引用计数。

一、核心概念

  • 定义：基于 Boost.Asio 的网络编程。服务器端基本流程为 socket → bind → listen → accept → read/write；客户端为 socket → connect → write/read。Asio 支持同步和异步两种模式
  • 关键词：tcp::socket、tcp::acceptor、tcp::endpoint、async_accept/async_read/async_write、同步读写、异步回调、io_context
  • 适用场景/边界：同步模式适合简单原型和低并发场景（每连接一线程）；异步模式适合高并发服务器（单线程处理数千连接）

二、详细解析

  • 原理拆解（三层递进）：
    • 第一层——同步读写模型：客户端 connect() 阻塞直到三次握手完成，write() 阻塞直到数据发送到内核缓冲区，read() 阻塞直到接收完整数据。服务端 acceptor.accept() 阻塞等待新连接，每个连接创建一个线程调用同步 read()/write()。实现简单但 N 连接 = N 线程，C10K 问题无法解决
    • 第二层——异步读写模型：async_accept(acceptor, handler) 注册接受回调后立即返回，io_context 事件循环在有新连接时回调 handler。async_read(socket, buffer, handler) 同样异步——内核数据就绪后回调。单线程即可管理数千连接，线程开销仅在于业务处理
    • 第三层——Asio 封装下的 endpoint 与 socket 生命周期：tcp::endpoint(address::from_string("127.0.0.1"), 10086) 封装 IP+端口。服务端 acceptor 绑定 endpoint 后监听，每个新连接通过 acceptor.async_accept() 获取新 socket 对象（用 shared_ptr 管理以保证回调时对象存活）
  • 关键数据结构/接口：tcp::socket(io_context) 绑定 io_context 后可异步；tcp::acceptor 监听 + 接受连接；boost::asio::buffer(data, len) 包装数据缓冲区；错误码 boost::system::error_code 判断操作成败
  • 关键公式：同步模型线程数 = 连接数（不可扩展）；异步模型线程数 = CPU 核数 × N（N 由业务决定）；async_accept 必须链式调用——回调中再次 async_accept 保持监听不中断

工程经验：(1) bind 必须在新 socket 创建前完成，accept 后才真正建立连接；(2) 异步回调中检查 error_code——连接断开、超时都通过 ec 通知；(3) 同步服务器适合学习网络编程流程，生产环境异步是主流。

五、源码解析和实践感悟

5.1 源码解析

async_read_some 与 async_write 的差异

async_read_some 是”尽力读”——底层 recv 一次返回多少就回调多少，适合流式数据（如 HTTP 请求行不固定长度）。async_write 是”保证写”——内部循环调用 send 直到所有数据发送完毕，适合已知长度的响应。

shared_from_this 的引用计数保护

普通 shared_ptr(this) 会创建新引用计数块（double-delete），shared_from_this() 使用内部 weak_ptr 返回共享同一计数块的 shared_ptr。

Round-Robin 连接分配

新连接到达时分配到不同 io_context，该连接的所有后续 I/O 操作都在该 io_context 的线程中执行，避免了连接间的锁竞争。

5.2 实践经验

  1. 同步 vs 异步模型选择：同步模型代码简单但每连接一线程，C10K 问题下资源耗尽；异步模型单线程可处理上万连接
  2. delete this 的危险：同步 Session 中 delete this 假设没有其他地方持有引用，多线程环境极易悬空——应改用 shared_ptr+shared_from_this
  3. send_que 的必要性：异步发送时如果上次 async_write 未完成就再次发送，会导致数据交织或 async_write 重叠错误
  4. _self_shared 参数传递：每个回调都传递 shared_ptr<CSession>，形成闭包链，最后一个持有者析构时才真正销毁对象
  5. ClearSession 的线程安全：从 map 中删除 session 需要加锁或使用单线程 io_context 保证串行访问
  6. read_some vs async_read_some：同步版 read_some 会阻塞当前线程（适合独立线程模型），异步版注册回调后立即返回

六、面试准备

6.1 面试高频问答

Q1：async_read_some 和 async_read 的区别？

A：async_read_some 读到部分数据就回调（可能不填满缓冲区），适合流式解析。async_read 保证读满指定字节或出错才回调，内部循环调用 async_read_some。

Q2：为什么用 shared_from_this() 而不是 this？

A：shared_from_this() 返回与其他 shared_ptr 共享引用计数的智能指针，避免 double-delete。shared_ptr(this) 会创建独立的引用计数块。

Q3：异步回调中 delete this 有什么风险？

A：如果有其他地方持有对象指针或正在执行其他回调，delete this 会导致悬空指针/use-after-free。应用 shared_ptr 管理生命周期。

Q4：为什么需要 send_que 发送队列？

A：async_write 未完成时再次调用会触发 operation_not_supported 错误。队列让发送串行化：正在发时 push 到队列，完成时从队列取下一个。

Q5：enable_shared_from_this 的内部实现？

A：基类持有 weak_ptr<T>。shared_from_this() 返回从该 weak_ptr lock 得到的 shared_ptr。对象必须已经被某个 shared_ptr 管理过才能调用。

Q6：同步服务器每连接一线程，高并发下会有什么问题？

A：线程数 = 连接数，C10K 场景下 10000 线程的内存（栈+TCB）约 10GB，上下文切换频繁（CPU 时间浪费在调度上），吞吐量急剧下降。

Q7：异步服务器的 io_context::run() 在哪执行？

A：在 main 线程或 IOServicePool 的工作线程中执行。run() 阻塞等待 I/O 事件，有事件时调用对应回调，回调返回后继续等待。

Q8：async_accept 回调中再次调用 start_accept() 的作用？

A：保持 acceptor 始终在监听状态。如果不递归注册，accept 一次连接后就不再接受新连接。

6.2 陷阱与反问

陷阱1：shared_from_this() 在构造函数中调用 → weak_ptr 尚未初始化，未定义行为
陷阱2：忘记把 _self_shared 传递给下一个异步操作 → 对象可能在中间回调执行后提前析构
陷阱3：多线程 model 下 CServer 的 _sessions map 未加锁 → 数据竞争
陷阱4：同步版 read 在独立线程中阻塞，但线程数过多时 OS 调度开销超过 I/O 等待
陷阱5：回调 lambda 捕获引用 [&] 而引用对象已销毁 → 悬空引用

反问：同步和异步服务器的内存/CPU 开销各有什么特点？
答案：同步模型内存开销大（每线程栈 ~1MB），CPU 浪费在上下文切换。异步模型内存开销小（每连接只需 buffer），CPU 集中在 I/O 多路复用系统调用。但异步代码复杂度更高（回调地狱）。

6.3 一句话答案

  1. async_read_some：读到部分数据就回调，不保证填满缓冲区
  2. async_write：保证全部数据发送完才回调，内部循环 send
  3. shared_from_this：返回与其他 shared_ptr 共享引用计数的智能指针
  4. send_que：串行化异步发送，防止重叠 write
  5. enable_shared_from_this：基类持有 weak_ptr，保证 shared_from_this 安全
  6. start_accept 递归：保持 acceptor 持续监听新连接
  7. C10K 问题：单机 10000+ 并发连接的处理挑战，异步 I/O 是核心解决方案
