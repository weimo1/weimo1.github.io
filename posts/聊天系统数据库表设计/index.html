聊天系统数据库表设计（参考手册）

适用范围：IM 聊天系统数据库表结构参考、DDL 语句、字段说明、索引设计速查

一、项目/模块概述

  • 模块定位：本文提供 IM 聊天系统的完整数据库表结构参考，涵盖用户、消息、会话、单聊、群聊、好友关系的 DDL 定义和字段说明，作为开发和面试快速查阅手册。
  • 技术栈与依赖：MySQL 8.0 InnoDB、UTF8MB4 字符集、BIGINT 主键、复合索引。
  • 模块边界：本文聚焦表结构定义和字段约束，业务逻辑细节见《IM数据库表设计》。

二、架构设计

表关系图

核心设计决策

决策 选择 原因
引擎 InnoDB 支持事务、行锁、外键、崩溃恢复
字符集 utf8mb4 完整 UTF-8，支持 Emoji
主键类型 BIGINT UNSIGNED 支持 2^64 条记录，自增无溢出风险
时间格式 DATETIME(3) 毫秒精度，不受 2038 问题限制
消息状态 TINYINT 枚举 0未读/1已读/2撤回，可扩展

三、核心实现

3.1 用户表（users）

字段名 类型 说明 约束
user_id BIGINT 用户唯一ID AUTO_INCREMENT, PK
username VARCHAR(64) 用户名 UNIQUE
password_hash CHAR(64) SHA-256 密码哈希 NOT NULL
salt CHAR(32) 密码盐值 NOT NULL
avatar_url VARCHAR(255) 头像链接 DEFAULT NULL
online_status TINYINT 0离线/1在线 DEFAULT 0
last_active_at DATETIME 最后活跃时间 DEFAULT NULL

3.2 聊天消息表（chat_message）

索引说明：

  • idx_thread_created：消息时间线查询（”查看某会话最近消息”）
  • idx_thread_message：消息分页（WHERE thread_id=? AND message_id<? ORDER BY message_id DESC）

3.3 会话表（conversations）

字段名 类型 说明 约束
session_id VARCHAR(64) 会话ID PK
user_id BIGINT 用户ID FK(users.user_id)
session_type TINYINT 0单聊/1群聊 DEFAULT 0
unread_count INT 未读消息数 DEFAULT 0
last_message_id BIGINT 最后一条消息ID FK(messages.message_id)
updated_at DATETIME(3) 最后更新时间 DEFAULT NOW(3)

3.4 单聊表（private_chat）

关键约束：UNIQUE(user1_id, user2_id) 保证每对用户只有一个私聊会话。查询时需 WHERE (user1=A AND user2=B) OR (user1=B AND user2=A)。

四、工程实践

  • 索引设计原则：(thread_id, created_at) 复合索引让同一会话的消息物理上聚集，减少磁盘 I/O。
  • 字符集选择：utf8mb4（非 utf8）支持 Emoji 等 4 字节字符，utf8mb4_unicode_ci 提供完整排序规则。
  • 时间字段：TIMESTAMP 自动设置 CURRENT_TIMESTAMP，但范围仅到 2038 年。超长期存储用 DATETIME(3)。
  • 分库分表预留：以 thread_id 作为分片键，同一会话的所有数据在同一分片，避免跨库 JOIN。
  • 字段注释：COMMENT 详细标注字段含义和枚举值，减少文档依赖。

六、面试准备

6.1 高频问法

Q1：IM 系统的核心表有哪些？各自作用？
users（用户基础信息）、chat_message（消息存储和索引）、conversations（会话预览和未读计数）、private_chat（单聊关系）、group_chat + group_chat_member（群聊与成员）、friend_request（好友申请）、friend_relationship（好友关系）。

Q2：消息表为什么有两个复合索引？
(thread_id, created_at)：消息时间线查询（”最近消息”）。(thread_id, message_id)：分页拉取（WHERE thread_id=? AND message_id<? ORDER BY message_id DESC）。两者覆盖不同的查询模式。

Q3：UNIQUE(user1_id, user2_id) 如何保证单聊唯一？
插入时总是 user1 = min(A,B), user2 = max(A,B)，确保同一对用户只有一行。查询时 WHERE (user1=A AND user2=B) OR (user1=B AND user2=A) 覆盖双向。

Q4：BIGINT vs INT 的选择依据？
IM 系统消息量巨大：微信日消息量千亿级，INT（21 亿）几个月就溢出。BIGINT（922 亿亿）不会溢出，且自增 ID 全局唯一。

Q5：utf8mb4 和 utf8 的区别？
MySQL utf8 实际是 utf8mb3（最多 3 字节），不支持 Emoji（4 字节）。utf8mb4 是完整 UTF-8 实现。

Q6：会话表和消息表如何协同？
会话表维护消息预览（最后一条 + 未读数），打开聊天列表只需查会话表。进入会话后按需查消息表。减少一次性加载量。

Q7：消息撤回如何实现？
更新 status = 2（撤回），不物理删除。好处：可追溯审计、恢复简单、索引无需重建。

Q8：好友关系为什么是双向表？
查询”我的好友”只需 WHERE user_id = ?，性能简单高效。代价是插入/删除需操作两行，但这是低频操作。

Q9：群成员表为什么用复合主键？
(thread_id, user_id) 复合主键：快速查询某群的所有成员、某用户是否在某群。单独 user_id 索引支撑”某用户加入的所有群”。

Q10：如何做分库分表？
以 thread_id 作为分片键（sharding key）：同一会话的所有消息落在同一分片，(thread_id, message_id) 索引查询只需访问单分片，无需跨库聚合。

6.2 反问点

  • 消息表的容量规划是多少？预计多久需要分库分表？
  • 好友关系是双行还是单表？为什么这样设计？
  • 有没有考虑用 NoSQL（如 MongoDB）存储消息？为什么选 MySQL？
  • 消息的读写比例大概是多少？有没有缓存层（Redis）？

6.3 一句话答案

  • 核心 7 表 = users + chat_message + conversations + private_chat + group_chat + group_chat_member + friend_*
  • 消息双索引 = (thread_id, created_at) 时间线 + (thread_id, message_id) 分页
  • UNIQUE 单聊 = 插入时 min/max 保证顺序，查询时 OR 双向覆盖
  • BIGINT ≈ 922 亿亿；INT ≈ 21 亿
  • utf8mb4 = 完整 UTF-8（4 字节），支持 Emoji
  • 会话表 = 预览层；消息表 = 详情层
  • 撤回 = status=2（软删除，可追溯）
  • 分片键 = thread_id，同会话数据同分片
