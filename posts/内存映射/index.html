内存映射

内存映射（mmap）是将磁盘文件直接映射到进程虚拟地址空间的技术，通过操作内存指针即可读写文件，由操作系统负责数据和磁盘的同步。它既是一种高效的 I/O 手段，也是共享内存、零拷贝等高级技术的基础。

一、核心概念

  • 定义：内存映射文件（Memory-Mapped File）是通过操作系统将文件内容与进程虚拟内存地址建立映射关系。映射后，对内存的读写操作会直接反映到文件上，无需显式调用 read/write 系统调用。
  • 关键词：mmap、page cache、零拷贝、共享内存、按需分页、缺页异常、MAP_SHARED、MAP_PRIVATE
  • 适用场景/边界：
    • 适用：大文件随机读写（数据库、日志分析）、进程间共享内存通信、零拷贝文件传输、持久化数据结构
    • 边界：不适合频繁小文件读写（mmap 开销大于直接 read）、不适合网络流式数据（非文件描述符不可 mmap）

二、详细解析（≥200字）

原理拆解（三层递进）

第一层：基本工作原理

内存映射文件的核心流程：

  1. 进程调用 mmap() 系统调用，指定文件描述符、偏移、长度、访问权限
  2. 内核在进程的虚拟地址空间中分配一段连续的虚拟地址区域（VMA）
  3. 内核将文件与这段虚拟地址建立映射关系，但此时并不将文件数据读入内存
  4. 进程首次访问映射区域时触发缺页异常（Page Fault）
  5. 内核的缺页处理程序从磁盘读取对应文件页到 Page Cache，并更新页表
  6. 后续对该区域的读写直接操作 Page Cache 中的数据
  7. 内核在适当时机（msync、munmap、内存压力）将脏页写回磁盘

这就是”按需分页”（Demand Paging）——只在实际访问时才加载数据。

第三层：两种映射模式

模式 标志 行为 用途
共享映射 MAP_SHARED 内存修改会写回文件，其他进程可见 进程间通信、文件持久化
私有映射 MAP_PRIVATE 内存修改不写回文件，COW隔离 只读大文件、代码加载

私有映射使用写时复制（Copy-on-Write）：修改时内核分配新物理页拷贝原数据，修改只对当前进程可见。

mmap vs 传统 I/O 的选择策略

场景 推荐方案 原因
小文件（< 几KB）顺序读写 read/write mmap 的页表建立和缺页处理开销大于直接拷贝
大文件随机访问 mmap 按需分页，只加载访问的页，避免整文件读入
大文件顺序读写 read/write（大 buffer） 预读取 + 顺序访问的预判更可控
进程间共享内存 mmap MAP_SHARED 天然支持多进程共享
需要写入后持久化 mmap + msync 直接操作内存，比 write 更灵活

常见陷阱与注意事项

  1. 文件大小限制：mmap 映射大小不能超过文件的现有大小（需 ftruncate 预扩展），且受虚拟地址空间限制（32 位系统约 3GB）
  2. SIGBUS 错误：如果文件被截断后访问已映射但超出文件大小的区域，会收到 SIGBUS 信号而非 SIGSEGV
  3. mmap 不适合网络文件系统：NFS 等网络文件系统的 page cache 一致性问题可能导致数据丢失
  4. mmap 的延迟写入：mmap 的写操作不会立即落盘，依赖内核的回写机制。对持久化要求严格时需显式 msync 或使用 O_SYNC

与其他主题的关联

  • Page Cache：mmap 映射的物理内存来自 Page Cache，是零拷贝的基础
  • 虚拟内存：mmap 本质是建立 VMA（虚拟内存区域）的过程
  • 共享内存：mmap + MAP_SHARED 是实现 System V 共享内存外的另一种 POSIX 共享内存方式
  • 内存管理：mmap 在内核中与 malloc 的大块分配（>128KB）共用 mmap 系统调用路径
  • Copy-on-Write：MAP_PRIVATE 的私有映射依赖 COW 机制

为什么 mmap 比 read 快——从源码级别理解：

read() 系统调用每次需要：

  1. 分配用户态缓冲区
  2. copy_to_user() 将 Page Cache 数据拷贝到用户空间
  3. 涉及两次上下文切换（用户态↔内核态）

mmap 只建立映射：

  1. 创建 VMA（一次性开销）
  2. 后续访问直接通过 MMU 硬件进行地址转换
  3. 没有 copy_to_user 开销
  4. 仅首次访问时触发缺页（按需加载）

这就是为什么随机访问大文件时 mmap 显著优于 read——read 每次都需要拷贝数据，而 mmap 只拷贝访问到的页。

msync 的四种同步模式：

标志 行为
MS_SYNC 同步写入，阻塞直到数据落盘
MS_ASYNC 异步写入，立即返回，内核稍后回写
MS_INVALIDATE 使其他映射的缓存失效，强制从磁盘重新读取

难点与易错点

  1. mmap 的页对齐要求：mmap 的 offset 必须是系统页大小（通常 4096 字节）的整数倍，否则返回 EINVAL。实际应用中需用 sysconf(_SC_PAGE_SIZE) 获取页大小。

  2. mmap 的内存释放并非 real-time：munmap 后虚拟地址立即回收，但物理页的释放由内核惰性处理。大量 mmap/munmap 操作可能导致内存碎片。

  3. SIGBUS 的预防：如果文件可能被其他进程截断，mmap 映射区域可能产生 SIGBUS。解决方案：使用 sigaction 捕获 SIGBUS，或在映射前通过 fcntl 设置文件锁。

  4. mmap vs malloc 的关系：glibc 的 malloc 对大于 MMAP_THRESHOLD（默认 128KB）的分配使用 mmap 而非 sbrk。这意味着大对象的分配实际上就是匿名 mmap。

经验总结

  1. mmap 不是银弹：对于小于 4KB 的顺序读写，mmap 的页表建立和缺页处理开销可能超过直接 read。需根据访问模式权衡。
  2. 数据库为何钟爱 mmap：MongoDB（早期）、LevelDB、RocksDB 都用 mmap 实现存储引擎——随机读性能优异、代码简洁（直接指针操作）。
  3. mmap + MAP_SHARED 是进程间通信的利器：相比 System V 共享内存（shmget/shmat），mmap 的 API 更简洁、生命周期管理更自然（文件描述符引用计数）。
  4. 生产环境必须处理 mmap 失败：虚拟地址空间是有限的，长时间运行的进程中大量 mmap 可能导致 ENOMEM。需要监控 /proc/<pid>/maps 中的 VMA 数量。

六、面试准备

6.1 高频问法（≥10个）

Q1：什么是 mmap？它的工作原理是什么？

A：mmap 将文件内容映射到进程虚拟地址空间，建立 VMA 与文件 Page Cache 的关联。访问时触发缺页异常，内核从磁盘加载到 Page Cache 并更新页表。后续访问直接操作内存（Page Cache），无需额外 read/write 系统调用。

Q2：mmap 比 read/write 快在哪里？

A：mmap 省去内核空间到用户空间的数据拷贝（copy_to_user），直接操作 Page Cache。对于随机访问大文件，mmap 只加载访问到的页（按需分页），而 read 每次都需要完整拷贝。缺点是页表建立和缺页处理有一定开销。

Q3：MAP_SHARED 和 MAP_PRIVATE 的区别？

A：MAP_SHARED：对映射区的修改会写回文件，其他进程的相同映射可见修改。MAP_PRIVATE：修改不写回文件，采用写时复制（COW）——修改时分配新物理页，只对当前进程可见。MAP_PRIVATE 适合只读大文件。

Q4：mmap 映射失败可能的原因有哪些？

A：1）offset 不是页大小整数倍（EINVAL）；2）映射长度超出文件大小且未设置 MAP_FIXED（访问时会 SIGBUS）；3）虚拟地址空间不足（ENOMEM）；4）文件描述符无效或不支持 mmap（如 socket、pipe）；5）权限不足（fd 是 O_WRONLY 但 prot 含 PROT_READ）。

Q5：匿名映射（MAP_ANONYMOUS）是什么？

A：不与任何文件关联的映射，fd 传 -1。映射区域初始化为零，用于：1）malloc 的大块分配（>128KB）；2）父子进程共享内存；3）自定义内存分配器。MAP_SHARED | MAP_ANONYMOUS 等价于 /dev/zero 映射。

Q6：msync 有什么作用？不调用会丢数据吗？

A：msync 将映射区的修改同步到磁盘。munmap 时会自动同步，但非正常退出（crash、kill -9）可能导致未同步数据丢失。MS_SYNC 阻塞等待落盘，MS_ASYNC 异步处理。对持久性要求高的场景必须显式调用 msync。

Q7：mmap 与 sendfile 在零拷贝上的区别？

A：mmap：用户可修改数据后发送，适合需要处理的传输（如加 Header）。sendfile：数据直接从 Page Cache 到 Socket Buffer，纯内核态完成，适合静态文件原样传输。sendfile 拷贝次数更少但灵活性更低。

Q8：为什么 mmap 不适合小文件？

A：mmap 以页（4KB）为单位操作。映射 100 字节的文件仍需分配 4KB 物理页。页表的建立/销毁和缺页处理开销是固定的，小文件场景下这个固定成本可能超过数据拷贝成本。此外 mmap 的 VMA 数量受 /proc/sys/vm/max_map_count 限制。

Q9：mmap 的文件可以被删除吗？

A：可以。mmap 后即使 unlink 删除文件，已映射区域仍可正常访问。原因：文件删除只移除目录项，inode 和 Page Cache 在 mmap 持有引用期间不会释放。这提供了”临时文件”的优雅实现——创建 → mmap → unlink → 使用内存。

Q10：32 位系统中 mmap 映射大文件有什么问题？

A：32 位系统虚拟地址空间仅 4GB（用户态约 3GB），无法映射超过 3GB 的文件。需分段映射（mmap → munmap → mmap 下一段）。64 位系统用户态地址空间约 128TB，大文件映射不再是问题。

6.2 反问点/陷阱点（≥5个）

  • 贵团队在数据库存储引擎中对 mmap 和 Direct I/O 是如何选择的？有没有遇到过 mmap 导致的大页内存碎片问题？

  • 陷阱 1：”mmap 映射后就不需要文件描述符了？” — 错。fd 在 mmap 后可以立即 close，已映射区域仍然有效。但不关闭 fd 也不会影响 mmap——内核通过 inode 引用计数管理。

  • 陷阱 2：”mmap 的写操作是立即可见的？” — 对当前进程是的，但其他进程通过 MAP_SHARED 看到修改的时间取决于 CPU 缓存一致性和内存屏障。需要 msync 或 __sync_synchronize 保证。

  • 陷阱 3：”mmap 映射整个大文件不会消耗物理内存？” — 不会立即消耗，但访问后会消耗。映射 100GB 文件只需虚拟地址空间（64位够），实际物理内存按需分配。但极端情况（全部访问）OOM Killer 可能介入。

6.3 一句话答案（≥5个）

  • mmap 的核心价值是：将文件 I/O 变为内存操作，省去内核到用户的数据拷贝，实现按需分页的零拷贝访问。
  • mmap vs read 的选择标准：大文件随机访问用 mmap，小文件顺序访问用 read/write，网络 I/O 用 sendfile。
  • MAP_SHARED vs MAP_PRIVATE 的记忆方式：SHARED = 共享修改（写回文件），PRIVATE = 私有修改（COW 隔离）。
  • mmap 最常见的坑是：offset 不是页对齐、文件被截断导致 SIGBUS、忘记 msync 导致数据丢失。
  • 当被问到”mmap 的适用场景”时回答：”数据库存储引擎（随机读）、进程间共享内存（IPC）、大文件零拷贝传输——三大经典场景。”

原笔记：原理

内存映射文件，是从一个文件到一块内存的映射。内存映射文件与虚拟内存有些类似，通过内存映射文件可以将文件与内存中一个虚拟地址块关联在一起。从而在应用（包括多个进程）可以直接对内存执行读取和写入操作，从而读写文件。

优势：

  • 效率高：数据映射到内存进行操作（由 OS 负责在恰当时机将数据同步到磁盘）故效率高；直接将文件从硬盘拷贝到用户空间(没有拷贝到内核空间)，只进行了一次数据拷贝
  • 易用性：可以直接对内存执行读取和写入操作，从而读写文件，不必再对文件执行 I/O 操作
  • 按需映射：只将文件的部分内容映射到内存，在处理大数据量的文件时能起到相当重要的作用
  • 多映射共享：同一个文件可被多个进程映射到各自内存，各进程看到的内容一致，即该技术自身做到了”同步”

原笔记：实现内存持久化

共享内存持久化的实现中有重要的两点：

  • 共享内存映射的虚拟地址不是从 0 开始，而是从一个大地址开始（128M）
  • 共享内存映射的地址是连续的，并且指定了 MAP_FIXED 参数
  • 可以增量的扩展共享内存文件
  • 映射出来连续的地址空间，从而实现可以通过记录号查找记录数据
