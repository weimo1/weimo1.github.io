TCP

TCP 和 UDP 的区别

  • 连接性：TCP 是面向连接的协议；UDP 是无连接的协议
  • 可靠性：TCP 提供可靠的数据传输（确认和重传机制）；UDP 不提供可靠性
  • 流量与拥塞控制：TCP 提供；UDP 可能存在丢包情况
  • 头部开销：TCP 头部包含大量控制信息（管理连接、序列号）；UDP 头部较小（只包含基本信息）
  • 应用场景：TCP 适用于网页浏览、文件传输；UDP 适用于实时视频、语音通话

运行于TCP、UDP上的协议

TCP:

НТТР, HTTPS, FTP, SMTP, POP3/IMAP, Telnet, SSH

UDP：

DHCP：动态主机配置协议，动态配置IP地址

DNS：域名系统（DNS,Domain Name System）将人类可读的域名（如www.baidu.com）转化为机器可读的IP地址（如220.181.38.148），可将其理解为专为互联网设计的电话簿。实际上DNS同时支持UDP、TCP

TCP 头格式

  • 序列号：建立连接时生成随机数作为初始值（解决网络包乱序问题）
  • 确认应答号：下一次希望收到的数据序列号（解决丢包问题）
  • 控制位：ACK / RST / SYN / FIN

TCP 粘包

产生原因：一个完整的用户消息会被拆分为多个 TCP 报文进行传输，如果接收方的应用程序不知道消息的长度，也就是不知道消息边界，无法读取出有效的用户信息。

解决方式：

  • 固定长度的消息：认为 64 个字节就是一个完整的消息（不常用）
  • 特殊字符作为边界：HTTP 使用回车 + 换行作为报文的边界
  • 自定义消息结构：包头中包含消息的长度信息

TCP 流量控制

  • 含义：发送方根据接收方的实际接收能力控制发送的数据量（根据滑动窗口大小判断）

TCP 拥塞控制

  • 含义：避免发送方数据填满整个网络（通过拥塞窗口 cwnd 控制）
  • 拥塞判断：发送方没有在规定时间接收到 ACK 报文（发生超时重传）
  • 控制算法：
  • 慢启动：发送方每收到一个 ACK，cwnd 自增 1（指数增长）
  • 拥塞避免：当 cwnd 达到慢启动阈值，发送方每收到一个 ACK，cwnd 自增 1/cwnd（线性增长）
  • 拥塞发生：当触发超时重传机制，调整 cwnd 和慢启动阈值，进入快速恢复阶段（仅超时重传使用）
  • 快速恢复：收到三个重复的 ACK 后，拥塞窗口 cwnd = ssthresh + 3，收到重复 ACK cwnd 自增 1

TCP三次握手流程？

  • 主动建立连接一方：SYN_SENT
  • 接收连接请求一方：LISTEN / SYN_RECVD

客户端发送带有SYN标志的数据包到服务端，然后客户端进入SYN发送状态，等待服务端接收数据包
服务端发送带有SYN和ACK标志的数据包到客户端，然后服务端进入SYN接受状态，等待客户端接数据包
客户端发送带有ACK标志的数据包到服务端，然后客户端进入建立状态，当服务端接收到数据包后，服务端也进入建立状态，此时TCP连接建立完毕。

为什么要三次握手？

因为TCP要建立可靠的连接，需要通过三次握手**，让客户端知道自己和对方的发送接收能力正常，而服务端也需要知道自己和对方的发送接收能力正常，**也就是客户端要验证四个条件，服务端也要验证四个条件。

第一次握手，服务端接收到数据包，这样子**服务端就知道，服务端接收能力正常，客户端发送能力正常，**服务端验证了两个条件。但是客户端什么都验证不了。

第二次握手，客户端接收到数据包，**这样子客户端就能知道，客户端接收能力正常，发送能力也正常，并且知道服务端发送、接收能力也正常。**这个时候客户端已经验证完毕自己和对方的接收、发送能力都是正常的，客户端四个条件都验证了，所以可以放心进入建立状态了。而服务端还不知道自己的发送能力和客户端的接收能力是否正常，就需要第三次握手。

第三次握手，服务端接收到数据包，这样子服务端就知道自己的发送能力、客户端的接收能力正常，服务端剩余两个条件也验证了，也可以进入建立状态了。

为什么不是两次握手？

两次握手主要是为了避免服务端重复建立连接，浪费资源。
如果是两次握手，也就是当服务端接收到客户端的SYN标志的数据包后，就会建立连接。那么可能会出现，客户端发送一个SYN标志的数据包，但由于某些原因没办法阻塞了，服务端没接收到，就不会返回SYN+ACK标志的数据包。客户端收不到响应，就会重发，这时候服务端收到了，就建立连接。然后这个时候，原本旧的过期了的SYN数据包被服务端接收到了，服务端又建立连接。这样就导致了服务端会重复建立连接，浪费资源。
而三次握手的话，当服务端接收到客户端的旧的SYN数据包后，不会立刻再次连接，而是发送SYN+ACK标志数据包，等待客户端确认，如果客户端发现这个数据包是旧的，就不会发送可以建立连接的数据包，那么服务端就不会重复建立连接。

三次握手为什么是SYN、SYN+ACK、ACK这样的方式？

第一次握手是客户端告诉服务端自己的初始序列号，而第二次握手是服务端给出确认说，我收到你的初始序列号了，并且告诉客户端，我服务端的初始序列号。第三次握手则是客户端给出确认说，我客户端收到你服务器端的初始序列号了。

四次挥手流程

  • 主动关闭一方：FIN_WAIT_1 / FIN_WAIT2 / TIME_WAIT
  • 被动关闭一方：CLOSED_WAIT / LAST_ACK

  • 客户端向服务端发送FIN标志的数据包
  • 服务端向客户端发送ACK标志的数据包，发送后将未传输完的数据继续传输
  • 传输完数据后，服务端向客户端发送FIN标志的数据包
  • 客户端向服务端发送ACK标志的数据包，等待2倍的最大报文段的生存时间，如果没有收到回复，说明服务端已经收到数据包然后关闭了，那么客户端也可以关闭了

为什么要等待2倍的最大报文段的生存时间？

2倍的最大报文段的生存时间也就是指一个请求和响应来回的时间。如果第四次挥手发送的ACK标志的数据包没有被服务端收到，服务端就会重发，第三次挥手的FIN数据包，这个过程就是一个请求和响应的来回时间，如果过了这段时间还没有收到服务端发来的FIN数据包，就说明服务端已经收到ACK数据包了，就可以关闭连接。

既然握手是三次，为什么挥手不能是三次？

握手的三次分别是SYN ACK+SYN ACK，而挥手的ACK+FIN不能合并到一起，因为服务端可能还有数据没发完，得等发完后才能发送FIN，所以ACK和FIN得拆成两次，两次中间要把没发完的数据发完。

TIME_WAIT 状态过多有什么危害

客户端：如果占满了所有端口资源，那么无法向相同目的 IP + 端口的服务器发起连接（四元组是唯一标识）

服务端：不受端口资源限制，因为服务端只监听一个端口，但会消耗文件描述符、内存、CPU 等资源

为什么需要 TIME_WAIT状态

  • 足以让旧连接中两个方向的数据包都被丢弃，再出现的数据包一定是新连接产生的，不会出现数据错乱
  • 等待足够的时间确保发出的 ACK 能让被动关闭方接收，使其正常关闭（RST 不是一种优雅的关闭方式）

  • 没有数据要发送
  • 开启 TCP 延迟确认机制（等待一定时间和数据一起发送 FIN+ACK）

TCP如何保证可靠性？

通过三次握手、四次挥手、流量控制、拥塞控制、ARQ自动重传请求协议等方式来保证可靠性。

  • 数据包校验：接收数据包时会计算校验和（不一致说明数据传输过程中出现错误、丢弃）
  • 序列号：根据序列号重新组装数据（确保数据顺序正确）
  • 确认应答：收到数据包后回复 ACK 告诉发送端收到了哪些数据
  • 重传机制：超时重传
  • 流量控制：通过滑动窗口控制发送速率
  • 拥塞控制：网络出现拥堵时 TCP 会降低发送速率

TCP 重传机制

往返时延 RTT（Round-Trip Time）：数据发送到接收确认时刻的差值（数据包往返时间）

超时重传时间 RTO（Retransmission Timeout）

超时重传：RTO 略大于 RTT（多次超时使用指数退避算法）

自动重传请求 ARQ协议

发送方发送数据包后一段时间内如果没有收到ACK，就会自动重传请求。

ARQ自动重传请求也包括了停止等待ARQ和连续ARQ。

停止等待ARQ就是发完一个分组就停下来等待ACK，收到ACK后才会发送下一个分组，一段时间内没收到ACK，就会自动重传。

连续ARQ就是可以连续发送多个分组，然后累计确认ACK，如果中间某一个分组，一段时间内没收到ACK，这个分组以及之后的分组都会自动重传，也叫做go-back-n，也就是回退重传N个请求。

流量控制

含义：发送方根据接收方的实际接收能力控制发送的数据量（根据滑动窗口大小判断）

流量控制是通过滑动窗口实现的。因为发送方和接收方的速率不对等，所以就分别维护了发送窗口和接收窗口来实现流量控制，接收方根据自身接收窗口的接收能力，会在响应中携带消息给发送方，告诉他现在最大能发送的数据是多大。所以发送窗口的大小是取决于接收方的接受能力来动态滑动调整的。

拥塞控制

  • 含义：避免发送方数据填满整个网络（通过拥塞窗口 cwnd 控制）
  • 拥塞判断：发送方没有在规定时间接收到 ACK 报文（发生超时重传）
  • 控制算法：
  • 慢启动：发送方每收到一个 ACK，cwnd 自增 1（指数增长）
  • 拥塞避免：当 cwnd 达到慢启动阈值，发送方每收到一个 ACK，cwnd 自增 1/cwnd（线性增长）
  • 拥塞发生：当触发超时重传机制，调整 cwnd 和慢启动阈值，进入快速恢复阶段（仅超时重传使用）
  • 快速恢复：收到三个重复的 ACK 后，拥塞窗口 cwnd = ssthresh + 3，收到重复 ACK cwnd 自增 1

拥塞控制主要是为了防止过多的流量注入到网络中，会影响其他网络不可用。所以拥塞控制是保证网络全局的可靠性，而流量控制是保证端到端的可靠性。

拥塞控制维护了一个拥塞窗口，还有门限值，当主机开始发送数据，会执行慢开始算法，也就是每经过一个RTT往返时间，数据会翻倍发送，当数据达到门限值，就会执行拥塞避免算法，每经过一个RTT往返时间，数据会加一。

当连续收到三个ACK，就说明当前网络可能会出现问题，就执行快重传算法，直接重传消息。

并且快重传会配合快恢复算法使用，会把拥塞窗口减半，然后执行拥塞避免算法。

TCP的序列号

万物皆有源，TCP连接建立的初始包，序列号应该从哪个数字开始？这要引入一个概念：ISN（启动序列号，Initial Sequence Number），ISN即客户端和服务器在会话首包使用的序列号，客户端与服务器使用的ISN号码是不同的。在RFC 793中，产生ISN数字的算法应该尽可能的随机，从而避免序列号的冲突和序列号被攻击者猜测。

ISN

三次握手的一个重要功能是客户端和服务端交换ISN(Initial Sequence Number), 以便让对方知道接下来接收数据的时候如何按序列号组装数据。

如果ISN是固定的，攻击者很容易猜出后续的确认号。

M是一个计时器，每隔4毫秒加1。 F是一个Hash算法，根据源IP、目的IP、源端口、目的端口生成一个随机数值。要保证hash算法不能被外部轻易推算得出。

滑动窗口

为了解决可靠传输以及包乱序的问题，TCP 引入滑动窗口的概念。在传输过程中，client 和 server 协商接收窗口 rwnd，再结合拥塞控制窗口 cwnd 计算滑动窗口 swnd。在 Linux 内核实现中，滑动窗口 cwnd 是以包为单位，所以在计算 swnd 时需要乘上 mss（最大分段大小）。

如下图所示滑动窗口包含 4 部分：

  • 已收到 ack 确认的数据；
  • 已发还没收到 ack 的；
  • 在窗口中还没有发出的（接收方还有空间）；
  • 窗口以外的数据（接收方没空间）

在 TCP 协议中，滑动窗口机制用于控制数据的传输速率和保证可靠性

  1. 已发送且已被确认的字节（蓝色区域）：这些字节已经成功送达接收方，并收到了来自接收方的确认（ACK）。它们在窗口外，不再受窗口限制。
  2. 已发送但尚未被确认的字节（黄色区域）：这些数据已经发送出去，但发送方还没有收到接收方的确认。它们仍处于发送窗口之内。
  3. 尚未发送但接收方已经准备好接收的字节（绿色区域）：这些字节尚未发送，但根据接收方通告的窗口大小，发送方已经获得“发送许可”。只要发送方愿意，随时可以发出这些数据。
  4. 尚未发送且接收方还未准备好接收的字节（灰色区域）：这些数据还不能发送，因为接收方的接收窗口当前不够大，尚未准备好接收这些字节。

2.1 什么是拥塞控制

我们都知道，网络错综复杂，在这个复杂的网络中，很少有两台主机是直接相连。尽管如此，我们还是可以通过网络与其他主机通信，这是为什么？因为我们发送到网络中的数据，当达到网络中的一个节点时（假设是路由器），它会根据数据包含的地址，帮我们将数据转发到离目的地更近的路由器，或直接转发到目的地。但是，这些路由器不是直接就可以转发的，它们需要先将接收到的数据放入自己的内存（可能还要做一些处理），再从中取出进行转发。

这里就面临一个问题：路由器的内存是有限的，若同一时间到达某个路由器的数据太多，这个路由器将无法接收所有的数据，只能将一部分丢弃；或者同一台路由器数据太多，后面到达的数据将要等待较长的时间才会被转发。网络中的数据太多，导致某个路由器处理不过来或处理地太慢，这就是网络拥塞。若是对于TCP这种有重传机制的传输协议，当发生数据丢失时，重传数据将延长数据到达的时间；同时，高频率的重传，也将导致网络的拥塞得不到缓解。拥塞控制，就是在网络中发生拥塞时，减少向网络中发送数据的速度，防止造成恶性循环；同时在网络空闲时，提高发送数据的速度，最大限度地利用网络资源。说的简单点，就和堵车差不多，路就这么宽，来的车多了，自然过的就慢，所以在必要的时候要限号。

2.2 拥塞控制的方法

在理论中，拥塞控制有两种实现方式：

  • 端到端拥塞控制：在这种拥塞控制方法中，由发送数据的端系统自己来判断是否拥塞，然后调整传输速率。比如说发送的数据已经超时却还没有接收到确认报文，数据往返时延过高，接收到对同一个数据段的重复确认……都可以认为是网络拥塞的现象；若发送端检测到这种现象，就应该降低发送数据的速率，若没有，则可以慢慢提高速率；
  • 网络辅助的拥塞控制：由网络中的路由器来告诉发送方，网络的拥塞情况。一般有两种方式：（1）路由器直接向发送端发送报文，告知网络拥塞情况；（2）路由器更改数据段中的某个标志，来提示网络中的拥塞情况，然后数据将这个标志携带到目的主机，再由目的主机根据这个标志，向发送端发送报文，告知拥塞情况（被包含在确认报文中）；

2.3 TCP的拥塞控制方法

因为网络层不会提供拥塞的反馈信息，所以TCP协议采用的是第一种方式——自己判断网络的拥塞情况。当TCP检测到网络拥塞，则降低数据的发送速率，否则增加数据的发送速率。这里就将面临三个问题：

  1. TCP如何限制数据的发送速率；
  2. TCP如何检测网络中是否拥塞；
  3. TCP采用什么算法来调整速率（什么时候调整，调整多少）；

首先来回答第一个问题。了解TCP的应该知道，TCP不是发送一个数据段，接收到确认后再发送另一个数据段，它采用的是流水线的方式。TCP的每一个数据段都有一个序号，而TCP维护一个发送窗口来发送是数据，这个窗口就是一个区间。所有序号位于这个窗口内的数据段都会被一次性发送，而不需要等待之前发送的数据段被确认。而每当最早发送出去的数据段被确认，窗口就会向前移动，直到移动到第一个没有被确认的序号，这时候又会有新的数据段序号被包含在窗口中，然后被发送出去。所以限制数据发送速率最好的方式就是限制窗口的大小。在发送方的TCP程序会跟踪和维护一个叫做拥塞窗口的变量，用来进行拥塞控制。拥塞窗口被称为cwnd。在TCP发送端，所有被发送但是还没收到确认的数据段必须落在这个窗口中，所有，当网络拥塞时，TCP程序将减小cwnd，而网络通畅时，增大cwnd，以此来控制数据发送的速率。

接着来回答第二个问题。TCP程序将通过数据发送的一些现象来推测网络是否拥塞，比如：

  • 若发送一条数据段后，成功接收到了接收方的确认报文，则可以认为网络没有拥塞；
  • 若发送出一条数据段后，在规定时间内没有收到确认报文（丢失或时延太大），则可以认为网络出现了拥塞；
  • 若连续收到接收方对同一条报文的三次冗余确认（也就是四次确认），则可以推测那条报文丢失，即发生了拥塞；

上面的第三种情况，与TCP的快速重传机制有关，我这里不详细说明，只是大致介绍一下。TCP无法保证数据能够按顺序到达接收端，所以，可能出现序号靠后的数据报反倒先到达的情况。而TCP接收方并不是接收到哪一条报文，就向发送方发送哪条报文的确认，它是通过发送当前应该接收到的序号最小的报文进行确认。举个例子：

  1. 发送方同时发送了1，2，3，4，5这五个序号的报文，假设接收方接收到序号1的报文，于是将向发送方发送一个确认号为2的确认报文（TCP发送方通过确认号来判断接收方接收到的报文），告诉发送方我已经收到2之前的报文了，下一条报文我想要2；
  2. 接收方接收到2号报文后，发送确认号3，告诉发送方我接收到了3之前的所有报文；
  3. 这时候因为网络的不确定性，在3号没有到达前，4号报文先到达了，接收方接收到后，将它放入缓存，并依旧回复确认号3，表示它需要的是3号报文；
  4. 可是，之后到达的却5，于是它将5放入缓存，并依旧回复3；
  5. 直到3迟迟的到来，这时候接收方接收3，同时发现缓存中存在4和5，于是回复发送方确认号6，表示自己已经接收到了6之前的全部报文，下一条需要6；

在这里，发送方一共接收到了三条确认号为3的确认报文（确认号为3是对2号报文的确认），第一条正常，后面两条冗余。而所谓的快速重传就是指：若发送方接收到对同一条报文的三次冗余确认（也就是四次确认），就认为这条报文的下一条已经丢失，于是不管计时器是否超时，都直接重传这条报文的下一条。上面的例子中，2号报文被冗余确认了两次，还不构成快速重传的条件。而为什么是三次，其实就是概率和时间长短的折中选择。

下面回到正题，当快速重传的条件发生，发送方将认为出现了拥塞导致丢包。所有归根到底，TCP判断拥塞的方式就是检测有没有丢包。于是我们就可以回答第三个问题了，TCP如何调整发送速率——在没有丢包时慢慢提高拥塞窗口cwnd的大小，当发生丢包事件时，减少cwnd的大小。当然，具体的算法要复杂的多，TCP调整拥塞窗口的主要算法有 慢启动 ， 拥塞避免 以及 快速恢复 ，其中前两个是TCP规范要求必须实现的，而第三个则是推荐实现的，TCP根据情况在这三者之间切换。 下面我就来一一介绍。

2.4 慢启动

在讲解之前，首先得知道一些名词：

  • MSS：最大报文段长度，TCP双方发送的报文段中，包含的数据部分的最大字节数；
  • cwnd：拥塞窗口，TCP发送但还没有得到确认的报文的序号都在这个区间；
  • RTT：往返时间，发送方发送一个报文，到接收这个报文的确认报文所经历的时间；
  • ssthresh：慢启动阈值，慢启动阶段，若cwnd的大小达到这个值，将转换到拥塞避免模式；

慢启动是建立TCP连接后，采用的第一个调整发送速率的算法（或叫模式）。在这个阶段，cwnd通常被初始化为1MSS，这个值比较小，在这个时候，网络一般还有足够的富余，而慢启动的目的就是尽快找到上限。在慢启动阶段，发送方每接收到一个确认报文，就会将cwnd增加1MSS的大小，于是：

  • 初始cwnd=1MSS，所以可以发送一个TCP最大报文段，成功确认后，cwnd = 2MSS；
  • 此时可以发送两个TCP最大报文段，成功接收后，cwnd = 4 MSS；
  • 此时可以发送四个TCP最大报文段，成功接收后，cwnd = 8 MSS……

由于TCP是一次性将窗口内的所有报文发出，所以所有报文都到达并被确认的时间，近似的等于一个RTT（记住这个结论，后面所述的RTT都是基于这个结论）。所以在这个阶段，拥塞窗口cwnd的长度将在每个RTT后翻倍，也就是发送速率将以指数级别增长（所以不要被慢启动这个名字误导了）。那这个过程什么时候改变呢，这又分几种情况：

  • 第一种：若在慢启动的过程中，发生了数据传输超时，则此时TCP将ssthresh的值设置为cwnd / 2，然后将cwnd重新设置为1MSS，重新开始慢启动过程，这个过程可以理解为试探上限；
  • 第二种：第一步试探出来的上限ssthresh将用在此处。若cwnd的值增加到>= ssthresh时，此时若继续使用慢启动的翻倍增长方式可能有些鲁莽，所以这个时候结束慢启动，改为拥塞避免模式；
  • 第三种：若发送方接收到了某个报文的三次冗余确认（即触发了快速重传的条件），则进入到快速恢复阶段；同时，ssthresh = cwnd / 2，毕竟发生快速重传也可以认为是发生拥塞导致的丢包，然后cwnd = ssthresh + 3MSS；

以上就是慢启动的过程，下面来介绍拥塞避免。

2.5 拥塞避免

刚进入这个模式时，cwnd的大小近似的等于上次拥塞时的值的一半（这是由进入这个模式的条件决定的），也就是说当前的cwnd很接近产生拥塞的值。所以，拥塞避免是一个速率缓慢且线性增长的过程，在这个模式下，每经历一个RTT（请注意2.4中有关RTT的结论），cwnd的大小增加1MSS，也就是说，假设cwnd包含10个报文的大小，则每接收到一个确认报文，cwnd增加1/10 MSS。这个线性增长的过程什么时候结束，分为两种情况：

  • 第一种：在这个过程中，发生了超时，则表示网络拥塞，这时候，ssthresh被修改为cwnd / 2，然后cwnd被置为1MSS，并进入慢启动阶段；
  • 第二种：若发送方接收到了某个报文的三次冗余确认（即触发了快速重传的条件），此时也认为发生了拥塞，则，ssthresh 被修改为 cwnd / 2，然后cwnd被置为ssthresh + 3MSS，并进入快速恢复模式；

我们可以看到，慢启动和拥塞避免在接收到三个冗余的确认报文时，处理方式是一样的：判断发生了拥塞，并减小ssthresh的大小，但是cwnd的大小却不见得有减小多少，这一点让人疑惑。我个人认为是这样，虽然发送方通过接收三次冗余确认报文，判断可能存在拥塞，但是既然可以收到冗余的确认报文，表示拥塞不会太严重，甚至已经不再拥塞，所以对cwnd的减小不是这么剧烈。

2.6 快速恢复

快速恢复和上面两种模式不太一样，这种模式在TCP规范中并没有强制要求实现，只是一种推荐实现的模式。在快速恢复阶段，每接收到一个冗余的确认报文，cwnd就增加1MSS，其余不变，而当发生以下两种情况时，将退出快速恢复模式：

  • 第一种：在快速恢复过程中，计时器超时，这时候，ssthresh被修改为 cwnd / 2，然后cwnd被置为1MSS，并进入慢启动阶段；
  • 第二种：若发送方接收到一条新的确认报文（不是冗余确认），则cwnd被置为ssthresh，然后进入到拥塞避免模式；

这里有一个疑问，进入到此模式的条件就是接收到三次冗余的确认报文，判断报文丢失，那为什么再次接收到冗余确认报文时，cwnd还是要增长呢？我搜遍网上博客，只在一篇博客中找到一种说法，我认为还是有一定道理的：此时再次收到一条冗余的确认报文，表示发送端发出的报文又有一条离开网络到达了接收端（虽然不是接收端当前想要的一条），这说明网络中腾出了一条报文的空间，所以允许发送端再向网络中发送一条报文。但是由于当前序号最小的报文丢失，导致拥塞窗口cwnd无法向前移动，于是只好将cwnd增加1MSS，于是发送端又可以发送一条数据段，提高了网络的利用率。

一、核心概念

  • 定义：TCP（Transmission Control Protocol）是面向连接的、可靠的、基于字节流的传输层协议。核心机制：三次握手建连、四次挥手断连、序列号/确认应答保证可靠传输、滑动窗口流量控制、拥塞控制四大算法
  • 关键词：序列号（SEQ）、确认应答（ACK）、滑动窗口、拥塞窗口（cwnd）、慢启动、拥塞避免、快速重传、快速恢复、MSS、RTT、超时重传（RTO）、粘包/拆包、ISN
  • 适用场景/边界：TCP 适用于可靠性优先的场景——HTTP/HTTPS、文件传输（FTP）、邮件（SMTP/POP3）、SSH。不适用：实时音视频（优先 UDP）、广播/组播（TCP 不支持）

二、详细解析（≥200字）

  • 原理拆解（三层递进）：
    • 第一层——连接管理（三次握手 + 四次挥手）：三次握手本质是双方确认彼此的发送和接收能力。客户端 SYN → 服务端 SYN+ACK（确认客户端发送能力 + 宣告自己接收能力）→ 客户端 ACK（确认服务端发送能力）。四次挥手多一次是因为 TCP 半关闭特性——FIN 只表示”我不再发数据”，对方可能还有数据要发，所以 FIN 和 ACK 分开发
    • 第二层——可靠传输机制：序列号标识每个字节（ISN 随机初始化防历史包干扰），确认号 = 期望的下一个字节序号。超时重传（RTO）基于 RTT 动态计算（Jacobson 算法）。快速重传：收到 3 个重复 ACK 直接重传，不等超时。选择确认（SACK）让发送方精确知道丢失了哪些段
    • 第三层——流量控制与拥塞控制的区别：流量控制是点对点的——接收方通过窗口字段告诉发送方自己的缓冲区剩余空间，防止发送方淹没接收方。拥塞控制是全局的——发送方通过丢包/RTT 变化探测网络拥塞程度，调整 cwnd 防止网络过载。两者叠加：实际发送窗口 = min(滑动窗口, cwnd)
  • 关键数据结构/接口：TCP 头（20 字节）：源/目的端口(4B) + 序列号(4B) + 确认号(4B) + 数据偏移+标志位(2B) + 窗口大小(2B) + 校验和(2B) + 紧急指针(2B)；控制位：SYN/ACK/FIN/RST/PSH/URG
  • 关键公式：RTO = SRTT + 4 × RTTVAR（超时重传时间）；有效窗口 = min(rwnd, cwnd)；慢启动阈值 ssthresh 初始为无穷大，首次丢包后设为 cwnd/2

5.2 实践经验

  1. TCP 拥塞控制不是单一算法，而是多种算法（BBR/CUBIC/Reno）可切换——sysctl net.ipv4.tcp_congestion_control
  2. 快速重传/快速恢复避免了超时重传的长等待，是 TCP 性能提升的关键
  3. 滑动窗口由接收方通告，过大导致内存浪费，过小限制吞吐量
  4. TCP_NODELAY 禁用 Nagle 合并，适合小包交互场景
  5. TCP_QUICKACK 禁用延迟 ACK，适合需要即时确认的场景
  6. 理解 TCP 状态迁移（CLOSE_WAIT/TIME_WAIT）对调试连接泄漏至关重要

六、面试准备

6.1 面试高频问答

Q1：TCP 拥塞控制的四个阶段？

A：慢启动（cwnd 指数增长到 ssthresh）、拥塞避免（cwnd 线性增长）、快速重传（3 个重复 ACK 立即重传）、快速恢复（不进入慢启动）。

Q2：快速重传为什么是 3 个重复 ACK？

A：1-2 个重复 ACK 可能由乱序引起（非丢包），3 个重复 ACK 大概率是丢包。TCP 平衡了延迟（等太多）和误判（等太少）。

Q3：ssthresh 的作用？

A：慢启动阈值，cwnd 超过它后从指数增长切换为线性增长（拥塞避免），防止 cwnd 增长过快引发拥塞。

Q4：滑动窗口和拥塞窗口的区别？

A：滑动窗口是接收方驱动的流量控制（不要让接收方溢出），拥塞窗口是发送方驱动的拥塞控制（不要让网络拥塞）。发送窗口 = min(拥塞窗口, 滑动窗口)。

Q5：TIME_WAIT 状态为什么需要 2MSL？

A：确保最后一个 ACK 能到达对端（丢失时对端重发 FIN），同时让旧连接的残留包在网络中消失。2MSL = 2 * 报文最大生存时间。

Q6：CLOSE_WAIT 大量堆积说明什么？

A：服务端收到 FIN 但没有调用 close()，即应用层未关闭 socket。通常是代码缺陷（忘记 close 或异常路径未处理）。

Q7：BBR 和 CUBIC 的区别？

A：CUBIC 基于丢包判断拥塞（可能误判 bufferbloat），BBR 基于带宽和 RTT 建模（更适应高带宽高延迟网络，如 Google B4 网络）。

Q8：Nagle 算法和延迟 ACK 同时开启时的问题？

A：两者互等形成死锁——Nagle 等 ACK 才发小包，延迟 ACK 等下一个数据包才确认。解决方案：TCP_NODELAY 或 TCP_QUICKACK。

6.2 陷阱与反问

陷阱1：忘记关闭 socket → CLOSE_WAIT 泄漏
陷阱2：SO_LINGER 配置不当 → 强制 RST 关闭导致数据丢失
陷阱3：理解错发送窗口 = min(cwnd, rwnd)，单方面调大缓冲区不提升吞吐
陷阱4：TIME_WAIT 过多导致端口耗尽 → 需 tcp_tw_reuse + SO_REUSEADDR
陷阱5：把 Nagle 和 TCP_CORK 混淆 → Nagle 合并小包，CORK 强制聚合到一定量

反问：TCP 为什么不直接用 RTT 计算超时时间？
答案：RTT 波动大，直接用 RTT 会导致大量误超时。TCP 使用 SRTT（平滑的 RTT）+ RTTVAR（偏差），超时时间 = SRTT + 4RTTVAR，有足够容错余量。*

6.3 一句话答案

  1. 慢启动：cwnd 从 1 MSS 指数增长到 ssthresh
  2. 拥塞避免：cwnd 每 RTT 线性增长 1 MSS
  3. 快速重传：3 个重复 ACK 立即重传，不等待超时
  4. 快速恢复：不降到慢启动，cwnd = ssthresh + 3
  5. 滑动窗口：接收方通告的可用缓冲区大小，控制流量
  6. TIME_WAIT：主动关闭方等待 2MSL，防旧包干扰新连接
  7. BBR：基于带宽和 RTT 建模的拥塞控制，替代丢包判断
