处理粘包问题

粘包问题

当客户端连续发送多个数据包时，服务器底层tcp接受缓冲区收到的数据是连粘在一起的，比如

连粘数据

粘包原因

1）socket收发原理

发送数据并不是直接发送给对端, 而是应用程序将数据发送到本机操作系统的缓存里边, 当数据量小, 发送的时间间隔短, 操作系统就会在缓存区先攒够一个TCP段再通过网卡一起发送, 接收数据也是一样的, 先在操作系统的缓存存着, 然后应用程序再从操作系统中取出数据。

2）粘包原因

  • 客户端的发送频率远高于服务器的接收频率，接收方没有及时接收缓冲区的包，造成多个包接收（客户端发送了一段数据，服务端只收了一小部分，服务端下次再收的时候还是从缓冲区拿上次遗留的数据，产生粘包）recv会产生黏包（如果recv接受的数据量(1024)小于发送的数据量，第一次只能接收规定的数据量1024，第二次接收剩余的数据量）
  • 发送端需要等缓冲区满才发送出去，造成粘包（tcp底层的安全和效率机制不允许字节数特别少的小包发送频率过高，tcp会在底层累计数据长度到一定大小才一起发送，发送数据时间间隔很短，数据也很小，会合到一起，产生粘包）send 也可能发生粘包现象。（连续send少量的数据发到输出缓冲区，由于缓冲区的机制，也可能在缓冲区中不断积压，多次写入的数据被一次性发送到网络

如何处理粘包

处理粘包的方式主要采用应用层定义收发包格式的方式，这个过程俗称切包处理，常用的协议被称为tlv协议(消息id+消息长度+消息内容)，如下图

  • 固定长度的消息：认为 64 个字节就是一个完整的消息（不常用）
  • 特殊字符作为边界：HTTP 使用回车 + 换行作为报文的边界
  • 自定义消息结构：包头中包含消息的长度信息

1   copy_len记录的是已经处理过数据的长度，因为存在一次接收多个包的情况，所以copy_len用来做已经处理的数据长度的。

5   因为存在_b_head_parse为true，也就是包头接收并处理完的情况，但是包体未接受完，再次触发HandleRead，此时要继续处理上次未接受完的消息体，大体逻辑和3，4一样。

一、核心概念

  • 定义：TCP 粘包是指发送端多次发送的小数据包在接收端被合并或拆分，导致应用层无法正确识别消息边界。解决方案是通过应用层协议（TLV：Type-Length-Value）在每个消息前添加头部，包含消息 ID 和消息长度
  • 关键词：粘包/拆包、TLV 协议、消息边界、async_read_some 循环读取、HeadNode/MsgNode、Nagle 算法
  • 适用场景/边界：所有 TCP 应用层协议都必须处理粘包问题。UDP 天然无粘包（有消息边界）

二、详细解析

  • 原理拆解（三层递进）：
    • 第一层——粘包产生的根因：TCP 是字节流协议，无消息边界。发送端连续 send 多次小数据 → Nagle 算法合并为一个 TCP 段发送（粘包）；或一次 send 大数据被 TCP 拆为多个 MSS 分多次发送（拆包）。接收端 recv 可能一次读到多个消息或半个消息
    • 第二层——TLV 协议解包流程：头部固定 2 字节存消息长度（HEAD_LENGTH）。HandleRead 中的状态机：_b_head_parse=false 时先凑齐头部 → 解析长度 → 创建 MsgNode → _b_head_parse=true → 继续读取直到凑齐消息体 → 回调处理 → 重置头部状态。关键：一次 HandleRead 可能处理多个完整包（while(bytes_transferred > 0) 循环）
    • 第三层——边界条件处理：收到的数据不足头部大小 → 缓存到 HeadNode 继续异步读；收到头部但消息体不足 → 缓存到 MsgNode 继续异步读；头部长度非法（> MAX_LENGTH）→ 断开连接防恶意包
  • 关键数据结构/接口：HeadNode（缓存未完整头部）、MsgNode（缓存未完整消息体）、_b_head_parse（头部解析状态标志）、copy_len（已处理字节数偏移）
  • 关键公式：单次接收处理 = 循环直到 bytes_transferred == 0；头部长度验证：if (data_len > MAX_LENGTH) → 断开连接

粘包的 TCP 层面根因

TCP 是面向字节流的协议，不保留消息边界。发送端 send("ABC") + send("DEF") 在接收端可能一次 recv 收到 "ABCDEF"（粘包）或分两次收到 "AB" + "CDEF"（拆包）。TCP 只保证字节序和可靠性，不做消息边界保护。

5.2 实践经验

  1. 固定头部长度的 TLV 是最简单可靠的自定义协议方案，2 字节头支持 0~65535 字节消息体
  2. async_read_some 每次只读部分数据，必须用循环 + 状态机处理多次触发
  3. 头部长度校验（data_len > MAX_LENGTH）防止恶意超大包攻击（内存耗尽）
  4. recv_msg_node 用 shared_ptr 管理，避免多线程环境下的生命周期问题
  5. 接收缓冲区 _data 每次处理完后 memset 清零，防止残留数据污染下一条消息
  6. HTTP 用 \r\n\r\n 做边界也是一种粘包方案，但 TLV 更高效（不需要逐字节扫描分隔符）

六、面试准备

6.1 面试高频问答

Q1：TCP 为什么会粘包？

A：TCP 是字节流协议，不保留消息边界。发送端 Nagle 算法合并小包、接收端缓冲区积压、应用层读取不及时都会导致多条消息粘连。

Q2：粘包和拆包的区别？

A：粘包：接收端一次 recv 读到多条消息；拆包：一条消息被分到多次 recv 中收到。本质都是 TCP 不保留消息边界。

Q3：常见的粘包解决方案有哪些？

A：(1) 固定长度消息；(2) 特殊分隔符（如 HTTP 的 \r\n、Redis 的 \r\n）；(3) TLV 协议——头定长+体变长；(4) 消息头+消息体。TLV 是最通用的方案。

Q4：为什么 async_read_some 需要循环处理？

A：async_read_some 不保证读取指定字节数，可能返回部分数据。循环处理确保每次回调中尽可能多地消费缓冲区数据。

Q5：头部长度校验为什么重要？

A：防止恶意或损坏的包声明超大 body_len，导致分配过量内存（如声明 2^31-1 字节），引发 OOM。

Q6：_b_head_parse 标志位的作用？

A：记录当前状态机处于”解析头部”还是”解析体”阶段，确保重入 HandleRead 时能正确恢复状态。

Q7：copy_len 变量的作用？

A：记录已从接收缓冲区消费的字节数。一次 async_read_some 可能包含多条完整消息+一条不完整消息，copy_len 追踪消费进度。

Q8：http 协议怎么处理粘包？

A：HTTP/1.1 通过 Content-Length 头（定长体）或 Transfer-Encoding: chunked（分块传输）来确定消息边界，不需要额外的 TLV 包装。

6.2 陷阱与反问

陷阱1：忘记 memset(_data, 0, MAX_LENGTH) 清零 → 残留数据污染下一条消息
陷阱2：头部长度字段为大端序，直接 memcpy → 字节序错误（网络序通常大端）
陷阱3：data_len 为 0 时不处理 → 空消息泄漏到回调
陷阱4：状态机未在连接关闭时重置 → 下次重连状态错乱
陷阱5：body_len 超过 MAX_LENGTH 只打印日志不断连 → 攻击者持续发送恶意包

反问：UDP 有粘包问题吗？
答案：没有。UDP 是面向数据报的协议，每个 sendto 对应一个独立数据报，接收端 recvfrom 一次只收一个。但如果 UDP 包大于路径 MTU 会发生 IP 分片，这是另一个问题。

6.3 一句话答案

  1. 粘包原因：TCP 字节流不保留消息边界 + Nagle 算法合并小包
  2. TLV 协议：Type-Length-Value，头定长标记消息体长度，最通用的粘包方案
  3. 状态机处理：_b_head_parse 切换 HEAD/BODY 状态，支持分次接收
  4. async_read_some：只读部分数据，需循环 + 状态机配合处理
  5. 长度校验：防止恶意包声明超大 body 导致 OOM
  6. copy_len：追踪缓冲区消费进度，处理一条 read 含多包的情况
  7. 内容长度 vs 分块传输：HTTP 的两种边界方案，对应 TLV 和分隔符思路
