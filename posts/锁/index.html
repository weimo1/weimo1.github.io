锁

C++ 多线程详解之互斥锁 mutex

如何保证数据安全

有时候我们可以将对共享数据的访问和修改聚合到一个函数，在函数内加锁保证数据的安全性。但是对于读取类型的操作，即使读取函数是线程安全的，但是返回值抛给外边使用，存在不安全性。比如一个栈对象，我们要保证其在多线程访问的时候是安全的，可以在判断栈是否为空，判断操作内部我们可以加锁，但是判断结束后返回值就不在加锁了，就会存在线程安全问题。

我们提供了两个版本的pop操作，一个是带引用类型的参数的，一个是直接pop出智能指针类型，这样在pop函数内部减少了数据的拷贝，防止内存溢出，其实这两种做法确实是相比之前直接pop固定类型的值更节省内存，运行效率也好很多。我们也完全可以基于之前的思想，在pop时如果队列为空则返回空指针，这样比抛出异常更有好一些

死锁怎么造成的

死锁一般是由于调运顺序不一致导致的，比如两个线程循环调用。当线程1先加锁A，再加锁B，而线程2先加锁B，再加锁A。那么在某一时刻就可能造成死锁。比如线程1对A已经加锁，线程2对B已经加锁，那么他们都希望彼此占有对方的锁，又不释放自己占有的锁导致了死锁。

产生死锁的四个必要条件？

产生死锁的四个必要条件（死锁一定满足这四个条件，但满足这四个条件不一定是死锁）

1.互斥 资源是非共享的

2.占有并等待 占有一个资源，并且等待其他资源

3.不可抢占 资源不能够被抢占

4.循环等待 线程a等待的资源被线程b占有，线程 b等待的资源被线程c占有，线程c等待的资源被线程a占有，形成一个循环链

解决死锁的四个角度？

解决死锁的四个角度（预防、避免、检测、解除）

1.预防 破坏死锁产生的四个必要条件之一

  • 互斥和不可抢占这两个条件破坏了没什么意义，毕竟锁的目的就是互斥和不可抢占的
  • 破坏占有并等待 即在执行前就获取线程所需要的全部资源 但可能会浪费资源
  • 破坏循环等待 保证多个资源的获取的先后顺序都是一样的

2.避免 允许四个条件存在，但分配资源前需要先进行试探，如银行家算法，会先判断安全性，如果能得到分配资源的安全序列才真正分配资源 否则不分配

3.检测 此时已经可能出现死锁了，通过第三方工具来检测是否发生了死锁如阿里的Arthus

4.解除 如果检测到发生死锁了，应该将死锁解除 如杀死进程或回收资源

解决办法

同时加锁

当我们无法避免在一个函数内部使用两个互斥量，并且都要解锁的情况，那我们可以采取同时加锁的方式。我们先定义一个类,假设这个类不推荐拷贝构造，但我们也提供了这个类的拷贝构造和移动构造

接下来我们定义一个类对上面的类做管理，为防止多线程情况下数据混乱， 包含了一个互斥量

层级锁

现实开发中常常很难规避同一个函数内部加多个锁的情况，我们要尽可能避免循环加锁，所以可以自定义一个层级锁，保证实际项目中对多个互斥量加锁时是有序的。

层级锁能保证我们每个线程加锁时，一定是先加权重高的锁。
并且释放时也保证了顺序。
主要原理就是将当前锁的权重保存在线程变量中，这样该线程再次加锁时判断线程变量的权重和锁的权重是否大于，如果满足条件则继续加锁。

unique_lock

unique_lock和lock_guard基本用法相同，构造时默认加锁，析构时默认解锁，但unique_lock有个好处就是可以手动解锁。这一点尤为重要，方便我们控制锁住区域的粒度(加锁的范围大小),也能支持和条件变量配套使用，

和lock_guard一样，unique_lock也支持领养锁

锁的粒度

锁的粒度表示加锁的精细程度，一个锁的粒度要足够大，保证可以锁住要访问的共享数据。

同时一个锁的粒度要足够小，保证非共享数据不被锁住影响性能。

而unique_ptr则很好的支持手动解锁。

共享锁

读操作并不是互斥的，同一时间可以有多个线程同时读，但是写和读是互斥的，写与写是互斥的，简而言之，写操作需要独占锁。而读操作需要共享锁。

要想使用共享锁，需使用共享互斥量std::shared_mutex,std::shared_mutex是C++17标准提出的。C++14标准可以使用std::shared_time_mutex,

自旋锁

自旋锁可以理解为一种忙等锁，它的基本思想是，当一个线程尝试获取锁时，如果锁已经被其他线程持有，那么该线程就会不断地循环检查锁的状态，直到成功获取到锁为止。与此相对，std::mutex 互斥量是一种睡眠锁。当线程请求锁（lock()）而未能获取时，它会放弃 CPU 时间片，让其他线程得以执行，从而有效利用系统资源。

从性能上看，自旋锁的响应更快，但是睡眠锁更加节省资源，高效。

五、源码解析和实践感悟

5.1 源码解析

std::mutex 的两阶段锁机制（futex）

futex 的精妙：无竞争时纯用户态 CAS（10ns），有竞争时陷入内核（1μs）。old==2 标记确保只在有等待者时才内核唤醒——避免不必要的系统调用。

std::lock 如何避免死锁——同时获取多把锁

关键设计：① try_lock 非阻塞尝试第二把锁；② 失败则全部释放并 yield；③ 部分实现会随机交换锁顺序，防止对称活锁。

层级锁的 thread_local 值校验

thread_local 变量 _this_thread_hierarchy_value 记录当前线程已持有锁的最高层级，加锁前检查新锁层级是否更高——违反则抛异常。这是运行期死锁检测的轻量级方案。

5.2 实践经验

  1. lock_guard 优先于 unique_lock：lock_guard 零开销（不存储 owns 标志），不需要手动解锁时优先用
  2. 多个锁用 std::lock：std::lock(l1, l2) 保证同时获取无死锁，比手动加锁安全
  3. 层级锁是开发期保护：上线应禁用（性能开销），配置 debug 构建启用
  4. shared_mutex 不要滥用：读锁也有 atomic 开销；读多写少（读写比 > 10:1）才收益明显
  5. spinlock 内部禁止 sleep/IO/系统调用：任何可能阻塞的操作都会让其他自旋的线程疯狂浪费 CPU
  6. 锁的粒度用延迟解锁控制：unique_lock::unlock() 提前释放——例如日志写完后立即解锁，之后的格式化在锁外做

六、面试准备

6.1 面试 Q&A

Q1: lock_guard 和 unique_lock 的区别？什么时候用哪个？

特性 lock_guard unique_lock
手动 unlock ❌ ✅
延迟 lock ❌ ✅
配合条件变量 ❌ ✅
内存开销 0 1 byte (owns flag)

默认用 lock_guard（零开销），需要条件变量或手动控制粒度时用 unique_lock。

Q2: 产生死锁的四个必要条件和对应解法？

条件 含义 破坏方法
互斥 资源独占 无锁数据结构
占有并等待 持有 A 等 B 一次性获取全部资源
不可抢占 不能抢别人的锁 允许抢占（try_lock 超时放弃）
循环等待 A→B→C→A 固定加锁顺序（层级锁）

Q3: std::lock 如何避免死锁？

内部用 try-and-backoff 策略：先锁第一把，第二把用 try_lock 尝试——成功则完成，失败则释放第一把并 yield，部分实现会随机化顺序防止活锁。

Q4: shared_mutex 读写锁的性能收益场景？

读操作 >> 写操作（如缓存查询）。shared_lock 允许多个读者并发，lock_guard 独占写。但注意：read lock 的 atomic 递增开销 > 1 CPU cycle，读写比不够高时收益为负。

Q5: 自旋锁和互斥锁各适合什么场景？

自旋锁：临界区 < 1μs、线程数 ≈ CPU 核数、不允许睡眠（中断上下文）。互斥锁：临界区可能较长、线程数 >> CPU 核数、允许睡眠。Linux 内核中自旋锁用于中断处理，用户态用 std::mutex。

Q6: 层级锁的原理和作用？

每个锁分配一个层级值（数值越大优先级越高），线程用 thread_local 变量记录当前持有的最高层级。加锁时检查新锁层级必须小于已持有层级——违反即抛异常。作用是运行期检测加锁顺序违规，防止循环等待。

Q7: adopt_lock 的用途？

当互斥量已经被当前线程锁定（外部加锁），但仍需要 RAII 自动解锁时，用 std::lock_guard(mtx, std::adopt_lock) 领养已持有的锁——析构时自动 unlock。用于将外部加锁纳入 RAII 管理。

Q8: 如何用 try_lock 避免死锁？

加锁 A 后用 try_lock(B) 尝试加锁 B——成功则继续，失败则释放 A、休眠/yield、重试。这是 std::lock 的内部实现策略。

6.2 常见陷阱与面试反问

  1. 陷阱：pop() 返回引用——锁释放后引用的对象可能已被其他线程修改。修复：pop 返回 shared_ptr 或值类型，在锁内完成拷贝。

  2. 陷阱：const 成员函数加锁，互斥量未声明 mutable → 编译错误。修复：互斥量声明为 mutable——它是同步设施，不影响逻辑 const。

  3. 陷阱：异常路径忘记解锁 → 死锁。修复：用 RAII（lock_guard/unique_lock），析构自动解锁。

  4. 反问：「你能想到什么情况适合用自旋锁替代互斥锁？」希望听到：临界区极短（几行赋值）、线程数 ≤ CPU 核数、锁持有时间确定且可控。

  5. 反问：「C++17 的 scoped_lock 和 lock_guard 有什么区别？」希望听到：scoped_lock 是可变参数模板，可同时锁定多个互斥量（内部调 std::lock），lock_guard 只接受一个。scoped_lock 基本替代了 lock_guard。

6.3 一句话答案速记

问题 一句话答案
lock_guard 原理？ RAII 构造加锁析构解锁，零开销
死锁四个条件？ 互斥、占有并等待、不可抢占、循环等待
固定加锁顺序？ 所有线程按相同顺序加锁，破坏循环等待
std::lock 策略？ try_lock 失败则全释放 + 重试
shared_mutex？ 读共享写独占，读写比 > 10:1 才明显收益
层级锁？ thread_local 记录层级，违反加锁顺序即抛异常
adopt_lock？ 领养已持有的锁，纳入 RAII 管理
scoped_lock？ C++17 可变参数版 lock_guard，支持多锁
