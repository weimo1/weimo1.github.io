分布式存储

适用范围：IM 系统中的离线消息与历史消息存储方案——扩散写模型与分级存储架构

  • 原内容一字不删：所有原有文字、代码、注释、图片必须全部保留。
  • 代码块必须标注语言。
  • 字数硬指标：二≥200字、四≥500字、五≥1000字、六≥10问法+5反问+5一句话。

一、项目/模块概述

  • 模块定位：IM 即时通讯系统中的消息存储子系统，负责离线消息和历史消息的持久化存储与拉取，支撑消息漫游、多端同步等核心功能。是项目存储引擎模块在 IM 业务场景的具体应用。
  • 技术栈与依赖：KV 存储引擎（LevelDB/RocksDB 风格）、消息队列、扩散写模型
  • 模块边界：
    • 输入：发送方投递的消息
    • 输出：接收方拉取的离线/历史消息
    • 上下游：消息路由层（扩散写分发）、客户端拉取层



二、架构设计（≥200字）

第一层：离线消息 vs 历史消息

离线消息：用户离线期间收到的消息，具有时效性（默认保留 7 天），用户上线后全量拉取。

历史消息：用户所有聊天消息的持久化存储（默认保留半年），按会话分页拉取。

第二层：扩散写模型

离线消息的存储模式我们用的是扩散写。

如上图所示：每个用户都有自己单独的收件箱和发件箱：
1）收件箱存放的是需要向这个接收端同步的所有消息；
2）发件箱里存放的是发送端发出的所有消息。

以单聊为例：聊天中的两人会话中，消息会产生两次写，即发送者的发件箱和接收端的收件箱。

而在群的场景下：写入会被更加的放大（扩散），如果群里有 N 个人，那一条群消息就会被扩散写 N 次。

小结一下：
1）扩散写的优点是：接收端的逻辑会非常清晰简单，只需要从收件箱里读取一次即可，大大降低了同步消息所需的读的压力；
2）扩散写的缺点是：写入会被成指数地放大，特别是针对群这种场景。

补充：扩散写是 IM 系统的经典时间线模型（Timeline Model）——每个用户维护独立的收件箱时间线。钉钉、微信等均采用此模型。群消息的写扩散是主要瓶颈——万人群一条消息产生万次写入。

三、核心实现（代码走读）

3.1 离线消息存储

IM消息投递的一般做法

在通常的IM消息系统中，对于实时消息、离线消息、历史消息大概都是下面这样的技术思路。

**对于在线用户：**消息会直接实时发送到在线的接收方，消息发送完成后，服务器端并不会对消息进行落地存储。

**而对于离线的用户：**服务器端会将消息存入到离线库，当用户登录后，从离线库中将离线消息拉走，然后服务器端将离线消息删除。

这样实现的缺点就是消息不持久化，导致消息无法支持消息漫游，降低了消息的可靠性。

（**PS：**实际上，这其实也不能算是缺点，因为一些场景下存储历史消息并不是必须的，所谓的消息漫游能力也不是必备的，比如微信。）

而在我们设计的消息系统中，服务器只要接收到了发送方发上来的消息，在转发给接收方的同时也会在离线数据库及历史消息库中进行消息的落地存储，而历史消息的落地也就能支持消息漫游等相关功能了。

3.2 离线消息拉取逻辑

对于IM客户端而言，离线消息的获取针对的是自己的整个离线消息，包括所有的会话（直白了说，就是上线时拉取此次离线过程中的所有未收取的离线消息）。

离线消息的获取是自上而下的方式（按时间序），我们的经验是一次获取 200 条（PS：如果离线消息过多，会分页多次拉取，拉取1”次”可以理解为拉取1”页”）。

在客户端拉取离线消息的信令中，需要带上当前客户端缓存的消息的最大时间戳。

通过上节的图我们应该知道，离线消息我们存储的是一个线性结构（指的是按时间顺序），Server 会根据这个时间戳向下查找离线消息。当重装或者新安装 App 时，客户端的”当前客户端缓存的消息的最大时间戳”可以传 0 上来。

Server 也会缓存客户端拉取到的最后一条消息的时间戳，然后根据业务场景，客户端类型等因素来决定从哪里开始拉取，如果没有拉取完 Server 会在拉取消息的应答中带相应的标记位，告诉客户端继续拉取，客户端循环拉取，直到所有离线消息拉完。

3.3 历史消息拉取逻辑

历史消息的获取通常针对的是单一会话。

在拉取过程中，需要向服务端提交两个参数：
1）对方的 ID（如果是单聊的话就是对方的 UserID，如果是群则是群组ID）；
2）当前会话的最前面消息的时间戳（即当前会话最老一条消息的时间戳）。

Server据这两个参数，可以定位到这个客户端的此会话，然后一次获取 20 条历史消息。

消息的拉取时序上采用的是自下而上的方式（也就是时间序逆序），即从最后面往前翻。只要有消息，客户端可以一直向前翻，手动触发获取会话的历史消息。

上面的拉取逻辑，在IM界面功能上通常对应的是下拉或点击”加载更多”



四、工程实践（≥500字）

4.1 分级存储和异构存储带来的复杂性

在 IM 系统中，消息存储涉及多种存储介质的协同——热数据（最近消息）在内存/SSD，温数据在 SSD/HDD，冷数据在对象存储。这带来了：

  • 数据迁移策略（何时从热 → 温 → 冷）
  • 查询路由（请求应该打到哪一层）
  • 一致性保证（迁移过程中数据不丢不重）



4.2 生产环境考量

群消息写放大控制

  • 大群（>1000 人）采用”读扩散”替代”写扩散”——消息只存一份，成员拉取时再扩散
  • 小群（<500 人）使用写扩散——简单高效

消息可靠性

  • 消息落地后才返回 ACK 给发送方——防止消息丢失
  • 离线消息拉取后标记已读（不立即删除），防止客户端崩溃后重新拉取

存储成本优化

  • 图片/视频等富媒体消息：只存储 URL/索引，大文件存对象存储
  • 消息内容压缩：文本消息 gzip 压缩存储
  • 冷数据归档：超过半年的消息迁移至低成本存储

五、源码解析和实践感悟（≥1000字）

5.1 扩散写的核心权衡

扩散写本质上是以写放大换取读简化。在 IM 场景中，写操作（发送消息）的频率远低于读操作（查看消息列表），因此这个权衡是合理的。但群消息场景下的 N 倍写放大需要在架构上做特殊处理——大群自动切换为读扩散。

5.2 难点与易错点

陷阱1：离线消息的时间戳边界

陷阱2：消息去重

陷阱3：已删除消息的展示

5.3 经验总结

  1. 扩散写是小规模 IM 的最优解——实现简单、读性能好
  2. 大群必须用读扩散——否则写入量不可承受
  3. 消息 ID 是分布式 IM 的基石——全局唯一、单调递增、携带时间戳信息
  4. 分级存储是成本控制的唯一手段——不能把所有消息永远存在内存/SSD

六、面试准备（≥10问法+5反问+5一句话，均带回答）

6.1 高频问法（≥10个）

Q1：什么是扩散写？为什么 IM 系统用它？
A：扩散写是将一条消息复制到每个接收者的收件箱。优点是接收者只需读自己的收件箱（读简单），缺点是写入放大 N 倍。IM 读多写少，所以用写放大换读简化。

Q2：离线消息和历史消息有什么区别？
A：离线消息有时效性（保留 7 天），用户上线后全量拉取并标记删除。历史消息永久保留（如半年），按会话分页拉取。离线消息关注”未读”，历史消息关注”漫游”。

Q3：群消息为什么不能用纯扩散写？
A：万人群一条消息写 10000 次——写放大不可承受。大群需切换为读扩散（消息存一份，成员各自拉取）。

Q4：消息的全局 ID 如何设计？
A：需要全局唯一+趋势递增。常用方案：雪花算法（Snowflake——时间戳 + 机器 ID + 序列号）或 Redis incr。ID 用于去重、排序、分页拉取的游标。

Q5：如何保证消息不丢失？
A：1) 消息先持久化再返回 ACK；2) WAL（预写日志）保证崩溃恢复；3) 接收方 ACK 机制——未 ACK 的消息超时重试。

Q6：消息分页拉取的时间戳游标有什么坑？
A：如果多条消息在同一毫秒产生，时间戳相同可能漏拉。解决方案：用消息 ID（全局递增）代替时间戳做游标，或用 (时间戳, 序号) 复合游标。

Q7：消息撤回如何实现？
A：不删除已扩散的消息——追加一条”撤回通知消息”。客户端收到撤回通知后，将原消息在 UI 上替换为”对方撤回了一条消息”。这保证了所有终端的展示一致。

Q8：多端同步如何实现？
A：每个设备维护自己的同步位点（sync point）。服务端存储用户的完整消息时间线，各端增量拉取新消息。位点通常用消息 ID 或时间戳表示。

Q9：如何处理消息的已读/未读状态？
A：已读状态单独存储（不修改消息本身）。常见方案：每个会话维护 last_read_msg_id，msg_id > last_read_msg_id 的即为未读。群聊的已读需要记录每个成员的阅读位点。

Q10：IM 系统的消息存储应该用 SQL 还是 NoSQL？
A：现代 IM 倾向 NoSQL（如 HBase/TiKV/自研 KV）——消息是时序追加的、KV 模型天然匹配。SQL 适合需要事务和复杂查询的场景（如好友关系）。

6.2 反问点/陷阱点（≥5个）

  • 贵团队的 IM 系统中，群消息的扩散策略是如何做”大群自动切换读扩散”的？切换阈值是多少？

  • 你们的消息存储成本中，富媒体消息（图片/视频）和文本消息的比例大概是多少？

  • 陷阱问题1：”消息存储和消息同步是一回事吗？”——不是。存储是持久化，同步是客户端拉取最新消息。离线消息是同步的一种（全量），历史消息是存储的查询（分页）。

  • 陷阱问题2：”接收方不在线，消息存在发送方的发件箱还是接收方的收件箱？”——两者都要存。发件箱存发送记录，收件箱存待拉取的离线消息。两者用途不同。

  • 陷阱问题3：”消息删除后磁盘空间会立即释放吗？”——通常不会。类似 LSM-Tree，删除标记（tombstone）直到 Compaction 才真正清理。

6.3 一句话答案（≥5个）

  • IM 消息存储的核心设计理念是：扩散写换读简单——空间换时间，写入放大换读取简化。

  • 离线消息和历史消息的本质区别：离线消息有时效性、关注未读；历史消息永久保留、支持漫游。

  • 群消息扩散策略：小群扩散写（<500人），大群读扩散——以群大小为阈值动态切换。

  • 消息可靠性的三个支柱：先持久化再 ACK + 全局唯一 ID 去重 + 接收方 ACK 重试。

  • 这个设计的最大优点是读写分离、横向扩展友好；最大代价是存储冗余（多份副本）和写放大。

  • 当被问到”为什么不用 Kafka 做消息存储？”——回答：”Kafka 是 pub-sub 模型，按 topic 分区消费，适合流处理；IM 需要按用户 ID 随机读取历史消息，KV 存储更合适。”
