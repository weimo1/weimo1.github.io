一、项目/模块概述

  • 模块定位：回答分布式 KV 存储引擎选型中最核心的架构问题——为什么用 LSM-Tree + Raft 而不是 B+Tree + Raft。

二、架构设计（≥200字）

第一层：为什么不用 B+树做分布式，而用 KV

LSM树 + Raft 可不可行？

分布式KV存储系统要解决两个问题：单机存储引擎的性能和多机之间的数据一致性。

LSM-Tree 就是用来解决单机存储引擎的性能的。它把随机写入操作转化成顺序写入操作。

特性 优势 适用场景
顺序写 写入操作先在内存中进行，然后批量、顺序写入磁盘。顺序写性能远高于随机写，所以写入吞吐量非常的高。 写多读少、高并发写入的场景
空间效率 用日志结构进行数据压缩和垃圾回收，空间利用率很高。 大规模数据存储。
WAL LSM-Tree本身就是日志结构，跟 Raft 的预写日志（WAL） 机制在设计理念上一致，能减少重复的I/O操作。 分布式一致性复制。

Raft 就不多说了，是非常成熟的分布式一致性算法，就是解决多机之间的数据一致性。

这种架构的 Raft 负责日志的持久化和复制，LSM-Tree作为Raft的状态机。

第二层：B+树 + Raft 可不可行？

完全可以。

Raft算法本身不关心底层状态机用什么存储结构。只要该存储结构能接受一系列的操作日志并最终达到一致的状态，就可以作为Raft的状态机。

所以，任何基于B+树的单机存储引擎都可以作为Raft的底层存储。OceanBase的早期版本就是用B+树结合Raft/Paxos实现分布式一致性。

那为什么B+树没有成为主流分布式KV存储？B+树（和B树）是经典的就地更新结构，目标是优化随机读取和范围查询。

  1. 写入性能差。B+树的更新操作是要找到相应的磁盘页，然后直接覆盖或修改数据。如果发生页分裂，就还要修改父节点，会有大量的随机I/O。在高写入负载下，B+树的随机I/O和页分裂会放大，严重拖慢写入速度，没法做到分布式KV存储追求的高吞吐量。
  2. 双重写入：把B+树作为Raft的状态机，写入操作会经历两次持久化：写入操作先顺序写入Raft的日志（WAL）文件； Raft 把操作应用到B+树会执行随机写来更新内部结构，同时B+树引擎自身还要写入Redo Log/Undo Log来保证单机事务和崩溃恢复。双重写入（Raft WAL的顺序写 + B+树的随机写）产生写放大和更差的写入性能，白白浪费 Raft WAL的顺序写优势。
  3. 分布式代价高：B+树把一个平衡树结构分散到集群上，保持平衡和一致性的代价非常大，实现难度很高。

现在的 OceanBase 用LSM-Tree 和 B+树结合的架构。 纯粹的只用 B+树 + Raft 的分布式KV系统相很少，因为 LSM-Tree 更适合分布式KV的高写入和分片需求。

第三层：结语

简单的说，分布式KV存储主流用 LSM 树 + Raft 架构，是因为这种组合能实现极高的写入吞吐量，也是分布式KV存储最看重的特性。

三、核心实现（代码走读）

补充：LSM-Tree + Raft 的写入路径：

  1. 客户端写入 → Raft Leader 收到请求
  2. Leader 将操作写入 Raft Log（顺序写磁盘）
  3. Raft 复制到 Follower（网络 + Follower 的顺序写）
  4. 多数派确认后，Leader Apply 到 LSM-Tree（写入 MemTable）
  5. MemTable 写满后 dump 为 SSTable（顺序写）

四、工程实践（≥500字）

4.1 写放大的量化分析

LSM-Tree + Raft 的一次写入的实际磁盘 IO：

  • Raft Log 写入：1 次（顺序写）
  • MemTable 写入：0 次（内存操作）
  • SSTable dump：约为 1/(MemTable 大小 / 平均写入大小) 次（分摊后极低）
  • Compaction 重写：取决于写放大因子（通常 10-30×）

总计：原始 1 次写入 × 写放大因子

B+Tree + Raft 的双重写入：

  • Raft Log 写入：1 次（顺序写）
  • B+Tree 页更新：1-N 次随机写
  • B+Tree Redo/Undo Log：1+ 次

4.2 实际场景选择

场景 推荐方案 理由
高写入吞吐量 LSM + Raft 顺序写优势
低延迟点查 B+Tree 无 Compaction 延迟抖动
TP 事务 B+Tree 就地更新支持锁
时序数据 LSM + Raft 追加为主

五、源码解析和实践感悟（≥1000字）

5.1 为什么 LSM 和 Raft 是”天作之合”

LSM-Tree 和 Raft 在设计哲学上高度契合：

  1. 都是日志结构：LSM 通过 WAL + SSTable 组织数据，Raft 通过 Log + Snapshot 组织状态
  2. 都追求顺序写：LSM 将随机写转为顺序写，Raft 的 Log 也是顺序追加
  3. 都有 Compaction/Snapshot：LSM 的 Compaction 和 Raft 的 Snapshot 都是垃圾回收和状态压缩

当 LSM 作为 Raft 的状态机时，Raft Log 可以直接复用 LSM 的 WAL，消除双重写入。

5.2 难点与易错点

陷阱1：Raft Log 和 LSM WAL 的重复

陷阱2：Snapshot 的时机

5.3 经验总结

  1. LSM + Raft 是分布式 KV 的事实标准——TiKV、etcd、CockroachDB 均采用
  2. 写放大是最大敌人——通过分级 Compaction、通用 Compaction 策略缓解
  3. WAL 合一是关键优化——避免 Raft Log + LSM WAL 的双重写入
  4. 读放大需要 Bloom Filter + Cache 弥补——LSM 的弱点，但不是致命缺陷

六、面试准备（≥10问法+5反问+5一句话，均带回答）

Q1：为什么分布式 KV 用 LSM-Tree 而不用 B+Tree？
A：LSM 将随机写转为顺序写，写入吞吐量远超 B+Tree。分布式 KV 的核心需求是高写入吞吐量（支撑大规模写入负载），而非低延迟单点读取。

Q2：B+Tree + Raft 有什么问题？
A：双重写入（Raft Log 顺序写 + B+Tree 随机写 + Redo/Undo Log）导致严重写放大；B+Tree 的页分裂在分布式环境下代价高昂。

Q3：LSM-Tree 的三大优势？
A：顺序写（高吞吐量）、空间效率（日志结构压缩）、WAL 天然兼容（可与 Raft Log 合一）。

Q4：Raft 和 LSM-Tree 如何协作？
A：Raft 负责多机一致性（Log 复制），LSM-Tree 作为 Raft 的状态机（Apply Log 到 MemTable → dump SSTable）。理想情况下 Raft Log 即 LSM WAL。

Q5：什么是写放大？LSM-Tree 的写放大是多少？
A：写放大 = 实际写入磁盘的数据量 / 应用层写入的数据量。LSM 的写放大主要来自 Compaction 反复重写数据，典型值 10-30×。

Q6：OceanBase 为什么后来改用 LSM + B+ 混合？
A：纯粹 B+Tree + Paxos 的写入性能不足。LSM 处理高吞吐写入，B+Tree 处理低延迟查询，各取所长。

Q7：LSM-Tree 的读放大如何解决？
A：布隆过滤器（快速否定）、Block Cache（缓存热数据）、分层 Compaction（减少层级）、合理配置 SSTable 大小。

Q8：etcd 为什么用 BoltDB（B+Tree）而不是 LSM？
A：etcd 是配置存储（读多写少、数据量小），B+Tree 的低延迟读取更适合。BoltDB 的 B+Tree 支持事务（ACID）。

Q9：RocksDB 相比 LevelDB 的主要改进？
A：多线程 Compaction、通用 Compaction 策略（减少写放大）、Column Family（逻辑分区）、Bloom Filter 优化、更灵活的 Block Cache。

Q10：TiKV 的 Raft + RocksDB 架构中，Raft Log 和 RocksDB WAL 是否合一？
A：是的。TiKV 采用 Raft Log 即 WAL 的设计，避免双重写入。Raft Log 持久化后，Apply 直接写入 RocksDB MemTable。

6.2 反问点/陷阱点（≥5个）

  • 你们的 TiKV/RocksDB 集群中，如何监控 Compaction 导致的写放大和延迟抖动？

  • 对于需要低延迟 + 高吞吐的混合负载，你们是分集群部署还是用分层存储解决？

  • 陷阱1：”LSM 的读性能一定比 B+Tree 差吗？”——不一定。热数据在 Block Cache 中时，LSM 的读也是纯内存操作。只有冷数据需要读磁盘（且可能多层）。

  • 陷阱2：”Raft + B+Tree 完全不能用吗？”——能用（如 etcd），但前提是写入量低、数据量小。大规模 KV 存储的主流选择仍是 LSM。

  • 陷阱3：”WAL 合一会导致 Raft Log 无限增长吗？”——不会。Raft 的 Snapshot + LSM 的 Compaction 协同控制日志大小。

6.3 一句话答案（≥5个）

  • 分布式 KV 存储的核心设计选择：LSM-Tree（高吞吐）+ Raft（一致性）= 事实标准。
  • B+Tree 不适合大规模分布式 KV 的根本原因：写放大 + 双重写入 + 分布式代价高。
  • Raft + LSM 的优雅之处：同为日志结构，WAL 可合一，消除双重持久化。
  • LSM 的代价是读放大和 Compaction 抖动——用 Bloom Filter + Block Cache 缓解。
  • 当被问到”选 LSM 还是 B+Tree？”——回答：”看场景——高吞吐写选 LSM，低延迟读选 B+Tree，两者可共存（OceanBase 方案）。”
