长连接

长连接是 IM 系统实时通信的基础设施。通过维护客户端与服务端的持久连接，实现消息的实时推送，避免轮询带来的延迟和带宽浪费。

一、核心概念

  • 定义：长连接是指基于 TCP/UDP/QUIC/WebSocket 等协议建立的、可以持续收发消息的数据通路。区别于短连接的”请求-响应-关闭”模式，长连接在建立后长时间保持，支持全双工通信。
  • 关键词：持久连接、全双工、数据推送、长轮询、QUIC、WebSocket、Mars、心跳保活
  • 适用场景/边界：
    • IM 消息实时推送
    • 实时数据同步（协作编辑、游戏状态）
    • 消息通知推送
    • 不适合：低频请求场景（长连接维护有成本）

二、详细解析（≥200字）

原理拆解（三层递进）

第一层：为什么需要长连接

主要解决数据实时性问题。数据推送的演进：

  1. 周期性轮询（Polling）：启动定时器周期性请求接口。间隔太短→无效查询多，间隔太长→实时性差
  2. 长轮询（Long Polling）：发送 HTTP 请求后，服务端无新数据则挂起不返回。减少无效查询，但频繁连接建立关闭
  3. 全双工数据通道：浏览器 WebSocket，移动端 TCP/UDP/QUIC。一次建立，持续收发

第二层：协议选择与性能对比

方案 首次连接 连接复用 代表
TCP + TLS 1.2 3RTT (~600ms) 2RTT (~400ms) 传统 HTTPS
TCP + TLS 1.3 2RTT (~400ms) 1RTT (~200ms) 现代 HTTPS
QUIC 1RTT (~200ms) 0RTT (0ms) HTTP/3

以 RTT=200ms 为例：

  • TCP + TLS 1.2 首次需要 600ms（TCP 握手 + TLS 握手）
  • TLS 1.3 减少为 400ms（减少一次握手）
  • QUIC 首次仅需 200ms（QUIC 握手），连接复用为 0ms

第三层：请求优化——代理 HTTP 请求

在海量用户场景下，一次完整 HTTPS 请求涉及 DNS 解析、TCP 握手、TLS 握手、HTTP 请求/响应等步骤。移动端弱网下任何环节都可能出错。

优化方案：

  • 复用底层连接：将 HTTP 请求封装，通过全双工通道发送，网关在内网组装 HTTP 请求
  • 直接用 IP 连接：通过长连接下发域名 IP，绕过 DNS 解析（防 DNS 污染）
  • 使用更高版本 TLS 或 QUIC：减少握手次数

长连接模块划分

客户端长连接模块（如微信 Mars）：

  • 连接管理（建立/断开/重连）
  • 协议编解码
  • 心跳保活
  • 弱网优化（智能心跳、多 IP 竞速）
  • 数据压缩和加密

服务端长连接网关：

  • TCP socket 管理（epoll 多路复用）
  • 连接状态维护
  • 消息路由和转发
  • 负载均衡和故障转移

参考：微信 2017 年开源的 Mars 长连接库。

四、进阶应用（≥500字）

与其他主题的关联

  • QUIC 协议：基于 UDP 的传输协议，解决 TCP 的队头阻塞问题，弱网环境下性能更优
  • WebSocket：浏览器端长连接的标准方案
  • 心跳保活：应用层维持长连接的核心机制
  • Mars：腾讯开源的跨平台长连接库

工程中的真实用法

  • 微信 Mars：TCP 长连接 + 智能心跳 + 多 IP 竞速（赛马机制）
  • 钉钉/飞书：WebSocket + TCP 混合方案
  • Telegram：自研 MTProto 协议，支持多数据中心

常见优化策略

  • 智能心跳：前台短间隔（如 30s），后台探测 NAT 超时后自适应
  • 多 IP 竞速（赛马机制）：并发连接多个 IP，取最快响应的连接
  • 协议降级：TCP → QUIC → 短轮询逐级降级
  • 数据压缩：Protobuf 序列化 + gzip/zstd 压缩

五、源码解析和实践感悟（≥1000字）

运营商 NAT 对长连接的影响

移动网络环境下，运营商 NAT 会对空闲连接进行回收，超时时间各运营商不同（通常 5-30 分钟）。心跳间隔必须小于 NAT 超时时间，否则连接被回收后服务端无法 push 消息。

自适应心跳策略：

  • 前台：固定心跳（如 30s）
  • 后台：逐步增加心跳间隔（如 30s → 1min → 2min → 4min），探测 NAT 超时
  • 发现 NAT 超时后，回退到安全间隔

长连接 vs 短连接的资源权衡

长连接的优势（高频通信）：

  • 避免 TCP/TLS 握手开销
  • 全双工实时推送
  • 减少连接数（连接池复用）

长连接的代价：

  • 内存占用（每连接维持 socket buffer、协议状态）
  • 心跳带宽（每连接周期性发送心跳包）
  • 有状态服务（扩容难、优雅关闭难）

何时用长连接？

  • 消息频率 > 1条/分钟 → 长连接
  • 消息频率 < 1条/小时 → 短连接 + 推送通知唤醒

经验总结

  1. TCP 的 KeepAlive 不够用：默认 2 小时，远大于运营商 NAT 超时。必须应用层心跳
  2. 心跳是双刃剑：太短 → 心跳潮汐、耗电、带宽浪费。太长 → 断线感知慢
  3. 弱网场景的终极方案：多 IP 竞速 + QUIC + pull 兜底
  4. QUIC 的 0RTT 重连是移动端弱网的杀手锏，但 0RTT 有重放攻击风险，需要应用层做幂等

六、面试准备（高频问法≥10个，反问点/一句话答案≥5个，均带回答）

6.1 高频问法（≥10个）

Q1：长连接和短连接的区别是什么？

A：短连接是”请求-响应-关闭”，每次请求建立新连接。长连接建立后长久保持，支持全双工通信和服务端 push。长连接适合高频实时通信，短连接适合低频请求。

Q2：为什么 QQ 用 UDP 而不是 TCP？

A：1) UDP 无连接开销，弱网更灵活 2) 自建可靠传输机制比 TCP 更可控 3) 减少资源消耗。但现代方案更多用 QUIC（基于 UDP 但内置可靠传输）。

Q3：长轮询和 WebSocket 各有什么优缺点？

A：长轮询兼容性好（普通 HTTP），但服务端挂起连接消耗资源，频繁新数据时不断重建连接。WebSocket 全双工高效，但需要浏览器和代理支持。

Q4：QUIC 相比 TCP+TLS 有什么优势？

A：1) 0RTT 重连（TCP+TLS 至少 1-2RTT）2) 无队头阻塞（UDP 多流独立）3) 连接迁移（切换网络不需重连）4) 内置加密。

Q5：心跳机制如何设计？

A：应用层心跳（TCP KeepAlive 不够用）。自适应策略：前台固定间隔（如 30s），后台探测 NAT 超时。心跳包尽量小（<500byte），随机打散避免潮汐。

Q6：运营商 NAT 对长连接有什么影响？

A：运营商 NAT 会回收空闲连接（通常 5-30 分钟）。心跳间隔必须小于 NAT 超时，否则连接被回收服务端无法 push 消息。

Q7：多 IP 竞速（赛马机制）的原理是什么？

A：客户端同时/串行连接多个 IP 地址，取最先成功建立连接的 IP 使用。在弱网环境下可有效降低连接建立延迟。

Q8：长连接代理 HTTP 请求有什么好处？

A：复用底层 TCP 连接避免 DNS 解析和 TLS 握手开销；绕过 DNS 污染；内网转发降低整体延迟。

Q9：如何选择 TCP、UDP 还是 QUIC？

A：TCP：稳定可靠、兼容好。UDP：灵活但需自建可靠传输。QUIC：综合二者优势，弱网和移动端推荐。实际中通常 TCP 为主 + QUIC 为备。

Q10：长连接服务的资源开销主要有哪些？

A：1) 内存：每连接 socket buffer（~4KB×2）+ 协议状态 2) FD：每连接占用一个文件描述符 3) CPU：epoll 事件处理 + 心跳处理 4) 带宽：心跳包周期性消耗。

6.2 反问点/陷阱点（≥5个）

  • 贵公司在选择长连接协议时，是如何权衡 TCP 的可靠性和 QUIC 的 0RTT 优势的？

  • 在面对海外用户（高延迟、弱网）时，长连接做了哪些特殊优化？

  • 陷阱 1：”TCP KeepAlive 心跳就够了？” — 不够。默认 2 小时间隔远大于运营商 NAT 超时。且 TCP KeepAlive 只能检测连接是否存活，无法检测应用层是否正常。

  • 陷阱 2：”长连接越多越好？” — 不是。每个长连接有维护成本（内存/FD/heartbeat），低频用户用短连接 + push notification 更经济。

  • 陷阱 3：”WebSocket 一定能穿透所有代理？” — 不一定。某些企业代理不支持 WebSocket 升级，需要 fallback 到长轮询。

6.3 一句话答案（≥5个）

  • 长连接的核心是：一条连接持续使用，服务端主动 push 消息，避免频繁建立连接和轮询延迟。
  • 心跳的本质是：在运营商 NAT 回收连接之前发送数据保活——是”给运营商看的”，不是给自己看的。
  • QUIC 优于 TCP+TLS 的关键是：0RTT 重连和无队头阻塞，特别适合移动端弱网场景。
  • 多 IP 竞速的核心是：并行连接多个 IP，谁快用谁——简单粗暴但极有效。
  • 当被问到”长连接如何保活”时回答：”应用层心跳（TCP KeepAlive 不够）+ 自适应间隔 + 随机打散防止潮汐 + 断线重连兜底。”
