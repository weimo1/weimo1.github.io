智能指针

C++ 智能指针是 RAII 思想在堆内存管理上的直接体现，通过 unique_ptr（独占所有权）、shared_ptr（共享所有权）和 weak_ptr（弱引用）实现自动内存释放，从根本上消除了”忘记 delete”和”double free”两类最常见的内存错误。

一、核心概念

  • 定义：智能指针是封装裸指针的 RAII 类模板，在析构函数中自动调用 delete 或自定义删除器，将堆对象的生命周期与栈对象绑定。C++11 引入 std::unique_ptr、std::shared_ptr、std::weak_ptr，C++14 补充 std::make_unique，C++20 补充 std::atomic<std::shared_ptr>。
  • 关键词：RAII、unique_ptr、shared_ptr、weak_ptr、控制块（Control Block）、引用计数、make_shared、enable_shared_from_this、循环引用、atomic
  • 适用场景/边界：
    • unique_ptr：独占所有权、所有权转移、工厂函数返回值、PIMPL 惯用法
    • shared_ptr：多个对象共享同一资源、观察者模式、异步回调生命周期管理
    • weak_ptr：打破循环引用、观察者（不拥有）、缓存（生命到期自动失效）
    • 边界：不要用 shared_ptr 替代一切——引入不必要的引用计数和 control block 开销

二、详细解析（≥200字）

原理拆解（三层递进）

第一层：unique_ptr——零开销的独占所有权

unique_ptr 内部只存储一个裸指针（默认情况下），大小与裸指针完全一致。它禁止拷贝（拷贝构造和赋值被删除），只允许移动语义：

所有权转移三剑客：

  • release()：交还裸指针，unique_ptr 自身变为空——调用者负责释放
  • reset(p)：释放当前对象，接管新指针 p
  • std::move：移动构造/赋值，源变为空

添加删除器后的 sizeof 变化：

删除器类型 sizeof(unique_ptr) 原因
默认 std::default_delete 8 字节（64位） EBO 优化，无额外存储
无捕获 lambda 同默认（可能 8 字节） 编译器优化为静态函数
函数指针 void(*)(T*) 16 字节 额外存储 8 字节指针
有捕获 lambda 8 + 捕获大小 存储有状态的函数对象

第二层：shared_ptr——双指针 + 控制块

shared_ptr 内部包含两个指针：

引用计数的原子操作：use_count 的增减使用 std::atomic::fetch_add + std::memory_order_relaxed（增加）和 std::memory_order_acq_rel（减少，需要确保控制块安全销毁）。

make_shared 为什么只分配一次：普通 shared_ptr<T>(new T) 分配两次（T 对象 + Control Block），make_shared 分配单块内存同时容纳 T 和 Control Block。代价：weak_ptr 存在时对象内存无法释放（Control Block 和 T 在同一块内存中）。

enable_shared_from_this 原理：类内部持有一个 weak_ptr<T>（从第一个 shared_ptr 初始化），shared_from_this() 调用 weak_ptr.lock() 返回共享指针。不能在构造函数中调用 shared_from_this()——此时 weak_ptr 尚未初始化。

第三层：weak_ptr——不增加强计数的观察者

weak_ptr 必须从 shared_ptr 构造，不增加 use_count，但增加 weak_count。通过 lock() 尝试提升为 shared_ptr——如果对象已析构则返回空。

四、进阶应用（≥500字）

选择指南：三指针决策树

make_unique / make_shared 优劣

优势：

  • 性能：make_shared 一次内存分配 vs 两次
  • 异常安全：process(shared_ptr<Widget>(new Widget), may_throw()) 中如果 may_throw 在 shared_ptr 构造前抛出，new Widget 泄漏。make_shared 无此问题
  • 简洁：auto sp = make_shared<Widget>(args) 无需重复类型名

劣势：

  • make_shared 不支持自定义删除器
  • 括号初始化 vs 花括号初始化：make_shared<vector<int>>(10, 20) 调用 vector(size, value) 而非 initializer_list
  • make_shared 对象 + 控制块在同一内存，weak_ptr 存在时对象内存无法及时释放

性能陷阱与优化

陷阱 后果 优化
按值传 shared_ptr 不必要的引用计数原子操作 传 const shared_ptr<T>& 或裸指针/引用
make_shared + weak_ptr 长存 对象内存延迟释放 用 shared_ptr<T>(new T) 替代
shared_ptr<T[]> (C++17+) 用错删除器（delete vs delete[]） 使用 vector 替代
过多 shared_ptr 引用计数缓存行颠簸 审视是否真的需要共享所有权

与其他主题的关联

  • RAII：智能指针是 RAII 在堆内存上的应用
  • 移动语义：unique_ptr 的转移依赖移动构造，是移动语义的经典场景
  • 内存管理：智能指针替代裸 new/delete，是 C++ 内存管理现代化的标志
  • PIMPL：unique_ptr 完美支持 PIMPL 惯用法（配合分离编译）

引用计数的线程安全保证：

  • use_count 增减：原子操作，多线程同时拷贝/析构 shared_ptr 指向同一对象是安全的
  • 被管理对象的访问：不加锁！如果多线程同时读写同一对象，需要额外同步
  • shared_ptr 对象本身（不是它指向的对象）的读写：非原子！多线程操作同一 shared_ptr 对象需要 atomic<shared_ptr>

难点与易错点

  1. 构造函数中不要调用 shared_from_this()：此时 shared_ptr 尚未建立，weak_this_ 为空，会抛 std::bad_weak_ptr。

  2. shared_ptr<T>(this) 的陷阱：直接用 this 创建新的 shared_ptr 会创建另一个控制块，导致同一对象被 delete 两次。必须用 enable_shared_from_this::shared_from_this()。

  3. weak_ptr 的 lock() 需要检查：lock() 可能返回空指针（对象已析构）。每次使用前必须检查返回值。

  4. 循环引用不是编译期错误：无法在编译期检测。一旦形成（A→B→A），两个对象都无法释放。解决方案：将其中一个 shared_ptr 改为 weak_ptr。

  5. 线程安全性需要分层次理解：引用计数线程安全 ≠ 对象线程安全 ≠ shared_ptr 对象本身线程安全。

经验总结

  1. 默认用 unique_ptr，需要共享再用 shared_ptr：unique_ptr 零开销，不会引入隐式的 ownership 混淆。
  2. 优先用 make_unique/make_shared：异常安全 + 性能 + 代码简洁，三位一体。
  3. 传参时避免按值传 shared_ptr：除非真的需要参与共享（延长生命周期），否则传 const T& 或 T*。
  4. 设计类时若需要 shared_from_this()，必须保证对象由 shared_ptr 管理：栈对象上调用会抛异常。
  5. Profiling 后才优化 shared_ptr 开销：引用计数的原子操作开销在大多数业务代码中可以忽略不计。

六、面试准备

6.1 高频问法（≥10个）

Q1：unique_ptr 和 shared_ptr 的区别？

A：unique_ptr 独占所有权（不可拷贝只可移动），shared_ptr 共享所有权（引用计数）。unique_ptr 大小等于裸指针（默认），shared_ptr 需要额外控制块指针。unique_ptr 零运行时开销，shared_ptr 有原子引用计数开销。选择：明确独占用 unique_ptr，需要共享用 shared_ptr。

Q2：shared_ptr 的引用计数是线程安全的吗？

A：引用计数的增减是线程安全的（使用 std::atomic 操作）。但被管理对象本身的并发访问需要额外的同步。shared_ptr 对象本身的赋值/重置在多线程下不是线程安全的——C++20 提供了 atomic<shared_ptr>。

Q3：为什么要用 make_shared 而不是 new？

A：1）一次内存分配（vs 两次），性能更好；2）异常安全——f(shared_ptr<T>(new T), g()) 中如果 g() 抛异常，new T 会泄漏，make_shared 不会；3）代码更简洁。缺点：不支持自定义删除器。

Q4：weak_ptr 有什么用？

A：1）打破 shared_ptr 的循环引用（A↔B，将一方改为 weak_ptr）；2）实现安全的观察者模式——观察者不阻止被观察对象析构；3）实现缓存——lock() 返回空时自动重建。weak_ptr 从 shared_ptr 构造，不增加 use_count。

Q5：enable_shared_from_this 是什么？为什么需要？

A：当类成员函数需要返回指向自身的 shared_ptr 时，不能直接用 shared_ptr<T>(this)（会创建新的控制块导致 double delete）。继承 enable_shared_from_this<T> 后调用 shared_from_this() 返回与现有 shared_ptr 共享控制块的智能指针。原理是内部持有 weak_ptr<T>，由第一个管理该对象的 shared_ptr 自动初始化。

Q6：循环引用如何产生？如何解决？

A：当两个对象互相持有对方的 shared_ptr 时（A 有 shared_ptr，B 有 shared_ptr），两者的引用计数都至少为 1，谁也无法析构对方，形成内存泄漏。解决：将其中一个 shared_ptr 改为 weak_ptr（不增加引用计数）。典型例子：父节点持有子节点的 shared_ptr，子节点持有父节点的 weak_ptr。

Q7：shared_ptr 的构造函数中，为什么需要控制块？

A：控制块存储引用计数（强引用和弱引用）、删除器和分配器。多个 shared_ptr 共享同一控制块实现对同一对象的联合管理。控制块在最后一个 shared_ptr（或最后一个 weak_ptr）销毁时释放。

Q8：unique_ptr 支持自定义删除器，sizeof 会变大吗？

A：取决于删除器类型。默认删除器（std::default_delete）通过 EBO（Empty Base Optimization）不增加大小。无捕获 lambda 类似。但函数指针（void(*)(T*)）会增加 8 字节，有捕获 lambda 增加捕获变量大小。

Q9：weak_ptr 的 lock() 是原子操作吗？

A：是。lock() 等价于原子地检查 use_count > 0 并递增它。如果 use_count 为 0，返回空 shared_ptr。这是 C++ 中少数不需要外部锁即可线程安全地将”检查 + 操作”合二为一的机制。

Q10：C++20 的 atomic 解决了什么问题？

A：解决了多线程同时读写同一个 shared_ptr 对象的安全问题。之前需要用 std::atomic_load/std::atomic_store 等自由函数（实现通常用全局锁），atomic 提供了标准化的原子接口，可能使用无锁实现（取决于实现）。典型场景：配置的热更新、无锁数据结构的节点管理。

6.2 反问点/陷阱点（≥5个）

  • 贵团队的 C++ 代码中裸指针的占比如何？有没有形成”unique_ptr 优先，shared_ptr 谨慎使用”的团队规范？

  • 线上有没有遇到过 shared_ptr 循环引用导致的内存泄漏？是如何发现和解决的？

  • 陷阱 1：”shared_ptr 可以安全地在线程间传递” — 引用计数安全 ≠ shared_ptr 对象安全。两个线程同时对同一个 shared_ptr 赋值仍是 data race。需要 atomic<shared_ptr>。

  • 陷阱 2：”使用了智能指针就不会有内存泄漏” — 循环引用（shared_ptr 互相持有）仍会导致泄漏。weak_ptr 是解决方案但不是自动的——需要开发者识别并替换。

  • 陷阱 3：”make_shared 总是比 new shared_ptr 好” — 如果存在长期存活的 weak_ptr，make_shared 的对象内存无法及时释放（因为 Control Block 和 T 在同一内存块）。高频创建销毁+长 lived weak_ptr 的场景，new shared_ptr 可能更好。

6.3 一句话答案（≥5个）

  • unique_ptr 的核心理念：独占所有权 + 零开销 + 移动转移，用法简单到”忘记 delete 的存在”。
  • shared_ptr 的性能代价：两次内存分配（make_shared 解决）、两次原子操作（每次拷贝/析构）、控制块持久到最后一个 weak_ptr 消亡。
  • 智能指针的选择法则：默认 unique_ptr，需要共享用 shared_ptr，打破循环用 weak_ptr。
  • enable_shared_from_this 的记忆口诀：”想安全返回 this 的 shared_ptr，就继承我，但别在构造函数里调我”。
  • 当被问到”C++ 为什么不用 GC”时回答：”智能指针提供了确定性的资源释放，比 GC 的不可预测暂停更适合系统编程。RAII 是比 GC 更’可控’的哲学。”

原笔记：unique_ptr

std::unique_ptr 是一种独占所有权的智能指针，任何时刻只能有一个 unique_ptr 实例拥有对某个对象的所有权。不能被拷贝，只能被移动。

主要特性：独占所有权、轻量级（没有引用计数）、自动释放。

所有权转移：release() 返回裸指针并置空、reset() 释放并接管新指针、std::move 移动转移。

删除器对 sizeof 的影响：默认删除器 ~= 裸指针大小；无状态 lambda ~= 默认；函数指针 +8 字节；有状态 lambda +捕获大小。

原笔记：shared_ptr

shared_ptr 内部包含两个指针：一个指向目标对象 T，一个指向控制块 Control Block。控制块包含引用计数（reference count）、弱计数（weak count）和其他数据（删除器、分配器等）。

引用计数使用 std::atomic::fetch_add + memory_order_relaxed 递增，递减需要更强的内存排序确保控制块安全销毁。

主要特性：共享所有权、引用计数、自动释放。

构造函数：默认构造（空）、指针构造（接管裸指针）、拷贝构造（增加计数）、移动构造（转移所有权）。

std::make_shared 减少内存分配：一次分配同时容纳对象和控制块（vs new 的两次）。

线程安全性：引用计数修改是线程安全的，但多线程访问同一被管理对象需要额外同步。

enable_shared_from_this：类内部有 weak_ptr，shared_from_this() 调用其 lock() 返回共享指针。

原笔记：weak_ptr

不增加引用计数，主要解决 shared_ptr 之间的循环引用问题。从 shared_ptr 或另一个 weak_ptr 构造。

访问需要 lock() 转换为 shared_ptr 并检查是否为空。

原笔记：选择指南

  • unique_ptr：独占所有权、单一管理者、轻量
  • shared_ptr：共享所有权、多指针共同管理
  • weak_ptr：观察不拥有、避免循环引用、临时访问

原笔记：make_unique / make_shared 优劣

优势：性能更好（单次内存分配）、异常安全（避免 new 和 shared_ptr 构造之间的泄漏）、代码简洁

劣势：不支持自定义析构器、小括号初始化限制、make_shared 对象内存与 weak_ptr 绑定

原笔记：atomic

std::atomic<std::shared_ptr> 本质上是用标准库的智能指针机制替代手动实现的引用计数和风险指针，让并发编程更简单、更安全。
