数据结构

redis有五种基本数据结构，分别为：String(字符串)、List(列表)、Hash(哈希)、Set(集合)、Zset(有序集合)

除此之外还有，bitmap、Hyperloglog、Geo、Stream等类型

1. String（字符串）#

常用操作#
操作命令 描述
SET key value 存入字符串键值对
MSET key value [key value …] 批量存储字符串键值对
SETNX key value 存入一个不存在的字符串键值对（不存在则设置）
GET key 获取一个字符串键值
MGET key [key …] 批量获取字符串键值
DEL key [key …] 删除一个或多个键
EXPIRE key seconds 设置一个键的过期时间（秒）
INCR key 将 key 中储存的数字值加 1
DECR key 将 key 中储存的数字值减 1
INCRBY key increment 将 key 所储存的值加上 increment
DECRBY key decrement 将 key 所储存的值减去 decrement

应用场景#

  • 单值缓存：SET key value
  • 对象缓存：两种方式
  • 方式 1：set user:1 '{"name":"roy","balance":1888}'
  • 方式 2：MSET user:1:name roy user:1:balance 1888（更灵活）
  • 分布式锁：SETNX product:10001 true（获取锁）、DEL product:10001（释放锁），推荐SET product:10001 true ex 10 nx（防止死锁）

2. Hash（哈希）#

常用操作#
操作命令 描述
HSET key field value 存储一个哈希表 key 的键值
HSETNX key field value 存储一个不存在的哈希表 key 的键值（field 不存在则设置）
HMSET key field value [field value …] 在一个哈希表 key 中存储多个键值对
HGET key field 获取哈希表 key 对应的 field 键值
HMGET key field [field …] 批量获取哈希表 key 中多个 field 键值
HDEL key field [field …] 删除哈希表 key 中的 field 键值
HLEN key 返回哈希表 key 中 field 的数量
HGETALL key 返回哈希表 key 中所有的键值
HINCRBY key field increment 为哈希表 key 中 field 键的值加上增量 increment

应用场景#

  • 对象缓存：HSET user:1 name roy balance 1888（比 String 更易管理对象属性）
  • 电商购物车：
  • 以用户 id 为 key（如cart:1001）
  • 商品 id 为 field，商品数量为 value
  • 操作：添加商品（hset cart:1001 10088 1）、增减数量（hincrby）、删除商品（hdel）等

优缺点#

  • 优点：同类数据整合存储，便于管理；比 String 更省内存和 CPU
  • 缺点：过期功能仅作用于 key，不支持 field 单独过期；Redis 集群下不适合大规模使用

3. List（列表）#

常用操作#
操作命令 描述
LPUSH key value [value …] 将一个或多个值插入到 key 列表的表头（最左边）
RPUSH key value [value …] 将一个或多个值插入到 key 列表的表尾（最右边）
LPOP key 移除并返回 key 列表的头元素
RPOP key 移除并返回 key 列表的尾元素
LRANGE key start stop 返回列表 key 中指定区间内的元素（start/stop 为偏移量）
BLPOP key [key …] timeout 从表头弹出元素，若为空则阻塞等待 timeout 秒（0 为永久）
BRPOP key [key …] timeout 从表尾弹出元素，若为空则阻塞等待 timeout 秒（0 为永久）

应用场景#

  • 数据结构实现：
  • 栈：LPUSH + LPOP
  • 队列：LPUSH + RPOP
  • 阻塞队列：LPUSH + BRPOP
  • 实际场景：视频列表、签到列表、排队机、简化版消息队列（MQ）

注意点#

  • 容量上限：2^32-1 个元素（约 40 亿），但需避免大 key 问题
  • 底层为双向链表：双端操作性能高，中间节点索引操作性能低

4. Set（集合）#

常用操作#
操作命令 描述
SADD key member [member …] 往集合 key 中存入元素（元素存在则忽略，key 不存在则新建）
SREM key member [member …] 从集合 key 中删除元素
SMEMBERS key 获取集合 key 中所有元素
SCARD key 获取集合 key 的元素个数
SISMEMBER key member 判断 member 是否存在于集合 key 中
SRANDMEMBER key [count] 从集合 key 中选出 count 个元素（不删除）
SPOP key [count] 从集合 key 中选出 count 个元素（删除）
SINTER key [key …] 计算多个集合的交集
SINTERSTORE destination key [key …] 将交集结果存入新集合 destination
SUNION key [key …] 计算多个集合的并集
SUNIONSTORE destination key [key …] 将并集结果存入新集合 destination
SDIFF key [key …] 计算多个集合的差集
SDIFFSTORE destination key [key …] 将差集结果存入新集合 destination

应用场景#

  • 微信抽奖小程序：
  • 参与抽奖：SADD key {userID}
  • 查看参与者：SMEMBERS key
  • 抽奖：SRANDMEMBER key [count]（不删除）或SPOP key [count]（删除）
  • 点赞 / 收藏 / 标签：
  • 点赞：SADD like:{消息ID} {用户ID}
  • 取消点赞：SREM like:{消息ID} {用户ID}
  • 检查是否点赞：SISMEMBER like:{消息ID} {用户ID}
  • 社交关系：
  • 共同关注：SINTER set1 set2
  • 推荐好友：SDIFF set1 set2

5. Sorted Set（ZSet，有序集合）#

常用操作#
操作命令 描述
ZADD key score member [[score member]…] 往有序集合 key 中加入带分值元素
ZREM key member [member …] 从有序集合 key 中删除元素
ZSCORE key member 返回有序集合 key 中元素 member 的分值
ZINCRBY key increment member 为有序集合 key 中元素 member 的分值加 increment
ZCARD key 返回有序集合 key 中元素个数
ZRANGE key start stop [WITHSCORES] 正序获取有序集合 key 从 start 到 stop 下标的元素（带分值可选）
ZREVRANGE key start stop [WITHSCORES] 倒序获取有序集合 key 从 start 到 stop 下标的元素（带分值可选）
ZUNIONSTORE destkey numkeys key [key …] 计算多个有序集合的并集并存入 destkey
ZINTERSTORE destkey numkeys key [key …] 计算多个有序集合的交集并存入 destkey

应用场景#

  • 排行榜：
  • 点击新闻计数：ZINCRBY hotNews:20190819 1 守护香港
  • 当日排行前十：ZREVRANGE hotNews:20190819 0 9 WITHSCORES
  • 七日榜单：ZUNIONSTORE合并 7 天数据后查询

6. Bitmap（位图）#

常用操作#
操作命令 描述
SETBIT key offset value 将二进制数组的 offset 位置设置为 value（0 或 1）
GETBIT key offset 返回二进制数组 offset 位置的值
BITCOUNT key [start end [BYTE BIT]] 返回二进制数组中 1 的个数
BITPOS key bit [start [end [BYTE BIT]]] 返回 bitmap 中第一个值为 bit 的 offset 位置
**BITOP AND OR XOR

应用场景#

  • 每日签到：
  • 签到记录：SETBIT dailycheck:1 100 1（1 号用户第 100 天签到）
  • 签到次数：BITCOUNT dailycheck:1
  • 首次签到时间：BITPOS dailycheck:1 1

优点#

  • 快速、高效、节省空间（用 bit 存储，1 字节可存 8 天签到状态）

7. HyperLogLog#

作用#

用于统计集合中不重复元素的个数（基数统计），适合大数据量场景（如 UV 统计）。

功能很简单，底层的算法不简单。他的效率非常高，适合大数据量场景下的统计

常用操作#
操作命令 描述
PFADD key element [element …] 添加元素到 HyperLogLog
PFCOUNT key 统计 key 中不重复元素的个数
PFMERGE destkey [sourcekey …] 合并多个 HyperLogLog 数据到 destkey

应用场景#

  • 网站 UV 统计：PFADD visitlog 用户IP 记录访问，PFCOUNT visitlog 统计独立访客

8. Geo（地理空间）#

常用操作#
操作命令 描述
**GEOADD key [NX XX] [CH] longitude latitude member …**
GEOPOS key [member …] 返回指定地点的经纬度
**GEODIST key member1 member2 [M KM
GEORADIUS key longitude latitude radius 单位 [选项] 查询指定经纬度附近的地点（带距离、坐标等可选）
**GEOSEARCH key FROMMEMBER FROMLONLAT …**

应用场景#

  • 地理位置相关功能：
  • 添加商家地址：GEOADD changsha 113.017489 28.200454 火车站 ...
  • 查找附近景点：GEORADIUS changsha 113.017489 28.200454 2 KM

9. Stream（流）#

作用#

类似 “阻塞队列 + 发布订阅” 的结合体，可作为 Redis 版消息队列（企业应用较少）。

常用操作#
操作命令 描述
**XADD key [选项] * id field value …**
XDEL key id [id …] 删除队列中的消息
XLEN key 获取队列长度
XRANGE key start end [COUNT count] 查询队列中的消息（- 表示开始，+ 表示结尾）
**XGROUP CREATE key groupname 0 $**
XREADGROUP GROUP groupname consumername COUNT n STREAMS key > 消费者组内消费消息（> 表示未消费消息）

应用场景#

  • 简化版消息队列（MQ）

数据类型和底层结构的对应关系
string list hash set sorted set
简单动态字符串 双向链表、压缩链表 压缩链表、哈希表 压缩链表、整数数组 压缩链表、跳表

各个底层实现的时间复杂度如下：

数据类型和底层结构的对应关系
跳表 双向链表 压缩链表 哈希表 整数数组

可以看出除了 string 类型的底层实现只有一种数据结构，其他四种均有两种底层实现，这四种类型为集合类型，其中一个键对应了一个集合的数据；

五、源码解析和实践感悟

1. Redis String——SDS（Simple Dynamic String）

Redis 没有使用 C 原生的 char*，而是自研了 SDS。核心优化：O(1) 获取长度、二进制安全、预分配减少内存重分配。

2. Redis ZSet——跳表+哈希表的双重索引

ZSet 同时维护跳表（按 score 排序）和哈希表（按 member 快速查找），用空间换时间，实现 O(logN) 范围查询 + O(1) 点查。

3. Redis List——quicklist（ziplist + 双向链表的混合体）

Redis 3.2 后默认用 quicklist 替代 linkedlist：每个链表节点是一个压缩列表（ziplist），兼具链表的灵活性和数组的紧凑性。

实践经验

  1. Redis 选择数据结构的原则是”内存效率优先”：SDS 省掉 strlen 的 O(n)；ziplist 紧凑排列省指针；intset 对纯整数自动升级编码。每个数据结构都为内存做了极致优化。
  2. ZSet 的双索引是经典空间换时间：dict 实现 O(1) 的 ZSCORE，跳表实现 O(logN) 的 ZRANGE。删除需同步更新两者（zslDelete + dictDelete），务必保证原子性。
  3. Hash 的小数据优化：少量 field 时用 ziplist（顺序查找省内存），超阈值 hash-max-ziplist-entries（512）或单 field 超 hash-max-ziplist-value（64B）时转 hashtable。这解释了为什么生产环境不推荐 Hash 存太多 field。
  4. Bitmap 的空间效率逆天：一年签到只需 365 bits≈46 字节。10 亿用户约 46GB（分片存储）。对比 Set 存签到日期（每个 member 几十字节），相差数十倍。
  5. HyperLogLog 的误差是设计权衡：标准误差 0.81%，12KB 固定内存可统计 2^64 个不同元素。核心原理是 Bernoulli 试验 + 调和平均数。适合 UV 统计（允许少量误差），不适合精确计数。
  6. Stream 是 Redis 对消息队列的补课：相比 List 做 MQ（无消费者组、无 ACK），Stream 支持 XGROUP、XACK、XPENDING。但 Redis 不是专业 MQ，相比 Kafka 缺少分区有序、持久化保障、堆积能力。

六、面试准备

面试问答

Q1: Redis 五种基本数据结构的底层实现分别是什么？
A: (1) String：SDS（简单动态字符串）；(2) List：3.2 后用 quicklist（ziplist+链表混合）；(3) Hash：ziplist（小数据）+ hashtable（大数据）；(4) Set：intset（纯整数）+ hashtable；(5) ZSet：ziplist（小数据）+ 跳表+hashtable（大数据）。所有”小数据用紧凑结构”的优化都是内存优先考量。

Q2: Redis 跳表和 MySQL B+ 树为什么使用场景完全不同？
A: 核心差异在存储介质。Redis 是内存数据库，无磁盘 IO，跳表实现简单且 O(logN) 完全满足。MySQL 数据在磁盘，B+ 树每个节点恰好一个磁盘页（16KB），一次 IO 加载整个节点，最大分支因子 1170，3 层存 2000 万行仅 2 次 IO。跳表在磁盘上节点分散，随机 IO 过多。

Q3: SDS 相比 C 字符串有什么优势？
A: (1) O(1) 获取长度（C 的 strlen 是 O(n)）；(2) 二进制安全（不依赖 '\0'，可存任意二进制数据）；(3) 杜绝缓冲区溢出（每次修改前检查空间，不够自动扩容）；(4) 空间预分配（<1MB 翻倍，≥1MB +1MB）+ 惰性释放。

Q4: 布隆过滤器的原理？为什么会有误判？
A: 对 key 做 k 个不同哈希函数，映射到 m 位位图的 k 个位置，全部为 1 则”可能存在”。误判来自哈希冲突：不同 key 的哈希位可能恰好相同。误判率 p ≈ (1 - e^{-kn/m})^k。最优 k = m/n × ln2。只能保证”一定不存在”（无假阴性），不能保证”一定存在”（有假阳性）。

Q5: 100G 日志文件找出现次数最多的 IP——为什么哈希切割能解决？
A: 核心：相同 IP 经过相同哈希函数一定落到同一个小文件。(1) 对每个 IP 计算 hash(ip) % N，追加到第 N 个小文件；(2) 每个小文件用 unordered_map 统计频率（单文件大小可控，内存放得下）；(3) 取每个文件 top1，再取全局 top1。N 选择取决于内存：1G/64B≈1600 万个不同 IP。

Q6: Redis 的 ziplist（压缩列表）是什么？
A: ziplist 是一块连续内存，所有 entry 紧密排列无指针。每个 entry 编码为 <prevlen, encoding, data>。省内存：省去了 hashtable 桶数组+指针、链表 next/prev 指针。但插入删除需 memmove 后续元素（O(n)），仅适合元素少且小的场景。

Q7: 位图如何扩展支持计数（如统计出现 2 次）？
A: 双位图法——用 2 个位图，每个元素 2 bits，表示 4 种状态（00=未出现，01=1次，10=2次，11=3次及以上）。通用方案是 Counting Bloom Filter：每个 bit 扩展为 4-bit 计数器。内存开销随计数上限线性增长。

Q8: Redis Geo 类型的底层是什么？
A: Geo 底层就是 ZSet。GEOADD 将经纬度通过 GeoHash 编码为 52-bit 整数作为 score，地点名作为 member 存入 ZSet。GEORADIUS 利用 ZSet 的范围查询（ZRANGEBYSCORE）找到附近的 GeoHash 格子，再精确计算距离过滤。本质是对 ZSet 的语义包装，零额外存储。

陷阱与反问

陷阱 错误认知 正确理解
Redis List 底层就是链表 Redis 6.x 默认 quicklist（链表+压缩列表混合） 纯双向链表已废弃，quicklist 既省内存又保留双端操作
Hash 的 field 可单独设过期 过期只作用于整个 key，不支持 field 级别 需 field 级过期应拆分多个独立 key 或用 ZSet+score 存时间戳
布隆过滤器可以说”一定存在” 只能保证”一定不存在”，有假阳性 布隆过滤器无假阴性（不会漏），但允许误判存在
HyperLogLog 可统计精确 UV 标准误差约 0.81% 需精确 UV 用 Set 或 Bitmap（用户 ID 映射到 bit 位）
ZSet 排名是实时遍历计算的 跳表节点中 span 字段预计算了排名 ZRANK 是 O(logN)，追索路径累加 span 即可
