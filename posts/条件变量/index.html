1.条件变量

假设我们正在一辆夜间运行的地铁上，那么你要如何在正确的站点下车呢？

  1. 一直不休息，每一站都能知道，这样就不会错过你要下车的站点，但是这会很疲惫。
  2. 可以看一下时间，估算一下地铁到达目的地的时间，然后设置一个稍早的闹钟，就休息。这个方法听起来还行，但是你可能被过早的叫醒，甚至估算错误导致坐过站，又或者闹钟没电了睡过站。
  3. 事实上最简单的方式是，到站的时候有人或者其它东西能将你叫醒（比如手机的地图，到达设置的位置就提醒）。

这和线程有什么关系呢？其实第一种方法就是在说”忙等待（busy waiting）”也称“自旋“。也就是我们在文章一开始说的，线程一直处于while循环中来判断队列中是否有待处理的消息。

第二种方法就是加延时，这种实现进步了很多，减少浪费的执行时间，但很难确定正确的休眠时间。这会影响到程序的行为，在需要快速响应的程序中就意味着丢帧或错过了一个时间片。循环中，休眠②前函数对互斥量解锁①，再休眠结束后再对互斥量上锁，让另外的线程有机会获取锁并设置标识（因为修改函数和等待函数共用一个互斥量）。

第三种方式（也是最好的）实际上就是使用条件变量了。

通过另一线程触发等待事件的机制是最基本的唤醒方式，这种机制就称为“条件变量”。

如何使用条件变量

C++ 标准库对条件变量有两套实现：std::condition_variable 和 std::condition_variable_any，这两个实现都包含在**<condition_variable>** 头文件中。

为什么std::condition_variable 的 wait 方法只能与 std::unique_lockstd::mutex 配合使用，而不能与 std::lock_guardstd::mutex 一起使用？

锁的管理:

  • std::unique_lock 提供了更灵活的锁管理功能，可以在等待条件时释放锁并在条件满足后重新获取锁。
  • std::lock_guard 是一个简单的 RAII（资源获取即初始化）封装，用于自动管理互斥锁的获取和释放，但它不支持在持有锁的状态下进行锁的释放。

条件等待机制：

  • std::condition_variable::wait 方法会在等待期间释放锁，并在条件满足时重新获取锁。只有 std::unique_lock 能够在等待时有效地管理这个过程。
  • std::lock_guard 无法在持有锁的情况下释放锁，这样就无法在条件变量等待期间进行其他线程的操作，导致无法实现正确的等待机制。

灵活性:

  • std::unique_lock 可以在等待条件时根据需要手动控制锁的状态，例如延迟锁定或条件变化时的重新锁定，而 std::lock_guard 的使用较为简单，无法实现这种灵活性。

wait() 的重载

两种wait函数的实现如下:

  • 第一个重载的功能是：释放锁并等待，直到其他线程调用 notify_one() 或 notify_all()；
  • 第二个重载的功能是：在释放锁后，等待直到 pred() 返回 true。此函数会在被唤醒后重新获得锁，并检查 pred() 的返回值

wait函数的作用：1）wait会释放与 lock 关联的互斥量（std::mutex），允许其他线程访问共享资源；2）进入等待状态，直到被其他线程唤醒；3）一旦被唤醒，wait() 方法会重新获取锁，并返回到调用点

五、源码解析和实践感悟

5.1 源码解析

condition_variable::wait 的内核路径

wait 的两个原子步骤：① 原子地释放互斥量并进入等待（避免信号丢失的竞态窗口）；② 被 notify_one/notify_all 唤醒后原子地重新获取锁。这两步如果分开执行，通知可能发生在释放锁之后、等待之前——信号丢失。

带谓词的 wait 如何防止虚假唤醒

虚假唤醒（spurious wakeup）：条件变量可能在没有 notify 的情况下返回（操作系统调度原因）。while (!_Pred()) 循环确保即使虚假唤醒，也会重新检查条件并继续等待。

线程安全队列的 push 端竞争分析

锁内 notify_one 可能导致被唤醒线程立即阻塞在锁上（hurry-up-and-wait）。优化策略：先用局部变量标记是否需要通知，unlock 后再 notify。但文中实现将 notify 放在 lock_guard 作用域内，简洁性优于微优化。

5.2 实践经验

  1. always use predicate wait：永远用 cv.wait(lock, pred) 而非 cv.wait(lock)——防止虚假唤醒导致逻辑错误
  2. notify 可以不在锁内调用：锁外 notify 更高效（避免 hurry-up-and-wait），但要保证条件变量的同步语义不变
  3. 条件变量不能单独使用：必须配合互斥量——条件本身就是共享状态，需要锁保护
  4. notify_one vs notify_all：只有一个线程等待时用 notify_one（更高效）；多个线程等待不同条件时用 notify_all（避免通知到错误的线程）
  5. mutable 关键字的妙用：const 成员函数中需要加锁时，互斥量必须声明为 mutable——互斥量是同步设施，不影响对象逻辑上的 const 语义
  6. 条件变量 + 队列 = 线程安全的生产者-消费者：这几乎是并发编程中最经典的模式，muduo、Asio 等网络库都在用

六、面试准备

6.1 面试 Q&A

Q1: 条件变量为什么必须配合互斥量使用？

条件本身是共享状态（如队列非空），需要互斥量保护。wait 的语义是原子地释放锁并进入等待——如果这两步分开，通知可能丢失在释放锁和等待之间。

Q2: 虚假唤醒（spurious wakeup）是什么？如何解决？

即使没有线程调用 notify，wait 也可能返回——OS 调度层面的”意外唤醒”。解决：使用带谓词的 wait(lock, pred)，内部用 while(!pred()) 循环检查。

Q3: lock_guard 和 unique_lock 的区别？为什么条件变量要用 unique_lock？

特性 lock_guard unique_lock
手动解锁 ❌ ✅
延迟锁定 ❌ ✅
与条件变量配合 ❌ ✅

condition_variable::wait 需要在等待时释放锁、唤醒后重新获取——这需要 unique_lock 的灵活性，lock_guard 做不到。

Q4: notify_one 应该放在锁内还是锁外？

各有优劣。锁内：安全但可能 hurry-up-and-wait；锁外：更高效但需保证通知和条件修改不产生竞态。实际开发中锁内通知通常是安全的，除非性能 profile 显示此处是瓶颈。

Q5: 如何用条件变量实现交替打印 121212？

两个条件变量 cvA、cvB，一个共享变量 num。线程 A wait 直到 num==1，打印后 num=2 并 notify cvB；线程 B 相反。详见文中交替打印代码。

Q6: wait_for 返回 false 时锁的状态？

超时时 wait_for 返回 false，调用者仍然持有锁——重新获取锁发生在返回之前。这保证了超时后访问共享状态的安全性。

Q7: condition_variable 和 condition_variable_any 的区别？

condition_variable 只能配合 unique_lock<mutex>；condition_variable_any 可配合任何 Lockable 类型（如自定义锁、shared_lock），但内部实现有额外开销。

Q8: 为什么 mutex 在 const 成员函数中要用 mutable？

const 语义是”不修改对象的逻辑状态”，互斥量是同步机制，不影响逻辑状态。mutable 允许在 const 函数中修改互斥量，既保证线程安全又不破坏 const 语义。

6.2 常见陷阱与面试反问

  1. 陷阱：条件判断用 if 而非 while → 虚假唤醒后继续执行 → 数据不一致。修复：永远用带谓词的 wait(lock, pred)。

  2. 陷阱：多个线程等同一条件却用 notify_one → 只有一个被唤醒，其他饥饿。修复：用 notify_all 或为不同线程设不同条件变量。

  3. 陷阱：在 wait 返回后不重新检查条件 → 可能读取到已被其他线程修改的过期数据。修复：唤醒后立即在锁保护下重新检查条件。

  4. 反问：「不用条件变量，纯用互斥量怎么实现生产者-消费者？」希望听到：用互斥量 + 轮询（忙等）→ CPU 浪费。条件变量正是为了解决忙等问题而设计。

  5. 反问：「为什么 Linux 的 futex 比纯用户态自旋更高效？」希望听到：futex 在无竞争时用用户态 atomic 操作（快路径），有竞争时才陷入内核睡眠（慢路径）——两阶段锁。
