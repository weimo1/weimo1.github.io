设计模式

SOLID Design Principles

SOLID is an acronym which stands for the following design principles (and

their abbreviations):

Single Responsibility Principle (SRP)

单一职责原则

单一职责原则的定义是：应该有且仅有一个原因引起类的变更

单一职责的好处

  1. 类的复杂性降低，实现什么职责都有清晰明确的定义；

  2. 可读性高，复杂性降低，可读性自然就提高了；

  3. 可维护性提高，可读性提高了，那自然更容易维护了；

  4. 变更引起的风险降低，变更是必不可少的，如果接口的单一职责做得好，一个接口修改只对相应的实现类有影响，对其他的接口无影响，这对系统的扩展性、维护性都有非常大的帮助。

Open-Closed Principle (OCP) 开闭原则

开闭原则是指一个软件实体如类、模块和函数应该对扩展开放，对修改关闭。也就是说一个软件实体应该通过扩展来实现变化，而不是通过修改已有的代码来实现变化。我们以书店销售书籍为例来说明什么是开闭原则。

Liskov Substitution Principle (LSP) 里氏替换原则

在面向对象的语言中，继承是必不可少的、非常优秀的语言机制，它有如下优点：

  1. 代码共享，减少创建类的工作量，每个子类都拥有父类的属性和方法；
  2. 提高代码的重用性；
  3. 子类可以形似父类，但又异于父类；
  4. 提高代码的可扩展性；
  5. 提高产品或项目的开放性。

有优点就必然存在缺点：

  1. 继承是侵入性的。只要继承，就必须拥有父类的属性和方法。
  2. 降低代码的灵活性。子类会多一些父类的约束。
  3. 增强了耦合性。当父类的常量、变量、方法被修改时，需要考虑子类的修改。

为了让“利”的因素发挥最大的作用，同时减少“弊”带来的麻烦，引入了里氏替换原则（LSP）。

历史替换原则最正宗的定义是：如果对每一个类型为S的对象o1，都有类型为T的对象o2，使得以T定义的所有程序P在所有的对象o1都代替o2时，程序P的行为没有发生变化，那么类型S是类型T的子类型。

通俗点讲，就是只要父类能出现的地方，子类就可以出现，而且替换为子类也不会产生任何错误或异常。

Interface Segregation Principle (ISP) 接口隔离原则

接口隔离原则就是客户端不应该依赖它不需要的接口，或者说类间的依赖关系应该建立在最小的接口上

Dependency Inversion Principle (DIP)

依赖倒置原则

  1. 模块间的依赖通过抽象发生，实现类之间不直接发生依赖关系，其依赖关系是通过接口或抽象类产生的；

  2. 接口或抽象类不依赖于实现类；

  3. 实现类依赖接口或抽象类。

说白了，就是“面向接口编程”。

依赖倒置原则可以减少类间的耦合性，提高系统的稳定性，降低并行开发引起的风险，提高代码的可读性和可维护性。

依赖倒置原则的使用建议：

（1）每个类尽量都有接口或抽象类，或者接口和抽象类两者都具备。

（2）变量的表面类型尽量是接口或抽象类。

（3）任何类都不应该从具体类派生。

（4）尽量不要重写基类的方法。如果基类是一个抽象类，而且这个方法已经实现了，子类尽量不要重写。

（5）结合里氏替换原则使用。

总结六大设计原则

  1. 单一职责原则：一个类或接口只承担一个职责。

  2. 里氏替换原则：在继承类时，务必重写（override）父类中所有的方法，尤其需要注意父类的protected方法（它们往往是让你重写的），子类尽量不要暴露自己的public方法供外界调用。

  3. 依赖倒置原则：高层模块不应该依赖于低层模块，而应该依赖于抽象。抽象不应依赖于细节，细节应依赖于抽象。

  4. 接口隔离原则：不要对外暴露没有实际意义的接口。

  5. 迪米特法则：尽量减少对象之间的交互，从而减小类之间的耦合。

  6. 开闭原则：对软件实体的改动，最好用扩展而非修改的方式。

5.2 实践经验

  1. SOLID 不是教条，是权衡工具：开闭原则对「频繁变更」的模块最重要，对「稳定不变」的模块过度设计反而增加复杂度
  2. 单一职责的粒度看”变更原因”：两个功能如果总是 同时变更，可以放在一起；如果 独立变更，必须分离
  3. 依赖倒置实践 = 构造函数注入 + 接口隔离：C++ 用 unique_ptr<Interface> 做依赖注入，用纯虚函数做接口
  4. 里氏替换原则在 C++ 的体现 = 虚函数契约：重写函数不能收紧前置条件、不能放宽后置条件、不能抛新异常
  5. 接口隔离的极端：每个类只有一个纯虚函数 → 过度。正常粒度是一个「角色」一组方法（如 IReader、IWriter）
  6. 学好 SOLID 看代码更高效：看到 switch(type) + 向下转型 → 违反 OCP；看到构造中 new Concrete() → 违反 DIP

六、面试准备

6.1 面试 Q&A

Q1: 用一句话说清楚 SOLID 五大原则？

原则 一句话
SRP 单一职责 一个类只干一件事
OCP 开闭 扩展开放，修改关闭
LSP 里氏替换 子类必须能替换父类
ISP 接口隔离 不强迫依赖不需要的接口
DIP 依赖倒置 依赖抽象不依赖具体

Q2: 单一职责和接口隔离有什么区别？

SRP 讲的是类的职责（一个类不该有多个变更原因），ISP 讲的是接口的粒度（一个接口不该让调用方依赖不需要的方法）。SRP 导致接口天然较小，ISP 要求进一步拆分臃肿接口。

Q3: 开闭原则在 C++ 中如何实现？

核心手段：虚函数（多态）+ 继承 + 策略模式/模板方法模式。通过基类定义稳定接口，子类扩展可变行为。C++ 还有模板方案（编译期多态），但不如虚函数灵活。

Q4: 依赖倒置和依赖注入有什么关系？

依赖倒置是原则（高层和低层都依赖抽象），依赖注入是实现手段（通过构造函数/Setter 将依赖传递进来）。DIP 告诉你”应该这样做”，DI 告诉你”具体怎么做”。C++ 中常见用 std::unique_ptr<I> 做构造注入。

Q5: 为什么里氏替换原则跟 C++ 的虚函数紧密相关？

LSP 要求”子类必须能替换父类”。C++ 中通过虚函数实现多态替换。违反 LSP 的典型：子类重写虚函数抛出父类未声明的异常、子类返回比父类更窄的类型（C++ 协变返回类型除外）、子类改变函数语义。

Q6: 迪米特法则（最少知识原则）的核心思想？

一个对象应对其他对象有最少了解——只与直接的朋友通信，不和”朋友的朋友”交互。代码上体现为：a.getB().getC().doSomething() 违反迪米特，应封装为 a.doSomethingThroughB()。

Q7: SOLID 原则之间有冲突吗？

有。最典型：遵循 ISP 拆分接口 → 产生大量小接口/类 → SRP 自然满足，但可能违背 OCP（需要修改多处才能扩展）。需要根据模块稳定性权衡——稳定模块优先 OCP，易变模块优先 ISP。

Q8: 实际项目中如何度量是否符合 SOLID？

代码审查 checklist：① SRP：一个类是否因多个原因被改过？（git log 看变更分布）；② OCP：加功能是加文件还是改现有文件？③ DIP：类内部是否 new 具体类（不含工厂/POJO）？工具辅助：CppDepend、SonarQube。

6.2 常见陷阱与面试反问

  1. 陷阱：追求完美 OCP → 为每处「可能」变化预留扩展点 → 过度设计。修复：等到第二处相似变更出现时再重构抽象，YAGNI 原则。

  2. 陷阱：LSP 只关注语法（编译通过）→ 忽略语义（行为正确）。修复：椭圆-矩形问题——Rectangle.setWidth(5).setHeight(3) 期望 area=15，Square 继承后违反此语义。

  3. 陷阱：构造函数中调用虚函数 → 此时子类尚未构造，多态失效。修复：构造后调用两阶段初始化（init()）或工厂函数。

  4. 反问：「你在实际项目中遇到过哪些 SOLID 原则解决的具体问题？」期望有实例——如通过策略模式消除 if-else 实现 OCP、通过依赖注入让单元测试可 Mock 外部依赖。

  5. 反问：「Go 语言没有继承，如何实现 SOLID？」期望：Go 用接口+组合替代继承，LSP 自然满足（接口只声明行为），OCP 通过接口+struct embedding 实现。
